## 1. 为什么要有离线预处理

Nanite 的运行时只做三件事：**剔除**（选哪些簇）、**光栅**（把这些簇画出来）、**着色**（写 GBuffer）。
它默认**不**做"把网格切成簇、逐级简化、量化打包"——这些如果放在运行时：

| 放在运行时 | 后果 |
|---|---|
| 每次加载都切簇 + 简化 | Sponza 级别要数秒，且每台机器的 meshopt 结果可能不同 |
| 每帧都可能重建 | 完全不可接受 |
| 错误只在加载后暴露 | 只能在"画面不对"时反推，代价高 |
| 无法做回归 | 没有稳定产物，改一行动不动就"画面变了" |

因此本仓库把这一整段固化成**工具 + 纯函数库 + 文件格式**：

- 工具：`Tools/MeshPreprocess`（`MeshPreprocess.exe`），一次性把 glTF 转成 `.nanite`；
- 纯函数库：[`NaniteUpload.h`](../../Engine/Render/Nanite/NaniteUpload.h) 里的 `BuildNaniteClusters` /
  `BuildNaniteClusterDAG` / `PackNaniteClusters` / `WriteNaniteFile` / `ReadNaniteFile`，
  全部 RHI-free、只收 `std::span`、写调用方出参 ⇒ **可单测、可逐字节比对**；
- 文件格式：[`NaniteTypes.h`](../../Engine/Render/Nanite/NaniteTypes.h) 定稿的 `.nanite` v3。

> 一句话：**离线负责"几何怎么组织"，运行时负责"每帧怎么挑、怎么画"**。

## 2. 全流程总览

```
 glTF (Sponza.gltf)
   │
   │ ① NaniteGltfReader：解析 JSON / accessor / 节点变换，输出"已烘焙世界变换的三角形汤"
   ▼
 多个 primitive（position/normal/uv/index/materialIndex）
   │
   │ ② 选单位（--granularity）
   │    primitive：1 份资产 = 1 个 primitive
   │    mesh     ：1 份资产 = 1 个 mesh（多 primitive 合并，索引加 baseVertex）
   │    material ：1 份资产 = 1 种材质（跨 mesh 收集）
   ▼
 一份"单位"的合并几何 A（位置/法线/UV/索引/材质记录/源 primitive 区间）
   │
   │ ③ L0 簇切分：每簇 ≤ 64 三角形 / ≤ 128 顶点
   │    （按源 primitive 分组切分，避免"一个簇横跨两种材质"）
   ▼
 L0 簇集合 + 每簇 AABB/包围球 + 每簇三角形与局部顶点
   │
   │ ④ LOD 链（meshopt_simplify，每级 ~50%，最多 6 级）
   │    + DAG 去重（内容哈希：局部量化几何 + 局部三角形）
   │    + 父链（childClusterOffset/childCount）+ 误差链（maxParentLODError）
   ▼
 DAG（簇记录数组 + 各级簇区间 + 共享内容表）
   │
   │ ⑤ 量化与编码
   │    位置：10+10+10 位，相对"簇 AABB 中心"，尺度 = 整网格最大范围
   │    法线：八面体 10+10 位；UV：unorm16（编码域 [-64,64]）
   │    索引：3×u16 → 8B；材质：32B 记录（因子 + 纹理哈希/掩码）
   ▼
 字节镜像（五段 + 可选扩展段）
   │
   │ ⑥ 写出 .nanite（版本 3）+ ⑦ --verify 读回逐字节比对
   ▼
 .nanite 资产
   │
   │ 运行时：NaniteRenderer 加载 → 校验 → 上传 GPU 缓冲（簇/顶点/三角形/材质/每簇尺度）
   ▼
 剔除三阶段 → 硬光栅（默认全部簇）→ GBuffer
```

## 3. 步骤①：读 glTF

实现：[`NaniteGltfReader.h`](../../Engine/Render/Nanite/NaniteGltfReader.h)。

它做三件事：

1. **解析**：JSON（节点树 / mesh / primitive / 材质 / accessor / bufferView）；
2. **烘焙世界变换**：沿节点树累乘 `matrix`/`translation`/`rotation`/`scale`，把顶点变换到**场景空间**
   （所以 `.nanite` 资产里的坐标就是世界坐标，运行时实例变换默认取"恒等"或由资产实例表给定）；
3. **展开成三角形汤**：每个 primitive 输出 `positions`（`float3`）、`normals`、`uvs`、`indices`，
   并保留 `materialIndex` 供后续按材质拆分。

> **口径**：变换在上游做掉，后面所有步骤都只处理"世界空间三角形"，不再碰节点树。

---

## 4. 步骤②：划分"资产单位"

工具选项 `--granularity`（[`Tools/MeshPreprocess/main.cpp`](../../Tools/MeshPreprocess/main.cpp)）决定"一份 `.nanite` 装什么"：

| 粒度 | 一份资产 = | 用途 | Sponza 份数 |
|---|---|---|---|
| `primitive`（默认） | 一个 glTF primitive | 多资产档的验收件 | 103 |
| `mesh` | 一个 glTF mesh（含其全部 primitive） | **04 主样例的默认档**（整场景一份） | 1 |
| `material` | 一种材质（跨 mesh 收集同材质 primitive） | 实验：让"同一份资产只含一种材质" | 25 |

**合并几何时要注意的两件事**：

1. **索引平移**：`mesh`/`material` 粒度把多个 primitive 的顶点拼到一张表里时，索引要加 `baseVertex`；
2. **材质记录是"一 range 一条"**：同一材质的多个 primitive 各自留一条材质记录（
   `NaniteSourceMeshRange` 记录"簇 → 源 primitive"）。
   因此"按材质拆分"的校验判据**不是**"材质记录数 == 1"，而是**所有记录的 baseColor 贴图哈希一致**
   —— 哈希才是材质身份（运行时也按它查数组层号，见 §12）。

> 这一步的产物是 `NanitePackedAsset` 的输入：合并后的 `positions/normals/uvs/indices` +
> `materials[]` + `meshes[]`（每个源 mesh 的三角形区间与材质下标）。

## 5. 步骤③：L0 簇切分

关键常量（[`NaniteTypes.h`](../../Engine/Render/Nanite/NaniteTypes.h)）：

```cpp
kNaniteMaxClusterTriangles = 64u;   // 每簇最多 64 个三角形
kNaniteMaxClusterVertices  = 128u;  // 每簇最多 128 个顶点（= GPU 网格着色器每组的输出上限）
kNaniteIndicesPerTriangle  = 3u;
```

**做法**：把单位几何按"空间邻近"贪心聚成簇，每簇不超过上述上限（实现见
`BuildLevel0ClustersByMesh` / `BuildNaniteClusters`）。

**关键选择：L0 必须按"源 mesh/primitive"分组切分**。
如果直接在整条合并索引上切，一个簇可能同时包含"地板"和"柱子"两种材质 ⇒ 运行时按簇二选一写材质时，
大块表面会拿到邻居的材质（实测：**整片地板变绿/变灰**）。分组切分保证
"**一个簇只属于一个源 mesh**"，材质从此不会串。

每簇记录里同时算出：

- `boundsCenterRadius`：**簇 AABB 中心 + 到最远顶点的距离**（不是 meshopt 的最小包围球；
  原因见 §6 的去重要求 —— AABB 中心与顶点顺序无关、对整数平移逐位可交换）；
- `triangleOffset` / `triangleCount` / `vertexOffset`：簇在三角形表、顶点表里的区间；
- `materialID`：簇内三角形的多数票材质（L0 分组后其实就是唯一材质）。

## 6. 步骤④：LOD 链与 DAG

### 6.1 LOD 链：每级近似减半

对每一级：

1. 把上一级的簇组**合并回一张索引表**；
2. 用 `meshopt_simplify` 把三角形数减到约一半：

```cpp
targetIndexCount = targetTriangles * 3;
meshopt_simplify(..., /*target_error=*/0.002f, /*options=*/0u, &relativeError);
```

`target_error = 0.002f`（2‰）是**实测调出来的**：
传 1.0（100%）时 meshopt 会把整级简化成极端粗糙的代理、误差链直接顶到上限，
运行时 LOD 判据 `parentError × focal > threshold × distance` 恒成立 ⇒ **一律选根簇**（只画几十个巨三角形）；
逐步收到 0.2% 后误差才随级平滑增长、LOD 割稳定落在细级。

3. 对简化后的网格重新走 §5 的切簇；
4. 记录本级的**绝对误差**：

```cpp
absoluteError = relativeError * meshopt_simplifyScale(positions, vertexCount, stride);
```

### 6.2 三条终止条件（任一命中即停）

| # | 条件 | 目的 |
|---|---|---|
| ① | 下一级目标三角形数 `< 64`（一个满簇） | 再简也凑不满一个簇 |
| ② | `meshopt_simplify` 没有减少索引数 / 返回 0 / 不是 3 的倍数 | 防死循环 |
| ③ | 已达 `kNaniteMaxLODLevels = 6`（含 L0） | 上限 |

例：`262267 → 131133 → 65565 → 32760 → 27034 → 10538`（Sponza 实测，共 6 级；每级约为上一级的一半，最后一级因收益耗尽而变缓）。

### 6.3 DAG 去重：为什么用"簇内局部"内容哈希

每簇的内容键 = **相对该簇 AABB 中心的量化局部几何 + 簇内局部三角形**：

- 位置词 = `NaniteQuantizePositionAxis(v, 簇心, 网格最大范围)`，三轴打包成 `R10G10B10A2`，
  与落盘 `NaniteVertex::packedPosition` **同一位域**；
- 三角形 = `3×u16` 局部下标；
- **世界位置不在内容里**：它由 `boundsCenterRadius` 提供。

于是"同一份子网格的**平移副本**"（例如重复的门框）会算出**逐位相同**的位置词 ⇒ 真正共享同一份数据。
若改用绝对坐标当量化原点，则只有"完全重合"的重复簇才会命中，平移副本一律去重不了。

配套的两个防错细节：

- **顶点顺序无关**：先按内容键对局部顶点排序，再把每个三角形按"三种循环旋转里字典序最小"归一；
- **量化尺度取整网格最大范围**（不是每簇半径），这样"同一形状被放大/缩小"不会被误判成同一个簇。

### 6.4 父链与误差链

去重完成后填三样东西：

| 字段 | 含义 |
|---|---|
| `childClusterOffset` / `childCount` | 细级簇 → 粗级父簇的链接（DAG 的边） |
| `maxParentLODError` | "切到父级"的误差阈值 ⇒ 运行时判据的另一半 |
| `flags & 1` | **根簇**标记：根簇没有父级，LOD 判据必须显式放行 |

运行时 LOD 选择（DAG 割）的判据是：

```
ownError   * focalPixels > threshold * distance  ⇒ 本簇太细，拒绝（继续往上找）
根簇                                             ⇒ 选中
parentError* focalPixels > threshold * distance  ⇒ 选中（父级显得够粗，就用它）
```

其中 `threshold` 是**像素**阈值（04 样例校准为 0.25 px）。

## 7. 步骤⑤：量化与编码

### 7.1 顶点位置（10+10+10 位）

```
world = clusterCenter + (q / 1022) * meshMaxExtent      q ∈ [-512, 511]
```

- 原点 = 簇 AABB 中心（自包含，解码时不需要额外表）；
- 尺度 = **整份资产**的最大范围（`meshMaxExtent`，运行时从文件头 bbox 取）；
- 每轴 10 位（1024 档，有效步数 1022）；
- `quantBias` 字段存 512（编码偏置，落盘保留）。

误差上界 = `meshMaxExtent / (2 × 1022)`，Sponza（3720 单位）约 **1.8 单位**。

### 7.2 法线：八面体 10+10 位

`packedNormal` 把单位法线投影到八面体（octahedral）上，两轴各 10 位。
解码误差上限 `kNaniteNormalAngleErrorBoundDegrees` 在头文件里钉住。

### 7.3 UV：unorm16，编码域 `[-64, 64]`

**v3 起 UV 编码域从 `[0,1]` 扩展到 `[-64, 64]`**：

- 编码：`q = round((uv / 128 + 0.5) × 65535)`，解码反之；
- 为什么必须扩：Sponza 的 UV 是**平铺**的，实测 u ∈ [-27.8, 32.3]、v ∈ [-5.0, 7.6]；
  旧 `[0,1]` 口径会把它们截断 ⇒ 整张贴图错乱；
- 一个量化步 = `128 / 65535 ≈ 0.00195` 个 UV 单位。

### 7.4 三角形索引：3×u16 → 8B

每三角形的三个顶点是**簇内局部下标**（`< 128`），因此 u16 足够：

```cpp
struct NanitePackedTriangle { u32 w0; u32 w1; };   // 8B：低16/i0, 高16/i1, 再 i2
```

### 7.5 材质记录（32B）

```cpp
struct NaniteMaterialRecord {
    float baseColorFactor[4];   // 0..15
    float metallicFactor;       // 16
    float roughnessFactor;      // 20
    u32   textureMask;          // 24：bit0=baseColor，bit1=MR，bit2=normal
    u32   bindlessTextureBase;  // 28：离线下是 baseColor 贴图的 FNV-1a 哈希；
                                //     运行时被翻译成"数组纹理的层号"
};
```

- **离线下只存哈希**，不存句柄：句柄是运行时概念（bindless/Vulkan 描述符）；
- 运行时按哈希在"贴图哈希 → 数组层号"表里查到层号，再写回 `bindlessTextureBase`（见 §12）；
- `textureMask` 记录"这个材质到底有哪些贴图"，没有的通道不做采样。

## 8. 步骤⑥：打包与写出

打包函数 `PackNaniteClusters` 把 DAG + 共享内容表落成**字节镜像**，写出函数 `WriteNaniteFile` 写盘：

**固定五段（偏移由头部计数纯函数推导，不落盘）**：

```
[NaniteFileHeader 96B]
[clusterCount × 64B]     簇记录
[vertexCount  × 16B]     量化顶点（位置/法线/UV/偏置）
[triangleCount× 8B]      三角形（3×u16）
[materialCount× 32B]     材质记录
[lodLevelCount+1 × u32]  各级簇区间（lodOffsets）
```

**v2 起的扩展段**（16B 段表 + 载荷，载荷各自 16B 对齐）：

| 段类型 | 载荷 | 用途 |
|---|---|---|
| `MaterialDesc` | `NaniteMaterialDesc[]`（64B） | 材质描述（贴图 URI 等，bindless 运行时翻译） |
| `SourceMeshRange` | `NaniteSourceClusterRange[]` | 簇 → 源 primitive 归属 |
| `FallbackMesh` | 头 + 顶点/索引 | 低模（IA / 光追回退用） |

读取器**忽略不认识的段类型**（只按 offset/size 跳过）⇒ 后续新增段不会打破旧读取器。

## 9. `.nanite` v3 文件格式速查

### 9.1 文件头（96B，`alignas(16)`）

| 偏移 | 字段 | 说明 |
|---:|---|---|
| 0 | `magic[8]` | `"NANITE01"`（无 NUL） |
| 8 | `u32 version` | **= 3**（读取器要求 ≥ 3；v1/v2 一律拒绝） |
| 12 | `u32 clusterCount` | 簇数 |
| 16 | `u32 vertexCount` | 量化顶点数 |
| 20 | `u32 indexCount` | 索引总数（`= 各级三角形数之和 × 3`，必须是 3 的倍数） |
| 24 | `u32 materialCount` | 材质数 |
| 28 | `u32 lodLevelCount` | LOD 级数（含 L0） |
| 32 | `u32 flags` | bit0 = hasDAG |
| 36 | `float bboxMin[3]` | 量化范围下界 |
| 48 | `float bboxMax[3]` | 量化范围上界 |
| 60 | `float maxLODError` | 最大几何误差 |
| 64 | `u32 _reserved[8]` | 保留；`_reserved[5]` 存**扩展段数** |

> **为什么段偏移不落盘**：偏移是头部计数的纯函数，落盘只会制造两份可以互相矛盾的真相。

### 9.2 簇记录（64B，与 GPU 布局同构）

| 偏移 | 字段 |
|---:|---|
| 0 | `float boundsCenterRadius[4]`（xyz=中心，w=半径） |
| 16 | `NaniteConeAxisAngle cone`（轴 xyz + cosHalfAngle） |
| 32 | `u32 triangleOffset`（三角形下标） |
| 36 | `u32 triangleCount`（≤ 64） |
| 40 | `u32 vertexOffset`（顶点下标） |
| 44 | `u32 materialID` |
| 48 | `float maxParentLODError` |
| 52 | `u32 childClusterOffset`（0 = 叶子） |
| 56 | `u32 childCount` |
| 60 | `u32 _pad` |

### 9.3 校验（`ValidateNaniteFile`）

失败原因枚举 `NaniteFileError`：

```
BadMagic / BadVersion / BadIndexCount / Misaligned / OutOfBounds
BadExtSectionCount / BadExtSection / TooSmall / NullData
```

**版本门禁**：`kNaniteMinReadableFileVersion = 3`。
v2 及更早的资产会被拒绝加载（而不是"能读但 UV 错误"）——因为 v3 的 UV 编码域变了，
继续读旧文件会静默把贴图错位，比报错危险得多。

## 10. 步骤⑦：自校验

`MeshPreprocess --verify` 做两件事：

1. **读回刚写出的文件**（走运行时同一条 `ReadNaniteFile` + `ValidateNaniteFile` 路径）；
2. **与内存里的资产逐字节比对固定五段**（簇/顶点/三角形/材质/LOD 区间）。

这就是"**离线产物 = 运行时构建产物**"的可执行口径：

```powershell
# 三条粒度各跑一遍，全部应输出"校验通过"
build\bin\Debug\MeshPreprocess.exe Content\gltf\Sponza\glTF\Sponza.gltf Content\Processed   --granularity=mesh     --verify
build\bin\Debug\MeshPreprocess.exe Content\gltf\Sponza\glTF\Sponza.gltf Content\Processed\primitives --granularity=primitive --verify
```

## 12. 运行时如何使用这些资产

离线产物的每一段在运行时都有明确去向（详见 `10.Nanite实现分析.md`）：

| 离线段 | 运行时去向 |
|---|---|
| 簇记录 | `NaniteScene` 解包 → GPU 簇缓冲（剔除端与光栅端共用） |
| 顶点 / 三角形 | GPU 顶点/索引缓冲（硬光栅直接读；软光栅回退也读） |
| 材质记录 | 材质缓冲 + **哈希 → 数组层号**翻译（baseColor/MR/法线三张 `Texture2DArray`） |
| 文件头 bbox | `meshMaxExtent` → push constant + **每簇量化尺度表**（binding 22） |
| `lodOffsets` + `maxParentLODError` + 父链 | 剔除 Phase 3 的 DAG 割（`lodSelected`） |
| 扩展段 `SourceMeshRange` | 多资产/流式场景的"簇属于哪个源 mesh" |

几个运行时的关键约定（写在这里是因为**它们由离线口径决定**）：

1. **每簇量化尺度**：离线按资产 bbox 定尺度，运行时把 bbox 范围填进
   "每簇尺度缓冲"，着色器 `pos = center + q/1022 × extent[cluster]` ⇒ 多资产档每份资产可以有不同尺度；
2. **材质身份 = 贴图哈希**：离线写哈希、运行时查表换层号，因此新增资产**不能复用同一哈希给不同贴图**；
3. **默认全部簇走硬光栅**（mesh shader）：`softMaxTriangles = 0`。离线数据的 64 tri/簇 上限正好对上
   "1 个 mesh 工作组 = 1 个簇"的派发口径；实测这比软光栅路径快 2.6×（545 → 207 ms）。

## 13. 工具用法

```
MeshPreprocess <in.gltf> <out-dir> [选项]

  --granularity=primitive|mesh|material   资产粒度（默认 primitive）
  --fallback-ratio=0.02                   低模回退（FallbackMesh 段）的简化比例
  --bake-average                          把 baseColor 贴图平均色烘进材质因子（无纹理绑定时的兜底）
  --stats                                 打印逐级打包统计
  --verbose                               打印逐簇细节
  --verify                                读回文件并与内存资产逐字节比对
```

**输出命名**：`<out-dir>/<单位名>.nanite`（单位名取自 mesh/material 名，非法字符会被清洗）。

**推荐流程**：

```powershell
# 1) 生成（换资产/改阈值/改量化口径后必须重跑）
build\bin\Debug\MeshPreprocess.exe Content\gltf\Sponza\glTF\Sponza.gltf Content\Processed --granularity=mesh --verify

# 2) 让样例指向它（cfg）
#    nanite_offline=1
#    nanite_offline_path=Processed/Sponza_0.nanite
```

> **改了 §§5–7 里任何一条口径，都必须重新生成并重跑 `--verify`**：
> 旧资产不会自动失效（版本号只保护"字节布局"，不保护"算法口径"）。

## 14. 经验教训（踩过的坑）

| 坑 | 表现 | 结论 |
|---|---|---|
| UV 编码域 `[0,1]` | 平铺 UV 被截断 ⇒ 贴图整片错乱 | v3 扩到 `[-64,64]`，并拒绝旧版本 |
| 全局切簇（不按源 mesh 分组） | 整块地板变绿/变灰（簇跨材质） | L0 必须按源 mesh 分组 |
| 简化误差给 100% | LOD 一律选根簇、只画几十个巨三角形 | `target_error = 0.002f`，逐级平滑 |
| 用绝对坐标做去重哈希 | 平移副本全部无法共享 | 量化原点 = 簇 AABB 中心（簇内局部口径） |
| 用最小包围球当量化原点 | 球心随顶点顺序漂移 ⇒ 副本去重失败 | 改用 AABB 中心（顺序无关） |
| "按材质拆分"按记录数判断 | 同材质多 primitive 各留一条记录，误判失败 | 判据改为"贴图哈希一致" |
| per-material 资产独立建 LOD 链 | 同材质的分散几何被简化合并成跨距很大的粗簇 ⇒ 画面碎片化 | 该粒度只作实验/验收件；生产路径用整场景合并资产 |
| 资产版本没升就改口径 | 旧资产能读但几何/贴图错位（静默错图） | 口径变更必须升版本 + 抬 `kNaniteMinReadableFileVersion` |
