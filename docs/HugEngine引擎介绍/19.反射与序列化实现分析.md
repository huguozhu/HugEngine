## 2. 宏驱动的类注册

### 2.1 `HE_CLASS()` 展开成什么

`ReflectionMacros.h:28-32`：

```cpp
#define HE_CLASS() \
public: \
    static const ::he::reflect::ClassInfo* StaticClass(); \
    virtual const ::he::reflect::ClassInfo* GetClass() const { return StaticClass(); } \
private:
```

三点事实：

1. `StaticClass()` 只有**声明**，定义由 `.cpp` 里的 `HE_BEGIN_REGISTER` 提供；漏了注册就会是链接错误，而不是运行时静默失败。
2. `GetClass()` 是**虚函数且在类体内内联定义**。因为它在每个派生类里各自展开一次（`Component.h:27`、`CubeComponent.h:15` …），未限定名的 `StaticClass()` 解析到**该类自己的**静态成员，所以 `comp->GetClass()` 返回最派生类型的 `ClassInfo`——这正是 `ForEachProperty<Base>(obj,…)` 能拿到派生属性的原因（`ReflectionAPI.h:117-125`）。
3. `HE_CLASS()` 前后是 `public:` / `private:`，所以必须写在类体最前面（`Component.h:26-28` 就是这么用的）。

`HE_COMPONENT()` 与 `HE_RESOURCE()` 当前只是 `HE_CLASS()` 的同义别名（`ReflectionMacros.h:34-35`），没有任何附加语义。`HE_RESOURCE()` 在 `Engine/`+`Samples/`+`Tests/`（排除 `External`）中 **0 处使用**，只出现在宏定义行本身。

`TypeInfo.h` 是兼容入口，同时 include 稳定 API 与宏后端（`TypeInfo.h:12-13`）；`Component.h:3` 走的就是这条路径。`Reflect/README.md:7-10` 描述的 `^T`/`meta::info`/`Splicer`/`PropertyDescriptor` 属于**未实现**的规划内容（本工程无这些符号）。

### 2.2 `HE_BEGIN_REGISTER` / `HE_END_REGISTER` 展开成什么

`ReflectionMacros.h:41-49` + `ReflectionMacros.h:89-94` 合起来是：

```cpp
const ::he::reflect::ClassInfo* he::XxxComponent::StaticClass() {
    static ::he::reflect::ClassInfo s_Info;     // 函数内静态，零初始化
    static bool s_Initialized = false;          // 函数内静态守卫
    if (!s_Initialized) {
        s_Info.name     = "he::XxxComponent";   // #ClassName 原样字符串化
        s_Info.size     = sizeof(he::XxxComponent);
        s_Info.typeHash = ::he::reflect::HashString("he::XxxComponent");
        s_Info.factory  = []() -> void* { return new he::XxxComponent(); };
        // ... HE_REGISTER_PROPERTY 块在此展开 ...
        s_Initialized = true;
        ::he::reflect::TypeRegistry::Instance().RegisterClass(&s_Info);
    }
    return &s_Info;
}
```

关键点：

- **`s_Info` 地址稳定**：函数内 `static`，注册表存的是裸指针 `const ClassInfo*`（`ReflectionAPI.h:102`），生命周期到进程结束，所以没有悬垂问题。
- **不是线程安全的一次性注册**：`s_Initialized` 是普通 `bool`，没有 `std::call_once`/`std::atomic`（`ReflectionMacros.h:44-45,90`）。当前所有首次 `GetClass()` 都发生在主线程（`World::AddComponent`、`ForEachComponent`、测试），所以没暴露；但多线程首次触碰同一类型是数据竞争。
- **`parent` 永不赋值**（`ReflectionAPI.h:64` 默认 `nullptr`）。宏不填它，全工程也没有任何读写 `ClassInfo::parent` 的代码 → 继承关系在元数据里**是断的**。这也解释了为什么 `SpotLight` 要把基类 `color/intensity/castShadow` 再注册一遍（`SceneReflect.cpp:100-122` 注释里也说明了这一点）。

### 2.3 `StaticClass()` 的惰性注册时机

宏不产生任何静态初始化语句，也没有"启动时遍历所有类注册一遍"的入口。所以注册时机完全取决于**谁先调用 `StaticClass()`（或虚 `GetClass()`）**：

- 典型触发点是 `World::AddComponent<T>()`（组件构造后 `GetClass()` 被调用）与 `World::ForEachComponent`；
- `TestWorldModel.cpp:89-92` 直接给出了这条约束的书面说明与对策：

  > `// TypeRegistry 为惰性注册（StaticClass() 首次调用才注册），先触发这三个类的注册`
  > `he::SpotLight::StaticClass(); he::RectLight::StaticClass(); he::CameraComponent::StaticClass();`

  即：**没有造过实例的类型，在 `TypeRegistry` 里就是查不到的**。`TestDecal.cpp:142` 同样在 `FindClass` 之前先手动 `d->StaticClass()`。

- 直接后果：`SceneSerializer::Load` 与 `LevelLoader::AddComponentByHash` 都靠 `FindClassByHash` 找类型，而这两个路径**恰恰不会先造实例**——它们是"从文件造实例"的路径。在空世界里打开 `.hescene` 时，先前的 `StaticClass()` 只可能来自同进程更早的构建步骤（例如 `AddComponent<T>` 或 `ForEach`），不存在"为保证 Load 可用"而做的强制注册。

## 3. 属性注册

### 3.1 `HE_REGISTER_PROPERTY` 展开

`ReflectionMacros.h:54-61`：

```cpp
#define HE_REGISTER_PROPERTY(ClassName, Type, Member) \
        { \
            ::he::reflect::PropertyInfo prop; \
            prop.name     = #Member; \
            prop.offset   = offsetof(ClassName, Member); \
            prop.size     = sizeof(Type); \
            prop.typeName = #Type; \
            prop.flags    = ::he::reflect::PF_Serializable;
```

配合 `HE_END_PROPERTY()`（`ReflectionMacros.h:85-87`）闭合并 `push_back`。

必须理解的 4 个设计约束（注释里只在 `ReflectionMacros.h:52-53` 提到第 1 条）：

1. **`ClassName` 必须显式传入**：宏参数不能跨宏传递，所以每个属性都要把类名再写一遍（`ReflectionMacros.h:52-53`）。
2. **`typeName` 是宏实参的**原样字符串**，不是 `typeid`/规范化类型名**。所以 `float` 与 `f32` 会得到两个不同的字符串 `"float"` / `"f32"`——尽管 `using f32 = float`（`Core/Types.h:30`）它们是同一个 C++ 类型。这是后面 §6.3/§7 一系列"类型不在分派表里"问题的**根因**。
3. **`flags` 初值是 `PF_Serializable`**（`ReflectionMacros.h:61`），即**默认所有注册属性都参与存档**；`HE_ATTR_READ_ONLY`/`HIDDEN`/`REPLICATED`/`DEPRECATED` 是在此基础上 `|=`（`ReflectionMacros.h:68-73`）。
4. `offsetof` 要求类型是**标准布局**；`SpotLight`/`RectLight` 注册基类 `LightComponent` 的成员（`SceneReflect.cpp:100`、`251` 的注释）之所以可行，是因为 `Component` 只有虚函数 + 标准布局成员，没有虚基类/多重继承。`Component` 自身含虚析构（`Component.h:30`），严格说 `offsetof` 在此属于实现定义行为——实际 MSVC/GCC/Clang 都按预期工作，故列为 §11 的未复核项。

`PropertyInfo::size` 的"无效"还有一个具体细节值得记下：`float3` 在 HugEngine 里是 `glm::vec3`（`Core/Math/Math.h:25`），而 `Math.h:9` 打开了 `GLM_FORCE_DEFAULT_ALIGNED_GENTYPES` → `defaultp = aligned_highp`（`glm/detail/qualifier.hpp:26-27`）→ `vec<3,float,aligned_highp>` 用 `storage<3,T,true>`，其定义为 `struct alignas(4*sizeof(T)) { T data[4]; }`（`glm/detail/qualifier.hpp:101-107`）。所以 `sizeof(float3) == 16` 而不是 12，`prop.size` 若被当成"字节数"使用会与真实序列化长度（12 字节，见 §6.2）不一致。二者今天都没人用，所以不构成现有 bug，但**是接线时的坑**。

## 5. TypeRegistry

### 5.1 哈希键算法

`ReflectionAPI.h:77-84`：

```cpp
constexpr u64 HashString(StringView str) {
    u64 hash = 14695981039346656037ull;
    for (char c : str) {
        hash ^= static_cast<u64>(c);
        hash *= 1099511628211ull;
    }
    return hash;
}
```

即标准 FNV-1a 64 位，`constexpr` 因而编译期/运行期皆可：

$$h_0 = 14695981039346656037,\qquad h_{k+1} = \left( h_k \oplus c_k \right) \times 1099511628211 \bmod 2^{64}$$

`c_k` 是类型名字符串的**有符号 char**（`for (char c : str)` → `static_cast<u64>(c)`）。对纯 ASCII 的名字来说符号扩展不产生差异；若类型名含非 ASCII 字节（当前不存在），符号扩展会让哈希与"无符号字节"版本不同——这是**格式稳定性**上的潜在隐患，因为 `.hescene` 里存的就是这个哈希。

### 5.2 查找路径

`TypeRegistry.cpp:8-32`。注册表本体是 `std::unordered_map<u64, const ClassInfo*>`（`ReflectionAPI.h:102`），**只有哈希一个键**，没有名字索引：

| 入口 | 实现 | 说明 |
|---|---|---|
| `Instance()` | `static TypeRegistry s_Registry; return s_Registry;`（`TypeRegistry.cpp:8-11`） | 函数内静态单例（懒初始化，C++11 起线程安全） |
| `RegisterClass(info)` | `m_ClassMap[info->typeHash] = info;`（`TypeRegistry.cpp:13-16`） | **后注册覆盖先注册**，无重复检测、无告警 |
| `FindClass(name)` | 先 `HashString(name)` 再转 `FindClassByHash`（`TypeRegistry.cpp:18-21`） | 所以"按名查"要求调用方给出**与注册时逐字节相同**的名字，含命名空间 |
| `FindClassByHash(hash)` | `map.find(hash)`，未命中返回 `nullptr`（`TypeRegistry.cpp:23-26`） | 唯一被生产代码使用的查找入口 |
| `ForEachClass(cb)` | 遍历 map，跳过空指针（`TypeRegistry.cpp:28-32`） | **迭代顺序 = `unordered_map` 桶序**，非确定性；`WorldModel::TypeSchema()` 的输出顺序因此不稳定 |

按名查找必须带命名空间，这一点有代码佐证：`Tests/TestDecal.cpp:143` 写的是 `FindClass("he::DecalComponent")`（不是 `"DecalComponent"`）。这条事实正是 §1.3/§7.3 那个死分支问题的根据。

两个生产调用点：`SceneSerializer.cpp:124` 与 `LevelLoader.cpp:42` 用 `FindClassByHash`；`WorldModel.cpp:141` 用 `ForEachClass`。`FindClass(StringView)` 在生产代码里 **0 调用**（只有测试用）。

### 5.3 `factory` 的生成与"当前无消费方"

生成（`ReflectionMacros.h:49`）：

```cpp
s_Info.factory = []() -> void* { return new ClassName(); };
```

`ClassInfo::factory` 的类型是 `std::function<void*(void)>`（`ReflectionAPI.h:66`）。语义上有三点值得注意：

1. **返回裸 `void*`**：调用方拿到后必须自己知道该 `delete` 成什么类型/或转换后交给谁，接口本身不提供析构器（对比 `factory` 无配对的 `deleter`）。
2. **构造的是默认对象**：`new ClassName()` 走默认构造函数，之后还需要靠 `PropertyInfo` 逐字段回填才能还原一个有意义的组件——也就是"工厂 + 属性反射"必须成对使用才有用。
3. **构造后没有 `OnCreate()` 触发**：`Component` 的生命周期是 `OnCreate/OnStart/OnUpdate/OnDestroy`（`Component.h:33-36`），`World::AddComponent<T>` 会负责状态迁移与 `OnCreate`（这一点是组件接入 World 的既有约定，`SceneBuilder.cpp:137,145,204,211` 在改完几何参数后要**手动**再调 `OnCreate()`，反证 `AddComponent` 之后改参数不会自动重建）。`factory` 返回的对象是游离的，与 `World` 的存储/`SceneGraph` 无关。

**"无消费方"的复核方式与结果**：对 `Engine`+`Samples`+`Tests`（排除 `External`）全量搜 `\bfactory\b`，命中只有：

- `Engine/Reflect/Reflect/ReflectionAPI.h:66` —— 成员声明
- `Engine/Reflect/Reflect/ReflectionMacros.h:49` —— 唯一赋值点

其余命中都属于**同名的其它东西**，与反射无关：`he::ai::aigc::GenerativeAssetFactory`（`Engine/AI/AIGC/AIGCProvider.cpp:26`、`Samples/07.AISamples/Features/*.cpp`、`Tests/TestAIGCProvider.cpp:59`）、Jolt 的 `JPH::Factory`（`Engine/Physics/Physics/PhysicsWorld.cpp:23`）、DXGI Factory（`VulkanDevice.cpp:1325` 注释）。

> 结论：`ClassInfo::factory` **仍然没有消费方**，§17 P0-3 的这条判断成立且未过期。

## 6. 序列化

### 6.1 Archive 接口

`Archive.h:17-55`。`ArchiveMode` 只有 `Read`/`Write`（`Archive.h:20`），`IArchive` 用 `IsWriting()/IsReading()` 做分支（`Archive.h:29-30`）。

接口分三层：

1. **纯虚标量/字符串**：`bool,i32,u32,i64,u64,f32,f64,String`（`Archive.h:33-40`）
2. **非纯虚向量**：`float3,float4,quat`（`Archive.h:41-43`，声明为 `virtual` 但无 `= 0`），由 `IArchive` 提供默认实现（`BinaryArchive.cpp:86-104`）——即"向量 = 逐分量递归调用标量重载"。因为这三个不是纯虚，`BinaryArchive` 不覆写它们（`BinaryArchive.h:22-33` 的 override 列表里确实没有）。
3. **结构/数组边界**：`BeginObject/EndObject`、`BeginArray(name, u32& count)/EndArray`（`Archive.h:46-51`）

`Archive.h:11-15` 的注释说"支持 Binary（紧凑）和 JSON（人类可读）两种格式"，但全工程 `IArchive` 的实现**只有 `BinaryArchive` 一个**（`BinaryArchive.h:12`），没有 JSON 归档类。`Serialize/CMakeLists.txt` 的源文件列表也只有 `Archive.h` + `BinaryArchive.{h,cpp}` 三个文件。

### 6.2 BinaryArchive 的编码

| 方法 | 位置 | 编码 |
|---|---|---|
| `WriteBytes` | `BinaryArchive.cpp:14-19` | 按需 `resize` 后 `memcpy`，`m_Pos += size`；**越界视为扩容** |
| `ReadBytes` | `BinaryArchive.cpp:21-25` | `if (m_Pos + size > m_Buffer.size()) return;` —— **静默失败，不前进不报错**，也没有 `IsError()` 之类的标志 |
| `Serialize(bool/i32/u32/i64/u64/f32/f64&)` | `BinaryArchive.cpp:27-53` | 7 个重载**全部忽略 `name` 形参**（源码里写成 `StringView /*name*/`），直接 `Write(v)`/`Read(v)` 写 `sizeof(T)` 字节。原生小端序、无字节序转换、无版本标记 |
| `Serialize(String&)` | `BinaryArchive.cpp:55-66` | `u32 len` + `len` 字节原始数据；读侧 `v.resize(len)` 后 `ReadBytes(v.data(), len)` |
| `Serialize(float3/float4/quat&)` | `BinaryArchive.cpp:86-104` | 逐分量：`float3`→3 次 `f32`；`float4`/`quat`→4 次 `f32`。**四个分量共用同一个 `name`**（`BinaryArchive.cpp:92-97` 传的都是 `name`） |
| `BeginObject`/`EndObject` | `BinaryArchive.cpp:68-69` | **空实现**（不写任何标记） |
| `BeginArray`/`EndArray` | `BinaryArchive.cpp:71-76` | 写/读 `u32 count`；`EndArray` 空实现 |

由"`name` 全被忽略 + Object 边界为空实现"可推出：**`BinaryArchive` 是纯位置流**，读回时完全依赖"同一份 `ClassInfo`、同样的属性顺序、同样的分派分支"。因为读侧靠 `PropertyInfo::offset` 直接定位成员（`SceneSerializer.cpp:145` → `SerializeProperty` 用 `*(T*)ptr`），所以流里的字节数与属性顺序必须与写侧逐条对齐，**一旦写侧多写/漏写一条属性，后续所有属性都会错位且无任何告警**（`ReadBytes` 静默返回 + 无错误标志，`BinaryArchive.cpp:22`）。

单个组件的数据段长度（写侧 `w32((u32)d.size())`，`SceneSerializer.cpp:71`）为：

$$S_{\mathrm{comp}} = \sum_{k \in K} n_k \, s_k + \sum_{j \in J} \left( 4 + L_j \right)$$

其中 $K$ 是该组件里**分派表支持**的类型名集合，$s_k$ 是其字节宽度（`bool` 1、`i32`/`u32`/`f32` 4、`i64`/`u64`/`f64` 8、`float3` 12、`float4` 16、`quat` 16），$J$ 是 `String` 属性集合，$L_j$ 是该字符串的 UTF-8 字节长度。**注意 `s_{float3}=12` 而不是 `sizeof(float3)=16`**：写侧走成员访问（`BinaryArchive.cpp:86-90` 的 `v.x/v.y/v.z`），不写 glm 的对齐填充。

`Save`（`SceneSerializer.cpp:44-87`）自建 `std::vector<u8> buffer`，用手写 `w32`/`w64` 小端辅助函数（`SceneSerializer.cpp:46-47`）拼装，最后一次性 `std::ofstream` 二进制写出（`SceneSerializer.cpp:82-84`）。布局：

要点与已确认的缺失：

- **扩展名 `.hescene`** 由调用方给出路径，不是 API 的一部分：编辑器硬编码 `"Content/Scenes/scene.hescene"`（`EditorApp.cpp:409,412`），内容浏览器按扩展名识别并触发加载（`ContentBrowserPanel.cpp:78,92-96`）。`Content/Scenes/` 只放了 `.gitkeep`——**仓库里没有任何 `.hescene` 样本文件或往返测试夹具**（`Tests/` 46 个测试文件中没有 `TestSceneSerializer*`）。

- **`kVersion` 有校验但无兼容分支**：`Load` 版本不等直接报错返回（`SceneSerializer.cpp:103`）；`LevelLoader` 读了版本号却**丢掉不校验**（`LevelLoader.cpp:73` 的 `u32 ver = r32();` 之后无引用）。
- **`typeHash` 是跨构建的唯一类型标识**（`= HashString(#ClassName)`，`ReflectionMacros.h:48`）：重命名类型的命名空间/类名即破坏旧存档，且无任何提示（`FindClassByHash` 返回 `nullptr` → `SceneSerializer.cpp:125` 的 `p+=ds; continue;`）。
- **属性顺序即格式**：data 段里没有属性名、没有属性数、没有属性尺寸表（§6.2），所以**给某个类增删一条已注册属性即破坏旧 `.hescene`**。
- GPU 资源不入存档（`MeshComponent` 空注册，`SceneReflect.cpp:57-58`），与 `§9` 注释"GPU 资源不序列化，靠原 glTF 重建"一致。

### 7.3 Load 为什么仍靠名字 if-else —— 两级失效

`SceneSerializer.cpp:127-138`：

```cpp
// 按类型名创建组件（通过 AddComponent）
StringView cn=cls->name;
Component* added=nullptr;
if      (cn=="TransformComponent")  added=world.AddComponent<TransformComponent>(ent);
else if (cn=="MeshComponent")       added=world.AddComponent<MeshComponent>(ent);
else if (cn=="CubeComponent")       added=world.AddComponent<CubeComponent>(ent);
else if (cn=="SphereComponent")     added=world.AddComponent<SphereComponent>(ent);
else if (cn=="DirectionalLight")    added=world.AddComponent<DirectionalLight>(ent);
else if (cn=="PointLight")          added=world.AddComponent<PointLight>(ent);
else if (cn=="SpotLight")           added=world.AddComponent<SpotLight>(ent);
else if (cn=="LightComponent")      added=world.AddComponent<LightComponent>(ent);
else { p+=ds; continue; }
```

**第一级（§17 P0-3 说的问题，成立）**：不做 `factory` 接线，硬编码 8 个分支，其余 28 个已注册类型全部走 `p+=ds; continue`（`SceneSerializer.cpp:138`）——数据被跳过。

**第二级（本次新发现，让第一级失去意义）**：`cls->name` 是 `"he::TransformComponent"`，永远不会等于 `"TransformComponent"`。证据链：

1. `s_Info.name = #ClassName;`（`ReflectionMacros.h:46`）——宏实参原样字符串化；
2. 全部 36 个 `HE_BEGIN_REGISTER` 调用点都传**带命名空间**的名字（`SceneReflect.cpp:39` 的 `he::Component`、`PhysicsReflect.cpp:14` 的 `he::RigidBodyComponent`、`AgentReflect.cpp:17` 的 `he::ai::AgentComponent`）；
3. `TestDecal.cpp:143` 也按这个约定写：`FindClass("he::DecalComponent")`；
4. `WorldModel` 侧为此专门写了 `StripNamespace`（`WorldModel.cpp:22-26`），并在用 `cls->name` 前先剥前缀（`WorldModel.cpp:97,149`）——反证"带前缀"是事实，而不带前缀的比较是 bug；
5. `StringView` 就是 `std::string_view`（`Core/Types.h:37`），`==` 是逐字节比较，没有归一化。

**推断结论**：这 8 个分支全部不可达，`Load` 的组件覆盖数实际是 **0**。而 `World::CreateEntity`（`World.cpp:23-29`）只往 `m_Entities` 里塞一个 `Entity`，**不自动加 `TransformComponent`**，所以一次 `Load` 的结果是"一批没有任何组件的实体 + 正确的层级"。这也解释了为什么这个 bug 没被测试抓到：没有 `.hescene` 往返测试（§6.4），而人工打开编辑器时看到的是"场景空了"，很容易被当成路径写错。

**交叉验证用的另一份表**：`LevelLoader::AddComponentByHash`（`LevelLoader.cpp:41-56`）同构且分支更多（10 个：`MeshComponent`/`CubeComponent`/`SphereComponent`/`DirectionalLight`/`PointLight`/`SpotLight`/`LightComponent`/`SkyboxComponent`/`CameraComponent`/`AnimationComponent`），同样是裸名比较，同样全部不可达。

### 7.4 `LevelLoader` 的额外差异

`LevelLoader` 用于 `LevelComponent`（Level 资产）的分块加载/卸载（`LevelLoader.h:20-30`）。与 `SceneSerializer` 的差异（`LevelLoader.cpp:59-125`）：

1. **每个实体无条件先加 `TransformComponent`**（`LevelLoader.cpp:86`），再走 `AddComponentByHash` 补其它组件。因为 `AddComponentByHash` 的分支表里**没有 `TransformComponent`**，存档中的 transform 数据被跳过后，实体使用默认 transform（位置 0、缩放 1）——"能看见但位置全错"，比"什么都没有"更难察觉。
2. **不校验 version**：读了 `ver` 却不用（`LevelLoader.cpp:73`）。
3. **`DeserProp` 是只读版本，且是一个独立复制的分派表**（`LevelLoader.cpp:26-39`），与 `SceneSerializer::SerializeProperty` 当前逐条一致（因此"两边同时漏 `float`"是自洽的），但这是**靠人工同步**维持的一致：任何一侧单独补一个类型，读写字节数就会错位（§6.2 无错误检测）。
4. **层级收尾**：把没有合法 parent 的根实体挂到 `LevelComponent` 的实体下（`LevelLoader.cpp:117-121`），并记录 `children` 以便 `UnloadLevel` 逆操作（`LevelLoader.cpp:127-133`）。
5. `LevelComponent` 自身是空注册（`SceneReflect.cpp:191-192`），所以 `levelPath`/`bExpanded` 等字段不入档、也不进 AI 快照。

### 9.1 新增一个组件：改动面清单

### 9.2 新增一个属性：比新增组件轻，但有两个暗礁

- 属性粒度上，反射**自动**覆盖：存档写入（分派表 #2 × `PF_Serializable`）、AI 快照（若带 `AiVisible`）、`SetProperty`（若带 `AiWritable`）；编辑器面板仍需手写控件。
- **暗礁 1（类型）**：`typeName` 若是 `float`/`int`/`u8`/`float2`，则至少有一张表不认识它（§6.3 表），表现为"静默不存/不导出"，没有任何编译或运行期告警。用 `f32` 写能多过 #1/#2/#3 却过不了 #4。
- **暗礁 2（顺序）**：给已注册类**插入或删除**一条属性会改变 data 段布局，旧 `.hescene` 立刻失效（§6.4）。追加到末尾是唯一"相对安全"的位置，但这只是因为没有属性名/尺寸表，**追加在结构上并不比插入更安全**：`Load` 的属性顺序来自同一份 `ClassInfo`，字节数却来自文件，二者错位后 `ReadBytes` 的静默越界（`BinaryArchive.cpp:22`）会让错误数据被当成合法值写入成员。

## 10. 已知缺口与改进方向

每条给出代码位置。**不含工期/优先级排序**，只列缺口与最小改动点。

### 10.1 `ClassInfo::factory` 未接线

- 现状：`factory` 在 `ReflectionMacros.h:49` 生成、`ReflectionAPI.h:66` 声明，0 消费方；`SceneSerializer::Load` 用 8 分支 `if-else`（`SceneSerializer.cpp:128-138`），`LevelLoader::AddComponentByHash` 用 10 分支（`LevelLoader.cpp:41-56`）。
- 接线前必须先解决的两件事（否则接上也无效）：
  1. **`cls->name` 带命名空间**（§7.3）——要么在 Load 侧 `StripNamespace`（照抄 `WorldModel.cpp:22-26`），要么把 `factory` 当作唯一入口从而不再比名字；
  2. **`factory` 返回裸 `void*` 且无配对析构**（`ReflectionAPI.h:66`）——`World` 的组件存储是 `unique_ptr<Component>`（`ComponentEntry`），从 `void*` 转成 `Component*` 再交出所有权是可行的（所有注册类都派生自 `Component`），但契约需要写下来。
- 另需注意：`factory` 造出的对象**不在 `World` 的存储里**，也不会触发 `OnCreate/OnStart`。要真正可用，路径应是"`factory()` 造 `Component*` → `World` 接管并注册 `ClassInfo`"，而不是"工厂直接返回可用的组件"。

### 10.2 类型分派表收敛到一处

- 6 处位置见 §6.3 表。其中 #1 `Archive.h:72-83` 的 `SerializeObject<T>` 是**现成的收敛目标**（覆盖度 92.3%），且 0 调用点。
- 收敛的现实约束：6 处**方向不同**（#1/#2/#3 是 Archive 流、#4 是 Archive→JSON、#5/#6 是 JSON↔内存），不能简单合并成一个函数；可行方向是"一张 `typeName → {宽度, 读写函数指针}` 注册表"，让 Archive 流与 JSON 两条路径都从同一张表取元数据。
- 收敛后必须**补齐缺失类型**（`float`/`int`/`u8`/`float2`/`f32`），否则只是把 6 份不一致的表换成 1 份不一致的表。

### 10.3 `float`（52 条）在存盘路径上完全静默丢失

- 根因：`typeName` 是宏实参字符串（`ReflectionMacros.h:60`），`using f32 = float`（`Core/Types.h:30`）导致同一类型产生两个名字。
- 现象：`SceneSerializer.cpp:32` 只认 `"f32"`，`SceneSerializer.cpp:38` 是静默跳过；`LevelLoader.cpp:33` 同理。
- 最小改动：在 #2/#3 各加一条 `else if (typeName == "float")` 分支（照抄 `Archive.h:79` 的写法）；更彻底的做法是让 `HE_REGISTER_PROPERTY` 把 `float`/`f32` 归一（例如统一写 `f32`），但那会改变已有 `typeName` 字符串，影响 `.hescene` 与 AI 快照/`Action` 的匹配面，需要一并评估。

### 10.4 `u8`/`int`/`float2`/`f32` 等已注册类型的静默丢失

- 逐条位置：`DecalComponent::blendMode`（`SceneReflect.cpp:294`）、`CollisionComponent::shape`（`SceneReflect.cpp:304`）、`RigidBodyComponent::shape`（`PhysicsReflect.cpp:15`）为 `u8`；`SplineMeshComponent::segments`（`SceneReflect.cpp:369`）、`NavMeshComponent::width/height`（`SceneReflect.cpp:384,387`）为 `int`；`BillboardComponent::size`（`SceneReflect.cpp:253`）、`DecalComponent::size`（`SceneReflect.cpp:282`）为 `float2`；`AgentComponent::thinkInterval`（`AgentReflect.cpp:24`）为 `f32`。
- 覆盖面：`u8` 只有分派表 #4 认（`WorldModel.cpp:36`），所以这三个"形状/混合模式"字段能进 AI 快照却存不进盘；`float2` 也只有 #4 认（`WorldModel.cpp:38-42`），于是"贴花尺寸"在 AI 眼里有值、存档回来是默认值；`f32` 反过来——能存盘，但 `WorldModel.cpp:30-65` 不认它，`TypeSchema()` 会把它列进字段表、`Snapshot()` 却**读不出值**（走 `WorldModel.cpp:63` 的 `HE_CORE_WARN`，且 `Snapshot` 连 warning 都不打，因为 `Snapshot` 用的也是同一个 `SerializeValue`）。
- 建议的写法：让"注册阶段"就拒绝不在支持表里的类型（编译期 `static_assert` 或运行期注册时告警），把静默失败变成显式失败。

### 10.5 加载路径的组件覆盖不全（含两个独立 bug）

1. **命名空间不匹配**（§7.3）：`SceneSerializer.cpp:130-137`、`LevelLoader.cpp:45-54` 的裸名比较全部不可达 → 实际覆盖 0 种组件类型。
2. **`LightComponent` 基类分支的顺序陷阱**：`SceneSerializer.cpp:137` 把 `"LightComponent"` 放在 4 个光源子类之后，逻辑上是对的（子类优先），但由于 1 完全无效；修 1 时要注意保持这个顺序。
3. **`LevelLoader` 无条件加 `TransformComponent`**（`LevelLoader.cpp:86`）会把存档里的 transform 覆盖成默认值（因为 `AddComponentByHash` 表里没有 `TransformComponent`）。
4. **`LevelComponent` 等 28 个已注册类型在 Load 侧无任何分支**；`MeshComponent` 虽在表内（`SceneSerializer.cpp:131`）但它是空注册（`SceneReflect.cpp:57-58`），所以网格的材质参数本来就不在档里。
5. **`idMap` 用 `operator[]` 还原层级**（`SceneSerializer.cpp:154`）会在缺键时插入 `Entity{0}`，应改为 `find` 命中检查（`LevelLoader.cpp:112-113` 就是正确写法，可对照）。

### 10.6 元数据字段"写了没人读"

`ClassInfo::size`（`ReflectionAPI.h:62`）、`ClassInfo::parent`（`ReflectionAPI.h:64`，且永不赋值）、`PropertyInfo::size`（`ReflectionAPI.h:43`）、`GetMemberPtr`（`ReflectionAPI.h:110-114`）、`AttributeValue`（`ReflectionAPI.h:26-29`）、`kReflectionBackend`（`ReflectionMacros.h:20`）、`SerializeObject`（`Archive.h:61-90`）——全部 0 消费方，是"接口先摆好"的沉淀，需要一个清理或接线的决定。

其中 `ClassInfo::parent` 永不赋值会**误导读者以为有继承链**：`SpotLight` 把基类的 `color/intensity/castShadow` 重复注册（`SceneReflect.cpp:105,108,120`）正是"元数据没有继承"的直接后果——同类问题在 `PointLight`/`RectLight` 上也都存在（`SceneReflect.cpp:88,91`、`136,139,148`）。

### 10.7 编辑器属性面板与反射脱节

`DetailsPanel.cpp` 不 include 任何 `Reflect/*` 头（`DetailsPanel.cpp:3-17` 的 include 列表），字段控件全部是 `GetComponent<T>` + 手写 `ImGui::`（`DetailsPanel.cpp:98-437`），"Add Component" 菜单也是 `strcmp` 硬编码 9 项（`DetailsPanel.cpp:81-89`）。因此 `HE_ATTR_CATEGORY`（104 处）、`HE_ATTR_RANGE`、`HE_ATTR_DISPLAY_NAME`、`HE_ATTR_TOOLTIP`、`HE_ATTR_READ_ONLY` 这些注解即使补上调用点也没有渲染方。
