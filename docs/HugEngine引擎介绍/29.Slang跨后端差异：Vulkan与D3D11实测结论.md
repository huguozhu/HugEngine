# 29.Slang 跨后端差异：Vulkan / D3D11 / D3D12 的实测结论

> 本文记录**同一份 Slang 源码同时服务三个后端**时的行为差异，以及本引擎为消除差异所做的改造：
> Vulkan（SPIR-V）、D3D11（HLSL → DXBC / SM 5.0）、D3D12（HLSL → DXIL / SM 6.6+）。
>
> 结论均来自 `slangc`（Vulkan SDK 1.4.341.1）与本仓库 `Tools/ShaderToDxil` 的实测，不是推测。
>
> 【文件名说明】文件名沿用早期的"Vulkan 与 D3D11"，是为了不打断已有链接；内容已覆盖 D3D12。
>
> 【历史包袱】本文早期版本描述过一套 `HE_DECL_*` 宏 + `Tools/ShaderToDxbc` 的方案，那套代码**已不在树中**：
> 现在不改写着色器的绑定声明，改为**在工具侧做寄存器文本补丁**（见 §2.3）。差异与实测仍然有效，方案已换代。

---

## 1. 为什么需要这份文档

引擎的着色器统一用 Slang 编写，一份源码要产出三套字节码：

| 后端 | 目标 | 编译器 | 产物 | 数量 |
|---|---|---|---|---|
| Vulkan | SPIR-V | `slangc -target spirv` | `*.spv.h` | 144 个 |
| D3D12 | HLSL → DXIL（SM 6.6；VS 用 6.8）| `slangc -target hlsl` → `dxc` | `*.dxil.h` | 144 个 |
| D3D11 | HLSL → DXBC（SM 5.0）| `slangc -target hlsl` → `fxc`（`D3DCompile`）| `*.dxbc.h` | 117 / 144（见 §9）|

问题在于：**Slang 对 D3D 目标的绑定处理与 Vulkan 完全不同**，而 C++ 侧按**固定绑定编号**绑定资源；
编号一旦变化，整个渲染就错乱。此外 SM 5.0 与 SM 6.6 的可表达范围也差着一代。

---

## 2. 核心差异一：绑定声明（最关键）

### 2.1 实测结论（三个后端都验证过）

| 写法 | → SPIR-V | → HLSL（DXBC / DXIL） | 说明 |
|---|---|---|---|
| `[[vk::binding(3, 0)]] T u;` | ✅ 绑定 = 3 | ❌ **被忽略**，自动编号成 `t0` | `vk::` 命名空间只对 SPIR-V 有效 |
| `[[register(t3)]] T u;` | ⚠️ `warning E31000: unknown attribute` | ❌ 无效 | **不是合法属性**，会被静默忽略 |
| `[register(t3, space0)]` | ⚠️ 同上 | ❌ 无效 | 同上 |
| **`T u : register(t3, space0);`** | ✅ | ✅ **编号保留** | **声明后缀语法**，Slang 原生支持 |
| 不写任何绑定 | ✅ 自动编号 | ✅ 自动编号 | 按声明顺序，违背"固定编号"契约 |

**关键结论：Slang 的 `register` 是"声明后缀"语法，不是属性语法。**
写成属性（`[[register(...)]]`）只会得到一个被忽略的警告，退出码仍是 0 —— 这一点极具欺骗性。

### 2.2 后缀语法与 Vulkan 的属性语法位置相反

```slang
// Vulkan：绑定属性在声明**之前**
[[vk::binding(3, 0)]] StructuredBuffer<float> u_Input;

// D3D：寄存器后缀在声明**之后**
StructuredBuffer<float> u_Input : register(t3, space0);
```

⇒ 单个"前缀宏"无法同时满足两者 —— 但本引擎**也不再为此写宏**（见 2.3）。

### 2.3 现状：一份 `[[vk::binding]]` 源码 + 工具侧寄存器文本补丁

着色器里**只写 `[[vk::binding(B, S)]]`**（Vulkan 口径即唯一口径），D3D 的 `register/space` 由
`Tools/ShaderToDxil` 在编译前**按源码补出来**：

```slang
// PBR.frag.slang:37-39   —— 只有 vk::binding，没有 register 后缀
[[vk::binding(kGPUBinding_Lights,     kGPUDescSet_PerFrame)]] StructuredBuffer<GPULight>     u_Lights;
[[vk::binding(kGPUBinding_ObjectData, kGPUDescSet_PerFrame)]] StructuredBuffer<GPUObjectData> u_Objects;
[[vk::binding(kGPUBinding_ShadowData, kGPUDescSet_PerFrame)]] StructuredBuffer<GPUShadowData> u_ShadowData;
```

补丁怎么知道 `B / S`：`slangc` 输出的 HLSL 里保留着 `#line N "xxx.slang"`，工具按行号回读 Slang 源码，
取该声明的 `vk::binding(B, S)`（`ShaderPatch.cpp` 的 `FindSourceDecl` / `ParseVkBinding`）。然后：

| 目标 | 展开 | 由谁做 |
|---|---|---|
| D3D12 | `: register(tB, spaceS)`；cbuffer 用 `b(S+8)`（`b0..b7` 留给推送常量的 root CBV）| `PatchRegisters`（`main.cpp`）|
| D3D11 | `: register(tB)` / `uB` / `s<n>` / `b<n>`，**去掉 space**，并按 §3.2 重新编号 | `PatchRegistersD3D11`（`ShaderPatch.cpp`）|
| Vulkan | `[[vk::binding]]` 原样生效 | 不需要补丁 |

**例外（必须手写后缀）**：bindless 数组在 D3D12 下要显式写 `space2`，而 D3D11 下整段换成纹理数组桶，
所以 `common.slang:80-81` 是**两套绑定都写**的：

```slang
[[vk::binding(kGPUBinding_BindlessTextures, kGPUDescSet_PerFrame)]]
Texture2D<float4> u_Textures[HE_BINDLESS_DIM] : register(kGPUBinding_BindlessTextures_hlsl, kGPUDescSet_Bindless_hlsl);
```

## 3. 核心差异二：`space`（寄存器空间）

### 3.1 API 事实

| 后端 | `space` 支持 |
|---|---|
| Vulkan | ✅ 相当于 `descriptor set` |
| D3D12（SM 5.1+） | ✅ |
| **D3D11（SM 5.0）** | ❌ **不支持** |

### 3.2 D3D11 的寄存器重新分配（不是"省略 space"这么简单）

SM 5.0 既没有 space，槽位数量也远小于 D3D12，所以 `--dxbc` 模式必须**重新编号**（`D3D11RegisterResult`）：

| 类别 | D3D11 规则 | 上限 |
|---|---|---|
| 推送常量 | 固定 `b0` | 1 块 |
| 描述符集 cbuffer | 按声明顺序压到 `b1..b14` | 14 |
| SRV | `t<binding>` | 128 |
| UAV | `u<binding>`；**像素阶段**平移到 `u(8+binding)`（像素阶段 RTV 与 UAV 共用编号）| 64 |
| 采样器 | 按声明顺序压到 `s0..s15` | 16 |

规则写在 `RHI/RHI/DxbcBindTable.h:43-54`；槽位越界或重叠**不静默**，记入 `errors` 并让该着色器在 D3D11 下不可用。
绑定结果还会序列化成一张**绑定表**附在 DXBC 容器之后，后端按它做逐绘制绑定（见 `26.Bindless体系` §9.3）。

### 3.3 光追的 space 分布（D3D12 侧）

光追着色器里的可绑定资源分布在 space 1 / space 2（`RT_*.rchit.slang`）。D3D12 的库目标靠
`PatchUnboundedArraysToBindlessSpace` 把无界数组统一归到 `space2` 的 `t0` / `s0`，
与光栅路径的 bindless 约定一致（`D3D12CommandList::PrepareSetTables` 把 bindless 堆绑在 space2 的表上）。
D3D11 不编译光追，这条规则不影响它。

## 4. 核心差异三：资源数组的动态索引

### 4.1 规则

| 写法 | Vulkan | D3D12 | D3D11（SM 5.0） |
|---|---|---|---|
| `Texture2D t[N]` 动态索引 | ✅ | ✅ | ❌ |
| `StructuredBuffer b[N]` 动态索引 | ✅ | ✅ | ❌ |
| `SamplerState s[N]` 动态索引 | ✅ | ✅ | ❌（`X3512: sampler array index must be a literal`）|
| `Texture2DArray` 的动态 **slice** | ✅ | ✅ | ✅（唯一例外） |
| 单个 `StructuredBuffer` 的动态元素索引 | ✅ | ✅ | ✅（允许） |

### 4.2 D3D11：bindless 的替代物（两层）

D3D11 侧**没有** bindless，靠渲染层与后端配合（细节见 `26.Bindless体系` §9.3）：

1. **逐绘制绑定**：`IRHICommandList::SetNonBindlessHandle(binding, handle)` + 渲染层 `SetDrawNonBindlessHandles`，
   绑定号是固定槽位（材质纹理 `t100..t103` 等）；
2. **纹理数组桶**：静态 2D 纹理按（宽, 高, mip, 格式）拷进 ≤ 8 个 `Texture2DArray`，
   配一张句柄映射表（`StructuredBuffer<uint>`）与一个桶采样器。

着色器侧的调用点**只有一处宏**（`common.slang:88-89`）：

```slang
#define HE_MAT_SAMPLE(base, slot, uv) u_Textures[base + slot].Sample(u_Samplers[base + slot], uv)
#define HE_TEX_SAMPLE(handle, uv)     u_Textures[handle].Sample(u_Samplers[handle], uv)
```

`HE_SHADER_D3D11` 下这两个宏改成"先查桶映射表 → 采样 `Texture2DArray`；未命中再退回逐绘制绑定"，
其余两个后端保持原来的 bindless 写法。**同一份着色器源码，三种展开。**

### 4.3 D3D12：定长数组

D3D12 不允许同一 space 内出现多个无界资源（`dxc` 报 `more than one unbounded resource in space 2`），
所以 bindless 数组改成定长：纹理 / 采样器 `[HE_BINDLESS_DIM]`（= 1024，`common.slang:23`），
四个 SSBO 区间各 256（详见 `26.Bindless体系` §9.2）。

## 5. 核心差异四：数组形态的语法位置

```slang
// 错误：数组括号跑到 register 后面
Texture2D<float4> u_Tex : register(t2)[4];   // ✗

// 正确：数组括号紧跟在名字后、register 之前
Texture2D<float4> u_Tex[4] : register(t2);   // ✓
```

⇒ `PatchRegisters` / `PatchRegistersD3D11` 都用"在 `: register(` 之前找 `[]`"的方式识别数组，
数组维度写成 `int(4)` 是 Slang 输出的形态（HLSL 合法）。

## 6. 核心差异五：入口点命名与语义

### 6.1 入口点

| 文件后缀 | Slang 入口名 | 说明 |
|---|---|---|
| `*.vert.slang` | `vertexMain` | |
| `*.frag.slang` | `fragmentMain` | |
| `*.comp.slang` | `main` | |
| `*.mesh.slang` | 网格入口 | D3D12 走 `ms_6_6`；D3D11 不支持 |
| `*.rgen/.rchit/.rmiss/.rahit/.rcall` | 各自入口 | D3D12 走**库目标** `lib_6_6`（不带 `-E`）；D3D11 不支持 |

CMake 生成字节码时必须用正确的入口名，否则 `slangc` 报 "undefined identifier"。

### 6.2 HLSL 输出缺少语义（X3502 / X3503）

Slang 生成的 HLSL 里，入口结构体的成员**没有语义**：

```hlsl
struct FSInput_0
{
    float2 uv_0;      // ← 缺语义
};
float4 fragmentMain(FSInput_0 input_0) : SV_TARGET
```

编译器报 `X3502: input parameter 'input_0' missing semantics`。
而 Slang 自动编造的语义名也不是 `[[vk::location(n)]]` 对应的 `TEXCOORDn`，而是它自己的 `VERTEX_IN_n`：

```
D3D11 ERROR: The provided input signature expects to read an element with
SemanticName/Index: 'VERTEX_IN_'/0, but the declaration doesn't provide a matching name.
```

### 6.3 解法

- **语义注入**：`ShaderPatch::InjectSemantics` 按"成员名 + 同名出现次序"分配 `SV_Position` / `TEXCOORDn`
  （按名字而非声明序号，避免 VS / PS 各自裁剪成员后撞号）；
- **输入布局**：D3D12 用 DXIL 反射生成；D3D11 用 `D3DReflect` 从 DXBC 反射真实签名，
  系统语义（`SV_VertexID` / `SV_InstanceID`）自动排除；
- **顶点实例号**（D3D12）：SM 6.8 起用 `SV_StartInstanceLocation`（`PatchStartInstanceLocation` 给入口追加参数并把
  起始实例号加进实例号），SM 6.8 以下与 D3D11 都退回"逐实例属性 `HE_INSTANCEINDEX` + 后端绑 0,1,2… 序号缓冲"；
- **网格着色器签名**（D3D12）：`PatchMeshSignature` 去掉 Slang 多写的 `inout`，否则 dxc 报
  `duplicate HLSL parameter usages`。

## 7. 核心差异六：编译器（fxc vs dxc）

| 项 | D3DCompiler (fxc) | DXC |
|---|---|---|
| 输出 | DXBC（SM 5.0） | DXIL（SM 6.0+） |
| D3D11 能否用 | ✅ | ❌ |
| D3D12 能否用 | 部分 | ✅ |

⇒ **D3D11 只能走 DXBC**，而 DXBC 只能由 fxc 生成。这带来 fxc 特有的限制与对策
（`Tools/ShaderToDxil/main.cpp` 的 `RunDxbc`）：

| 限制 | 报错 | 应对 |
|---|---|---|
| 严格模式下强制展开带 `break` 的循环 | `X3511: unable to unroll loop` | 去掉 `D3DCOMPILE_ENABLE_STRICTNESS`；剥离 `[unroll]` |
| 动态边界的大循环也被尝试展开 | `X3511` | 只给**最外层**循环注入 `[loop]`（`PatchLoopsFxc`）|
| 嵌套循环加 `[loop]` | `X3531: can't unroll loops marked with loop attribute` | **逐循环重试**：把报 X3531 的位置加入"不加 `[loop]`"名单重编，最多 16 次；仍失败则整体不加 |
| 复杂控制流 + 密集 UAV 写入 | `internal error: flattened side effect` / `X3694` | **整体重试一轮**：给所有 `if` 加 `[branch]`（`PatchBranchesFxc`）后重编 |
| 结构化缓冲里矩阵被按行主序解释 | 画面转置（不报错）| `PatchStructuredMatricesFxc` 在读取处包一层 `transpose` |

## 8. 各后端的绑定映射总表

| 后端 | SRV | UAV | CBV | Sampler | `space` | bindless 数组 |
|---|---|---|---|---|---|---|
| **Vulkan** | `[[vk::binding(n, s)]]` | 同 | 同 | 同 | ✅（`set`）| ✅ 无界 `[]`（引擎按 1024 声明）|
| **D3D12** | `: register(t<n>, space<s>)` | 同 | 同（`b(s+8)`）| 同 | ✅ | ✅ 定长：纹理 1024、SSBO 每段 256 |
| **D3D11** | `: register(t<n>)` | `u`（像素阶段 `u(8+n)`）| `b`（推送常量 `b0`）| `s0..s15` 压缩 | ❌ | ❌ 逐绘制绑定 + 纹理数组桶 |

> D3D12 / D3D11 两列都由工具生成，着色器源码里**只写 Vulkan 的那一套**（例外见 §2.3）。

## 10. 经验教训

| 教训 | 说明 |
|---|---|
| **Slang 的 `[[register]]` 是非法属性** | 只报警告、退出码 0，极易误判为"支持" |
| **`vk::binding` 对 D3D 目标完全无效** | 且不会报错，只是静默地自动编号 |
| **不要为跨后端改写着色器** | 早期用 `HE_DECL_*` 宏生成整条声明（396 处、97 个文件）；现在改成工具侧按 `#line` 回读 `vk::binding` 再补寄存器，**源码零改动**、Vulkan 侧天然不变 |
| **着色器文本补丁要保守** | 曾把 cbuffer 全归一到 `b0`，多个 cbuffer 重叠导致那一批 DXIL 全是坏的（已回退）；补丁只做"加属性 / 改寄存器"，不动结构 |
| **`space` 只在 SM 5.1+ 存在** | D3D11 侧必须重新编号，不能只删 `space` 字样 |
| **D3D11 的 bindless 不可实现** | 不是工作量问题，是 SM 5.0 的硬限制；绕法是纹理数组桶 + 逐绘制绑定 |
| **D3DCompiler 的 `X3511`/`X3531` 是矛盾的一对** | 加 `[loop]` 解决前者，但嵌套时会触发后者 ⇒ 需要逐循环重试 |
| **`flattened side effect` 无解（对单条着色器而言）** | fxc 内部缺陷，只能整体加 `[branch]` 重试或重写该着色器 |
