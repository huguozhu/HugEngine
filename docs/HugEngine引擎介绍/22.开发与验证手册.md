# HugEngine 开发与验证手册

> 整理日期：2026-09-22 | 范围：构建 / 示例 / 测试 / 验证工具 / 开关 | 依据：构建脚本、CMake 配置、脚本注释与源码

## 本文怎么读

本文是仓库里**唯一**一份讲"怎么把东西跑起来、怎么证明它是对的"的文档。它不解释渲染算法 （那是 `docs/HugEngine引擎介绍/` 下各子系统分析文档的事），只回答三个问题：**怎么构建、 怎么运行、怎么验证**。

三类读者可以这样切入：

- **新上手**：只读 §1 → §3 里你最关心的那个示例 → §8。目标是在半小时内让画面出现在屏幕上。
- **要跑验证**：读 §1 的命令约定 → §5 工具清单 → §7 典型验证流程。**先读 §5 开头的
  "三条硬前置"**，否则你会在脚本的守卫处直接撞墙。
- **要加新特性**：读 §2（构建与 shader 目标）→ §3 里最接近你改动的示例 → §4（怎么加单测）
  → §5/§7（既有判据是怎么写出来的、照着写一条新的）→ §8（既有约定，别踩）。

**引用约定**：所有结论都带 `文件:行号`。行号以当前工作树的文件内容为准（`read` 工具口径）。 本手册**只写能从配置文件/脚本/源码里读出来的命令**；读不出来的东西一律进 §9 未复核清单， 不编造。

## 1. 快速上手

### 1.1 前置条件

| 依赖 | 要求 | 依据 |
|---|---|---|
| CMake | ≥ 3.28 | `CMakeLists.txt:1` |
| 生成器 | Visual Studio 18 2026 或 MinGW Makefiles（GCC 16） | `CMakePresets.json:7`、`CMakePresets.json:19` |
| Vulkan SDK | 必须含 `include/vulkan/vulkan.h` 与 `Lib/vulkan-1.lib`，且含 `slangc` | `cmake/VulkanSDK.cmake:27-29`、`Engine/Shader/CMakeLists.txt:19-22` |
| Python 3 | 构建期无条件需要（SPIR-V → C++ 头）；分析脚本需要 `numpy` | `Engine/Shader/CMakeLists.txt:388`、`Engine/Shader/CMakeLists.txt:396`、`Tools/gi/timing_check.py:7-8` 之外的 13 个 `.py` |
| Git | 配置期必需（下载 Sponza + 子模块） | `CMakeLists.txt:47`、`cmake/DownloadAssets.cmake:19-23` |
| GPU | Vulkan 1.3+；光追 / mesh shader 按示例可选 | 见 §3 各示例"硬件与降级" |

Vulkan SDK **不写死路径、不联网下载**：`VULKAN_SDK_ROOT`（默认 `C:/VulkanSDK`， `cmake/VulkanSDK.cmake:17`）下按版本号选最新且**内容完整**的目录（`:20-35`），选中后写入 `ENV{VULKAN_SDK}`（`:49`）供 `find_package(Vulkan)` 与 `find_program(SLANGC)` 使用； 找不到任何可用 SDK 时**直接 `FATAL_ERROR` 终止配置**（`:38-43`）。

### 1.2 最短路径（可直接复制）

```powershell
# 0. 工作目录：仓库根（转储目录 build/verify/ 是相对路径，见 §8.2）
cd D:\Source\HugEngine

# 1. 初始化第三方依赖（7 个子模块，见 .gitmodules）
git submodule update --init --recursive      # README.md:19

# 2. 配置（生成器 VS 2026，构建目录 Build，示例与编辑器 ON、测试 OFF）
cmake --preset default                        # CMakePresets.json:5-15

# 3. 构建一个示例（Release；目标名 = exe 名）
cmake --build Build --config Release --target 01.Triangle

# 4. 运行
Build\bin\Release\01.Triangle.exe
```

- `cmake --preset default` 会顺带检查并（缺失时）用 `git sparse-checkout` 下载 Sponza 到
  `Content/gltf/Sponza`（`cmake/DownloadAssets.cmake:9-10`、`:18-38`）。
- **产物落点**：`Build/bin/<Config>/`（`CMakeLists.txt:26` 设
  `CMAKE_RUNTIME_OUTPUT_DIRECTORY = ${CMAKE_BINARY_DIR}/bin`，多配置生成器自动追加配置名）。
  现有 `Build/bin/` 下已有 `Debug`、`Release`（也可 `MinSizeRel`、`RelWithDebInfo`）。
- 示例的 CMakeLists **都没有** `RUNTIME_OUTPUT_DIRECTORY`/`OUTPUT_NAME`（逐个核对
  `Samples/*/CMakeLists.txt`），所以 **exe 名恒等于目标名**。

### 1.3 打开测试并跑一次

测试默认是**关**的（`CMakeLists.txt:35` 默认 `OFF`，`CMakePresets.json:12` 也显式 `OFF`）， 必须重新配置打开：

```powershell
# 命令行 -D 覆盖 preset 里的 cacheVariables（本机实测：cmake 4.3.1 下生效）
cmake --preset default -DHUGENGINE_BUILD_TESTS=ON

cmake --build Build --config Release --target HugEngineTests
Build\bin\Release\HugEngineTests.exe

# 只跑一个用例（doctest 过滤，见 §4.3）
Build\bin\Release\HugEngineTests.exe --test-case="*NaniteTypes*"

# 列出全部用例名
Build\bin\Release\HugEngineTests.exe --list-test-cases
```

### 1.4 跑一次 GI 验证（最短的一条）

```powershell
# 前置：先构建 06.GILab，且至少成功启动过一次以生成基线 cfg
cmake --build Build --config Release --target 06.GILab
Build\bin\Release\06.GILab.exe            # 正常关窗退出即写出 Content/Config/06_GILab.cfg

# 单源隔离采样（4 组层栈配置，各一次运行）

# 离题分析（无 CLI，读 <repo>/Build/verify）
python Tools/gi/analyze_gi.py
```

## 2. 构建系统

### 2.1 preset 清单

`CMakePresets.json` 只有 2 个 **configurePreset**，**没有** `buildPresets` / `testPresets` （全文件 32 行，`CMakePresets.json:1-32`）：

| preset | 生成器 | 用途 | 关键 cache 变量 | 行号 |
|---|---|---|---|---|
| `default` | `Visual Studio 18 2026` | Windows 默认（MSVC） | `HUGENGINE_BUILD_SAMPLES=ON`、`HUGENGINE_BUILD_EDITOR=ON`、`HUGENGINE_BUILD_TESTS=OFF`、`HUGENGINE_RHI_VULKAN=ON` | `CMakePresets.json:5-15` |
| `gcc` | `MinGW Makefiles` | GCC 16 MinGW，编译器/`mingw32-make` 路径写死为 `C:/gcc16/mingw64/bin/*` | 同上四个开关 | `CMakePresets.json:17-30` |

两者 `binaryDir` 都是 `${sourceDir}/Build`（`:8`、`:20`）—— **同一个目录**，所以 MSVC 与 GCC 两次配置会互相覆盖同一份 cache。切编译器请先删 `Build/` 或改 `binaryDir`。

`gcc` preset 是**单配置**生成器，此时 exe 直接落在 `Build/bin/`（不带配置子目录）；MSVC 则落在 `Build/bin/<Config>/`。

> 因为没有任何 `buildPresets`，`cmake --build --preset=default` **不可用**；构建一律写
> `cmake --build Build [--config Release] [--target <目标>]`。同理 `ctest --preset=...` 不可用。
> 另：多配置生成器下 `cmake --build Build` 不写 `--config` 时构建 **Debug**（CMake 标准行为），
> 而验证脚本默认找的是 **Release**（如 `Tools/gi/dump_gi.ps1:35`）。

### 2.4 `CompileShaders` 目标

着色器管线的全貌在 `Engine/Shader/CMakeLists.txt`（424 行）：**Slang → SPIR-V → 内嵌 C++ 头**。

1. 找编译器：`find_program(SLANGC NAMES slangc HINTS ENV VULKAN_SDK ...)`（`:19-22`）；
   找不到则 `FATAL_ERROR`（`:423`）。
2. 入口 shader **显式列表**（不用 `file(GLOB)`，因为 GLOB 跟踪不到新增文件，`:30`）：
   `VERT_SLANG`（`:40-72`）、`FRAG_SLANG`（`:73-132`）、`COMP_SLANG`（`:133-214`）、
   `RT_SLANG`（`:218-247`）、`MESH_SLANG`（`:250-260`），外加共享头 `SLANG_INCLUDES`
   （`:264-281`，改动它们会触发**全部** shader 重编，这是有意的契约代价，见 `:275-278`）。
3. 每个入口一条 `add_custom_command`，按 stage 传不同 entry 名：
   顶点 `-entry vertexMain -stage vertex`（`:294`）、片元 `-entry fragmentMain -stage fragment`
   （`:310`）、compute/RT/mesh 统一 `-entry main -stage <stage>`（`:326`、`:355`、`:378`），
   统一 `-target spirv -I "${SHADER_DIR}" -o <out>.spv -Wno-39001`。
   RT 的扩展名 → Slang stage 映射见 `:339-351`；mesh/task 见 `:368-374`。
4. SPIR-V → 头：`python <Engine/Shader/spv_to_header.py> <spv_dir> <spv...>`（`:388`、`:394-399`），
   每个 `.spv` 独立生成 `.spv.h`，逐文件增量。
5. 汇总目标：`add_custom_target(CompileShaders ALL DEPENDS ${SPV_HEADERS} SOURCES ...)`
   （`:415-418`），并把 `HugEngineShader` 挂上去（`:420`）。`SOURCES` 只影响 IDE 视图，
   不构成构建依赖（`:402-407` 说明了为什么不用 GLOB）。

**全部 9 个示例目标都 `add_dependencies(<target> CompileShaders)`** （`Samples/01.Triangle/CMakeLists.txt:12`、`Samples/02.Cube/CMakeLists.txt:20`、 `.../03.Sponza-Forward:21`、`.../04.Sponza-Deferred:4`、`.../05.Sponza-PathTracing:4`、 `.../06.GILab:6`、`.../07.AISamples:37`、`.../07.Nanite:6`、`Samples/Editor/CMakeLists.txt:56`）， 所以**改一行 `.slang` 就会连带重编 SPIR-V 头并重链接示例**。

### 2.5 测试目标如何打开

`HUGENGINE_BUILD_TESTS` 为 ON 时才 `enable_testing()` + `add_subdirectory(Tests)` （`CMakeLists.txt:89-92`）。测试目标名 **`HugEngineTests`**（`Tests/CMakeLists.txt:7`）。

注意：`Tests/CMakeLists.txt` **没有任何 `add_test`**（全仓 grep `add_test` 零命中），所以 `ctest` 跑出的是 0 个用例；测试必须直接运行 exe（见 §4）。

### 2.6 常见构建问题与对策

| 症状 | 原因 | 对策 | 依据 |
|---|---|---|---|
| `未在 "C:/VulkanSDK" 下找到可用的 Vulkan SDK` | SDK 未装或目录不完整（缺 `vulkan.h` / `vulkan-1.lib`） | 装 SDK，或 `-DVULKAN_SDK_ROOT=<路径>` | `cmake/VulkanSDK.cmake:17`、`:38-43` |
| `slangc NOT found` | SDK 里没有 `slangc` | 装完整 Vulkan SDK；`SLANGC` 已按 `ENV{VULKAN_SDK}` 搜索 | `Engine/Shader/CMakeLists.txt:19-22`、`:423` |
| 配置期 `python` 找不到 | 构建期要用 `spv_to_header.py` | 把 python 放进 PATH | `Engine/Shader/CMakeLists.txt:396` |
| `Build` 里出现旧目标名（`03.Sponza`、`04.Deferred`、`05.AISamples`、`05.LLMScene`、`JoltProbe`） | `Build/` 是**改名前的过期 configure 产物** | 重新 `cmake --preset default` 后再构建；别直接手工跑旧 exe | `Build/CMakeCache.txt`、`Build/Samples/`、`Build/Tests/JoltProbe.vcxproj` |
| Sponza 加载失败但配置成功 | 下载失败只 `WARNING`，不会终止配置 | 检查网络后重跑 configure，或手工补 `Content/gltf/Sponza/glTF/Sponza.gltf` | `cmake/DownloadAssets.cmake:41`、`:47` |
| 改共享 shader 头后行为没变 | 增量 Slang 构建**不可靠地**重编包含被改头的所有 shader | 触碰（touch）相关入口 shader 或全量重编；`Tools/gi/rtgi_furnace_check.ps1` 内建了新鲜度门 | `Tools/gi/rtgi_furnace_check.ps1:22-28`、`:57-71` |

## 3. 示例程序导读

共 **9** 个（`Samples/CMakeLists.txt:2-10`）。**全部示例都没有命令行参数**（都是无参 `int main()`，全仓 `argc/argv` 在 `Samples/**/*.cpp` 零命中），所以"怎么跑"永远是 "设环境变量 + 起 exe"，"怎么调"只有三条通路：**环境变量 → cfg 的 key=value → 运行期 ImGui 面板**。

统一约定：

- exe 路径 `Build\bin\<Config>\<目标名>.exe`（§2.2）。
- **必须从仓库根目录启动**：05/06/07 的转储写相对路径 `build/verify/`（NTFS 上大小写不敏感，
  即 `Build/verify/`），从别处启动会把文件写进嵌套目录且**不报错**（见 §8.2）。
- 需要 Content 资产的示例都用 `HUGE_CONTENT_DIR` 拼**绝对路径**，因此资产查找与工作目录无关。

### 4.5 需 GPU 与不需 GPU 的分界

**结论：现有 331 个用例全部不需要 GPU、不需要 Vulkan 设备。** 依据：

1. `Tests/CMakeLists.txt:91-101` 只链接 `HugEngineAI / HugEngineScene / HugEngineAsset /
   HugEngineCore / HugEnginePhysics / Jolt / meshoptimizer` —— **没有 `HugEngineRender`、没有
   `HugEngineRHI`**。注释说明了原因：链接 Render 会连带拉入 RHI/Vulkan 与 slangc 生成的 SPV 头
   （`:77-80`、`:98-100`）。
2. 头文件白名单同样只加 include 路径，不加链接：`Engine/Render`（GI 数据模型 / 探针网格 /
   PT 载荷镜像，`:81`）、`Engine/External`、`Engine/External/doctest`、`meshoptimizer/extern`（`:75-84`）。
3. `Tests/TestNaniteBuilder.cpp:8`、`Tests/TestNaniteStream.cpp:9`、`Tests/TestNaniteTypes.cpp:6`
   都明确写了"被测实现是 RHI-free 的"。
4. 全仓 `Tests/*.cpp` 中没有任何 `IRHIDevice`/`vk::`/`CreateDevice`/`Swapchain` 的实际使用
   （`Tests/TestBindlessHeap.cpp:4-7` 只用与后端无关的环形化基础件；`TestDecal.cpp:157` 仅断言
   与 Vulkan 推送常量上限的量级关系）。

这些用例用 `REQUIRE(...)` 而非跳过：**资产缺失时用例会 FAIL（而不是 SKIP）**（如 `TestNaniteMaterialMap.cpp:167` 的 `REQUIRE(LoadMerged(path.c_str(), g))`）。Sponza 由 configure 阶段自动下载（`cmake/DownloadAssets.cmake:12-48`），`Content/Models/Skeletal/*` 是仓库自带资源。

### 4.6 怎么加用例

1. 在 `Tests/` 新建 `Test<主题>.cpp`，`#include "doctest.h"`，写 `TEST_CASE("...")`。
2. 把文件名加进 `Tests/CMakeLists.txt:8-72` 的 `add_executable(HugEngineTests ...)` 列表
   （**是显式列表，不会自动发现**）。
3. 如果被测实现需要额外头文件，加 `target_include_directories`（`:74-85`）——**优先只加 include
   路径不加链接**，别把 RHI/Vulkan 拉进单测（`:77-80` 的注释是纪律说明）。
4. 如果被测翻译单元是 RHI-free 的 `.cpp`，可以像 `Engine/Render/Nanite/NaniteUpload.cpp`
   那样**直接把源文件列进目标**（`:67-71`），这也是一条"任何 RHI 依赖闯进来就会编译失败"的钉子。
5. 需要读资产时用 `HUGE_CONTENT_DIR`（`Tests/CMakeLists.txt:87-89`）。
6. 打印验收要的数字用 `MESSAGE(...)`（既有 Nanite 系列测试都这么做，例如
   `TestNaniteBuilder.cpp:155`、`:1275`），这样"读数"会和 PASS/FAIL 一起出现在输出里。

## 7. 典型验证流程

下面每条都把 5 个工具串成"能跑完"的流程。**共同前置**：`cmake --build Build --config Release --target <目标>`；从仓库根运行；首次先手工跑一次示例生成基线 cfg（§5.0）。

### 7.1 白炉（能量守恒）数值校验

目的：证明某个 GI 源的估计器**绝对量级**正确，而不是"看起来像"。

原理：白炉 = 均匀白环境（各方向辐射度 1）+ 接收面 albedo 1 + 直接光关。此时 $E = \int_{\Omega} L\cos\theta\,\mathrm{d}\omega = \pi$，于是 Lambert 出射 $L_o = \frac{\rho}{\pi} E = \rho$。**任何源的真值都是 1**，与场景几何无关。

```powershell
# ① SSGI 解析标定（内含一次 dump_gi.ps1 调用 + 白炉用例）
powershell -File Tools/gi/ssgi_cal_check.ps1 -Frame 120 -Config Release

# ② RTGI / RT 反射共享着色函数的白炉（先过 shader 新鲜度门）
powershell -File Tools/gi/rtgi_furnace_check.ps1 -Frame 120 -Config Release

# ③ 手动观察（面板化）
$env:HE_FURNACE='1'; $env:HE_FURNACE_PROBE='1'; $env:HE_GILAB_CONFIG="$PWD\Build\verify\furnace.cfg"
Build\bin\Release\06.GILab.exe     # GI 控制台里读「亮度比 中心/背景」与「中心亮度」
```

判据：`ssgi_cal_check.py` 要求中心与背景亮度都落在 $[0.90, 1.10]$（`:39-41`）； `rtgi_furnace_check.ps1` 要求探针中心落在 $[0.98, 1.02]$（`:131-132`）；面板上写的是 `白炉判据 0.98 ~ 1.02`（`06.GILab.cpp:1200`）。

```powershell
powershell -File Tools/gi/timing_check.ps1 -Frame 240 -Config Release # 断言读数真实（非零/恰零/随工作量缩放）
```

### 7.3 单源隔离与层栈正确性（最核心的一套）

原理：同一场景、同一相机，**只改漫反射层栈**，两次运行相减即隔离该源：

$$S_x = \mathrm{lum}(H_x) - \mathrm{lum}(H_{\varnothing})$$

直接光 / 天空 / 镜面在差分里精确抵消（`Tools/gi/dump_gi.ps1:4-10`）。

```powershell
# 基线采样：none / ddgi / ssgi / both 四组（每组一次运行）
powershell -File Tools/gi/dump_gi.ps1 -Frame 120 -Config Release

# 离线读数：合理性 + 量级 + 相关性（无退出码，纯打印）
python Tools/gi/analyze_gi.py

# 频率维判定：低通(SSGI) 是否 ≈ DDGI（决定"频率分离"还是"归一化加权"）
python Tools/gi/p5_spectrum.py

# 加权平均 / 加源不变亮 / 双源 = 两单源之均值
powershell -File Tools/gi/forward_stack_check.ps1 -Frame 120 -Config Release
# 层栈列出的源，其 pass 必须被注册（不变量 1）
```

平面镜判据值得单独说明，因为它是"解析闭式解"的范例：物体中心 $C$ 关于平面 $(\mathbf{n}, d)$ 的镜像点 $C' = C - 2(\mathbf{n}\cdot C + d)\mathbf{n}$，相机 $E$ 看向 $C'$ 的 射线与镜面交于

$$Q = E + t\,(C' - E), \qquad t = -\frac{\mathbf{n}\cdot E + d}{\mathbf{n}\cdot (C' - E)}$$

于是该物体的反射**必须**出现在像素 $\mathrm{project}(Q)$，容差 6 px （`Tools/gi/ssr_mirror_check.py:1-31`、`Tools/gi/ssr_mirror_check.py:40-42`）。

## 8. 已知缺口与易踩的坑

### 8.1 没有任何示例接受命令行参数

9 个示例都是无参 `int main()`（01:27、02:156、03:99、04:89、05:102、06:152、07.Nanite:155、 `07.AISamples:43`），`argc/argv` 在 `Samples/**/*.cpp` 零命中。**所以本文所有命令都是 "环境变量 + exe"**；想加一个 `--frames N` 这类开关，需要自己动手。

### 8.2 转储目录是相对路径，必须从仓库根启动

05/06/07 都写 `const String dir = "build/verify/";`（`05.Sponza-PathTracing.cpp:1002`、 `06.GILab.cpp:1700`、`07.Nanite.cpp:2062`），而脚本按 `<repo>/Build/verify` 去找 （如 `Tools/gi/dump_gi.ps1:31`）。NTFS 大小写不敏感所以 `build` 与 `Build` 是同一目录， **但工作目录错了会把产物写进嵌套目录且不报错**，脚本于是静默给出"没有差异"的假 PASS ——这一坑在 `docs/已实现功能/Nanite设计与实现.md:4315` 有完整记录（曾据此误报过一次回归）。

### 8.3 `Build/` 里躺着过期产物，旧 exe 名仍在磁盘上

现有 `Build/bin/{Debug,Release}` 里是 `03.Sponza.exe`、`04.Deferred.exe`、`05.AISamples.exe`、 `JoltProbe.exe`，`Build/Samples/` 下是 `03.Sponza/`、`04.Deferred/`、`05.LLMScene/`；而当前 源码的目标名是 `03.Sponza-Forward`、`04.Sponza-Deferred`、`07.AISamples`，且 `Tests/` 下已 没有 `JoltProbe`。**这是改名前的过期 configure 产物**，直接手工跑旧 exe 会得到与实际源码无关 的结论。规矩：**换目标名/删目标之后，先重新 `cmake --preset default` 再构建。**
