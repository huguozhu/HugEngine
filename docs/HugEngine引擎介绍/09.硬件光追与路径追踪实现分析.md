## 1. 结论速览

| 维度 | RT 阴影 | RTAO | RT 反射 | RTGI | 路径追踪（PT） |
|---|---|---|---|---|---|
| 主 Pass 类 | `RTShadowPass` | `RTAOPass` | `RTReflectionPass` | `RTGIPass` | `PTPass` |
| 基类 | `RTEffectPass` | `RTEffectPass` | `RTEffectPass` | `RTEffectPass` | 无（5 张 UAV，不继承） |
| 输出格式 | `R16_FLOAT` | `R8_UNORM` | `RGBA16_FLOAT` | `RGBA16_FLOAT` | 5 张：`RGBA16_FLOAT`/`R32_FLOAT`/`RGBA16_FLOAT`/`RG16_FLOAT`/`RGBA16_FLOAT` |
| 输出语义 | 遮罩（0=全影, 1=无影） | 遮罩（0=全遮蔽, 1=无遮蔽） | `rgb`=反射色, `a`=命中距离 | `rgb`=间接漫反射, `a`=有效性 | HDR / 深度 / 法线+粗糙度 / 速度 / albedo+metallic |
| 默认分辨率 | 1/2（`(w+1)/2`） | 1/2 | 1/2 | **1/4**（`(w+3)/4`） | 全分辨率 |
| 每像素射线 | 每光源 1 条（软阴影 `softSPP` 条） | `cvRTAOSPP` 条（默认 2） | 1 条 | `cvRTGISPP` 条（默认 1） | `spp × maxBounces` |
| 最大追踪距离 | `cvRTShadowMaxDist`（200m） | `cvRTAOMaxDist`（2m） | `cvRTReflectionMaxDist`（500m） | `cvRTGIMaxDist`（30m） | 相机/次级射线 10000 |
| miss 回退 | `blocked=false`（未遮挡） | `blocked=false`（未遮蔽） | 天空色（`RT_Reflection.rmiss`） | 白炉→1；DDGI 不在层栈→探针 `E/π`；否则 0 | 天空色（`SampleSky`） |
| 载荷 | `bool blocked`（4B，管线取 `kRTMaxPayloadSize`=16） | 同左 | `float4 colorT`（16B） | `float4 radianceT`（16B） | `PathPayload`（**112B**） |
| 降噪链 | 时域 → 升采样 | 时域 → 升采样 | 时域 → 空间 → 升采样 | 时域 → 空间 → 升采样 | 时域累积 → A-Trous → ToneMap → FXAA |
| 每帧执行条件 | `GIConfig::ShouldRunRTShadow()` | 层栈 `ao` 含 `RTAO` | 层栈 `specular` 含 `RTReflection` | 层栈 `diffuse` 含 `RTGI` | `r.Pipeline.Mode=3` + 设备支持 RT |

一句话总结：**RT 效果不是「另一种管线」，而是被注册进 GI 层栈的一组源**（`RTEffectProvider`），
是否跑、以什么权重跑都由层栈决定；**PT 是独立的参考渲染器**，自己完成完整光照、不使用层栈。

### 2.3 push constant 的阶段掩码：三级都拓宽到同一份并集

RT 绑定点上的 push constant 推送使用**固定的 5 阶段并集**（不含 Intersection）：

```cpp
stage = VK_SHADER_STAGE_RAYGEN_BIT_KHR | VK_SHADER_STAGE_MISS_BIT_KHR
      | VK_SHADER_STAGE_CLOSEST_HIT_BIT_KHR | VK_SHADER_STAGE_ANY_HIT_BIT_KHR
      | VK_SHADER_STAGE_CALLABLE_BIT_KHR;      // VulkanCommandList.cpp:474-479
```

Vulkan 要求「发送的 stageFlags 是管线布局 stageFlags 的子集」，因此管线布局侧把范围也拓宽到同一并集
（`Engine/RHI/Vulkan/VulkanRT.cpp:472`–`:483`），效果 Pass 层再补一次
（`RTEffectPass.cpp:27`–`:34`）。净效果是：**调用方声明的 `stageMask` 实际上被覆盖**，
但三处保持一致所以不报错；副作用是 Intersection 阶段永远不在可见集合里。

### 2.5 场景数据为什么用「纹理」而不是 SSBO

这是 RHI 之上一处**明确记录在源码里的实现约束**，也是理解 RT ClosestHit 侧数据布局的前提：

> 用纹理而非 SSBO：ClosestHitKHR 中访问 StructuredBuffer 已知 GPU fault；
> 不依赖 position_fetch：GTX 1070 等设备不支持 `VK_KHR_ray_tracing_position_fetch`。

出处：`Engine/Render/Pipeline/RTPass.cpp:515`–`:516`（同义注释见 `RTPass.h:79`、
`Engine/Shader/Shaders/RT_HitCommon.slang:12`–`:13`、`Engine/Shader/Shaders/RayTracing/RT_Reflection.rchit.slang:8`–`:9`、
`Engine/Shader/Shaders/PathTracing/PT_Full.rchit.slang:6`–`:8`）。

因此命中侧的三份数据都是纹理（`RTPass::BuildSceneMaterialTexture`，`RTPass.cpp:527`）：

| 纹理 | 格式 | 布局 | 位置 |
|---|---|---|---|
| 场景材质纹理 | `RGBA32_FLOAT`，**11 行 × N 列**（每实例一列，列序与 TLAS 实例序一致） | `row0`=albedo.rgb+metallic，`row1`=roughness+ao，`row2`=(法线线性起始=tri*3, 三角形数, 法线纹理宽度, 0)，`row3`=emissive，`row4`=disneyA，`row5`=disneyB，`row6`=(disneyC, dielectricF0, ior, transmission)，`row7`=σ_t，`row8`=(materialID, textureMask, 0, 0)，`row9`=(baseColorFactor.rgb, metallicFactor)，`row10`=(roughnessFactor, 0, 0, 0) | `RTPass.cpp:542`–`:551`、`:589`–`:654` |
| 三角形顶点法线纹理 | `RGBA32_FLOAT`，宽 `normTexWidth`、高 `kNormTexHeight = 1024`；每三角形 3 条顶点法线按 TLAS 实例序扁平排列 | 线性索引 `lin = linBase + primId*3 + v` → `(col = lin % texW, row = lin / texW)`；宽度回写到材质纹理 `row2.z` | `RTPass.cpp:553`–`:559`、`RT_HitCommon.slang:59`–`:70` |
| 三角形顶点 UV 纹理 | `RG32_FLOAT`，布局与法线纹理一致 | PT 的 ClosestHit 靠它插值命中点 UV | `RTPass.h:202`、`PT_Full.rchit.slang:85`–`:96` |

法线**不用** `position_fetch`（`LoadHitNormal` 用 `BuiltInTriangleIntersectionAttributes` 的重心坐标
插值三条顶点法线），原因同样是设备兼容（`RT_HitCommon.slang:56`、`RT_Reflection.rchit.slang:26`）。

### 2.6 能力边界（RHI 侧）

- **载荷**：RT 效果统一取 `rhi::kRTMaxPayloadSize`（16B，`RTEffectPass.h:75`、`RTGIPass.cpp:119`）；
  PT 取 `kPathPayloadSize`（112B，`PTPass.cpp:156`）。
  ⚠ 但 `RTPipelineStateDesc::maxPayloadSize` 在 Vulkan 侧**没有任何 API 消费者**：`maxPayloadSize` /
  `maxHitAttributeSize` 只出现在日志里（`VulkanRT.cpp:517`–`:518`），
  真正传给 `vkCreateRayTracingPipelinesKHR` 的只有 `maxPipelineRayRecursionDepth`（`VulkanRT.cpp:501`）。
  设备的 `maxRayPayloadSize` / `maxRayHitAttributeSize` 属性**根本没有被查询**
  （`QueryRTCapabilities` 只读 `maxRayRecursionDepth` / `shaderGroupHandleSize` /
  `shaderGroupBaseAlignment` / `maxRayDispatchInvocationCount`，`VulkanRT.cpp:234`–`:241`）。
  也就是说 16B 与 112B 都是**引擎自定约定**，不是从设备能力推导出来的上限；
  `PTPass.cpp:158` 那条「设备 maxPayloadSize 可能 < 112B」的报错文案描述的是约定而不是实测的设备校验。
- **递归深度**：两侧都用 `rhi::kRTMaxRecursionDepth` = 2；PT 的循环在 RayGen 内，故深度 2 够用
  （`PTPass.cpp:151`–`:156`）。设备的 `m_MaxRayRecursionDepth` 被查询并暴露
  （`VulkanRT.cpp:234`、`Types.h:321`），但没有任何地方用它校验或钳制管线声明值。
- **dispatch 规模**：`maxRTDispatchSize` 被查询并暴露（`VulkanRT.cpp:237`、`Types.h:324`），
  但**从未与 `TraceRays` 的 `width × height × depth` 比较**。
- **SBT 命中组**：所有 TLAS 实例的 `sbtOffset` 恒为 0（`RTPass.cpp:396`），每个效果管线只注册 1 个
  Hit 组 → 命中处理不能按材质/实例分派。
- **无 BLAS refit 实际路径**：`BuildBLAS` / `BuildTLAS` 的 `bool update` 形参与 Vulkan 侧的
  `VK_BUILD_ACCELERATION_STRUCTURE_MODE_UPDATE_KHR` + `srcAccelerationStructure` 都已就位
  （`CommandList.h:181`、`:184`；`VulkanCommandList.cpp:1041`–`:1044`），
  但引擎调用点全传 `false`（`RTPass.cpp:370`、`:410`），且 BLAS 标志不含
  `ASBuildFlags::AllowUpdate`（`RTPass.cpp:341`）——即使传 `true` 也不满足 update 的前置条件。
- **无 AS 压缩**：`ASBuildFlags::AllowCompaction` 有映射（`VulkanDevice.cpp:50`），
  但没有 `vkCmdCopyAccelerationStructureKHR` 的加载与调用，也没有调用方请求该 flag。
- **只有三角形几何、且一律 OPAQUE**：`RTGeometryType::AABBs` / `Instances` 已定义但无使用点；
  BLAS 构建两处硬编码 `VK_GEOMETRY_TYPE_TRIANGLES_KHR` 与 `VK_GEOMETRY_OPAQUE_BIT_KHR`
  （`VulkanRT.cpp:310`、`:317`；`VulkanCommandList.cpp:1015`、`:1025`）
  → **不支持 AABB / 程序化几何、不支持非不透明（alpha-test）几何**。
- **无 OMM / 无 SER / 无 inline RT**：`DeviceCaps::supportsSER`（`Types.h:307`）与 `supportsOMM`（`Types.h:308`）
  只有声明，`GetCaps` 从未赋值（`VulkanDevice.cpp:133`–`:179`），故恒为 `false`；
  全仓库无 `RayQuery` / Inline RT 使用点。

## 3. 两类 RT 使用者

引擎里「用硬件光追」的代码只有两类，且它们的定位完全不同：

**（1）四个 RT 效果 Pass（`Engine/Render/RT/`）—— 作为 GI 源挂在 Deferred 帧图上。**
`RTEffectProvider` 用一个实现覆盖四种效果，效果种类由枚举区分：

```cpp
enum class Effect : u8 { Shadow, AO, Reflection, GI };   // Engine/Render/GI/RTProvider.h:32
```

它为每个效果提供身份（`GetSourceId`，`RTProvider.h:83`）、是否本帧产出（`NeedsPass`，`RTProvider.h:95`）、
输出纹理（`GetDiffuseOutput` / `GetSpecularOutput` / `GetAOOutput`，`RTProvider.h:134`–`:142`）
与降噪链（见第 4 节）。Deferred 侧在 RT 基础设施初始化完成后就地注册四个 Provider：

```
makeRT(RTEffectProvider::Effect::Shadow);
makeRT(RTEffectProvider::Effect::AO);
makeRT(RTEffectProvider::Effect::Reflection);
makeRT(RTEffectProvider::Effect::GI);
```
（`Engine/Render/Pipeline/DeferredPipeline.cpp:399`–`:402`；`RTEffectProvider` 的构造与依赖注入见 `:377`–`:398`）

帧图侧**不认识具体效果**，只做一次泛化遍历：`dynamic_cast<RTEffectProvider*>` → 取该效果对应的层栈通道 →
`SyncToStack` → `NeedsPass` → 注册主 Pass 与附属 Pass（`DeferredPipeline_FrameGraph.cpp:1158`–`:1230`）。

**（2）`PathTracingPipeline` + `PTPass` —— 参考渲染器，不使用 GI 层栈。**
源码明确了它的定位：

> 它不参与实时渲染，也不使用 GI 层栈（GIConfig）：PT 自己完成完整光照
（`Engine/Render/Pipeline/PathTracingPipeline.h:24`）

它与 Deferred 的唯一耦合是**共享同一份 BLAS/TLAS**（`SetSharedRTPass`，`PathTracingPipeline.h:67`–`:69`、
`PathTracingPipeline.cpp:166`），避免重复的加速结构内存。

两条路径的失效策略也不同：RT 效果在 `RTPass` 初始化失败时把 `m_RTEnabled` 置假、不注册任何 RT Provider
（`DeferredPipeline.cpp:236`、`:367`–`:371`）；PT 在设备不支持 RT 时同样整体关闭
（`PathTracingPipeline.cpp:87`、`:98`、`:108`）。
`RTPass` 自身在设备不支持光追时直接返回失败（`RTPass.cpp:41`–`:46`），这是设备能力的第一道闸。

> **本节的「两类」是就 GI 源与参考渲染器而言**。引擎里还有两处也用 RT 管线、但不属于这两类的使用者：
> `DDGITracePass`（DDGI 探针射线的光追 march，**不是**层栈源而是 DDGI 的求值前置，
> `DeferredPipeline.cpp:274`–`:281`）与 `LumenFarFieldPass`（Lumen 远场光追，
> `Engine/Render/Lumen/LumenFarFieldPass.h`）。两者同样取 `rhi::kRTMaxPayloadSize`
> （`DDGITracePass.cpp:69`、`LumenFarFieldPass.cpp:68`），本文不展开。

## 4. RTEffectPass 的参数化设计

### 4.1 公共能力（基类）

`RTEffectPass` 只做四件事（`Engine/Render/RT/RTEffectPass.h:39`–`:51`）：

| 能力 | 位置 | 说明 |
|---|---|---|
| set0 布局创建 + 描述符集分配 | `RTEffectPass.cpp:38`–`:50` | 效果自己的 RayGen 绑定表 |
| 独立效果 RT 管线 + SBT | `RTEffectPass.cpp:52`–`:60` | 走 `RTPass::CreateEffectPipeline` |
| 输出 UAV 纹理创建 | `RTEffectPass.cpp:62`–`:72` | 尺寸/格式/用途由子类传入 |
| `BindRT` + `TraceRays` 调度 | `RTEffectPass.cpp:156`、`:175` | 见下面的顺序约定 |

两条被注释反复强调的约定（都属于「踩过才知道」的实现细节）：

1. **push constant 的 stage 掩码必须补全**。`VulkanCommandList::SetPushConstants` 在 RT 绑定点上固定用
   「RayGen|Miss|ClosestHit|AnyHit|Callable」推送，而各效果 Pass 只声明 RayGen|ClosestHit；基类统一在
   `Initialize` 里把 `pcRange.stageMask` 补齐，避免每帧每级触发
   `VUID-vkCmdPushConstants-offset-01795`（`RTEffectPass.cpp:27`–`:34`）。
   注意第 `:55` 行传给 `CreateEffectPipeline` 的 `pcRange` 是**同一个按值参数**（已被 `|=` 修改），
   与 `m_PCRange` 一致。
2. **必须先绑 RT 管线、再推常量**。`vkCmdPushConstants` 使用当前绑定管线的布局；若顺序反了，
   常量会落到上一 Pass（例如降噪图形 PSO）的布局上，范围不匹配 → 写入失败 → RT 着色器读到过期数据
   （`RTEffectPass.h:50`、`RTEffectPass.cpp:150`–`:154`）。
   所有效果 Pass 的 `Execute` 都遵守 `BindRT → SetPushConstants → TraceRays` 这个顺序
   （例：`RTGIPass.cpp:184`–`:186`）。

输出纹理的屏障由 `PrepareOutputUAV` 统一处理：首帧 `Undefined → UnorderedAccess`，后续帧
`ShaderResource → UnorderedAccess`；反向转换交给 RenderGraph 依据消费端的读依赖自动生成
（`RTEffectPass.cpp:89`–`:105`；对应说明见 `RTShadowPass.cpp:184`–`:186`）。

### 4.2 Effect 枚举与「四效果同一份实现」

`RTEffectProvider` 里的 `Effect` 枚举（`RTProvider.h:32`）是唯一的效果种类真值，它同时决定：

| 由 Effect 决定的事 | 位置 |
|---|---|
| 源身份 `GISourceId`（Shadow → `None`，其余 → `RTAO` / `RTReflection` / `RTGI`） | `RTProvider.h:83`–`:90` |
| Pass 名（`"RT Shadow"` / `"RTAO"` / `"RT Reflection"` / `"RTGI"`） | `RTProvider.h:119`–`:126` |
| 主 Pass 有效性判定（`m_Shadow` / `m_AO` / … 是否非空） | `RTProvider.h:325`–`:332` |
| 主输出纹理选择 | `RTProvider.h:333`–`:340` |
| `Execute` 分派 | `RTProvider.h:399`–`:404` |

RT 阴影的特殊之处在于**它不在三个层栈通道里**（阴影是可见性乘法项，不是能量源，见
`Engine/Render/GI/GITypes.h:25`–`:33`）：`GetSourceId()` 返回 `None`，`NeedsPass` 改为读
`m_RTShadowWanted`，而该标志由帧图每帧用 `GIConfig::ShouldRunRTShadow()` 写入
（`RTProvider.h:94`–`:101`、`DeferredPipeline_FrameGraph.cpp:1161`）。

### 4.3 降噪链是 `std::vector<Stage>`：顺序即执行顺序

历史形态是两个固定指针 `m_Temporal` / `m_Spatial` 加一条「索引 0 是时域、1 是空间」的隐式约定；
现在链是数据（`RTProvider.h:37`–`:41`）：

```cpp
std::vector<Stage> m_Stages;   // 降噪链（顺序即执行顺序）   // RTProvider.h:366
```

`Stage` 用同一结构表示两种滤波器（`RTProvider.h:273`–`:286`），注入顺序写死在四个 `SetXPass` 里：

| 效果 | 链内容 | 位置 |
|---|---|---|
| RT 阴影 | Temporal（`RT_Shadow_Denoise`） | `RTProvider.h:47`–`:52` |
| RTAO | Temporal（`RT_AO_Denoise`） | `RTProvider.h:53`–`:58` |
| RT 反射 | Temporal（`RT_Reflection_Temporal`）→ Spatial（`RT_Reflection_Denoise`） | `RTProvider.h:59`–`:66` |
| RTGI | Temporal（`RT_GI_Temporal`）→ Spatial（`RT_GI_Denoise`） | `RTProvider.h:67`–`:74` |

链的取值规则：只有**就绪**的 stage 参与紧凑编号（`StageReady` / `ActiveStageCount` / `ActiveStageAt`，
`RTProvider.h:295`–`:313`）；第 i 级的输入是链上前一级的输出，第 0 级取主 Pass 输出
（`StageInput`，`RTProvider.h:318`–`:323`）；最终输出按「升采样级 → 链尾 stage → 主输出」回退
（`FinalOutput`，`RTProvider.h:341`–`:353`）。

### 4.4 分辨率与重建升采样

四种效果都是**亚分辨率产出**，链尾可挂一级「重建升采样」（`DenoiseUpscale`）：

> 升采样级不走 `m_Stages`：它不是"又一级滤波"，而是**链的出口形状** —— 是否启用取决于"主输出是否低于消费端分辨率"
（`RTProvider.h:43`–`:46`）

判定按**实测尺寸**而不是配置项：`m_Depth` 的宽或高大于主输出即启用（`UpscaleActive()`，
`RTProvider.h:154`–`:160`）；升采样用全分辨率的深度/法线做引导（`RTProvider.h:200`–`:202`）。
信号登记时 `needsUpscale` 也按同一尺寸判据填（`RTProvider.h:247`–`:254`）。

亚分辨率尺寸的算法（都向上取整）：

| 效果 | 尺寸 | 位置 |
|---|---|---|
| RT 阴影 | `(fullWidth + 1) / 2` × `(fullHeight + 1) / 2` | `RTShadowPass.cpp:46`–`:47` |
| RTAO | `(fullWidth + 1) / 2` × `(fullHeight + 1) / 2` | `RTAOPass.cpp:34`–`:35` |
| RT 反射 | `(fullWidth + 1) / 2` × `(fullHeight + 1) / 2` | `RTReflectionPass.cpp:37`–`:38` |
| RTGI | `(fullWidth + 3) / 4` × `(fullHeight + 3) / 4` | `RTGIPass.cpp:39`–`:40` |

Deferred 侧的实际取值由一个环境变量控制：`HE_RT_FULLRES=1` 时四种效果全部按全分辨率初始化
（作为「重建升采样」的参照档），否则 `rtHalfRes = true`
（`DeferredPipeline.cpp:246`–`:250`、`:254`、`:259`、`:264`、`:269`）。
注意 `RTGIPass::Initialize` 的第 4 个形参名叫 `quarterRes`（`RTGIPass.h:27`），
Deferred 传进来的却是变量 `rtHalfRes` —— 行为正确（默认 1/4 分辨率），但命名与语义不一致。

`HE_RT_UPSCALE=0` 可关掉升采样级（`DeferredPipeline.cpp:355`–`:365`），默认开启。

## 5. 四种 RT 效果的实现

四种效果共享同一套 set0 骨架：`b0`=TLAS，`b1`=输出 StorageImage，`b2`=GBuffer 深度，`b3`=GBuffer 法线
（`RTShadowPass.cpp:51`、`RTAOPass.cpp:39`、`RTReflectionPass.cpp:43`、`RTGIPass.cpp:46`）。
差异全在各自的 bindings 追加、着色器组合与 miss 策略上。

### 5.1 RT 阴影（`RTShadowPass`）

- **着色器组合**：`RT_Shadow.rgen` + `RT_Shadow.rahit`（AnyHit）+ `RT_Common.rmiss`
  （`RTShadowPass.cpp:64`–`:86`）；只有一个 Hit 组、`anyHitShader = 1`。
- **遮挡语义**：RayGen 用 `RAY_FLAG_ACCEPT_FIRST_HIT_AND_END_SEARCH | RAY_FLAG_SKIP_CLOSEST_HIT_SHADER`，
  AnyHit 置 `payload.blocked = true`，Miss 保持 `false` → 「命中即遮挡」，不需要最近命中计算
  （`RTShadowPass.h:21`–`:22`、`RT_Shadow.rgen.slang:135`–`:145`、`RT_Shadow.rahit.slang:16`–`:19`）。
- **软阴影**：`shadowFlags bit2` 打开时按 `softSPP` 在光源面（方向光按角度半径、点/聚光按圆盘）采样
  多条射线取平均；`spp == 1` 且 `radius.x == 0` 退化为硬阴影
  （`RT_Shadow.rgen.slang:75`–`:149`）。`cvRTShadowSoft` 默认 `false`（`RTQualityCVars.cpp:24`）。
- **早退**：`distance(worldPos, cameraPos) > maxShadowDist` 直接写 1.0（完全照亮）；
  天空像素同样写 1.0（`RT_Shadow.rgen.slang:164`–`:176`）。
- **光源数据**：`ShadowLightGPU`（64B/个，`static_assert` 见 `RTShadowPass.cpp:37`）从 `GPULight[]` SSBO
  每帧显式抽取到 UBO（`FillLightBuffer`，`RTShadowPass.cpp:192`–`:213`），UBO 容量
  `sizeof(ShadowLightGPU) * kShadowMaxLights` = 64B × 16（`RTShadowPass.cpp:113`–`:117`、`kShadowMaxLights` 见 `:39`）。

### 5.2 RTAO（`RTAOPass`）

- **着色器组合**：`RT_AO.rgen` + **复用** `RT_Shadow.rahit` + **复用** `RT_Common.rmiss`
  （`RTAOPass.cpp:51`–`:73`）—— AO 与阴影共用同一套「命中即遮挡」的载荷约定。
- **算法**：法线半球余弦采样 `n = max(1, min(sampleCount, 8))` 条射线，`TMax = maxDistance`（默认 2m），
  统计 `occluded`，输出 $ao = 1 - \frac{occluded}{n}$（`RT_AO.rgen.slang:85`–`:108`）。
  输出 `R8_UNORM`（`RTAOPass.cpp:102`）；天空像素写 1.0（不遮蔽，`:76`–`:78`）。
- **Push Constant**：`pc.lightCount = 0`（AO 不需要光源，`RTAOPass.cpp:144`）。

### 5.3 RT 反射（`RTReflectionPass`）

- **着色器组合**：`RT_Reflection.rgen` + `RT_Reflection.rchit` + `RT_Reflection.rmiss`
  （`RTReflectionPass.cpp:58`–`:80`）。
- **光线方向**：`roughness > 0.02` 时用 GGX 半向量重要性采样，否则镜面反射；采样结果若射向表面内侧
  则回退镜面（`RT_Reflection.rgen.slang:97`–`:104`）。
- **粗糙度上限回退**：`roughness > g_PC.maxRoughness`（`cvRTReflectionMaxRoughness`，默认 0.6）时
  **不发射射线**，直接写 `float4(0, 0, 0, -1)` 表示无效 → 合成端回退 IBL prefilter
  （`RT_Reflection.rgen.slang:87`–`:91`；`RTReflectionPass.cpp:165`）。
- **命中着色**：ClosestHit 只做「命中点出射辐射度」估计（`EvaluateHitRadiance`），
  输出 `float4(radiance, RayTCurrent())`，`a` 即命中距离（`RT_Reflection.rchit.slang:33`–`:36`）。
- **每像素只有 1 条射线**：`RTReflectionPass.cpp:164` 把 `cvRTReflectionSPP` clamp 到 `[1, 16]` 并写进
  `pc.sampleCount`，但 `RT_Reflection.rgen.slang` **完全不读** `sampleCount` —— 该 CVar 对反射不生效。

### 5.4 RTGI（`RTGIPass`）

- **着色器组合**：`RT_GI.rgen` + `RT_GI.rchit` + `RT_GI.rmiss`（`RTGIPass.cpp:63`–`:85`）。
- **额外绑定的场景数据**：`b4`=场景材质纹理、`b5`=命中点光源 UBO、`b6`=三角形法线纹理、
  `b7`=DDGI 探针 SSBO、`b8`=DDGI 网格参数 UBO（`RTGIPass.cpp:46`–`:56`）。
- **算法**：对 GBuffer 有效像素（`depth < 1.0 && depth > 0.0`）法线半球余弦采样
  `n = max(1, min(sampleCount, 8))` 条射线，`TMax = maxDistance`（默认 30m），命中取 ClosestHit 的
  出射辐射度、未命中走三条回退分支，最后 `radiance /= n`（分母恒为采样数）
  （`RT_GI.rgen.slang:83`–`:147`）。
- **miss 三分支**（这是 RTGI 最关键的一段）：
  1. 白炉（`flags & 4`）：直接累加 $(1,1,1)$ 并计入 `valid`（`RT_GI.rgen.slang:117`–`:121`）；
  2. DDGI 不在漫反射层栈里（`flags & 2 == 0`）：累加 `SampleDDGI(worldPos, dir) * (1/π)` 并计入 `valid`（`:131`–`:138`）；
  3. DDGI 在层栈里：**miss 贡献 0、不计入 valid**（`:139`），把远场低频交给 DDGI 槽位。
- **量纲一致性**：`SampleDDGI` 返回的是辐照度 $E$（`EvalDDGI_SH` 已施加 Lambert 卷积系数
  $A_0 = \pi$、$A_1 = 2\pi/3$，见 `RT_DDGI.slang:17`–`:39`），而 ClosestHit 给的是辐射度 $L$ ——
  两者不能直接相加，故 miss 路径按「局部环境近似均匀」做 $L = E/\pi$ 换算
  （注释与代码同址：`RT_GI.rgen.slang:132`–`:136`）。
- **有效性标记**：`g_Output[idx] = float4(radiance, valid > 0 ? 1.0 : 0.0)`
  （`RT_GI.rgen.slang:150`），合成端用它判定该像素本帧是否可用。
- **ClosestHit 的辐射度定义**：`EvaluateHitRadiance` 返回**出射辐射度** $L_o = \frac{\rho}{\pi} E$
  （环境项常数 $(0.22, 0.23, 0.26)$ + 各直接光的 $L_i \cos\theta \cdot atten$），
  函数自己完成 $1/\pi$ 换算、调用点不再换算；白炉分支返回 `albedo`
  （`Engine/Shader/Shaders/RT_HitCommon.slang:84`–`:135`）。

> **量纲这条为什么会写成注释**：同一函数曾被三处调用，只有 `DDGI_Trace.rgen` 在调用后除了 π，
> `RT_GI.rchit` 与 `RT_Reflection.rchit` 没有 —— 于是 RTGI 与 RT 反射的绝对量级各大约 3.14 倍。
> 现在换算收敛到函数内部（`RT_HitCommon.slang:84`–`:89`）。

### 5.5 四种效果的分辨率 / 量纲 / miss 对照

| 效果 | 输出 | 分辨率 | 量纲 | miss |
|---|---|---|---|---|
| RT 阴影 | 可见性遮罩 | 1/2 | 乘法因子（`color *= visibility`） | 未遮挡=1 |

### 6.3 弹射的组织方式：循环在 RayGen 内

`PT_Full.rgen.slang` 的结构是「两层循环 + 迭代式追踪」：

```
for s in [0, spp):
    相机光线（分层抖动 StratifiedJitter）
    throughput = 1, mediumSigma = 0
    for bounce in [0, maxBounces):
        TraceRay(..., PathPayload payload)        // 深度 1，循环在 RayGen 内
        介质衰减（若上一段在介质中）
        miss → 加天空 → break
        自发光 → 累加
        直接光：ReSTIR（仅 bounce 0）或 NEE
        IBL 环境光（仅 bounce 0）
        俄罗斯轮盘赌终止
        BSDF 采样 → 下一根光线
radiance /= spp
```

出处：`Engine/Shader/Shaders/PathTracing/PT_Full.rgen.slang:92`–`:264`。

几处关键实现：

| 环节 | 实现 | 位置 |
|---|---|---|
| 相机光线 | `StratifiedJitter` + `invViewProj` 反投影；`TMin=0.01`、`TMax=10000` | `PT_Full.rgen.slang:93`–`:105` |
| 阴影射线 | 哨兵 payload：命中不执行着色器（`a` 保持 0 = 被遮挡），miss 由 `rmiss` 写 `a = -1`；返回 `sp.emissiveT.a < 0 ? 1 : 0` | `PT_Full.rgen.slang:49`–`:67` |
| ReSTIR DI 应用 | 仅 `bounce == 0` 且 `flags & PT_FLAG_RESTIR`：读 `g_FinalReservoir[idx]`，1 条阴影射线替代 NEE 循环，权重 $w = W \cdot M / \sum \hat p$ | `PT_Full.rgen.slang:166`–`:183` |
| NEE | 遍历 `min(lightCount, PT_MAX_LIGHTS)` 个光源；MIS 用 `PowerHeuristic(lightPdf, brdfPdf)`；连续 BSDF 分支的 pdf 按 $(1-t)$ 折算 | `PT_Full.rgen.slang:184`–`:207`（折算见 `:198`） |
| 俄罗斯轮盘赌 | `bounce > 2` 后按 `survival = min(max(throughput), 1)` 终止，存活则 `throughput /= survival` | `PT_Full.rgen.slang:229`–`:235` |
| BSDF 采样 | `SampleBSDF` 三瓣（漫反射 / 各向异性 GGX / 清漆）+ delta 界面瓣；delta 分支权重由采样端给出 | `PT_Full.rgen.slang:237`–`:261` |
| 天空 | miss 与 IBL 都用程序渐变 `SampleSky`（`SampleSky` 定义见 `PT_Common.slang:348`） | `PT_Full.rgen.slang:217`、`:222` |

`flags` 位定义（`PT_Full.rgen.slang:38`–`:41`）：`PT_FLAG_RESTIR = 1<<0`、`PT_FLAG_MIS = 1<<1`、
`PT_FLAG_ROULETTE = 1<<2`、`PT_FLAG_NEE = 1<<3`；另外管线侧还有 `kPTFlag_Textures = 1<<4`
（`PathTracingPipeline.cpp:36`，着色器侧同址定义见 `PT_Full.rchit.slang:49`）。
`PT_FLAG_NEE` 恒开（`PathTracingPipeline.cpp:414`），`MIS` / `Roulette` / `Textures` 默认开、`ReSTIR` 默认关
（`PTQualityCVars.cpp`：`cvPTReSTIR` 默认 `false`）。

**光源硬上限**：`PT_MAX_LIGHTS` = 8（`PT_Full.rgen.slang:44`，注释指明对应 `kGPUMaxLights`），
与 `ShaderTypes.slang:207`（`kGPUMaxLights = 8`）和 `Material.h:42`（`MAX_LIGHTS = kGPUMaxLights`）三处一致。

### 6.4 `PathPayload`：112B 载荷与双端布局固定

```cpp

    float4 normalRough;              // 16  xyz=normal(world), w=roughness
```

### 6.6 体积介质与透射界面

PT 的介质数学是**一份公式、两处实现、靠测试钉住**：着色器侧 `PT_Common.slang`，CPU 侧
`Engine/Render/RT/PTVolumeMath.h`（注释明确「逐式同构」，改装 shader 公式必须同步，
`PTVolumeMath.h:10`–`:17`）。

| 公式 | Slang | CPU 镜像 |
|---|---|---|
| 电介质菲涅尔（Schlick）$F = f_0 + (1-f_0)(1-\cos\theta)^5$ | `PT_Common.slang:213` | `PTVolumeMath.h:20` |
| Snell 折射（$\eta = n_1/n_2$，`false` = 全内反射） | `PT_Common.slang:220` | `PTVolumeMath.h:27` |
| 均匀介质自由程采样（指数分布） | `PT_Common.slang:231` | `PTVolumeMath.h:37` |
| Beer-Lambert 透射率 $T = \exp(-\sigma_t d)$ | `PT_Common.slang:236` | `PTVolumeMath.h:42` |
| $\sigma_t$ 由 glTF `attenuationColor` / `attenuationDistance` 推导 | `RTPass.cpp:628`–`:630` | `PTVolumeMath.h:47` |

`SampleBSDF` 的做法是**按能量份额分配分支概率**（这是实现无偏的关键，`PT_Common.slang:240`–`:252`）：

$$p_{refl} = t \cdot F, \qquad p_{refr} = t \cdot (1-F), \qquad p_{bsdf} = 1-t$$

$t$ = transmission。delta 分支（菲涅尔反射 / 折射 / 全内反射）的权重是同一份额，故分支权重恒为 1
（反射）或 albedo（折射）；界面分支占用了 $[0, t)$ 的随机数区间，连续 BSDF 分支把 $u$ 映射回 $[0,1)$
（`PT_Common.slang:301`–`:302`），NEE 的 pdf 因此按 $(1-t)$ 折算（`PT_Full.rgen.slang:198`）。

介质衰减用的是**期望值而不是随机采样**：RayGen 记录上一段是否在介质中（`mediumSigma`），
命中后按该段长度乘 `BeerTransmittance`（`PT_Full.rgen.slang:117`–`:124`）。
`SampleDistanceInMedium` 定义了但 RayGen 未调用 —— 注释给出的理由是用期望值代替指数分布采样
可显著降方差且保持无偏（`PT_Full.rgen.slang:117`–`:119`）。

折射进入介质后的判定：`transmission > 0 && dot(N, wi) < 0` ⇒ `mediumSigma = payload.volumeParams.rgb`
（`PT_Full.rgen.slang:250`–`:251`）。

### 6.7 ReSTIR：只用于直接光重采样

`ReSTIRPass` 的三个 compute PSO 与 dispatch 顺序：`Init`（WRS 初始采样）→ `Temporal`（速度重投影 +
历史合并）→ `Spatial`（邻域共享）→ 写 `FinalReservoir`（`ReSTIRPass.h:34`–`:38`、`ReSTIRPass.cpp:221`）。
所有 dispatch 都是 `(w+7)/8 × (h+7)/8`（`ReSTIRPass.cpp:242`–`:243`），并带 RenderDoc marker
（`ReSTIRPass.cpp:264`、`:301`、`:326`）。

| 环节 | 内容 | 位置 |
|---|---|---|
| 蓄水池结构 | `PTReservoir { lightIndex, weightSum, M, W, lightPos }`，32B（`lightPos` 必须 `float4`） | `ShaderTypes.slang:428`–`:434` |
| 数据 | `InitialReservoir` + `TemporalReservoir[2]`（双缓冲）+ `FinalReservoir`，各 `W×H` 份 | `ReSTIRPass.h:93`–`:96` |
| 历史纹理 | `m_HistDepth[2]`（`R32_FLOAT`）+ `m_HistNormal[2]`（`RGBA16_FLOAT`），`EndFrame()` 交换槽位 | `ReSTIRPass.h:98`–`:101`、`:64` |
| 初始采样 | 每像素 `candidates` 个候选，目标函数 $\hat p = \mathrm{luminance}(f \cdot L_i) / p_{src}$，WRS 以 $\hat p / \sum \hat p$ 概率替换 | `ReSTIR_Init.comp.slang:76`–`:105` |
| 空间复用 | 邻域 `spatialSamples` 个样本，几何验证：位置差 > 1.0m 或 `dot(N, nbrN) < 0.9` 拒绝 | `ReSTIR_Spatial.comp.slang:70`–`:110`（阈值见 `:91`–`:92`） |
| 最终着色 | 反弹 0 读蓄水池 → `SampleLight` → 1 条阴影射线 → $f(y) \cdot W \cdot M / \sum \hat p$ | `PT_Full.rgen.slang:166`–`:183` |

**范围界定**：`lightIndex` 指向 `g_Lights`（直接光），蓄水池里没有次级顶点/路径信息，采样端也只重评估
「BRDF × 直接光辐射度」这一个量 —— 因此**只有 ReSTIR DI（直接光），没有 ReSTIR GI（间接）**。
ReSTIR 光源数上限 `RESTIR_MAX_LIGHTS = 8`（`ReSTIR_Init.comp.slang:26`、`:79`）。

生效条件有两层：CVar `r.PT.ReSTIR` 打开（默认关），且 `reservoirReady`（帧号 > 1 且光源数与本帧一致）
（`PathTracingPipeline.cpp:401`–`:409`）。`reservoirReady` 通过 `ReSTIRPushConstant.flags` 的 bit2 传到
shader（`ReSTIRPass.cpp:240`）。

`RT_Shadow.rgen.slang:48`–`:61`、`RT_Reflection.rgen.slang:31`–`:44`）。

## 8. 与 GI 层栈的集成

### 8.1 层栈结构

`GIConfig` 有四个通道：三个**能量通道** + 一个**可见性通道**（`Engine/Render/GI/GITypes.h:447`–`:453`）：

```cpp
GIChannelStack diffuse;    // 间接漫反射（IBL/DDGI/SSGI/RSM/RTGI）
GIChannelStack specular;   // 间接镜面（IBL/SSR/RTReflection）
GIChannelStack ao;         // 环境光遮蔽（SSAO/GTAO/RTAO）
ShadowChannel  shadow;     // 阴影（None / Raster / RT）—— 不进层栈
```

阴影之所以单独用枚举而不是进层栈，理由是量纲：阴影是**可见性（乘法项）**，合成运算是
`color *= visibility`，不参与加权求和，也没有「距离让位」（`GITypes.h:25`–`:33`）。

### 8.2 归一化加权：RT 源与屏幕空间源在同一口锅里竞争

合成模式由 `GIBlendMode` 给出，默认走归一化：

| 模式 | 语义 | 位置 |
|---|---|---|
| `Additive = 0` | 直接相加（旧行为，双重计数，仅作 A/B 对照） | `GITypes.h:39` |
| `Normalized = 1` | $\sum (c_i w_i) / \sum w_i$，权重和 = 1 → 无双重计数 | `GITypes.h:40` |

着色器侧的落地：`DeferredLighting.frag` 按 `GIChannelBlendParams` 逐源累加 `num/den`，
`den > 0` 才做除法（`Engine/Shader/Shaders/Lighting/DeferredLighting.frag.slang:452`–`:473`）。
RT 源的取值分支：RTGI 乘接收面 albedo（`:223`–`:224`）、RT 反射直接取 `rgb`（`:239`）、
RT AO 取 `.r` 并在有效时参与（`:498`）、RT 反射以 `a >= 0` 判有效（`:189`）。

**RTGI 与 SSGI 是同一物理量的两份估计**，这件事在引擎里有显式登记：

> 重复估计：同一物理量的「屏幕空间」与「光追」两份估计。成本翻倍且归一化会互相稀释——但这是有意设计，故仅提示、不强制剔除
（`GITypes.h:574`–`:576`、诊断代码 `:729`–`:740`）

对应关系由 `GIRegistry::RTCounterpartOf` 给出：`SSGI → RTGI`、`SSR → RTReflection`、
`SSAO / GTAO → RTAO`（`GITypes.h:695`–`:703`）。诊断分三类（`GIDiagnosticKind`）：

| 诊断 | 触发条件 | 位置 |
|---|---|---|
| `RedundantDuplicate` | SSAO + GTAO 同时在场（同一 pass、同一纹理，归一化等价于取自身） | `GITypes.h:719`–`:727` |
| `DuplicateEstimate` | 屏幕空间源与其光追对应源同时启用 | `GITypes.h:731`–`:740` |
| `CorrelatedEstimates` | RTGI + DDGI 同时在场（**非独立估计**） | `GITypes.h:742`–`:748` |

### 8.3 「不可回退 DDGI」的防双计约定

这是 RT 源接入层栈时最关键的一条约定，且它同时写在四处（C++ 判定、C++ 注入、注释、shader 分支）：

| 环节 | 位置 |
|---|---|
| 帧图判定「DDGI 是否自己也是漫反射层栈的源」并注入 | `DeferredPipeline_FrameGraph.cpp:1162`–`:1164` |
| Provider 存标志 | `RTProvider.h:114`–`:116` |
| 注入 `RTExecuteContext::ddgiIsStackSource` | `RTProvider.h:395` |
| 打进 `flags` 的 bit1 | `RTGIPass.cpp:176`–`:177` |
| shader 侧据此打断回退 | `RT_GI.rgen.slang:122`–`:139` |

理由（源码原文）：归一化合成假定每个源给出的是「同一物理量的独立估计」；若 RTGI 的 miss 又去查 DDGI，
DDGI 的信息会以（RTGI 槽位权重 + DDGI 槽位权重）的总权重进入画面，权重和不再等于 1，加权平均失去无偏性
（`RT_GI.rgen.slang:122`–`:130`）。**注意这不只是理论担忧**：同一段注释记录了实测读数差异（同一份 RTGI
输出的均值 0.0575 与 0.2034），并明确「DDGI 不在层栈里 ⇒ 保留回退，这是降级路径，不构成双重计数」
（`RT_GI.rgen.slang:129`–`:130`）。

### 8.4 屏幕覆盖置信度

RT 三源虽然不属于「像素级屏幕空间估计」这一类（`IsScreenSpaceSource` 不含它们，`GITypes.h:98`–`:104`），
但**被单独列入「受相机视口限制」**：入射方向从本像素出发，视口外没有数据、边缘退化，
故权重必须乘屏幕覆盖置信度（`GITypes.h:113`–`:130`）。判据由 C++ 逐槽写进 UBO（
`kGIConfCameraCoverage`，`GITypes.h:137`–`:161`），着色器只按掩码计算，避免两侧各写一份 id 列表。

### 8.5 RT 开关的真实来源

RT 效果「跑不跑」由层栈 + 设备能力决定，而不是 CVar：

| 判定 | 位置 |
|---|---|
| `GIConfig::AnyRTSource()`（四个效果任一被要求） | `GITypes.h:485`–`:487` |
| 帧图门控：`m_RTEnabled && m_GIConfig.AnyRTSource() && m_RTPass` | `DeferredPipeline_FrameGraph.cpp:1145` |
| 本 Provider 是否需要主 Pass（RT 阴影看枚举，其余看通道） | `RTProvider.h:95`–`:99` |
| 设备能力裁剪：`GIRegistry::IsAvailable` 对光追源要求 `rtSupported` | `GITypes.h:616`–`:623` |
| 降级：`GIRegistry::Degrade` 逐源裁剪，RT 阴影不可用则回退光栅阴影 | `GITypes.h:658`–`:673` |
| Ultra 预设把 RT 源权重置 1 | `GITypes.h:523`–`:527` |

## 10. 已知边界与限制

> 本节每条都在源码里核对过。带「⚠」的是**注释与实现不一致**或**能力写了但没接线**的条目。

### 10.1 算法性边界

1. **RT 效果全是「一次反弹 + 直接光」**。RTGI/RT 反射的 ClosestHit 只评估命中表面的**出射辐射度**
   （环境项 + 各直接光的 Lambert 项），不再发射二级射线（`RT_HitCommon.slang:100`–`:135`）。
   RT 阴影/RTAO 根本不执行 ClosestHit（只有 AnyHit）。
2. **PT 的 IBL 是近似项**，在反弹 0 直接加到结果上：漫反射按法线采样程序天空乘 `albedo * (1-metallic)`，
   镜面按反射方向采样乘 $F_0$（`PT_Full.rgen.slang:209`–`:227`）。这不是路径积分的自然结果，
   而是为了「避免相机可见面几乎全黑」加的经验项（注释自陈「间接光近似」）。
3. **介质只做吸收、不做散射**：RayGen 只乘 `BeerTransmittance`，没有介质内散射事件
   （`PT_Full.rgen.slang:117`–`:124`）；`SampleDistanceInMedium` 有定义但未被 RayGen 调用
   （`PT_Common.slang:231`、`PTVolumeMath.h:37`）。
4. **ReSTIR 只做直接光（DI）**，没有 ReSTIR GI：蓄水池只存 `lightIndex` 与直接光采样位置，
   采样端只重评估「BRDF × 直接光」（`ReSTIR_Init.comp.slang:85`–`:103`、`ShaderTypes.slang:428`–`:434`）。
   ReSTIR 还默认关闭（`PTQualityCVars.cpp` 的 `cvPTReSTIR`）。
5. **RT 阴影不区分材质透明度**：AnyHit 无条件置 `blocked = true`，没有 alpha test / 透明阴影
   （`RT_Shadow.rahit.slang:16`–`:19`）。
6. **RT 阴影是「任意命中即遮挡」**：用 `RAY_FLAG_ACCEPT_FIRST_HIT_AND_END_SEARCH`，不做半透明累积、
   不做最近命中，也就无法表达「部分遮挡」的解析解，只能靠软阴影面光源采样近似
   （`RT_Shadow.rgen.slang:135`–`:145`、`:75`–`:149`）。

### 10.2 上限与 clamp

7. **光源硬上限 8**：`kGPUMaxLights = 8`（`ShaderTypes.slang:207`）⇒ `MAX_LIGHTS = 8`（`Material.h:42`）
   ⇒ PT 的 `PT_MAX_LIGHTS = 8`（`PT_Full.rgen.slang:44`）、ReSTIR 的 `RESTIR_MAX_LIGHTS = 8`
   （`ReSTIR_Init.comp.slang:26`）。RT 效果的命中光源 UBO 容量是 16（48B × 16，
   `RTEffectPass.cpp:112`），但 CPU 侧永远最多写 8 个 —— 16 只是余量。
8. **SPP 上限在 C++ 与 shader 两侧不一致**：四个效果 Pass 都把 CVar clamp 到 `[1, 16]`
   （`RTGIPass.cpp:175`、`RTAOPass.cpp:142`、`RTShadowPass.cpp:174`、`RTReflectionPass.cpp:164`），
   但 rgen 内部再 clamp 一次到 8（`RT_GI.rgen.slang:93`、`RT_AO.rgen.slang:85`）。
   即 `r.RT.GI.SPP 12` 与 `8` 的实际效果相同。
9. **阴影的 `softSPP` 没有第二道 clamp**：`RTShadowPass.cpp:174` clamp 到 `[1,16]`，
   `RT_Shadow.rgen.slang:196` 直接 `spp = soft ? g_PC.softSPP : 1u` —— 也就是说这里的上限由 C++ 单独保证，
   shader 没有自保护（其余三个效果有）。
10. ⚠ **`r.RT.Reflection.SPP` 是空开关**：值被写进 push constant（`RTReflectionPass.cpp:164`），
    但 `RT_Reflection.rgen.slang` 全文不读 `sampleCount`，每像素恒 1 条射线。
11. ⚠ **分辨率标志位在 shader 侧无人读取**：`RTReflectionPass.cpp:166` 写 `flags` bit0、
    `RTAOPass.cpp:143` 写 bit0、`RTShadowPass.cpp:175` 写 bit1，三个 rgen 都不读该位
    （分辨率由 dispatch 尺寸决定）。RTGI 只读 bit1/bit2（`RT_GI.rgen.slang:131`、`:117`）。
12. **载荷上限**：四个 RT 效果共用 16B（`Types.h:43`）；PT 需要 112B，设备 `maxPayloadSize` 不足时
    直接禁用 PT（`PTPass.cpp:158`–`:159`）。

### 10.3 未实现的能力（字段存在但无实现）

13. **SER / OMM / inline RT 均未实现**：`DeviceCaps` 有 `supportsSER`（`Types.h:307`）与
    `supportsOMM`（`Types.h:308`），但 `VulkanDevice::GetCaps` 从不给它们赋值
    （`VulkanDevice.cpp:133`–`:179`），故恒为 `false`；引擎里也没有任何使用点，
    RT 管线描述里更没有 SER/OMM 相关字段（`RayTracing.h:121`–`:132`）。
14. **无 BLAS refit / 无 AS 压缩**：`ASBuildFlags::AllowUpdate` 与 `AllowCompaction` 只是枚举项
    （`RayTracing.h:30`、`:31`），`RTPass::BuildAS` 只用 `PreferFastTrace` 且几何变化时整体重建，
    `BuildBLAS(..., false)` 明确不更新（`RTPass.cpp:341`、`:370`）；也没有
    `vkCmdCopyAccelerationStructureKHR` 的加载与调用。
15. **命中组不能按材质分派**：TLAS 全部实例 `sbtOffset = 0`（`RTPass.cpp:396`），
    每个效果管线只有 1 个 Hit 组；`SBTSlot::dataOffset` / `dataSize` 从未写入 ⇒ 没有 SBT local data。
16. **只有三角形几何且一律不透明**：`RTGeometryType::AABBs` / `Instances` 无使用点，
    BLAS 硬编码 `VK_GEOMETRY_TYPE_TRIANGLES_KHR` + `VK_GEOMETRY_OPAQUE_BIT_KHR`
    （`VulkanRT.cpp:310`、`:317`；`VulkanCommandList.cpp:1015`、`:1025`）⇒ 无法做 alpha-test 几何、
    没有程序化（Intersection）命中组（`ShaderStage` 里也没有 `Intersection`，`Types.h:182`–`:195`）。
17. **无间接光追调度**：没有 `vkCmdTraceRaysIndirect` 的加载与调用；`maxRTDispatchSize` 被查询但
    从未用于校验 `TraceRays` 的尺寸（`VulkanRT.cpp:237`、`Types.h:324`）。
18. **无 ReSTIR GI / ReSTIR PT**：见 10.1-4；路径蓄水池（`PTReservoir` 之外的结构）在引擎中不存在，
    `PTReservoir` 也只承载直接光样本。
19. **无 PT 的累积帧数上限 / 目标 SPP 机制**：`r.PT.SPP` 上限 8（`PTPass.cpp:277`），
    累积完全交给降噪器的时域混合，没有「累积 N 帧后停止」的机制。
20. **载荷/深度上限是引擎约定而非设备校验**：`maxPayloadSize` 不传给 Vulkan
    （`VulkanRT.cpp:501`、`:517`），设备的 `maxRayPayloadSize` / `maxRayHitAttributeSize` 属性
    从未被查询；`maxRayRecursionDepth` 查询了但不用于校验（`VulkanRT.cpp:234`）。

### 10.4 ⚠ 注释与实现不一致（静态阅读即可确认）

21. **阴影光源 UBO 的注释尺寸写错**：`RTShadowPass.cpp:112` 的注释写「48B × 16 = 768B」，
    但 `ShadowLightGPU` 是 **64B**（`static_assert`，`RTShadowPass.cpp:37`），实际容量 64B × 16 = 1024B
    （`RTShadowPass.cpp:115`）。
22. **场景材质纹理行数注释过时（同一函数有四种说法）**：实现是 **11 行**（`RTPass.cpp:551` 的
    `n * 11 * 4`、`:542`–`:550` 的行语义注释、`RTPass.h:200`），但 `RTPass.cpp:511` 的函数头注释写「7×N」、
    `RTPass.h:74` 写「3×N」；着色器侧 `RT_HitCommon.slang` 一个文件里就出现了三种：
    `:4` 写「2×N」、`:18` 写「3×N」、`:40` 写「4×N」（该文件实际读取 row0/row1/row3 与 row2，
    行语义正确、行数描述过期）。`RTPass.cpp:460` 的 `CreateMaterialTexture` 注释写 3 行 ——
    那一份确实是另一张 3 行纹理（`RTPass.cpp:501`），不算冲突。
23. **`PT_Common.slang` 文件头写「48B 载荷」**（`PT_Common.slang:5`），同文件 `:22` 与结构定义均为 112B；
    同类的还有 `PTPass.cpp:151` 写「96B payload」，而实际传入的是 `kPathPayloadSize` = 112B
    （`PTPass.cpp:156`）。
24. **方向光符号约定在 RT 侧与光栅/PT 侧相反**：
    光栅光照与 PT 都取 `L = normalize(-light.directionType.xyz)`（`DeferredLighting.frag.slang:321`、
    `PBR.frag.slang:112`、`PT_Common.slang:364`–`:367`，后者注释明确「`L` 指向光源，须取反——`direction`
    字段为光传播方向」），而 `RT_HitCommon.slang:118` 与 `RT_Shadow.rgen.slang:87`、`:187` 直接用
    `normalize(l.directionType.xyz)`。
    静态推论：对传播方向为 $d$ 的方向光，RT 阴影的 `NdotL` 判定（`RT_Shadow.rgen.slang:191`–`:192`）
    与射线方向都会反向。**本文未运行验证该推论**（见第 11 节）。

    但 RayGen 的 miss 分支只读 `payload.radianceT.a`（哨兵），rgb 走的是白炉 / DDGI / 0 三条分支

### 10.5 CPU 侧约定

30. **命中光源是「每帧 CPU 拷贝」而不是 shader 直接读 SSBO**：`FillHitLightUB` 把 `GPULight[]`
    （64B/个）显式抽取成紧凑的 `RTHitLightGPU`（48B/个）并跳过 `colorIntensity.w <= 0` 的无效光源
    （`RTEffectPass.cpp:122`–`:148`）；阴影侧同理（`ShadowLightGPU`，`RTShadowPass.cpp:190`–`:213`）。
    原因是 ClosestHit 不访问 SSBO（见 2.5）。
31. **`RTEffectPass::Initialize` 会就地补全 push constant 的 stage 掩码**（`RTEffectPass.cpp:33`–`:34`），
    调用方不必自己记住；若未来新增 RT 效果而绕开基类，需要自己补（三级拓宽见 2.3）。
32. **`PrepareOutputUAV` 的首帧标志**只控制第一次过渡：RT 效果用 `m_OutputWritten`，
    PT 用 5 张纹理共用一个标志（`RTEffectPass.cpp:104`、`PTPass.cpp:226`）。
33. **RT 效果依赖「共享 RTPass」而不是自己建 AS**：Deferred 与 PT 可复用同一份 BLAS/TLAS
    （`PathTracingPipeline.h:67`–`:69`、`PathTracingPipeline.cpp:91`–`:100`），
    AS 构建在帧图里是 DDGI 段**之前**注册的共享前置（`DeferredPipeline_FrameGraph.cpp:1150`–`:1151`）。
