## 2. 构建配置

### 2.1 preset 清单与差异

两个 preset 的**唯一差异**是生成器/编译器路径，四个 `cacheVariables` 完全相同：

| preset | displayName | generator | binaryDir | 差异项 | 依据 |
|---|---|---|---|---|---|
| `default` | MSVC 2026 (Vulkan, Windows 默认) | `Visual Studio 18 2026` | `${sourceDir}/Build` | 无编译器路径（用 VS 默认工具链） | `CMakePresets.json:5-15` |
| `gcc` | GCC 16 MinGW (Vulkan) | `MinGW Makefiles` | `${sourceDir}/Build` | 写死 `CMAKE_C_COMPILER`/`CMAKE_CXX_COMPILER`/`CMAKE_MAKE_PROGRAM` 为 `C:/gcc16/mingw64/bin/*` | `CMakePresets.json:17-30` |

两者的 `cacheVariables` 均为 `HUGENGINE_BUILD_SAMPLES=ON`、`HUGENGINE_BUILD_EDITOR=ON`、`HUGENGINE_BUILD_TESTS=OFF`、`HUGENGINE_RHI_VULKAN=ON`（`CMakePresets.json:9-14`、`:21-29`）。

从**依赖治理**角度看，preset 是当前唯一的「依赖相关配置」载体，但它一个依赖版本也不表达：没有 `CMAKE_TOOLCHAIN_FILE`、没有包管理器集成、没有 SDK 版本 pin。构建与运行命令一律见《开发与验证手册》§1.2、§2.1。

### 2.2 生成器与 C++ 标准的传播关系

顺序很重要（`CMakeLists.txt:54-67`）：

1. `include(cmake/VulkanSDK.cmake)` + `find_package(Vulkan REQUIRED)`（`:42-43`）——**先**解决系统依赖；
2. `find_package(Git REQUIRED)`（`:47`）+ `include(cmake/DownloadAssets.cmake)`（`:52`）——**configure 期**可能联网；
3. `add_subdirectory(Engine/External)`（`:59`）——**此时** `CMAKE_CXX_STANDARD` 还没被工程设成 20；
4. 之后才 `set(CMAKE_CXX_STANDARD 20)`（`:65`）并 `add_subdirectory(Engine)`（`:84`）。

注释里写明了这一意图：避免把 `CXX_STANDARD` 传播给第三方的 sub-build（`CMakeLists.txt:56-58`）。后果是每个第三方库用**自己的**标准：

| 库 | 自己设的标准 | 依据 |
|---|---|---|
| Jolt | `CMAKE_CXX_STANDARD 17` | `Engine/External/JoltPhysics/Jolt/Jolt.cmake:2-3` |
| Taskflow | `CMAKE_CXX_STANDARD 20` | `Engine/External/taskflow/CMakeLists.txt:35-37` |
| GLFW | C99（`C_STANDARD 99`，C 语言工程） | `Engine/External/glfw/src/CMakeLists.txt:102` |
| 其余（glm/spdlog/meshoptimizer/imgui） | 未自行设置 ⇒ 用 CMake 默认（编译器默认标准） | 各库 CMakeLists 内无 `CXX_STANDARD` 设置 |

设 $S_{\text{engine}}$ 为工程标准、$S_{\text{lib}}$ 为库自设标准，则实际编译标准为

$$S_{\text{compile}} = \begin{cases} S_{\text{lib}} & \text{库自设时} \\ S_{\text{default}}(\text{编译器}) & \text{否则} \end{cases}$$

**含义**：`/Zc:preprocessor /bigobj /MP /utf-8` 与 `NOMINMAX` 这些 `add_compile_options`/`add_compile_definitions`（`CMakeLists.txt:70-71`）是在 `Engine/External` **之后**加的，因此**不会**作用于第三方（好在这是「第三方少受影响」而非「工程缺选项」）。反过来，第三方通过 `INTERFACE` 传播给工程的编译选项会直接影响工程——例如 `Taskflow` 的 `/wd4324`（`Engine/External/taskflow/CMakeLists.txt:308`）。

### 4.2 版本口径说明与不一致点

1. **Jolt 的 5.6.1 / 5.6.0**：版本头写 `5.6.1`（`Jolt/Core/Core.h:8-10`），CMake `project(JoltPhysics VERSION 5.6.0 ...)`（`Build/CMakeLists.txt:3`）。运行期打印的版本取版本头——`Jolt/RegisterTypes.cpp:80` 直接把 `JPH_VERSION_MAJOR/MINOR/PATCH` 拼进注册信息，所以**日志里会看到 5.6.1，而 CMake 缓存里是 5.6.0**。本文如实记录，不判定哪一个是「对的」。
2. **GLM 实际上是「库 + 头」而非纯头文件**：`GLM_BUILD_LIBRARY` 默认 `ON`（`Engine/External/glm/CMakeLists.txt:23`），因此 `glm` 走 `add_library(glm ...)` 分支，`glm::glm` 是静态库别名（`Engine/External/glm/glm/CMakeLists.txt:53-64`）；只有把 `GLM_BUILD_LIBRARY` 置 OFF 才会退化成 INTERFACE（`:65-68`）。工程侧只设了 `GLM_TEST_ENABLE OFF`（`Engine/External/CMakeLists.txt:17`）——该选项定义在 `glm/test/CMakeLists.txt:3`，而 `test/` 子目录只在 `GLM_BUILD_TESTS`（默认 = 非顶层工程 ⇒ OFF，`glm/CMakeLists.txt:24`、`:249-252`）为真时才加入，所以这条 `set` 在本工程里**不产生任何效果**；真正决定不建测试的是 `GLM_BUILD_TESTS` 的默认值。
3. **stb 没有库级版本号**：只有单文件版本（见 §4.1 第 5 行）与 `STBI_VERSION 1`（`stb_image.h:374`，该宏指**文件格式 API 版本**，不是库版本）。因此「stb 是哪个版本」只能按文件回答。
4. **spdlog 的版本三处一致**（`version.h:6-8`、`utils.cmake:4-16` 提取、`project(spdlog VERSION ...)`），无漂移。
5. **Taskflow 的版本编码**：`TF_VERSION 400100`（`taskflow.hpp:47`）按「百万位 = 主、千位 = 次、个位 = 补丁」编码，即

$$\text{TF\_VERSION} = major \times 10^{5} + minor \times 10^{3} + patch \Rightarrow 4 \times 10^{5} + 1 \times 10^{3} + 0 = 400100$$

与 `project(Taskflow VERSION 4.1.0)`（`CMakeLists.txt:32`）一致。
6. **meshoptimizer 的版本也是编码值**：`MESHOPTIMIZER_VERSION 220` 表示 $220 / 1000 = 0$、$(220 \bmod 1000)/10 = 22$，即 `0.22`（换算逻辑见上游 `gltf/gltfpack.cpp:22`）。

另外 `meshoptimizer/extern/` 里还有两个单头（`fast_obj.h`、`sdefl.h`）与 `cgltf.h`：它们**随子模块一起进仓库**，跨了两类（子模块内的 vendored 单头）。其中只有 `cgltf.h` 被工程实际使用（`Engine/Asset/CMakeLists.txt:18`）。

### 5.3 取舍：现状是「两者都要」，代价是三种不一致

| 不一致 | 具体表现 | 依据 |
|---|---|---|
| 声明与实际不符 | `Engine/External/CMakeLists.txt` 头注释写「External dependencies — git submodules（无网络依赖）」，但同目录有 4 个非子模块目录，且 configure 期确实会联网下载 Sponza | `Engine/External/CMakeLists.txt:1-4`、`:43` vs `cmake/DownloadAssets.cmake:12-27` |
| 升级路径分裂 | 子模块：`git submodule update`；vendored：手工替换文件。**两者都没有版本清单文件可供对照** | `.gitmodules:1-21`、`Engine/External/CMakeLists.txt:36-54` |
| 不可追溯 | 子模块的 commit 不在文本里；vendored 的 commit 连注释都没写全（imgui 只写「CDN 下载」） | `.gitmodules:1-21`、`Engine/External/CMakeLists.txt:43` |

**建议口径**（不改代码也能落地的部分）：把「子模块用于**需要 CMake target 的库**、vendored 用于**单头文件零构建的库**」这一现状写成显式规则，并落到 §7 的步骤里；同时在仓库里加一个版本清单文件（或校验脚本）把 §4.1 的表变成可 `git diff` 的事实。

### 6.1 判据：「必须入库」与「必须不入库」的分界

| 判据 | 例 | 为什么 |
|---|---|---|
| 生成它需要**工程外部的人工步骤**（离线脚本、手工运行） ⇒ **必须入库** | `STBNData.h` | 它是 PT/ReSTIR 着色器的**运行期前置**（`Engine/Render/RT/STBNTexture.cpp:3`、`:19`），但没有 CMake 规则会生成它；脚本本身注释「一次性离线运行」且产物有 21 MB，随构建生成会毁掉每次 configure 的体感（`Tools/gen_stbn.py:2-7`） |

## 7. 新增一个第三方依赖的完整步骤

### 7.0 先决策：走哪条路

| 判据 | 走法 |
|---|---|
| 只有头文件、且消费侧只需要 include 路径 | **方式 C（INTERFACE 目标）** |
| 单头文件、但需要「恰在一个 TU 展开实现」 | **方式 B（单头 + `*_IMPLEMENTATION`）** |
| 提供完整 CMake 工程（含 target 定义） | **方式 A（子模块 + `add_subdirectory`）** |
| 有一堆 `.cpp` 但**没有** CMakeLists（或上游 CMake 不适合被 `add_subdirectory`） | **方式 D（在 `External/CMakeLists.txt` 手写 `add_library`）** |
| 是系统级 SDK/库（随机器安装、由本机路径发现） | **方式 E（`find_package` + 探测脚本）** |

现成先例：A = glfw/glm/spdlog/taskflow/meshoptimizer/Jolt；B = stb/VMA/cgltf/doctest；C = `stb` 与 `nlohmann_json`（两者都是 INTERFACE，差别只在有没有实现展开）；D = `imgui`；E = Vulkan SDK + Git。

### 7.1 无论哪种方式都要做的 5 件事

| 步骤 | 要改的地方 | 依据（现有先例） |
|---|---|---|
| ① 放进 `Engine/External/`（或加入 `.gitmodules`） | `Engine/External/<lib>/`；子模块另需 `.gitmodules` 追加 entry | `Engine/External/` 目录结构、`.gitmodules:1-21` |
| ② 在 `Engine/External/CMakeLists.txt` 注册 | 设选项 → `add_subdirectory` / 手建 target；文件末尾的 `message(STATUS ...)` 只是提示，不必改 | `Engine/External/CMakeLists.txt:9-76` |
| ③ 决定**谁**链接它，并选 `PUBLIC`/`PRIVATE` | 消费方 `CMakeLists.txt` 的 `target_link_libraries` | 例：`Engine/Render/CMakeLists.txt:237`（PRIVATE，头只出现在 `.cpp`） |
| ④ 把 target 加进 IDE 分组清单 | 根 `CMakeLists.txt` 的 `_ext` foreach（漏了就会散落在解决方案根目录） | `CMakeLists.txt:104-111` |
| ⑤ 记录版本与许可证 | 仓库**当前没有**集中清单（见 §1.2）：至少要像 §4.1 那样能指到版本头与 LICENSE 文件；若采纳 §8 建议则写进新增的依赖清单文件 | `Engine/External/glm/glm/detail/setup.hpp:6-8`、`Engine/External/spdlog/include/spdlog/version.h:6-8`（版本头先例） |

### 7.2 方式 A：git 子模块 + `add_subdirectory`

**要改的文件**：`.gitmodules`、`Engine/External/CMakeLists.txt`、消费方 `CMakeLists.txt`、根 `CMakeLists.txt`（分组），必要时 `Tests/CMakeLists.txt`。

以 GLFW 为模板：

```cmake
# Engine/External/CMakeLists.txt（照抄 glfw 的四行模式：:9-14）
set(<LIB>_OPT_A OFF CACHE BOOL "" FORCE)
set(<LIB>_OPT_B OFF CACHE BOOL "" FORCE)
add_subdirectory(<lib>)
```

要点：
- 用 `CACHE BOOL "" FORCE` 覆盖上游默认值，**必须**在上游 `option()` 之前设置或在同文件内 `FORCE`（现有 7 处全部如此：`Engine/External/CMakeLists.txt:10-13`、`:17`、`:21-22`、`:26-27`、`:61-66`）；
- 若上游有「顶层工程才建样例/测试」的判断，**不要**去设它的 `TARGET_*` 选项（Jolt 的做法就是靠上游的 `CMAKE_CURRENT_SOURCE_DIR STREQUAL CMAKE_SOURCE_DIR` 自动跳过，`Build/CMakeLists.txt:363-370`）；
- 若上游自带 install/export 规则且**没有**开关（taskflow、meshoptimizer），`cmake --install` 会真的把它们装出去，需要评估是否可接受（`taskflow/CMakeLists.txt:359`、`meshoptimizer/CMakeLists.txt:140`）。

### 7.3 方式 B：单头文件 + 在某 TU 展开实现

**要改的文件**：`Engine/External/CMakeLists.txt`（建 INTERFACE 目标或只加 include 路径）、**恰好一个**消费 TU（`#define <LIB>_IMPLEMENTATION`）、消费方 `CMakeLists.txt`（include 路径/链接）、根 `CMakeLists.txt`（若建了 target 则加分组）。

三种现成模式，选一种并保持与全局一致：

| 模式 | 先例 | 写法 | 注意 |
|---|---|---|---|
| 建 INTERFACE 目标、含实现的 TU 由消费方提供 | `stb`（`Engine/External/CMakeLists.txt:31-34`） | `add_library(stb INTERFACE)` + `target_include_directories(...)`；消费侧 `#define STB_IMAGE_IMPLEMENTATION` + `#include <stb_image.h>`（`Samples/03.Sponza-Forward/03.Sponza-Forward.cpp:46-47`） | 实现必须**只在一个** TU 展开；当前同一个 stb 被 6 个样例各自展开（§1.2 末几行），加新样例时要遵守同一习惯 |
| 不建目标，只加 include 路径 | VMA（`Engine/RHI/CMakeLists.txt:88-90`）、cgltf（`Engine/Asset/CMakeLists.txt:18`） | 消费方自行 `target_include_directories`；实现在 `Engine/RHI/Vulkan/VulkanResources.cpp:7`、`Engine/Asset/Asset/glTFLoader.cpp:21-22` | 没有 target ⇒ 不会出现在链接排序里，也不会被 `_ext` 分组；新增时应优先考虑补一个 INTERFACE 目标 |
| 无目标、只给测试 include 路径 | doctest（`Tests/CMakeLists.txt:75`） | 实现在 `Tests/Main.cpp:14`（`DOCTEST_CONFIG_IMPLEMENT`） | 与上一条同样的代价 |

### 7.4 方式 C：纯头文件（INTERFACE 目标）

**要改的文件**：`Engine/External/CMakeLists.txt`、消费方 `CMakeLists.txt`、根 `CMakeLists.txt`（分组）。

模板（照抄 `nlohmann_json`，`Engine/External/CMakeLists.txt:36-41`）：

```cmake
if(NOT TARGET <lib>_target)
    add_library(<lib>_target INTERFACE)
    target_include_directories(<lib>_target INTERFACE ${CMAKE_CURRENT_SOURCE_DIR})
endif()
```

`if(NOT TARGET ...)` 是为了防止重复定义；include 根要选到「消费侧写裸文件名/路径能对上」的那一层——`nlohmann_json` 的 include 根是 `Engine/External`，所以消费侧写 `"nlohmann/json.hpp"`（`Engine/AI/DeepSeekClient.cpp:4`）；`stb` 的根是 `Engine/External/stb`，所以写 `<stb_image.h>`（`Samples/03.Sponza-Forward/03.Sponza-Forward.cpp:47`）。

### 7.5 方式 D：手写 `add_library(... STATIC ...)` 源文件列表

**要改的文件**：`Engine/External/CMakeLists.txt`（新增一段 `add_library` + include + 链接）、消费方 `CMakeLists.txt`。

模板（照抄 `imgui`，`Engine/External/CMakeLists.txt:43-54`）：显式列出 `.cpp`（不 GLOB，理由与着色器侧相同：`Engine/Shader/CMakeLists.txt:30`），`target_include_directories(PUBLIC ...)` 暴露根与子目录（imgui 暴露了 `${IMGUI_DIR}` 与 `${IMGUI_DIR}/backends`），`target_link_libraries(PUBLIC glfw Vulkan::Vulkan)` 把后端依赖显式声明。

**当心**：这正是「有库但无版本、无许可证文件」的高发区（imgui 现状），务必同时补 LICENSE 与版本记录。

### 7.6 方式 E：`find_package`（系统级依赖）

**要改的文件**：根 `CMakeLists.txt`（探测/查找 + 开关门控）、消费方 `CMakeLists.txt`（`target_link_libraries`）。

先例：Vulkan SDK 的探测脚本 `cmake/VulkanSDK.cmake`——**不写死版本路径、不下载**，按「目录名 `x.y.z.w` + 必需文件存在」筛选后取版本号最大者（`:20-35`），把结果写入 `ENV{VULKAN_SDK}` 供 `find_package(Vulkan)` 与 `find_program(SLANGC)` 共用（`:46-49`），并在 SDK 升级时清理指向旧版本的缓存项（`:51-58`）；找不到就 `FATAL_ERROR`（`:38-43`）。新增系统依赖时这套「探测 → 写环境变量 → 清缓存 → 失败即报错」的结构可以直接复用。

## 8. 依赖治理的已知问题与建议

按「值得修的优先级」排列；每条给出实据与**最小改动**。

### 8.1 Jolt 版本号两处不一致（最高优先：会被日志带出去）

- 实据：`Jolt/Core/Core.h:8-10` = `5.6.1`；`Build/CMakeLists.txt:3` = `5.6.0`；运行期日志取版本头（`Jolt/RegisterTypes.cpp:80`）。
- 影响：排查「用的是哪版 Jolt」时，看日志和看 CMake 缓存会得到两个答案；升级/回退时容易误判。
- 建议：在 §4.1 这类清单里**以版本头为准**并显式记一条差异说明（本文已这样做）；根治要提上游 issue 或本地打 patch（属子模块内改动，需评估维护成本）。

### 8.2 许可证文件缺失/不完整（合规硬伤，改动最小）

- 实据：`imgui` 源码写「See LICENSE.txt for copyright and licensing details (standard MIT License)」（`Engine/External/imgui/imgui.cpp:30`），但 `Engine/External/imgui/` 下**没有** `LICENSE.txt`；VMA/nlohmann/doctest 只有头内声明（`vk_mem_alloc.h:2-20`、`json.hpp:7-9`、`doctest.h:7-11`），无独立 LICENSE 文件。
- 影响：发布/第三方审计时缺文件即视作未声明；imgui 尤其明显（源码指向一个不存在的文件）。
- 建议：把 4 个 vendored 目录各补一个 `LICENSE`（内容取自各自头内正文/上游），并在仓库根加一份 `THIRD_PARTY_NOTICES.md` 汇总 §4.1 的「库 | 版本 | 许可证」三列。

### 8.3 子模块与 vendored 混杂，且声明与实现不符（认知成本最高）

- 实据：`Engine/External/CMakeLists.txt:1-4` 声称「External dependencies — git submodules（无网络依赖）」，但同目录有 `doctest`/`imgui`/`nlohmann`/`VulkanMemoryAllocator` 4 个**非子模块**目录，且 configure 期会 `git clone` Sponza（`cmake/DownloadAssets.cmake:18-27`）。
- 影响：新人按注释行动（以为 `submodule update` 就够了）会得到「imgui 目录空了也没人知道」的错觉；反过来 `git status` 里 vendored 目录的改动不会进子模块流程。
- 建议：把 `Engine/External/CMakeLists.txt` 头注释改成「7 个 git 子模块 + N 个入库副本（逐个列名）」，并在该文件内为每个 vendored 库补一行来源注释（imgui 的「CDN 下载」应具体到 tag）。

### 8.4 无 lockfile、无版本清单文件（可复现性）

- 实据：仓库根只有 `CMakeLists.txt`、`CMakePresets.json`、`.gitmodules`，**没有** `conanfile.txt`/`vcpkg.json`；`.gitmodules` 只记 URL（`.gitmodules:1-21`）；Vulkan SDK 版本取「本机最新」（`cmake/VulkanSDK.cmake:20-35`）。
- 影响：7 个子模块的 pin commit 只能从 git 索引读；半年后换机无法保证拿到同一份依赖。
- 建议：新增 `docs/` 外的根级 `DEPENDENCIES.md`（或 `deps/versions.json`）记录「库 | 版本 | 来源 | pin commit | 许可证 | 更新方式」；配一个 `Tools/check_dependencies.py` 做校验（仓库已有 `Tools/check_path_payload.py` 这类校验脚本先例，风格可直接沿用）。commit 一栏可由脚本用 `git ls-tree HEAD Engine/External/<lib>` 生成——注意这与「不自动执行 git 写操作」的仓库规则不冲突（只读）。

### 8.5 三处依赖「没有 CMake 目标」

- 实据：VMA（`Engine/RHI/CMakeLists.txt:88-90`）、cgltf（`Engine/Asset/CMakeLists.txt:18`）、doctest（`Tests/CMakeLists.txt:75`）都只以 include 路径形式存在，没有 `add_library(... INTERFACE)`。
- 影响：IDE 分组清单无法收编（§3.4）；链接顺序不受 `target_link_libraries` 约束；「谁依赖 VMA」只能靠 grep。
- 建议：给三者各补一个 INTERFACE 目标（照 §7.4 模板，成本约 4 行/个），消费侧改 `target_link_libraries`。

### 8.6 文档指向不存在的文件

- 实据：`Engine/External/CMakeLists.txt:68` 写「Jolt 库目标名固定为 "Jolt"（Build/Jolt/CMakeLists.txt）」——`Engine/External/JoltPhysics/Build/` 下只有 `Build/CMakeLists.txt` 与 `Build/Android/**/CMakeLists.txt`，目标实际定义在 `Jolt/Jolt.cmake:791`。
- 建议：改成 `Jolt/Jolt.cmake:791`。

### 8.7 `imgui` 的链接关系不闭合

- 实据：`HugEngineRender` **加了 imgui 的 include 路径**却不链接 `imgui`（`Engine/Render/CMakeLists.txt:231-232`），真正链接 imgui 的是 `HugEngineEditor`（`Engine/Editor/CMakeLists.txt:26`）；所有示例恰好都同时链了 `HugEngineEditor`（如 `Samples/06.GILab/CMakeLists.txt:4`），所以最终链接能过。
- 影响：任何「只链 Render 不链 Editor」的新目标会在链接期暴露 —— 症状离原因很远。
- 建议：要么让 `HugEngineRender` 也 `PRIVATE` 链 `imgui`（若其 `.cpp` 确实用了 imgui 符号），要么把 imgui 相关代码全部移到 Editor。

### 8.8 configure 期联网且失败非致命

- 实据：`cmake/DownloadAssets.cmake:12-13`（缺文件即开始 clone）、`:41` 与 `:47`（失败只 `message(WARNING)`）。
- 影响：离线机器上配置「成功」，运行到加载 Sponza 才失败。
- 建议：加一个显式开关（如 `HUGENGINE_DOWNLOAD_ASSETS`，默认 ON）与 `HE_REQUIRE_ASSETS`（默认 OFF 时保持现状，ON 时失败即 `FATAL_ERROR`），或把「资产是否就绪」写进配置摘要输出，方便 CI 拦截。

### 8.9 无 CI、无依赖一致性校验

- 实据：仓库内无 CI 配置；`Tools/` 只有 2 个脚本（`check_path_payload.py`、`gen_stbn.py`），没有任何针对依赖/版本/许可证的检查。
- 建议（最小可用）：一个脚本做 4 项断言 —— ①`.gitmodules` 的 path 集合 ⊆ `Engine/External/` 目录集合的反向检查；②每个 vendored 目录存在 `LICENSE*`；③每个库的版本头与 §4.1 清单一致；④`Engine/External/**/CMakeLists.txt` 里出现的每个新 target 都在根 `CMakeLists.txt` 的分组清单里。

### 8.10 IDE 分组清单漏项

- 实据：`_sample` 列表漏 `07.Nanite`（`CMakeLists.txt:123` vs `Samples/CMakeLists.txt:9`）；`_ext` 列表漏 `nlohmann_json`（`CMakeLists.txt:107`）。
- 影响：正是根 `CMakeLists.txt:104-105` 注释里警告过的后果（目标散落解决方案根）。
- 建议：把两张清单换成「从已知 target 自动收集」或加 §8.9 的第 ④ 项断言。
