## 1. 结论速览

| 部件 | 现状 | 成色 |
|---|---|---|
| `PostProcessChain` | 后处理 Pass 的**所有权容器 + 生命周期管理**，链逻辑不在这里，在 `DeferredPipeline::BuildFrameGraph` | 结构成立；`OnResize` 漏转发 3 个 Pass（见 §9.1） |
| `IPostProcessPass` | 统一 `SetInput` / `GetOutputFormat` / `OwnsOutput` / `GetOutputTexture` 契约 | 仅 `ToneMapPass`、`AA_*` 实现它；Bloom/DOF/MotionBlur/ColorGrading/CameraEffects 走 `LazyPostProcessPass`，**不实现该接口** |
| `LazyPostProcessPass` | `SetDevice` 注入 + `SetEnabled(true)` 触发 `EnsureInitialized` | 成立，是"声明了但没编译"这类浪费的正确答案 |
| `AutoExposurePass` | Compute 降采样到 256 组 + CPU 读回平均 + 时间混合 | 跑得通；`totalPixels` 传了不用；白点被 CVar 每帧覆写 |
| `BloomPass` | BrightPass(半分辨率) → 高斯(半分辨率) → Composite(全分辨率) | 成立；BrightPass 是**单点采样**，注释写的 4 像素 box 降采样不存在 |
| `DOFPass` | CoC(R16F) → 高斯(全分辨率) → Composite | 成立；CoC 用**未线性化**的原始深度；深度采样器**每帧新建** |
| `MotionBlurPass` | 沿 velocity 双向采样 12 次（共 25 tap） | 成立；velocity 用 HDR 采样器（非点采样） |
| `ToneMapPass` | ACES + SDR(sRGB) / HDR(PQ + BT.2020) 双路 | 成立；曝光由 AutoExposure × `exp2(exposureBias)` 给出 |
| `ColorGradingPass` | 饱和度 / Vibrance / 对比度 / 三段色彩平衡 | 成立；三段色彩平衡是**硬编码**且恒生效 |
| `CameraEffectsPass` | 畸变 / 色差 / 晕影 / 胶片颗粒，4 参数默认全 0 | 成立；`m_Time` 按固定 1/60 累加，与真实帧率无关 |
| `SkyboxPass` | 场景 Pass（不继承 `IPostProcessPass`），Lighting 之后 `depth=Equal` 叠加 | 成立；物理天空优先级高于 Cubemap |
| `Denoiser` | 5×5 双边模糊，`depthSigma`/`normalSigma` 可配（默认 10 / 8） | 成立；保住 `alpha<0` 的无效语义 |
| `DenoiseUpscale` | 3×3 源邻域 + 全分辨率深度/法线引导重建升采样 | 成立；源尺寸从纹理实况读，不缓存 |
| `RTDenoiser` | 时域累积（velocity 重投影 + 去遮挡 + 历史 swap） | 成立；历史可来自统一池 |
| `DenoiseHistoryPool` | 同名同尺寸同格式的历史**只建一次** | 成立 |
| `DenoiseSignalRegistry` | 每帧由 Provider `DescribeSignals` 登记，名字集合变化才打印 | 成立，是"多信号共存"的唯一视角 |
| `PTAtrousPass` | SVGF 风格 A-Trous（compute），迭代数 clamp 1..5 | 成立；仅在 PathTracing 管线使用 |
| `SSAO` | 半球核(64，种子 42) + 4×4 噪声 + Blur；GTAO 换 FS 复用同一 pass 类型 | 成立；两趟**各自独立**的离屏通道（原始 AO → 屏障 → 最终 AO）。修复前 Blur 采样的是自己正在写的附件，见 §7.3 |
| `AA_None` | 空对象，`IsEnabled()` 恒 false，输出透传输入 | 成立 |
| `AA_TAA` | 8 采样 Halton 抖动 + YCoCg AABB + 去遮挡；自拥有双缓冲历史 | 成立；**抖动已接进投影矩阵**（2026-09 画质阶段 0 第②项，§5.2） |
| `AA_FXAA` | LDR 单 Pass，3×3 亮度梯度，`edge<0.05` 早退 | 成立 |
| `AA_SMAA` | 3 Pass（EdgeDetect R8 → BlendWeight RGBA8 → Neighborhood → BackBuffer） | 成立；**无预计算 area/search LUT**，是简化版 |
| `AA_MSAA` | 靠 `OverrideTextureDesc` / `OverridePSODesc` 覆盖采样数 | **两个钩子在整个 Engine/Samples 中零调用点**；且 RHI 运行时 PSO 路径把采样数写死为 1（§6） |
| 管线分配 | Deferred：TAA(HDR) → ToneMap → [ColorGrading] → [CameraEffects] → [SMAA \| FXAA]；Forward：帧图里**没有 AA pass**；PathTracing：强制 FXAA | 见 §5.5 |

## 2. 后处理链的整体结构与数据流

### 2.1 所有权与访问

`PostProcessChain` 是纯容器：它按值持有 Bloom/DOF/MotionBlur/AutoExposure/ColorGrading/CameraEffects，按 `unique_ptr` 持有 ToneMap/Skybox/TAA/FXAA/SMAA/MSAA（`PostProcessChain.h:72-83`），
并通过 getter 把裸指针交给帧图（`PostProcessChain.h:42-63`）。

**链逻辑不在 `PostProcessChain` 里**——头文件自己写明了这一点：`RenderGraph 链逻辑保留在 BuildFrameGraph 中（避免破坏复杂的输入源选择逻辑）`（`PostProcessChain.h:24-25`）。
所以"后处理链"实际有两层：

| 层 | 位置 | 职责 |
|---|---|---|
| 容器层 | `PostProcessChain` | 建/销资源、转发 resize、AA 开关 |
| 编排层 | `DeferredPipeline::BuildFrameGraph`（`DeferredPipeline_FrameGraph.cpp:1588-1807`） | 决定谁读谁、谁写谁、注册 RenderGraph Pass |

### 2.2 `SetInput` / `GetOutput` 契约

`IPostProcessPass` 定义的契约只有五件事（`PostProcessPass.h:29-53`）：

| 成员 | 语义 |
|---|---|
| `SetInput(color, sampler)` | 管线在 Pass 执行前调用；Pass **不持有**输入所有权 |
| `GetOutputFormat()` | 供管线创建中间 RT；`ToneMap`/`FXAA` 为 `BGRA8_UNORM`，`TAA` 为 `RGBA16_FLOAT`（`PostProcessPass.h:42-43`） |
| `OwnsOutput()` | true = Pass 内部管理输出目标（默认 false，`PostProcessPass.h:48`） |
| `GetOutputTexture()` / `GetOutputSampler()` | `OwnsOutput()==true` 时有效（`PostProcessPass.h:51-52`） |

三个实现者的差别恰恰说明了契约的两种用法：

- `AA_TAA`：`OwnsOutput()==true`（`AA_TAA.h:47`），输出是内部双缓冲历史的当前 read 面（`AA_TAA.cpp:222-228`）。
- `AA_None`：`GetOutputTexture()` **原样返回输入**（`AA_None.h:45-46`），即链路透传；`GetOutputFormat()` 声明 `RGBA16_FLOAT` 但注释承认这只是"管线自行判断"（`AA_None.h:41-44`）。
- `AA_FXAA`：`OwnsOutput()==false` 且 `GetOutputTexture()` 返回的是**输入**（`AA_FXAA.h:37-39`）——因为它把结果直接画进 BackBuffer，没有可被下游采样的输出纹理；它在链上是终端 Pass。

`SkyboxPass` **刻意不继承** `IPostProcessPass`，它是场景 Pass 而非后处理链的一环（`PostProcessPass.h:27`），它继承 `IRenderSubsystem`（`SkyboxPass.h:17`）。

另有一批 Pass 完全不实现这两个接口，走的是各自的 `GetOutput()` / `GetOutputSampler()` / `PreBind()`：
`BloomPass`（`BloomPass.h:27-28`）、`DOFPass`（`DOFPass.h:27-28`）、`MotionBlurPass`（`MotionBlurPass.h:23-24`）、
`ColorGradingPass`（`ColorGradingPass.h:22-24`）、`CameraEffectsPass`（`CameraEffectsPass.h:23-25`）、`GaussianBlurPass`（`GaussianBlurPass.h:24-26`）。

### 2.3 Lazy 机制的动机

`LazyPostProcessPass`（`LazyPostProcessPass.h:17-47`）把"注入设备"和"分配 GPU 资源"拆成两步：

```
SetDevice(device, w, h)   → 只存字段，不建资源        （LazyPostProcessPass.h:26-28）
SetEnabled(true)          → 首次开启才 EnsureInitialized（LazyPostProcessPass.h:31-34）
EnsureInitialized()       → 未初始化且已注入设备时才 Initialize（LazyPostProcessPass.h:39-42）
```

动机是"默认关闭的 Pass 不该在启动时付纹理/PSO 的钱"。`PostProcessChain::Initialize` 因此分成两段：

- **立即初始化**：ToneMap、Skybox、TAA、AutoExposure，以及 LDR 中间纹理（`PostProcessChain.cpp:16-53`）。
- **只注入设备**：Bloom / DOF / MotionBlur / ColorGrading / CameraEffects（`PostProcessChain.cpp:55-62`）。
  注释把这一步的必要性写死了：`先注入设备/尺寸，否则 EnsureInitialized 拿不到 m_Device 永远不初始化（懒初始化失效）`（`PostProcessChain.cpp:57`）。

FXAA / SMAA / MSAA 是**第三类**：它们连 `SetDevice` 都不走，而是在 `EnableFXAA` / `EnableSMAA` / `EnableMSAA` 内部按需 `make_unique` + `Initialize`（`PostProcessChain.cpp:124-155`），
且 `enable==false` 时**不销毁**已有实例，只翻标志位（`PostProcessChain.cpp:125-126`、`137-138`、`149-150`）——所以"关掉再打开"不会重建。

所有 `LazyPostProcessPass` 派生类的 `Shutdown()` 与 `OnResize()` 都以 `if (!m_Ready) return;` 开头（`BloomPass.cpp:135`、`DOFPass.cpp:124`、`MotionBlurPass.cpp:72`、`CameraEffectsPass.cpp:74`），
即在懒初始化从未触发时是空操作。

### 2.4 LDR 中间纹理与虚拟深度

ToneMap 之后的链路是 LDR（`BGRA8_UNORM`）空间。为它单独准备了三样东西（`PostProcessChain.cpp:31-53`）：

| 资源 | 格式 | 用途 |
|---|---|---|
| `m_LDRTarget` | `BGRA8_UNORM` | ToneMap 的输出目标，同时也是 ColorGrading/CameraEffects/AA 的输入 |
| `m_LDRSampler` | Linear + ClampToEdge | 采样 LDR 中间纹理 |
| `m_LDRDummyDepth` | `D32_FLOAT` | **虚拟深度附件** |

虚拟深度的存在理由写在注释里：`ToneMap PSO 带 depthFormat，Offscreen 需 2 附件`，且`必须与 LDR target 同尺寸，否则 vkCreateFramebuffer 因附件尺寸不匹配失败`（`PostProcessChain.cpp:45-46`）。
ToneMap 的 PSO 确实声明了 `d.depthFormat=rhi::Format::D32_FLOAT`（`ToneMapPass.cpp:45`）。
`needLDR` 的判据是"任一 LDR 后处理启用"（`DeferredPipeline_FrameGraph.cpp:1680`），否则 ToneMap 直写交换链（`DeferredPipeline_FrameGraph.cpp:1714-1718`）。

### 2.5 Deferred 管线的完整链

Regraph Pass 顺序与数据源（全部在 `DeferredPipeline_FrameGraph.cpp`）：

```
Lighting ──→ HDR_C
   │
   ├─ Skybox        (:1491-1505)  读 gbDepth + HDR_C，写 HDR_C（LoadOp=Load，depth=Equal）
   ├─ CaptureRadiance(:1515-1522) 读 HDR_C → m_RadianceHistory（仅当有消费者声明）
   ├─ AutoExposure  (:1524-1532)  读 HDR_C，Compute 队列 → 256 组 SSBO → CPU 读回
   ├─ ParticleRender(:1535-1551)  读 + 写 HDR_C
   │
   ├─ Bloom         (:1595-1604)  输入 = Lighting HDR
   ├─ DOF           (:1607-1618)  输入 = Bloom 输出 > Lighting HDR；另读 GBuffer depth
   ├─ MotionBlur    (:1621-1636)  输入 = DOF > Bloom > Lighting HDR；另读 GBuffer velocity
   ├─ TAA_Resolve   (:1639-1665)  输入 = 后处理链最后一个激活者 > Lighting HDR；另读 depth/normal/velocity
   │
   └─ ToneMap       (:1683-1719)  输入 = TAA 输出 > 后处理链末级 > Lighting HDR
         │                        输出 = LDR 中间纹理（needLDR）或 BackBuffer
         ├─ ColorGrading (:1722-1737)  输入 = LDR
         ├─ CameraEffects(:1740-1757)  输入 = ColorGrading > LDR
         └─ SMAA | FXAA  (:1761-1807)  输入 = CameraEffects > ColorGrading > LDR → BackBuffer
```

关键点：

- **后处理链的三个 HDR Pass 的输入选择是嵌套三元表达式**，每一级都自己重算一遍上游（`:1611-1612`、`:1625-1630`、`:1644-1651`、`:1691-1696`），
  而不是"贯穿推进一个 `src` 变量"。Bloom/DOF/MotionBlur 的门控是三段 `IsEnabled() && GetOutput() != nullptr`（`:1589-1591`），
  但 ToneMap 那一处（`:1691-1693`）用的是**只有 `IsEnabled()`**、没有 `GetOutput() != nullptr`——两处判据并不完全同构。
- **两个终端的 LDR AA 互斥**用 `if (useSMAA) { ... } else if (useFXAA) { ... }` 实现（`:1761`、`:1787`）。
- **HDR 输出时四个 LDR 效果被强制关闭**：`if (isHDR) { useFXAA = useSMAA = useColor = useFX = false; }`（`:1677-1679`），
  理由是同注释：这些效果都是 `BGRA8` LDR 空间，与 `A2B10G10R10` 后备缓冲格式不匹配（`:1675-1676`）。
- **每个 Pass 都自己发 `PipelineBarrier`**（`:1599-1600`、`:1614-1615`、`:1632-1633`、`:1654-1659`、`:1699-1700`、`:1729-1730`、`:1749-1750`、`:1774-1777`、`:1799-1802`），
  即 `RenderTarget → ShaderResource` 的手工状态迁移；AA_SMAA 在内部也自己做两次（`AA_SMAA.cpp:175-180`、`211-216`）。
- TAA 的 Pass 声明**没有输出**（`:1641` 是空 `{}`），因为它的输出是自拥有的历史纹理，RenderGraph 不管理；它声明的 `hdrC` 读只是用来建立与前序的依赖序（`:1640`）。

## 3. 逐 Pass 实现

### 3.1 AutoExposure（Compute 降采样 + CPU 时间混合）

**算法要点**

1. Compute 着色器 `[numthreads(16,16,1)]`（`AutoExposure.comp.slang:20`），每组 256 线程做组内并行归约（`:29-34`），
   每组写出一个 partial sum 到 SSBO（`:37-40`）。
2. UV 是**固定 256×256 采样网格**，不是按纹理尺寸铺满：
   $\mathrm{uv} = \dfrac{\mathrm{dtid}_{xy} + 0.5}{256}$（`AutoExposure.comp.slang:24`）。
   注释说明了原因：`而不是硬编码 1920×1080（否则只采样纹理左上角，曝光值错误）`（`:22-23`）。
3. CPU 侧 Map SSBO、剔除 $|v| \ge 20$ 的异常值、求平均（`AutoExposurePass.cpp:102-114`）。
4. 时间混合：$L_{n} = L_{n-1} + (L_{cur} - L_{n-1}) \cdot t$，$t = \min(\mathrm{adaptSpeed} \cdot \Delta t,\ 1)$（`AutoExposurePass.cpp:115-116`）。
5. 曝光：$E = \dfrac{W \cdot L_{target}}{L_{avg} \cdot 80}$，其中 $L_{avg} = 2^{L_n}$（`AutoExposurePass.cpp:120-121`）。

**关键参数**

| 参数 | 值 | 位置 |
|---|---|---|
| `kNumGroups` | 256 | `AutoExposurePass.h:37` |
| `kMinExposure` / `kMaxExposure` | 0.005 / 200.0 | `AutoExposurePass.h:15-16` |
| `kDefaultDeltaTime` | 0.016（写死，与真实帧无关） | `AutoExposurePass.h:17`、`.cpp:93` |
| `m_AdaptSpeed` | 2.0 → $t = \min(0.032, 1)$ | `AutoExposurePass.h:44` |
| `m_TargetLum` | 0.18（push 的是 $\log_2$） | `AutoExposurePass.h:45`、`.cpp:92` |
| `m_PrevLogLum` 初值 | $-2.47$ | `AutoExposurePass.h:47` |
| `kSdrReferenceWhitePoint` | 80.0 | `AutoExposurePass.cpp:16` |
| `r.AutoExposure.WhitePoint` | 默认 80.0 | `AutoExposurePass.cpp:19` |
| SSBO 大小 | `256 * sizeof(float)` | `AutoExposurePass.cpp:52` |
| Dispatch | `(16, rhi::kStageMaskFragment, 1)` | `AutoExposurePass.cpp:99` |

`Dispatch` 的签名是 `Dispatch(groupCountX, groupCountY, groupCountZ)`（`RHI/CommandList.h:176`），
而 `kStageMaskFragment == 16`（`RHI/Types.h:57`）——所以这一行实际发起的是 16×16×1 = 256 组，恰好是设计意图。
把**阶段掩码常量当组数用**在这里数值上正确，但语义是借来的。

**已知限制**

- `totalPixels` push constant 在 CPU 侧算了并推入（`AutoExposurePass.cpp:94`），着色器里**声明了但从未使用**（`AutoExposure.comp.slang:13`）；着色器改用固定 256×256 网格自己算 UV。
- `m_DisplayWhitePoint` 每帧被 CVar 覆写（`AutoExposurePass.cpp:84`），所以 `SetDisplayWhitePoint()`（`AutoExposurePass.h:34`）写进去的值下一帧就没了。
- `deltaTime` 恒为 0.016：光照突变时的适应速度不随实际帧时长变化。
- 曝光结果是 1 个标量，整屏统一，没有局部/直方图加权。
- 该 Pass 在 Compute 队列（`DeferredPipeline_FrameGraph.cpp:1532`），Pass 体末尾手工 `SetPipeline(m_Lighting.GetPSO())` 恢复图形管线（`:1530`）。

### 3.2 Bloom（BrightPass + 分离高斯 + Composite）

**算法要点**

三段，全部是半分辨率或全分辨率的全屏三角形：

1. **BrightPass**：半分辨率（`BloomPass.cpp:24` `hw = width/2`），输出 `RGBA16_FLOAT`（`:62-66`）。
   亮度用 Rec.709：$L = 0.2126R + 0.7152G + 0.0722B$（`BrightPass.frag.slang:18-20`）；
   阈值不是硬截断而是平滑过渡：$C_{bright} = C \cdot \mathrm{smoothstep}(T,\ 2T,\ L)$（`:27`）。
2. **高斯模糊**：复用 `GaussianBlurPass`，在半分辨率上跑（`BloomPass.cpp:75`、`:210-214`）。
3. **Composite**：全分辨率，$\mathrm{out} = \mathrm{hdr} + \mathrm{bloom} \cdot k$（`BloomComposite.frag.slang:22`），保留 `hdr.a`（`:23`）。
   Bloom 纹理由线性采样器自动双线性上采样（`:21` 注释）。

**关键参数**

| 参数 | 值 | 位置 |
|---|---|---|
| `m_Threshold` | 3.0 | `BloomPass.h:35` |
| `m_Intensity` | 0.8 | `BloomPass.h:36` |
| 半分辨率尺寸 | `width/2, height/2` | `BloomPass.cpp:24`、`:162` |
| BrightPass 输出格式 | `RGBA16_FLOAT` | `BloomPass.cpp:53`、`:62` |
| BrightPass push constant | 16 B（1 float + 3 pad） | `BloomPass.cpp:41-43`、`:201-203` |
| Composite 输出格式 | `RGBA16_FLOAT` | `BloomPass.cpp:107`、`:116` |
| 描述符绑定 | Bright: b0=HDR；Composite: b0=HDR, b1=Bloom | `BloomPass.cpp:16-18`、`:81-82` |

**已知限制**

- `BrightPass.frag.slang:24` 声明了 `float2 ts = float2(1.0/1920.0, 1.0/1080.0);` 后**完全没有使用**，注释自己带着问号：`由 push constant 传入？`。
- 同文件 `:23` 的注释写 `4 像素 box downsample（半分辨率）`，但代码只有一次 `u_HDR.Sample(u_Sampler, input.uv)`（`:25`）——**没有 4 tap box**。所谓降采样完全靠光栅化到半分辨率目标时由采样率隐式完成。
- `hw = width/2` 是整数除法，奇数宽高时会丢一列/一行像素，没有取整保护。
- Bloom 是**单级**的：只有一档半分辨率，没有 mip 金字塔；大范围光晕只能靠 7×7（半径 3 texel @ 半分辨率）撑。
- Composite 不参与色调映射前的任何 clamp，`Threshold=3.0` 的高阈值意味着只有很亮的区域才发光。

**GaussianBlurPass（共用构件）**

类名叫"7×7 可分离"，但实现是**单 Pass 二维卷积**：内层双重循环 7×7 = **49 tap**（`GaussianBlur.frag.slang:27-34`），
权重表 7 个（`:18-20`）：

$$w = \{0.00598,\ 0.060626,\ 0.241843,\ 0.383103,\ 0.241843,\ 0.060626,\ 0.00598\}$$

核是 $\sigma \approx 1.0$、半径 3。着色器注释里"可分离"指的是**核可分离**（$w(x,y) = w_x \cdot w_y$，`:26`、`:30`），
不是"分两趟跑"——所以没有省掉一半采样。`texelSize` 由 push constant 传入（`GaussianBlurPass.cpp:128`）。

### 3.3 DOF（CoC + 散景 + 合成）

**算法要点**

1. **CoC Pass**：全分辨率 `R16_FLOAT`（`DOFPass.cpp:52`、`:58-63`）。
   弥散圆：$c = \mathrm{saturate}\!\left(\dfrac{|d - d_{focus}|}{\max(r_{focus},\ 10^{-4})}\right) \cdot c_{max}$（`DOF_CoC.frag.slang:22-23`）。
2. **模糊 Pass**：`GaussianBlurPass` 对**原始 HDR** 做 7×7 高斯（`DOFPass.cpp:192`），全分辨率。
3. **Composite**：$O = \mathrm{lerp}(S,\ B,\ \mathrm{saturate}(c \cdot k))$（`DOF_Composite.frag.slang:24-25`）。

**关键参数**

| 参数 | 值 | 位置 |
|---|---|---|
| `m_FocusDepth` | 0.5 | `DOFPass.h:37` |
| `m_FocusRange` | 0.1 | `DOFPass.h:38` |
| `m_Intensity` | 1.0 | `DOFPass.h:39` |
| `kDefaultMaxCoC` | 0.03 | `DOFPass.h:15` |
| CoC 纹理格式 | `R16_FLOAT` | `DOFPass.cpp:52`、`:59` |
| Composite 输出格式 | `RGBA16_FLOAT` | `DOFPass.cpp:99`、`:106` |
| 相机驱动 | `focusDepth = camera.focusDistance`、`intensity = camera.maxCoC` | `DeferredPipeline_FrameGraph.cpp:95-96` |
| 驱动条件 | 仅当 `camera.apertureDiameter > 0.0f` | `DeferredPipeline_FrameGraph.cpp:94` |

**已知限制**

- `DOF_CoC.frag.slang:21` 的注释写 `线性化深度（Vulkan NDC depth 0~1，reverse-Z 时 near=1 far=0）`，但下一行 `:22` 直接拿 `depth` 与 `focusDepth` 相减——**没有任何线性化**。因此 `m_FocusDepth = 0.5` 是 NDC 深度而非世界距离，焦平面的物理含义取决于投影矩阵。
- 深度采样器（Nearest）**每帧 `CreateSampler`**（`DOFPass.cpp:171`），代码里自己标了 `简便：每帧创建（可优化为复用）`（`:171`）。
- Composite 的描述符常量**名字与 shader 语义反了**：`kDOFCompositeBindCoC = 1` / `kDOFCompositeBindBlur = 2`（`DOFPass.cpp:18-19`），
  但 shader 里 `binding(1,0) = u_Blurred`、`binding(2,0) = u_CoC`（`DOF_Composite.frag.slang:10-13`）。
  实际接线是**对的**（`DOFPass.cpp:202-205`：binding 1 收 `m_Blur.GetOutput()`、binding 2 收 `m_CoCTex`），只是常量名误导。
- 散景（bokeh）**不存在**：模糊是各向同性 7×7 高斯，没有半径随 CoC 变化的采样、没有多边形孔径、没有高光加权。
  注释里说的 `CoC + 散景 + 合成` 的后半截在代码里只有固定半径高斯。
- CoC pass 的深度输入是 GBuffer depth（`DeferredPipeline_FrameGraph.cpp:1613`），所以在 TAA 之前、用当前帧的实心深度。

### 3.4 MotionBlur

**算法要点**

沿屏幕空间 velocity 双向采样后加权平均（`MotionBlur.frag.slang:28-36`）：
$$O = \frac{C_0 + \sum_{i=1}^{n}\left(C(uv + v k \tfrac{i}{n}) + C(uv - v k \tfrac{i}{n})\right)}{1 + 2n}$$
其中 $k$ = `intensity`、$n$ = `min(sampleCount, 16)`。**对称双向采样**意味着模糊是沿速度轴双向展开的，不是单向拖尾。

**关键参数**

| 参数 | 值 | 位置 |
|---|---|---|
| `m_Intensity` | 0.5 | `MotionBlurPass.h:29` |

| 着色器上限 `kMaxSamples` | 16 | `MotionBlur.frag.slang:20` |
| 实际 tap 数 | $1 + 2 \times 12 = 25$ | `MotionBlur.frag.slang:29-35` |
| 输出格式 | `RGBA16_FLOAT` | `MotionBlurPass.cpp:48`、`:55` |
| Intensity 来源 | `camera.motionBlurIntensity` | `DeferredPipeline_FrameGraph.cpp:98` |
| velocity 采样器 | `m_Lighting.GetHDRSampler()` | `DeferredPipeline_FrameGraph.cpp:1631` |

**已知限制**

- velocity 纹理用的**不是点采样器**：接的是 `m_Lighting.GetHDRSampler()`（`DeferredPipeline_FrameGraph.cpp:1631`），
  而 DOF（`DOFPass.cpp:169`）与 RTDenoiser（`RTDenoiser.cpp:42`）都专门建了 Nearest 采样器。
  同一个 `SetInputs` 签名里 HDR 与 velocity 共用的是一个 sampler 参数（`MotionBlurPass.h:19-20`），所以两者无法分别指定。
- **没有 velocity 长度钳制**：着色器直接 `velocity * intensity`（`MotionBlur.frag.slang:23`），
  快速甩镜头时单个像素可能采到屏幕外（靠 `ClampToEdge` 兜底，产生边缘拖影）。
- `sampleCount` 由 push constant 传入但**没有对外 API**，恒为 `kDefaultSamples = 12`（`MotionBlurPass.cpp:112`）。

### 3.6 ColorGrading

**算法要点**

着色器把 LDR 输入先解到线性（`ColorGrading.frag.slang:46`），依次做：

1. 饱和度：$c \leftarrow \mathrm{lerp}(\mathrm{lum},\ c,\ \mathrm{saturation})$（`:50`）
2. Vibrance：$\mathrm{vibFactor} = 1 + \mathrm{vibrance}(1 - \mathrm{avgSat})$，再按 $\mathrm{lum}$ 做一次 lerp（`:53-55`）
3. 对比度：$c \leftarrow (c - 0.5)\,\mathrm{contrast} + 0.5$，clamp 到 [0,1]（`:59-60`）
4. 三段色彩平衡：$c \leftarrow c + \mathrm{shadows}\cdot t_s \cdot 0.5 + \mathrm{midtones}\cdot t_m \cdot 0.3 + \mathrm{highlights}\cdot t_h \cdot 0.5$（`:69`），
   其中 $t_s = \mathrm{smoothstep}(0.3, 0, \mathrm{lum})$、$t_h = \mathrm{smoothstep}(0.6, 1, \mathrm{lum})$、$t_m = 1 - t_s - t_h$（`:66-68`）

最后回编码到 sRGB（`:73`）。

**关键参数**

| 参数 | 值 | 位置 |
|---|---|---|
| `m_Saturation` | 1.0 | `ColorGradingPass.h:35` |
| `m_Contrast` | 1.0 | `ColorGradingPass.h:36` |
| `m_Vibrance` | 0.0 | `ColorGradingPass.h:37` |
| shadows 平衡 | `(1.0, 1.0, 1.1)` | `ColorGradingPass.cpp:104-106` |
| midtones 平衡 | `(1.05, 1.0, 0.95)` | `ColorGradingPass.cpp:108-110` |
| highlights 平衡 | `(1.1, 1.05, 0.9)` | `ColorGradingPass.cpp:112-114` |
| push constant | 64 B（13 float） | `ColorGradingPass.cpp:33` |
| 输出格式 | `BGRA8_UNORM` | `ColorGradingPass.cpp:43`、`:49` |

**已知限制**

- **三段色彩平衡是硬编码且恒生效**：`shR..hlB` 九个值在 `Render()` 里就地赋常量（`ColorGradingPass.cpp:104-114`），
  类里没有对应成员、没有 setter。因此 `m_Saturation=1 / m_Contrast=1 / m_Vibrance=0` 的**默认状态并不是恒等变换**——
  画面仍会被"暗部偏蓝、中间偏暖、亮部偏暖"（`:107`、`:111`、`:115` 的注释）改色。
- `Render()` **不 `BeginOffscreenPass`**（`ColorGradingPass.cpp:91-124`），它只发 Draw；离屏通道由帧图包在外面（`DeferredPipeline_FrameGraph.cpp:1733-1735`）。
  这是个隐式契约：`PreBind` + `Render` 必须成对使用。
- `OnResize()` 既没有 `if (!m_Ready) return;`，也没有同尺寸短路（`ColorGradingPass.cpp:73-82`），
  与同类 Pass 的写法不一致（对比 `CameraEffectsPass.cpp:74-75`）；它还会重建纹理，而 `PostProcessChain::OnResize` **根本没有转发到它**（见 §9.1）。

### 3.7 CameraEffects

四个效果默认全关（`CameraEffectsPass.h:38-41` 全 0.0f），所以默认是恒等 Pass。

**算法要点**（`CameraEffects.frag.slang:26-51`）

1. 畸变：$\mathrm{duv} \leftarrow \mathrm{duv}\,(1 + \mathrm{distortion} \cdot r^2)$（`:32`）
2. 色差：R 与 B 分别在**畸变后**的向量上再乘 $(1 \pm \mathrm{caStrength})$，G 不偏（`:35-40`）

4. 颗粒：$\mathrm{color} \mathrel{+}= (\mathrm{hashNoise}(uv \cdot 1000 + t) - 0.5)\cdot \mathrm{filmGrain}$（`:48`），hash 为 $\mathrm{frac}(\sin(\cdot) \cdot 43758.5453)$（`:22-24`）

## 4. 降噪体系

后处理目录里与"降噪"相关的实现分工如下：

| 类 | 载体 | 空间/域 | 谁在用 |
|---|---|---|---|
| `Denoiser` | 图形 Pass（5×5 双边模糊） | 信号自身分辨率 | SSGI / SSR，经 `SpatialDenoiseAux` |
| `DenoiseUpscale` | 图形 Pass（3×3 引导重建） | 信号 → 全分辨率 | SSGI / SSR 的半分辨率档 |
| `RTDenoiser` | 图形 Pass（时域累积） | 信号分辨率 | 阴影 / AO / 反射 / GI / PT |
| `PTAtrousPass` | Compute Pass（A-Trous） | PT 全分辨率 | 仅 PathTracing |
| `DenoiseSignal` 系列 | 无 GPU 资源 | 元数据 | 帧图与 Provider |

### 4.1 `Denoiser`：5×5 双边模糊

权重（`Denoise.frag.slang:39-41`）：
$$w = e^{-|\Delta d| \cdot \sigma_d} \cdot \max(0,\ N \cdot N')^{\sigma_n}$$

只对 3 个标量做 push constant：`{texelSize, depthSigma, normalSigma}`（`Denoiser.cpp:74-78`）。
默认值就是改造前的硬编码常量：`kDefaultDepthSigma = 10.0f`、`kDefaultNormalSigma = 8.0f`（`Denoiser.h:20-21`）。

**"信号登记"机制之外的第一条契约：`alpha < 0`**

`Denoise.frag.slang` 的头部把语义写死了（`:3-9`）：

- `alpha < 0` ⇒ 该像素**本帧无数据**（SSR miss / 天空）；
- 无效样本**不参与**加权平均（`:35` `if(s.a<0.0)continue;`）；
- 邻域内全无有效贡献 ⇒ 输出 `alpha = -1`（`:46` `return float4(0,0,0,-1);`）；
- 有任一有效贡献 ⇒ 输出 `alpha = +1`（`:48`），**有效性不参与平均**。

C++ 侧的对应真值是 `denoise::kInvalidAlpha = -1.0f` 与 `denoise::IsValid(alpha) => alpha >= 0`（`DenoiseSignal.h:48-51`），
以及那句会被打进日志的契约文本（`DenoiseSignal.h:55-58`、`DenoiseSignal.cpp:163`）。
`DenoiseSignal.h:12` 说明了为什么"分母也要跳过"：把无数据的源按 0 计入分母会让同通道其它源被稀释，表现为画面变暗且无法归因。

### 4.2 `DenoiseUpscale`：降噪之后的引导重建

半分辨率信号的顺序被明确为**先降噪、再重建升采样**（`DenoiseUpscale.h:6-7`），理由是核尺度（`texelSize`）由输入尺寸决定，
把升采样塞进 `Denoiser` 会让半分辨率路径退化成"最近邻复制 + 全分辨率核"（`DenoiseUpscale.h:11-14`）。

权重在双边项之上再乘一个以**目标**纹素为单位的空间高斯（`Denoise_Upscale.frag.slang:47-52`）：
$$w = w_{d} \cdot w_{n} \cdot w_{s}$$

$$w_{d} = e^{-|\Delta d|\,\sigma_d}, \qquad w_{n} = \max(0,\ N \cdot N')^{\sigma_n}, \qquad w_{s} = e^{-0.5\,\|d\|^{2}}, \qquad d = \frac{\mathrm{suv} - \mathrm{uv}}{\Delta_{dst}}$$

其中 $w_d$ 是深度项、$w_n$ 是法线项、$w_s$ 是空间项（以目标纹素为单位）——前两项与 `Denoiser` 同形，第三项是本级新增。

源纹素尺寸**每帧从纹理实况读**（`DenoiseUpscale.cpp:104-105`），注释解释了不缓存的原因：半分辨率是运行时开关，缓存副本会与纹理漂移（`:103`）。
帧尺寸则为 3×3（`:39-40`），注释说明 2× 升采样时这覆盖了目标像素周围的全部候选低分辨率样本（`:38`）。
同一份 `alpha < 0` 协议在这里必须重现（`Denoise_Upscale.frag.slang:13-16`、`:43`、`:56`）。

### 4.3 `RTDenoiser`：时域累积

参数结构（`RTDenoiser.h:28-36`）：

| 字段 | 默认 | 说明 |
|---|---|---|
| `format` | `RGBA16_FLOAT` | 输出/历史格式，须与 RT Pass 输出一致 |
| `temporalBlend` | 0.1 | 当前帧混合权重（0=纯历史，1=纯当前帧） |
| `depthThreshold` | 0.05 | 去遮挡深度容差 |
| `normalThreshold` | 0.85 | 去遮挡法线 dot 阈值 |

渲染流程：绑历史（`RTDenoiser.cpp:195-197`）→ 首帧标记 `isFirstFrame = (m_FrameIndex <= 1)`（`:200`）→
push 32 B（`:203-219`）→ `Draw(3)`（`:223`）→ **裸指针 swap 历史与输出**（`:226`）→ `++m_FrameIndex`（`:227`）。
swap 用裸指针而非 `swap` 所有权，是因为历史可能来自统一池（`:226` 注释、`RTDenoiser.h:90-94`）。

`PreBind` 的存在理由比"性能"更硬：`BeginOffscreenPass` 是拿**当前已绑定的 PSO** 去取 RenderPass 建 Framebuffer 的，
若此刻绑着别的 PSO（例如带深度附件的图形 PSO）就会附件数不匹配，实测报 `VUID-VkFramebufferCreateInfo-attachmentCount-00876` 并让设备挂住（`RTDenoiser.cpp:174-179`、`RTDenoiser.h:60-65`）。
同样的约束在 `Denoiser`（`Denoiser.cpp:71` 直接 `SetPipeline`，调用方负责顺序）与 `DenoiseUpscale`（`DenoiseUpscale.h:38-39`）上也存在。

### 4.4 `DenoiseHistoryPool`：统一历史分配

`Acquire(name, w, h, fmt)` 按 **(名字, 宽, 高, 格式)** 四元组去重复用（`DenoiseSignal.cpp:25-29`），
`AcquireBuffer(name, bytes)` 按 **(名字, 字节数)** 去重（`:67-69`）。
`TotalBytes()` 用的是建档时按格式估算的 `bytesPerPixel` 表（`:39-52`），所以它是**记账值**而不是 `VkMemoryRequirements` 的真实值。
`OnResize` 把全部历史清空（`:89-97`），并提醒调用方复位各自的"首帧"标记，否则会把未初始化显存当历史（`:90-91`）。

谁在用池：`m_ShadowDenoiser`、`m_AODenoiser`、`m_ReflectionDenoiser`、`m_GIDenoiser` 四个 `RTDenoiser` 的 `Initialize` 都传了 `&m_DenoiseHistoryPool`（`DeferredPipeline.cpp:302`、`:314`、`:326`、`:342`），
LumenScene 也接了 `SetHistoryPool`（`DeferredPipeline.cpp:291`、`LumenScene.h:66`）。
**例外**：PathTracing 的 `m_PTDenoiser` 用的是两参数 `Initialize`（`PathTracingPipeline.cpp:139`），即自建历史。

### 4.5 `SpatialDenoiseAux`：SSGI/SSR 共享的两级附属链

它把"附属 pass 的数量/输入/输出/PreBind/Render"收敛成一份实现，Provider 只提供主输出、深度、法线与名字前缀（`SpatialDenoiseAux.h:6-10`）。
链条按信号分辨率自适应（`SpatialDenoiseAux.h:17-23`）：

| 形态 | pass 数 | 组成 |
|---|---|---|
| 信号 = 全分辨率 | 1 | `[Denoise]` |
| 信号 < 全分辨率 | 2 | `[Denoise@信号分辨率] → [Upscale→全分辨率]` |

形态由一个**环境变量**决定：`HE_DENOISE_HALFRES` 取 `off` / `denoise` / `full`，默认 `full`（`SpatialDenoiseAux.h:67-81`）。
`off` 时整条链都不注册，回到"半分辨率直接采样"（`:68`、`:82-85`）。
这个开关的目的是让三种形态共用同一份二进制与配置，使读数差只反映这一步本身（`:71-72`）。

两级尺寸**每帧核对**：降噪级跟信号分辨率、升采样级跟消费端分辨率，仅在真的不同时才 `OnResize`（`:53-64`）。
`Active()` 只看降噪器是否存在与模式，**不再带 `!halfRes`**（`SpatialDenoiseAux.h:83-85`）；调用侧同样如此（`SSGIProvider.h:154-156` 的注释直接说明此前那个 `!halfRes` 会让最需要降噪的一档被跳过）。

### 4.6 `DenoiseSignalRegistry`：单帧信号登记

`DenoiseSignal` 是一个"待降噪信号"的完整描述（`DenoiseSignal.h:65-91`），同时支持两种载体：

- 纹理信号：`input` / `output`（`:67-68`）
- 缓冲信号：`inputBuffer` / `outputBuffer`，用 `IsBufferSignal()` 区分（`:75-76`、`:89`）

并带三个可查询属性：`HasSpatialGuide()`（深度与法线都非空，`:90`）、时域（`velocity != nullptr`）、
`needsUpscale`（信号分辨率低于消费端，`:77-79`），以及按信号赋值的 `depthSigma` / `normalSigma`（`:83-84`）与给日志用的 `note`（`:87`）。

登记发生在每帧构图前后：帧图遍历 Provider 调 `DescribeSignals`（`DeferredPipeline_FrameGraph.cpp:1259`），
然后 `LogSummary("GI")`（`:1261`），再打印历史池账（`:1267-1270`）。
`LogSummary` 只在**信号名集合的 FNV-1a 哈希**变化时打印（`DenoiseSignal.cpp:133-142`），避免每帧刷屏。

SSGI/SSR 的登记内容见 `SSGIProvider.h:128-149`（`needsUpscale = AuxActive() && m_Aux.NeedsUpscale()`，`:145`），
RT 与 Lumen 各有自己的 `DescribeSignals`（`RTProvider.h:231`、`LumenProvider.h:281`）。

**按信号赋值目前仍取默认值**：`DeferredPipeline.cpp:149-154` 把 SSGI/SSR 的 sigma 都设成 `kDefaultDepthSigma` / `kDefaultNormalSigma`，
并在 `:139-148` 的注释里说明这是实测结论而非遗漏——瓶颈是 5×5 核本身与缺少时域累积，而不是这两个权重（`:146-148`）。

### 4.7 `PTAtrousPass`：SVGF 风格 A-Trous

### 5.2 TAA（HDR 空间）

**空间**：HDR。位置在 Lighting 之后、ToneMap 之前（`DeferredPipeline_FrameGraph.cpp:1639-1665`），
输出 `RGBA16_FLOAT`（`AA_TAA.h:44`）。

**自拥有输出**：双缓冲历史（`AA_TAA.cpp:66-73`），`GetOutputTexture()` 返回当前 read 面（`:222-224`），
`Render` 末尾推进指针（`:253-255`）。

**抖动序列**：8 样本 Halton(2,3) 表（`AA_TAA.cpp:22-23`），逐帧取模 8（`:212`），
再缩放为 NDC：$\mathrm{jitter}_x = \mathrm{raw}_x \cdot \dfrac{2}{W}$，$y$ 同理（`:215-216`）。
初值表与相邻注释里列的 Halton 值**不是同一组数**（表格是 `0.25, -0.25, 0.125, ...`，注释写 `0.5, -0.5, 0.25, ...`），
注释像是以 0.5 为基准的原始 Halton 值，而代码存的是去中心化后的结果。

**Resolve 算法**（`TAA_Resolve.frag.slang`）：

1. 重投影：$\mathrm{historyUV} = uv - \mathrm{velocity}$（`:76`）
2. 去遮挡：深度相对差 $\dfrac{|\Delta d|}{\max(d, 10^{-3})}$ 经 $\mathrm{smoothstep}(0.001, 0.01)$（`:91-92`）、
   法线差 $1 - N \cdot N'$ 经 $\mathrm{smoothstep}(0.001, 0.05)$（`:95-96`）、
   速度模长经 $\mathrm{smoothstep}(0.01, 0.05)$（`:99-100`），三者取 max；出屏直接取 1（`:101-103`）
3. 邻域裁剪：3×3 的当前帧颜色转到 YCoCg 求 AABB（`:45-60`），再向两侧各膨胀
   $\mathrm{ext} = 0.05 \cdot (max - min) + 0.001$（`:63-65`）
4. 混合：$\mathrm{blend} = \mathrm{lerp}(\mathrm{blendFactor},\ 0.3,\ \mathrm{disocclusion})$（`:119`），
   $\mathrm{resolved} = \mathrm{lerp}(\mathrm{clampedHist},\ \mathrm{currColor},\ \mathrm{blend})$（`:120`）；
   若 $\mathrm{disocclusion} > 0.95$ 或出屏则**直接输出当前帧**（`:107-108`）

`blendFactor` 由 CPU 给出：前两帧为 1.0（100% 当前帧，用于初始化历史），之后为 0.1（`AA_TAA.cpp:194-195`）。注释把 0.1 称作"10% 当前帧加速收敛"。

**Uniform 布局**：144 B = `prevViewProj`(64) + `invCurrViewProj`(64) + `resolution`(8) + `blendFactor`(4) + `unused`(4)（`AA_TAA.cpp:176-189`、`AA_TAA.h:48`）。

**采样器策略**：当前帧颜色、历史、深度、法线、速度**全部用 Nearest**（`AA_TAA.cpp:80-83`、`:151-152`、`:164-167`），
但 `GetOutputSampler()` 返回的是**线性**历史采样器（`:226-228`）供下游 ToneMap 使用。
`m_HistorySampler` 在 Resolve 里**没有被用到**（`:110` 用的是 `u_PointSampler`）。

**关键限制**

- ✅ **抖动已接进投影矩阵（2026-09 画质阶段 0 第②项）**。接线前 `GetJitterOffset()`（`AA_TAA.cpp:205-207`）
  在整个 Engine/Samples 中**没有任何调用点**：唯一的消费是把 `m_CurrentJitter` 作为 push constant 传进 Resolve
  着色器（`AA_TAA.cpp:243`），而该着色器声明了 `float2 jitterOffset`（`TAA_Resolve.frag.slang:30`）却**从未使用**。
  后果是每帧投影相同、当前帧颜色不含亚像素偏移 ⇒ 没有真正的亚像素累积，只有"历史 + 邻域 AABB 裁剪"这半截在起作用。
  现在：帧图帧首把当前帧偏移写进 `CameraData::jitterNdc`，由 `CameraData::GetProjMatrix()` 施加到投影矩阵
  （`Pipeline/Camera.h`，`m[2][0] -= δx; m[2][1] -= δy`）。
  - **只抖主视图**：阴影（CSM/Spot/Point）仍用**未抖动**的相机做级联拟合（帧图里 `sctx.camera = &cameraIn`），
    否则级联会逐帧亚像素摆动、阴影贴图 texel 对齐抖动；天空盒与几何同相位（同一份抖动投影）。
  - **速度矢量自带抖动差**：`prevViewProjMatrix` 传的是**上一帧含抖动的** VP（帧末 `m_PrevViewProj = m_CurrViewProj`），
    于是 `historyUV = uv − velocity` 正好落在"同一世界点在上帧被采样到的那个亚像素位置" ⇒ resolve **不需要**再补抖动项。
    这也是 `jitterOffset` push constant 至今没被用上的**原因**（有意保留，不是漏接线）。
  - **符号与量级有单测钉子**：`Tests/TestCameraJitter.cpp` 断言"同一点的 NDC 恰好平移 +δ、且与深度无关"，
    并断言 `jitterNdc = 0` 时投影矩阵与 glm 参考实现逐元素相同。
  - **实测证据**（同一构建，`build/verify/nanite_smoke.ps1` + `cmp_dumps.py`）：抖动生效时 `hdr` 有 6,069,303 个
    像素变化但 `meanAbs` 仅 1.65e-3、`albedo` 的 `meanAbs` 4.7e-3（亚像素相位；边缘像素整值翻转是预期），
    而 `rsm_*` / `ibl_irr` / `prov1_*` / `radiance` **逐位不变** ⇒ 抖动只作用于主视图；把抖动路径临时置 0 后
    整帧与接线前**逐位相同**（对照实验）。
  - **⚠ 暴露出的既有缺陷（本轮如实登记，未修）**：抖动让"静态相机"这一**退化情形**也产生了逐帧差异，
    于是 Lumen 的屏幕探针链在**逐趟重复运行**间不再收敛到同一结果 —— `06.GILab`（`gi_blend_diffuse_lumen=1`）
    同一配置两趟对比：`lumen_irradiance` + 4 个 `prov6_*` 有 **786,444 像素**不同、`maxULP=817`、
    `meanAbs=1.08e-4`（占 38% 像素）；把抖动临时关掉，同一对运行只剩既有的有界漂移（`maxULP=6`、

  而在 Build 末尾才 `m_PrevViewProj = m_CurrViewProj`（`:1855`）；`UpdateUniforms` 传的是**DeferredPipeline 的**成员
  `m_PrevViewProj`（`:1708`），不是 `AA_TAA` 自己的。
  即 `AA_TAA.h:118` 声明的 `m_PrevViewProj` 成员**从未被写入**，也从未被读取——`UpdateUniforms` 的形参叫 `prevViewProj`（`AA_TAA.cpp:173`），函数体只用形参（`:191`）。
- **TAA 默认开启且无法从 DeferredPipeline 关闭**：`IRenderSubsystem::m_Enabled` 初值为 `true`（`RenderSubsystem.h:114`），
  `AA_TAA` 没有覆写默认值；`PostProcessChain::Initialize` 无条件创建它（`PostProcessChain.cpp:23-27`）；
  而 `DeferredPipeline` 的公开接口只有 `EnableFXAA` / `EnableSMAA` / `EnableMSAA`（`DeferredPipeline.h:156-165`），**没有 TAA 开关**，`GetTAA()` 也没有对外暴露。
  唯一的关闭方式是 `PostProcessChain::GetTAA()->SetEnabled(false)`，但从 `DeferredPipeline` 拿不到这个指针。
- TAA 的 Pass 在 RenderGraph 里**未声明输出**（`DeferredPipeline_FrameGraph.cpp:1641`），历史纹理完全在 RG 的视野之外（不参与别名、不参与 barrier 推导）。
- 历史纹理**首次使用前没有初始化**，靠 `blendFactor = 1.0` 覆盖（`AA_TAA.cpp:194-195`）；但 `velocity` 在首帧为零意味着去遮挡检测不会触发，这正是注释里"首帧无历史数据"的处理。
- `OnResize` 会重建历史并复位 `m_JitterIndex`（`AA_TAA.cpp:134-145`），但**不复位 `m_FrameIndex`**——resize 之后不再是"首帧"，`blendFactor` 直接是 0.1。

### 5.3 FXAA（LDR 空间）

单 Pass、LDR、无需 GBuffer 与历史帧（`AA_FXAA.h:9-14`）。链位置在 ToneMap 之后（`DeferredPipeline_FrameGraph.cpp:1787-1807`）。

**算法**（`FXAA.frag.slang`）：

1. 3×3 采样取亮度，亮度用 **Rec.601** 系数（`:18`）
2. 水平/垂直梯度由 3 行/3 列的加权二阶差分构成（`:41-42`）
3. `edge = max(hGrad, vGrad)`；`if (edge < 0.05) return c11`（`:45-46`）
4. 沿梯度垂直方向做 3 tap 平均，再按端点亮度差比例回 lerp：
   `blended = (c01 + c11 + c21)/3`，`t = saturate(|l01-l21| / max(edge, 0.001))`，`blended = lerp(blended, c11, t*0.5)`（`:50-60`）

**关键参数**

| 参数 | 值 | 位置 |
|---|---|---|
| 输出格式 | `BGRA8_UNORM` | `AA_FXAA.cpp:112` |
| `depthFormat` | `D32_FLOAT` | `AA_FXAA.cpp:110` |
| 早退阈值 | 0.05 | `FXAA.frag.slang:46` |
| push constant | 16 B（`invScreenSize` + pad） | `AA_FXAA.cpp:96-98`、`:72-74` |
| 占位纹理 | 1×1 `BGRA8_UNORM` 白 | `AA_FXAA.cpp:23-37` |

`depthFormat` 必须声明的原因写在代码里：终稿 Pass 画进的是带 D32 深度附件的交换链 RenderPass，
管线 RP 若不同样声明深度就会每帧报 `VUID-vkCmdDraw-renderPass-02684`（`AA_FXAA.cpp:106-109`）。`depthTest`/`depthWrite` 仍为 false，附件声明只是为了兼容。

**已知限制**

- `AA_FXAA::GetOutputTexture()` 返回的是 `m_Input`（`AA_FXAA.h:38`），不是它画出的结果——因为它写 BackBuffer，没有可采样的输出。这在契约上是"诚实的"，但会让任何试图把 FXAA 放到链中间的用法静默拿到未抗锯齿的输入。
- `SetInput` 里 `m_Placeholder` / `m_PlaceholderSamp` 只被创建（`AA_FXAA.cpp:22-37`）与销毁（`:48-49`），**从未被绑定**。
- `AA_FXAA::OnResize` 只改宽高两个字段（`AA_FXAA.cpp:54`），不重建任何资源——正确，因为它的输出是 BackBuffer。
- 参数只有 `invScreenSize`：没有 `quality`/`contrast` 之类的可调项，与 FXAA 3.11 的完整版本相比是简化实现（文件头自称"简化的 FXAA 3.11"）。

### 5.4 SMAA（LDR 空间，3 Pass）

**三个阶段**（`AA_SMAA.cpp:151-217`、`:223-247`）：

| Pass | 输出 | 格式 | 尺寸 | 位置 |
|---|---|---|---|---|
| EdgeDetection | `m_EdgeTex` | `R8_UNORM` | 全分辨率 | `AA_SMAA.cpp:50-55`、`:168-171` |
| BlendWeight | `m_BlendTex` | `RGBA8_UNORM` | 全分辨率 | `AA_SMAA.cpp:58-63`、`:204-207` |
| Neighborhood | BackBuffer | `BGRA8_UNORM` | 全分辨率 | `AA_SMAA.cpp:368`、`AA_SMAA.h:49-51` |

第 1、2 阶段各自 `BeginOffscreenPass`/`EndOffscreenPass`（`AA_SMAA.cpp:168-171`、`:204-207`），
之后各自发一次 `PipelineBarrier(RenderTarget → ShaderResource)`（`:175-180`、`:211-216`）。
第 3 阶段**不开通道**，由调用方在 `BeginRenderPass(BackBuffer)` 内部调用 `RenderFinalPass`（`AA_SMAA.h:49-51`、`DeferredPipeline_FrameGraph.cpp:1781-1783`）。

**算法细节**

- 边缘检测：3×3 十字 + 对角亮度差，`hEdge`/`vEdge` 加权组合（`SMAA_EdgeDetect.frag.slang:37-43`），
  阈值 0.05（`:47`），编码 `edgeType = (hEdge > vEdge) ? 1.0 : 0.5`（`:53`）。
- 混合权重：沿边缘方向搜索，最多 16 步（`SMAA_BlendWeight.frag.slang:19`），
  遇到非边缘（`e < 0.01`）即返回归一化距离（`:27`）；然后
  `centerRatio = |distNeg - distPos| / (distNeg + distPos + 0.001)`，`blendAmount = centerRatio * 0.5`（`:52-56`）。
  **最大混合 50%**（`:56`）。
- 邻域混合：`lerp` 链式施加左/右/上/下四个权重（`SMAA_Neighborhood.frag.slang:44-47`），
  不重新归一化；权重和 < 0.001 时直接返回中心像素（`:32-34`）。

**已知限制**

- **没有预计算 LUT**。参考实现 SMAA 依赖 area/search 两张查找纹理，这里用解析近似（搜索 16 步 + 线性配比）替代；
  文件头自称"子像素形态学"但实现是亮度梯度 + 距离搜索的简化版。
- **边缘方向编码与注释不一致**：`SMAA_EdgeDetect.frag.slang:3` 的注释写 `R=0.5: 水平边缘, R=1.0: 垂直边缘`，
  而代码是 `hEdge > vEdge ? 1.0 : 0.5`（`:53`），消耗侧判 `isHorizontal = (edge > 0.75)`（`SMAA_BlendWeight.frag.slang:41`）——
  即 **1.0 被当作水平边缘**，与注释文字相反。三方（`AA_SMAA.h:4-5` 的头注释、EdgeDetect 注释、BlendWeight 注释）措辞也不统一。
- 没有金属度/亮度可配项；边缘检测的 `threshold = 0.05` 是着色器里的字面量（`SMAA_EdgeDetect.frag.slang:47`）。
- `RenderFinalPass` 与 `Render` 都各自检查 `!m_Ready || !m_Enabled || !m_Input`（`AA_SMAA.cpp:149`、`:224`）——若调用方只调了后者而忘了前者，会静默什么都不画。

### 5.5 管线的 AA 分配与互斥关系

| 管线 | 实际生效的 AA | 证据 |
|---|---|---|
| **Deferred** | TAA（HDR，**默认开**）→ ToneMap → ColorGrading → CameraEffects → **SMAA 或 FXAA**（LDR，二选一） | `DeferredPipeline_FrameGraph.cpp:1639-1665`、`:1761`、`:1787` |
| **Forward** | **帧图路径里没有 AA pass** | `ForwardPipeline_FrameGraph.cpp:263-271`（ToneMap 是最后一个 pass） |
| **Forward（非帧图路径）** | `m_AntiAliasing` 经 `SetInput` + `Render` 执行一次 | `ForwardPipeline.cpp:995-998` |
| **PathTracing** | FXAA **强制开启**（LDR，ToneMap 之后） | `PathTracingPipeline.cpp:49`、`:583`、`:617-627` |

**互斥关系**

- **SMAA 与 FXAA 互斥**：`if (useSMAA) { ... } else if (useFXAA) { ... }`（`DeferredPipeline_FrameGraph.cpp:1761`、`:1787`）。
  两者的输入选择链完全相同（`useFX → useColor → LDRTarget`，`:1762-1767` 与 `:1788-1793`）。
- **MSAA 与其他 AA 不互斥**：样例面板明确写`与 MSAA 可叠加`（`04.Sponza-Deferred.cpp:968`），
  MSAA 走的是 `EnableMSAA`，与 FXAA/SMAA 的标志位独立（`PostProcessChain.h:84` 三个独立 bool）。
- **HDR 与全部 LDR 后处理互斥**：`isHDR` 时 `useFXAA = useSMAA = useColor = useFX = false`（`DeferredPipeline_FrameGraph.cpp:1677-1679`）。
  TAA 不受影响（它在 HDR 空间，注释 `:1676`）。
- **TAA 与后处理链的顺序**：TAA 读的是"后处理链最后一个激活者"的输出（`:1644-1651`），
  即 **Bloom/DOF/MotionBlur 在 TAA 之前**。也就是说时域抗锯齿工作在已经过 Bloom/DOF/MotionBlur 的颜色上，
  而这些效果本身又会引入新的高频/时域变化；链的顺序在注释里写作 `Lighting(HDR) → TAA_Resolve → ToneMap`（`AA_TAA.h:15`），与实际接线不同。

**Forward 管线的 AA 落地细节**

`ForwardPipeline` 持有 `std::unique_ptr<IAntiAliasing> m_AntiAliasing`，默认构造为 `AA_None`（`ForwardPipeline.cpp:325-326`），
并提供 `SetAntiAliasing` 换实现（`ForwardPipeline.h:97-98`）。
帧图的 ToneMap（`ForwardPipeline_FrameGraph.cpp:264-271`）与 AA 之间**没有插槽**，所以经帧图渲染时 AA 不生效。
编辑器侧通过 CVar `render.aa_mode`（`EditorApp.cpp:148`）在 `none` / `fxaa` 之间切换，
选 `taa` 会警告并回落到 `none`（`EditorApp.cpp:255-260`），因为 `TAA requires DeferredPipeline`。

**PathTracing 管线的 AA**

初始化时无条件 `m_PostProcess.EnableFXAA(device, w, h, true)`（`PathTracingPipeline.cpp:49`），
注释给出的理由是`终端 AA 保证 RP 状态正确`（`:49`）——即 FXAA 在这里还承担了"把管线状态推回可进交换链 RenderPass"的角色：
进交换链前先 `ToneMap()->PreBind(c)` 再 `FXAA->Render(c)`（`:623-627`）。
HDR 下 FXAA 同样被跳过（`:583`、`:618`）。

## 6. MSAA 的实情

### 6.1 上层：只有描述符覆盖，且无人调用

`AA_MSAA` 的实现方式就是"覆盖两个描述符的 `sampleCount`"（`AA_MSAA.h:3-9`）：

```cpp
bool RequiresMultisampling() const override { return m_Enabled && m_Ready; }   // AA_MSAA.h:50-52
u32  GetSampleCount()        const override { return m_SampleCount; }           // AA_MSAA.h:53-55
void OverrideTextureDesc(rhi::TextureDesc& d) const override {                  // AA_MSAA.h:58-61
    if (!m_Enabled || !m_Ready) return;
    d.sampleCount = m_SampleCount;
}
void OverridePSODesc(rhi::PipelineStateDesc& d) const override {                // AA_MSAA.h:62-65
    if (!m_Enabled || !m_Ready) return;
    d.sampleCount = m_SampleCount;
}
```

`m_SampleCount` 默认 4（`AA_MSAA.h:80`），`m_Enabled` 默认 true（`:79`）。
`AA_MSAA` 没有任何独立 Pass：`Render` / `Bind` / `Update` 都是空实现（`AA_MSAA.h:31-33`），
`SetInput` 空实现（`:42`），`OwnsOutput()` 为 false（`:44`）。

创建路径：`PostProcessChain::EnableMSAA` → 懒建实例（`PostProcessChain.cpp:148-155`）；
`DeferredPipeline::EnableMSAA` 直接转发（`DeferredPipeline.cpp:621-622`）。
唯一的上层使用点是样例面板（`04.Sponza-Deferred.cpp:959-966`），且标注 `(重启生效)`（`:965`）。

**关键事实**：`OverrideTextureDesc` 与 `OverridePSODesc` 在整个 `Engine/` 与 `Samples/` 中**没有任何调用点**
（在 `Engine` 下的全量检索里，这两个函数只出现在 `AntiAliasing.h:72`、`:75` 的声明与 `AA_MSAA.h:58`、`:62` 的实现）。
`DeferredPipeline::Initialize` 里对应 MSAA 的只有一行日志，不做任何 RT/PSO 覆盖：

```cpp
// 硬件 MSAA：覆盖纹理和 PSO 的 sampleCount（委托给 PostProcessChain）
if (m_PostProcess.IsMSAAEnabled()) {
    HE_CORE_INFO("DeferredPipeline: MSAA enabled (HDR 目标多采样，GBuffer 保持 1x)");
}
```
（`DeferredPipeline.cpp:68-71`）

即：注释描述的行为（覆盖 `sampleCount`）**没有对应的代码**。`IsMSAAEnabled()` 的判据也只是"标志位为真且实例非空"（`PostProcessChain.h:62`），不检查任何 GPU 状态。

### 6.2 RHI 层：运行时 PSO 路径硬编码采样数为 1

RHI 的两条纹理创建路径**都**正确处理了 `desc.sampleCount`：

| 路径 | 处理 | 位置 |
|---|---|---|
| `VulkanTexture` 构造（`CreateTexture`） | `switch (desc.sampleCount)` → `VK_SAMPLE_COUNT_2/4/8/16/32/64_BIT`，default 1 | `VulkanResources.cpp:333-350` |
| `CreateTransientTexture` | 同样的 `switch` | `VulkanDevice.cpp:1287-1304` |

但 **PSO 的运行时创建路径把 `rasterizationSamples` 写死为 `VK_SAMPLE_COUNT_1_BIT`**，完全不读 `desc.sampleCount`：

| 路径 | 位置 | 写法 |
|---|---|---|
| 常规图形管线（`VulkanPipeline` 主路径） | `VulkanPipeline.cpp:307` | `out.multisample.rasterizationSamples = VK_SAMPLE_COUNT_1_BIT;` |
| Mesh Shader 图形管线（同文件另一条构建分支） | `VulkanPipeline.cpp:596` | `ms.rasterizationSamples = VK_SAMPLE_COUNT_1_BIT;` |

### 6.3 预热路径与运行时路径对采样数的处理不一致

PSO 预热（后台线程预编译进 `VkPipelineCache`）走的是**另一套**构建代码，它**读取并转换** `desc.sampleCount`：

```cpp
// Multisample
VkPipelineMultisampleStateCreateInfo ms{};
ms.sType                = VK_STRUCTURE_TYPE_PIPELINE_MULTISAMPLE_STATE_CREATE_INFO;
ms.rasterizationSamples = static_cast<VkSampleCountFlagBits>(desc.sampleCount);
```
（`PSOPrecompileManager.cpp:373-376`）

注意这里是**裸 `static_cast`**（把 `u32` 直接当 `VkSampleCountFlagBits`），没有像纹理路径那样走 `switch`。
数值上恰好成立（`VK_SAMPLE_COUNT_4_BIT == 4` 等），但 `desc.sampleCount == 0`（某些默认构造的 `PipelineStateDesc`）会被强转成 0，而不是 1。

**两条路径的差异可以直接被观察到**：管线缓存的 key 两侧都吃进了 `sampleCount`

- 运行时的 key：`h = hashU32(h, desc.sampleCount);`（`VulkanPipeline.cpp:110`）
- 库缓存的 key（`PipelinePartKind::FragmentOutput` 段）：`h = FnvHashU32(h, desc.sampleCount);`（`VulkanPipelineLibrary.cpp:86`）

所以当 `sampleCount != 1` 时，预热按该采样数编译出的管线与运行时按采样数算出的 key **相同**，
但运行时**实际建出来的是 1x 管线**——即"缓存里存在的那个变体"与"运行时真正使用的那个变体"不是同一个东西，
而按 key 去查也不会报错。

### 6.4 结论

把三类事实拼起来，MSAA 当前的状态是：

1. **上层的覆盖机制从未被触发**：`OverrideTextureDesc` / `OverridePSODesc` 零调用点，`EnableMSAA` 只置标志位（`PostProcessChain.cpp:148-155`），`DeferredPipeline::Initialize` 只打日志（`DeferredPipeline.cpp:68-71`）。
2. **即使触发，运行时也拿不到多采样管线**：纹理侧会按 `sampleCount=4` 建出 4x 图像（`VulkanResources.cpp:334-350`），
   而 PSO 侧 `rasterizationSamples` 恒为 1（`VulkanPipeline.cpp:307`、`:596`）——图像与管线采样数不匹配。
3. **预热与运行时口径分裂**：`PSOPrecompileManager.cpp:376` 按 `desc.sampleCount` 建，运行时路径按 1 建，
   而两者的缓存 key 都把 `sampleCount` 计入（`VulkanPipeline.cpp:110`、`VulkanPipelineLibrary.cpp:86`）。

因此 `AA_MSAA.h:8-9` 头注释里写的 `Forward ✅ / Deferred ⚠️` 两种兼容性、
以及 `AntiAliasing.h:88-91` 上 `MSAA=true（硬件采样覆盖 RT）` 的说明，描述的是**设计意图**；
从代码路径看，MSAA 在两条管线上都不会产生多采样光栅化。

另有两处相关的空转：

- `AA_MSAA::OnResize` 只更新 `m_Width/m_Height`（`AA_MSAA.h:34`），而 `PostProcessChain::OnResize` **根本没有调用它**（`PostProcessChain.cpp:90-122` 未包含 `m_MSAA`）。
- `AASettings::msaaSampleCount`（`AntiAliasing.h:34`，默认 4）与 `AA_MSAA::m_SampleCount`（`AA_MSAA.h:80`，默认 4）是**两个互不相干的字段**：`SetSettings` 只存 `AASettings`（`AntiAliasing.h:96`），没有任何地方把它同步到 `SetSampleCount`（`AA_MSAA.h:56`）。

## 7. SSAO 与屏幕空间效果的关系

### 7.1 位置：AO 是一个 GI 源，不是一个后处理 Pass

`SSAO` 虽然放在 `Engine/Render/PostProcess/` 目录下，但它在帧图里是通过 **GI Provider 注册表**接入的，不是后处理链的一环。

- 管线注册 `ScreenAOProvider` 并把 `&m_SSAO` 注入（`DeferredPipeline.cpp:171-174`）。
- 帧图在 GI 段落里遍历 Provider，挑出 `Handles(GISourceId::SSAO) || Handles(GISourceId::GTAO)` 的那些（`DeferredPipeline_FrameGraph.cpp:786-787`），
  经 `SyncToStack(m_GIConfig.ao)` 与 `NeedsPass` 两道门控后注册 pass（`:788-789`），
  pass 名取自 `prov->GetName()`（`:797`），尺寸用**AO 纹理的实际尺寸**以支持半分辨率（`:793-795`）。
- pass 体内：`PreBind` → `SetInputs(depth, normal, albedo)` → 以 `clear = (1,1,1,1)` 开离屏通道 → 计时 → `Render` → 关通道（`:798-808`）。
- 输出纹理由 `LightingPass` 通过 `in.ssaoTex` 消费（`DeferredPipeline_FrameGraph.cpp:1413`）。

`ScreenAOProvider` 一个类同时代表 SSAO 与 GTAO 两个源：`GetSourceId()` 按 `m_Pass->useGTAO` 返回当前生效者（`AOProvider.h:26-28`），
`Handles()` 对两者都返回 true（`:29-31`），`SyncToStack` 同时对齐 `enabled` 与 `useGTAO`（`:43-47`）。
`SyncToStack` 里对齐 `enabled` 的补充说明值得记下来：`此前只切模式、开关留给调用方设置，于是「层栈要求参与、子系统却关闭」会静默失效`（`AOProvider.h:40-42`）。

### 7.2 SSAO 本体

**参数**（均为 `public` 裸字段，`SSAO.h:24-36`）：

| 参数 | 默认 | 用途 |
|---|---|---|
| `enabled` | true | 由 `SyncToStack` 每帧覆写为"层栈是否含 SSAO 或 GTAO" |
| `radius` | 1.0 | 采样半径 |
| `bias` | 0.025 | 深度偏移 |
| `intensity` | 1.0 | AO 强度 |
| `sampleCount` | 16 | SSAO 模式的每像素采样数 |
| `halfRes` | false | AO 纹理降半（两张 AO 纹理按同一比例降半） |
| `useGTAO` | false | 切 GTAO 着色器 |
| `sliceCount` | 4 | GTAO 方位角切片数 |

**采样核**：64 个半球样本，`std::default_random_engine gen(42)`（`SSAO.cpp:26-39`，种子在 `:29`）。
每个样本先归一化、再乘一个随机长度，然后按 $\mathrm{scale} = \mathrm{mix}(0.1, 1.0, (i/64)^2)$ 向中心收缩（`:36-38`）——即核内密度偏向中心。
噪声纹理 4×4、`gen(123)`、`RGBA16_FLOAT`（`:42-56`、`:97-98`）。

**参数 UBO**：`64 * sizeof(float4) + sizeof(float4) + sizeof(float4x4) * 2` = 1024 + 16 + 128 = **1168 B**
（声明处 `SSAO.cpp:113`）。
布局为 `kernel[64]` → `params` → `u_InvProj` → `u_Proj`（`:298-330`）。
`params.w` 是**复用字段**：SSAO 模式塞 `sampleCount`，GTAO 模式塞 `sliceCount`（`:306-310`）。
自 2026-09 画质阶段 0 起，**每个帧槽一份 UBO + 一份描述符集**（`:109-121`、`SSAO.h:87-99`），
槽位由帧图经 Provider 注入（`SetFrameSlot`，`SSAO.h:53`）。

**投影矩阵来自真实相机**：优先用 `m_Camera->GetProjMatrix()`（`:318`），
只有 `m_Camera == nullptr` 时才退化为 `glm::perspectiveRH_ZO(radians(kDefaultFOV), aspect, kDefaultNearPlane, kDefaultFarPlane)`（`:320-323`）。
理由写在注释里：深度图是用真实相机投影渲染的，重建必须同源，否则非默认相机下 AO 采样位置会系统性错位（`:312-315`、`SSAO.h:46-49`）。

**PSO 惰性创建**：`Initialize` 只建描述符布局、UBO 与 `ShaderBytecode` 副本（`SSAO.cpp:102-143`），
并 `PrecompileQueuePSO(d)` 交给后台预热（`:144`）；真正的 `CreatePipelineState` 发生在首次 `PreBind`/`Render`（`:250-257`、`:263-271`）。
GTAO 与 Blur 走同一套模式（`:150-171`、`:172-196`），GTAO 与 SSAO **共用描述符布局与 UBO**，只换片段着色器（`:150-151`）。

### 7.3 两趟结构：SSAO 写原始 AO、Blur 读原始 AO 写最终 AO

`SSAO::Render`（`SSAO.cpp:260`）内部是**两个独立的离屏通道**；帧图只声明"本 pass 写最终 AO"这一个对外资源（`DeferredPipeline_FrameGraph.cpp:804-819`，通道的开关也因此从帧图 lambda 移进了本函数）：

```cpp
// Pass 1：SSAO / GTAO → m_RawAOTexture（原始 AO）
cmd->SetPipeline(useGTAO ? m_GTAO_PSO.get() : m_SSAO_PSO.get());    // SSAO.cpp:293
cmd->BeginOffscreenPass(m_RawAOTexture->GetNativeHandle(), ...);     // :332
cmd->Draw(3);                                                        // :334
cmd->EndOffscreenPass();                                             // :335

// 原始 AO 布局转换：RenderTarget → ShaderResource。
// render pass 自身的 finalLayout 转变不经过 barrier，必须显式发一条（与 AA_SMAA::Render 同款）
cmd->PipelineBarrier(rhi::PipelineStage::ColorAttachmentOutput,
                     rhi::PipelineStage::FragmentShader,
                     rhi::ResourceState::RenderTarget,
                     rhi::ResourceState::ShaderResource,
                     m_RawAOTexture.get());                          // :338-342

// Pass 2：Blur 读 m_RawAOTexture → 写 m_AOTexture（对外输出）
cmd->BeginOffscreenPass(m_AOTexture->GetNativeHandle(), ...);        // :354
cmd->Draw(3);                                                        // :356
cmd->EndOffscreenPass();                                             // :357
```

**为什么必须拆开**：修复前两趟共处**同一个**离屏通道、写**同一个**附件，Blur 通过描述符采样自己正在写的纹理 —— attachment feedback loop，Vulkan 明确把"在同一 subpass 内采样自己正在写的附件"列为未定义行为，结果取决于驱动的 tile/缓存行为。实测（同一构建、同一配置连跑）`hdr` 差 5.8 万像素、`prov0_ao_*` 差 2.2 万像素；把 AO 从层栈关掉（该 pass 不再注册）后全部转储逐位相同。修复后同一配置连跑三次**全部转储逐位一致**。

`m_BlurTexture`（旧名）正是为此准备的中间纹理，却一直没被用上；本次改名为 `m_RawAOTexture`（`SSAO.h:109`）并真正作为 Pass 1 的渲染目标。`GetAOTexture()` 的语义不变（仍是模糊后的最终 AO，`SSAO.h:59`），因此 `Lighting` 与帧图侧无需改动；另加 `GetRawAOTexture()`（`SSAO.h:60-61`）供诊断对比。

**同一处排查还发现并补上了消费侧的依赖**：`Lighting` 用 `in.ssaoTex = m_SSAO.GetAOTexture()`（`DeferredPipeline_FrameGraph.cpp:1436`）采样 AO，但帧图的 `lightingReads` 此前**没有声明**这个句柄（该列表自 `:1330` 起，SSGI/SSR/Lumen/RTGI 都有各自的 push_back）⇒ 帧图不给 AO→Lighting 插屏障，`Lighting` 会在 AO 纹理仍停在 `COLOR_ATTACHMENT` 布局、甚至仍被 Blur 趟写入时采样它。补上读依赖后（`:1337-1348`），同一构建连跑三次逐位一致。（这条路径本身未产生独立的校验层告警：日志里那几条启动期 `VUID-vkCmdDraw-None-09600` 是另一处已记录的既有豁免，见 `docs/已实现功能/全路径追踪管线规划.md:228`，本次修复前后计数不变。）

**"逐位一致"的验证口径**：`build/verify/nanite_smoke.ps1` + `cmp_dumps.py`，同一配置连跑 N 趟比对全部 18 个转储。修复前 OFF 配置连跑 7 趟出现 1 趟 `hdr` 差 133 万像素（差异集中在物体轮廓——AO 影响最强处）；修复后 OFF 3 趟、ON 2 趟全为 0 差异，且与修复前的**多数派**结果逐位相同（即这是纯同步修复，不改变稳态画面）。

### 9.4 其它边界

- **`Denoiser::Render` 不检查 `m_Input`**（`Denoiser.cpp:70-80`），与同目录其它 Pass 的写法不同（对比 `DenoiseUpscale.cpp:98`）。调用方若忘了 `SetInputs`，描述符集里会留着上一次的绑定。
- **`Denoiser` 与 `RTDenoiser` 都有"隐式的 PreBind/SetPipeline 顺序契约"**，`RTDenoiser` 把它写进了注释与代码（`RTDenoiser.h:60-65`、`.cpp:174-186`），`Denoiser` 只在 `Render` 里直接 `SetPipeline`（`Denoiser.cpp:71`），靠调用方保证早于 `BeginOffscreenPass`。
- **`SSAO` 的两趟各自独立开通道**（§7.3）：Blur 采样 `m_RawAOTexture`、写 `m_AOTexture`，中间显式发 RT→SRV 屏障；此前的"Blur 与 SSAO 共用同一附件"（读-写同一纹理）已修复。
- **`ColorGradingPass::OnResize` 缺少同类 Pass 都有的两道守卫**（`ColorGradingPass.cpp:73-82`，对比 `CameraEffectsPass.cpp:74-75`）；它当前不会被链调用（§9.1），所以这个差异暂时不可观测。
- **`AA_SMAA` 的边缘方向编码与注释文字相反**（§5.4）。
- **`DOF_CoC` 用的是未线性化的原始深度**（§3.3）。
- **`BrightPass` 没有 4 tap box 降采样**（§3.2）。
- **`Render()` 与离屏通道分离的隐式契约**：`ColorGradingPass`、`CameraEffectsPass`、`ToneMapPass`、`GaussianBlurPass`、`Denoiser`、`DenoiseUpscale`、`RTDenoiser` 都只发 Draw，通道由调用方开；`BloomPass`、`DOFPass`、`MotionBlurPass`、`AA_TAA`、`AA_SMAA`、`SSAO`（两趟，§7.3）自己开。同一目录里两种风格并存。
- **后处理链在 TAA 之前**：Bloom/DOF/MotionBlur 的输出是 TAA 的输入（`DeferredPipeline_FrameGraph.cpp:1644-1651`），与 `AA_TAA.h:15` 注释写的 `Lighting(HDR) → TAA_Resolve → ToneMap` 不一致（注释省略了中间三者）。
- **管线缓存 key 与"实际建出的管线"可能不一致**：见 §6.3。
