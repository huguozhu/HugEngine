## 1. 结论速览

| 维度 | 现状 |
|---|---|
| 归属 | 延迟管线里的**一个 GI 源**（`IGIProvider` 的一个实例），不是独立管线；不替代 Lighting |
| 源标识 | `GISourceId::Lumen`（`GITypes.h:49`）；分类为**世界空间源**（`GITypes.h:91-96`）；能力位同时给漫反射与镜面（`GITypes.h:352`） |
| 一帧产出 | 一张屏幕尺寸 RGBA16F 纹理，漫反射与镜面**共用**（`LumenProvider.h:61-62`） |
| 追踪 | 四级软件链路：Mesh SDF →（注入）Global SDF clipmap →（sphere tracing）Screen Probe 半球光线 →（近场 SDF / 远场硬件光追合并）命中点 |
| 着色 | 命中点从 Surface Cache atlas 取 albedo（`Lumen_SurfaceCacheSample.comp.slang`）；atlas 的材质来源是**本帧 GBuffer**（`SurfaceCache_Capture.comp.slang:8-13`） |
| 辐照度载体 | 屏幕空间 Screen Probe：16×16 像素一个单元、2×2 平坦单元合并；每探针二阶 SH（4 系数 × RGB = 12 float），96 B/探针（`ScreenProbe.slang:30-39`） |
| 降噪 | 3×3 单元 YCoCg AABB 空间滤波 + 时域重投影 EMA，历史走统一池 `DenoiseHistoryPool`（`LumenScene_ProbeFilter.cpp`） |
| Radiance Cache | **不新写**，就是升级后的现有 DDGI：输入换成 Screen Probe 的 SH（`GI_DDGI.h:47-57`），帧序上有一帧延迟 |
| 组合约束 | `SDF × SurfaceCache` 已实现；`SDF × HitLighting` **非法**（配置期拒绝）；`HWRT × HitLighting` 与 `Screen × 任意` 合法但**首版未实现**（显式报错，不静默回落） |
| 覆盖范围 | Mesh 场：101 个 mesh 全建（2 个因三角形数超限跳过）；Global SDF 仅 2 层 × 128³（设计写 512³ → 4×256³） |
| 成色 | SDF / Surface Cache / Screen Probe / 远场混合各有可断言读数（白炉 √π 相对偏差 4.0e-6、逐光线 SDF/三角形对照、分类不变量违例 0）；**1080p/60fps 未达成且工作暂停**，瓶颈在 CPU 侧而非 Lumen 本体 |
| 最硬的三条已知缺口 | ① 无 screen trace（两套表示的偏差没有兜底层）；② 无 Hit Lighting（镜面只能读卡片）；③ Surface Cache 页命中率长期在 10~16% 量级，"材质有内容"是主要瓶颈而不是容量 |

## 2. 在 GI 体系中的位置与数据流

### 2.1 Lumen 是一个 `IGIProvider`

`LumenProvider` 实现 `IGIProvider`（`LumenProvider.h:28`），注册进 `DeferredPipeline::m_GIProviders`（`DeferredPipeline.cpp:214-223`）：`LumenScene` 先 `Initialize`，再建 Provider、`SetScene` / `SetMeshBatcher`，最后 `push_back`。生命周期回调由 `DeferredPipeline::Shutdown`（`DeferredPipeline.cpp:537-544`）与 `OnResize`（`:687-691`）遍历 `m_GIProviders` 转调 —— 这正是《设计与实现》§12"架构前置"里那条（原先两处都不遍历）。

四条接口选择值得记下来：

- `GetSourceId()` 返回 `GISourceId::Lumen`；`Handles(id)` 只认自己（`LumenProvider.h:35-38`）。
- `GetPassKind()` 是 `GIPassKind::Offscreen`（`LumenProvider.h:39`）—— 它的主 pass 要在一个 offscreen render pass 里把结果**当颜色附件**写出去。
- `ProducedThisFrame()` 返回 `m_InStack`，由 `SyncToStack` 按层栈写入（`LumenProvider.h:47,53-55`）。**不能**用 `IsValid()` 当"本帧是否产出"的判据：Lumen 没进任何层栈时 `IsValid()` 也恒真，会让转储落到上一帧/未使用的纹理上，也会让降噪信号登记报一条没跑的源（`LumenProvider.h:44-47,279`；《设计与实现》§附四十二 ⑤）。
- `GetDiffuseOutput()` 与 `GetSpecularOutput()` 返回**同一张** `m_Scene->GetOutput()`（`LumenProvider.h:61-62`）。这正是帧图必须**按 Provider 而不是按 source id** 遍历的原因：能力位同时给了两个通道，按 id 分派会被两条循环各跑一遍（`DeferredPipeline_FrameGraph.cpp:919-922`）。

`NeedsRadianceHistory()` 保持 `false`（`LumenProvider.h:58`）：Screen Probe 的 miss 回退本可以用共享的前帧 HDR 辐射度，但骨架阶段不消费，声明为真会让 `CaptureRadiance` 白捕获一次。

### 2.2 一帧内的 stage 顺序

Lumen 的内部步骤全部录制在**一个**名为 `Lumen_SDF_Build` 的 compute pass 里（`DeferredPipeline_FrameGraph.cpp:966-1102`）。之所以是独立 compute pass 而不是塞进主 offscreen pass：Vulkan 不允许在 render pass 内 dispatch compute（`LumenProvider.h:111-113`、`DeferredPipeline_FrameGraph.cpp:955-958`）。

顺序（括号内是录制点行号）：

```
Lumen_SDF_Build (compute, 966)
 TransitionStorageImagesOnce 自持存储图像布局首帧转换            (990)
 StepSDF                     mesh 场构建 / clipmap 注入 + 洪泛      (991)
 StepSurfaceCache            页表推进 + GPU 镜像校验              (995)
 RunCardCapture              按预算捕获卡片写 atlas               (997)
 RunFeedback                 16×16 分块 → 请求 → 排序 → 置 Requested (999)
 RunProbePlacement           16×16 单元 → 探针（2×2 合并）        (1003)
 RunProbeTrace               半球光线 + SDF march                 (1005)
 RunFarFieldRT               同一条光线的硬件光追 + 对照 + 合并     (1012)
 RunSurfaceCacheShading      命中点从 atlas 取材质                (1015)
 RunScreenProbeSHProject     4 系数 × RGB 写回探针                (1018)
 RunProbeFilter              3×3 单元 YCoCg AABB + 时域 EMA        (1024)
 RunProbeIrradiance          逐像素辐照度（读过滤后探针）           (1027)
 RunSDFDebug                 逐像素 SDF 追踪可视化（默认开）        (1034)
Lumen（主 pass，offscreen, 1110）
 PreBind + DrawIrradiance    把辐照度纹理贴到 Provider 输出        (1119-1125)
Lighting (1346)
 in.lumenTex（binding 32）   本帧没产出则传 nullptr，回绑黑色占位    (1428-1431)
```

远场合并**必须夹在"追踪"与"着色"之间**：合并写回的命中点就是步骤 22 的输入，放到着色之后再跑等于白跑（写回的值会在下一帧被追踪覆盖，`DeferredPipeline_FrameGraph.cpp:1007-1009`）。探针滤波**必须夹在 SH 投影与逐像素辐照度之间**：后者读的是过滤后的探针缓冲（`:1020-1023`）。

三个"必须先于 Lumen"的前置，都在帧图里显式处理过：

1. **`MeshBatcher` 的 CPU 侧合并几何**：SDF 构建的输入，门控条件是漫反射或镜面层栈里含 Lumen（`DeferredPipeline_FrameGraph.cpp:104-115`）。
2. **`AS_Build`（TLAS）**：Lumen 的远场硬件光追**不属于** `AnyRTSource()`，也不是 DDGI。注册条件里专门加了 `lumenFarWanted = m_GIConfig.diffuse.Has(GISourceId::Lumen)`（`:665-670`）—— 不加这一项时 TLAS 为空，远场一条都命中不了（注释记的实测：RT 命中率 0.0% 而 SDF 命中率 93.8%）。
3. **DDGI 段**：注册在 Lumen 段**之前**，且它读的正是 Lumen 的探针缓冲（`:726-756`）。这既是"输入换成 Screen Probe"的落地位置，也造成了第 8 节要讲的一帧延迟。

Lumen 用的是帧图里的**第 8 条按 Provider 的循环**（`:917`），与前面 7 条按 source id 的循环不同。这是《设计与实现》§11 记的"逃生口"（新增源先用自己的循环接入，pass 仍只注册一次）在代码里的样子。

计时下标（`DeferredPipeline_FrameGraph.cpp:50-55`）：Lumen 计算 pass 整体 = 29、SDF 构建 = 25、页表+捕获+反馈 = 26、探针+追踪+着色+SH+辐照度 = 27、SDF 调试视图 = 28、远场光追 = 30（取 30 是为了不影响 Provider 的 0..10 读数）。

### 2.3 数据流总图

```
GBuffer(Normal / WorldPos / Albedo / Depth)
  ├─→ Screen Probe 布置（16×16 单元 → 探针 + 单元映射）→ 半球追踪（traceRep 条/探针）
  ├─→ Mesh SDF(128³/mesh, R16F) → 注入 → Global SDF clipmap(2×128³, 近层随相机)
  │        └─ 两层取 min 的 sphere tracing（eps = 0.1 近层体素 ≈ 2.1 世界单位）
  ├─→ Card 捕获（沿卡轴定步长 march + 投影采 GBuffer）→ atlas(3×512² RGBA16F)
  │
  └─ 命中点（近场 SDF / 远场硬件光追，重叠带 [t0,t1] smoothstep 混“材质”而非位置）
        → 命中点着色（卡 → 逻辑页 → 物理页 → atlas albedo；缺页返回 0.18）
        → SH 投影（4 系数 × RGB；白炉 l0 = √π 可断言）
        → 空间 YCoCg AABB + 时域重投影 EMA（历史走 DenoiseHistoryPool）
        → 逐像素辐照度 E(n) × albedo/π → Provider 输出 → Lighting (binding 32)
        → （上一帧的过滤后探针缓冲）→ DDGI 探针 SH
```

## 3. Mesh SDF 与 Global SDF

### 3.1 两级 SDF 的设计位置

`LumenSDF` 只负责第一层"每个 mesh 一张距离场"，全局层是它的下游（`LumenSDF.h:6-7`）。几何取自 `MeshBatcher` 的**未施加变换的合并顶点/索引**，配合 `GetDrawCommands()` 的 `(firstIndex, vertexOffset)` 切出每个 mesh 的三角形区间；每个场是**该 mesh 局部空间**的立方 AABB，与世界变换解耦（变换在 traced 阶段由实例数据提供）（`LumenSDF.h:9-12`）。首版两处刻意限制写在头注释里：分辨率与三角形数上限，超限的 mesh 不建场、回落到 Global SDF 覆盖（`LumenSDF.h:14-18`）。

### 3.2 Mesh SDF 的构建（scatter，不是 gather）

`LumenSDFConfig` 的实现默认值（`LumenSDF.h:34-56`）：分辨率 **128³**、`maxMeshes` **128**、`maxTrisPerMesh` **20000**、`meshesPerFrame` **4**。一段构建（`BakeOne`，`LumenSDF.cpp:355-473`）分四步：

| 步 | 做什么 | 位置 |
|---|---|---|
| ① 清空 | u32 距离场线性写成 `+inf`，dispatch = `ceil(res³/64)` | `LumenSDF.cpp:395-404` |
| ② scatter | **一个三角形一个线程组**，只扫自己的 AABB，`InterlockedMin` 写 `asuint(d)` | `LumenSDF.cpp:406-412` |
| ②b 洪泛 | **带种子坐标的 JFA（向量距离变换）**：先立种子，再按 `res/2 … 1` 逐级松弛，**每级 2 趟** | `LumenSDF.cpp:414-452` |
| ③ 转换 | u32 → **R16F** 场 + 写自检探针（用该 mesh 专属的描述符集） | `LumenSDF.cpp:454-473` |

三处刻意的取舍：

- **R16F 而不是 R32F**：每个 128³ 场 4.2 MB，近表面值在 fp16 下仍有约 0.01 单位分辨率，而追踪关心的正是这一段（`LumenSDF.cpp:364-365`、`LumenSDF.h:38-40`）。
- **每 mesh 一套描述符集**：注入要在同一提交里对多个 mesh 场各 dispatch 一次，共用一套描述符集会全部看到最后一次写入（描述符集别名），实测全局场因此在空旷处恒为 0（`LumenSDF.cpp:454-461`、`:668-673`）。
- **每级多趟（2 趟）**：就地竞争写的跳步洪泛靠"重复松弛到不动点"收敛，2 趟时 mesh 场在空旷处是 0/常数，全局场会被毒化（`LumenSDF.cpp:438-440`）。

向量距离变换（种子坐标 + **种子自己的距离**）是 mesh 场远场精度的分水岭：最大误差 **201.18 → 1.33 世界单位**（该 mesh 体素 21.8，即 0.06 体素），远场超差 28/63 → 0/63（《设计与实现》§附十四，第 2414-2444 行）。

构建按预算逐帧推进：`Phase::Baking` 每帧最多 `meshesPerFrame` 个（`LumenSDF.cpp:840-851`）；其余阶段是 `WaitSelfCheck → GlobalBuild → WaitGlobalCheck → March → WaitMarchCheck → Done` 的状态机（`LumenSDF.h:290`），每处回读都等 **3 帧**飞行帧（`LumenSDF.cpp:855-888`）。

自检探针针对 **AABB 最大**的 mesh（`LumenSDF.h:285-287`）—— 注释写明理由：只查 mesh 0（小网格）会把问题漏掉，实测全局层在探针处为 0 而该点真实距离 894。

### 3.3 Global SDF（clipmap）

`SetupGlobalGrid`（`LumenSDF.cpp:565-640`）按场景并集 AABB 定层：

- `sceneSide = max(ext) × 1.05`，`res = m_Config.globalResolution`（默认 **128**）；
- 层数 `globalLayers`（默认 **2**），**实际最外层**覆盖全场，更小的 L 是更细的近层：`layerSide = sceneSide × nearFraction^(stepsFromFar)`，`nearFraction` 默认 **0.50**（`LumenSDF.h:45-46,51`、`LumenSDF.cpp:589-592`）。用 `m_GlobalLayerCount` 而不是常量 `kMaxGlobalLayers` 是关键：用常量会让"只开 1 层"时唯一那层退化成近层（只覆盖场景中心 1/4 边长），几何大多落在场外 —— 实测 256/256 条验证射线起点都在场外，14 条"穿漏"全由此产生（`LumenSDF.cpp:586-588`）。
- **近层跟随相机**：`stepsFromFar > 0` 且相机位置已给定时，层中心取 `floor(camPos / voxel) × voxel`（取整到体素格，相机微动时内容不抖动）；以场景中心为心时，910 单位的盒子几乎覆盖不到任何几何 —— 实测 256/256 条自检射线都在盒外（`LumenSDF.cpp:593-603`）。相机位置由 `LumenProvider::StepSDF` 每帧传入，且必须在第一次 `Step` 之前给出（`LumenScene.h:82-86`、`LumenProvider.h:117-125`）。
- 每层三张 128³ 纹理：`R32_UINT scratch` + `R32_FLOAT field` + `R32_UINT seed`，日志文案记作 16.00 MB/层（`LumenSDF.cpp:609-617,634-638`）。

远层洪泛复用既有 `SDF_MeshFlood`（"每跳加步长"版，管线布局必须换成全局描述符集布局，否则崩 —— `LumenSDF.cpp:508-514`），因此全局层仍带约 8% 的图测地偏差；实际影响被 march 的 eps 盖住（见 5.2）。把向量距离变换用到全局两层是 §附十四 结尾明确留的后续项。

### 3.4 卡片生成（Surface Cache 的输入）

`BuildCards()` 是 **CPU 版**：复用自检已经准备好的顶点/索引副本，不引入新 GPU 资源（`LumenSDF.h:231-232`）。逐 mesh × **6 个轴向**把三角形投影成 2D 网格，texel 世界边长按 `cardTexelWorld = 4.0` 逐 mesh 自适应，分辨率夹在 **[64, 512]**（`LumenSDF.cpp:2043-2060`、`LumenSDF.h:48-49`）。保留判据是"一张卡至少 `cardMinFill = 0.25` 比例的 texel 落在表面上"（`LumenSDF.h:50`、`LumenSDF.cpp:2213`）。

覆盖率结论由一次面积加权采样（《设计与实现》§附十九 记录为 **418,329** 个表面点）算出，CPU 侧对同一批采样换阈值即可得到整条"阈值 ↔ 卡片数 / 覆盖率"曲线。1080p 实测：阈值 5% → 410 张卡 / 覆盖 89.7%；**25%（当前默认）→ 228 张 / 79.1%**；50% → 66 张 / 54.2%。残余 0% 的三个 mesh 都是薄结构（投影填充率天然很低）（《设计与实现》§附十九，第 2583-2598 行）。

### 3.5 SDF 调试视图（每帧都在跑）

`RunSDFDebug` 逐像素发射主射线做 sphere tracing，输出 RGBA16F 调试纹理（R = 命中层、G = t/最大距离、B = 步数比、A = 是否命中，`LumenSDF.h:163`）。它**默认开启**，实测稳态 **1.67 ms**，是 Lumen 计算 pass（4.9 ms）的 **34%**；关掉不影响画面（它不是 GI 输出，没有任何 pass 采样它），需要转储时用 `HE_LUMEN_SDF_DISABLE_DEBUG=1` 关（`LumenScene.h:92-101`、`LumenScene.cpp:24-30`）。默认保持开启的理由写在代码里：转储 `lumen_sdf_trace` 是既有验收凭据，改成"显式关"两边都不受影响（`LumenScene.cpp:26-27`）。

## 4. Surface Cache

### 4.1 页 = 卡片

`BuildPageTable()`（`LumenScene_SurfaceCache.cpp:65-113`）：

- **一张卡一页**。逻辑页数 = `min(卡片数, 1024)`（对应设计里的"1024 页上限"，`:71-76`）；
- 物理页 = atlas 的 `8×8 = 64` 块（`LumenScene.h:255-257`、`LumenScene_SurfaceCache.cpp:77`）；
- atlas 是 **3 张 512×512 RGBA16F**（albedo / normal / emissive），每张 8×8 页、每页 **64×64 texel**（`LumenScene.h:255-257`、`LumenScene_SurfaceCache.cpp:287-297`）。emissive 目前只写 alpha 有效位（`SurfaceCache_Capture.comp.slang:124`）；
- 前 **24 页**走一遍六态演示（保住六态齐全 + GPU 镜像校验的样本），**其余页留 `Invalid`**，交给真实的"反馈请求 → 分配 → 捕获 → LRU 淘汰"回路（`LumenScene_SurfaceCache.cpp:82-97`）。这条修正是必要的：此前所有页都走演示生命周期 ⇒ 没有任何页是 `Invalid`，而 `Request()` 只能从 `Invalid` 迁移 ⇒ 反馈回路彻底失效，全场景只捕获 53 页、页命中率 0.6%（注释 `:84-86`；《设计与实现》§附二十九，第 2916-2921 行）。

**与设计不一致的一处必须标清楚**：《设计与实现》§4（第 120-133 行）写的是"页面 128×128 texel、1024 页、3D Clipmap 世界空间对齐、虚拟分辨率 4096² → 8192²"。实现是 **64×64 texel/页 × 64 物理页、按卡片轴向投影组织（不是 3D clipmap）、每张卡一页**。显存也因此从预算的 402 MB 降到实测 **6.00 MB**（《设计与实现》§附三十六，第 3409 行、§15.3 第 1003 行）。

### 4.2 六态页状态机

状态与布局在 `Lumen/SurfaceCache.slang` 里与 C++ **共享一份定义**：六态常量 `:25-31`、`SurfaceCachePageEntry`（**32 B**，8 × u32）`:34-43`、`SurfaceCacheRequest`（16 B）`:46-51`。合法迁移链：

$$\text{Invalid} \to \text{Requested} \to \text{Allocating} \to \text{Capturing} \to \text{Captured} \to \text{Dirty} \to \text{Capturing}$$

并且**任何状态 → `Invalid` 都合法**（释放/淘汰是通用兜底，`SurfaceCacheTypes.cpp:23-34`）。唯一迁移入口是 `Transition()`：非法迁移 `HE_CORE_ERROR` + `HE_ASSERT`，Release 下**拒绝且不改状态**（`SurfaceCacheTypes.cpp:48-63`）—— "表永远不会进入非法状态"比"悄悄改坏"安全（`SurfaceCacheTypes.h:16-17`）。

两侧布局由 6 条 `static_assert` 在**编译期**钉死（大小 32 B + 6 个字段偏移，`SurfaceCacheTypes.cpp:138-145`），运行期另有一道 GPU 回读交叉验证：`SurfaceCache_PageCheck.comp.slang` 算 32 位 FNV-1a 校验和（字段位置也参与混合），与 CPU 侧同一公式比对（`SurfaceCacheTypes.cpp:120-135`、`LumenScene_SurfaceCache.cpp:218-240`）。不用 64 位是因为引擎没开 `shaderInt64`，64 位版 shader 会拿到 "Capability Int64 declared but not enabled" 而回读恒 0（`SurfaceCacheTypes.cpp:123-125`）。校验 pass 前 4 帧不派发、再等 3 帧读回，并有一处平台坑记在注释里：**描述符集必须在 `Initialize` 时分配**，帧中途 `AllocateDescriptorSet` 拿到的集合实测写不进（`LumenScene_SurfaceCache.cpp:213-218`）。

### 4.3 捕获：不是三角形光栅化，是"沿卡轴 march 一次可见性查询"

这是本引擎与 UE 的 Card Capture 最不一样的一处。`SurfaceCache_Capture.comp.slang`（`numthreads(16,16,1)`，`:68`）一次 dispatch 捕获**一张卡**：

1. texel 中心的世界坐标 = `planeOrigin + planeStepU*lx + planeStepV*ly`，再沿 `axis` 做**定步长 march**，用全局 SDF（近层/远层取 min）找该轴上第一个表面点（`SurfaceCache_Capture.comp.slang:87-98`）；
2. 命中点投影到屏幕 → 采 **GBuffer 的 albedo / normal**（`:100-121`）；存在性判据是 GBuffer 该像素深度落在 `(0,1)` 内（`:112-114`）；
3. 写进三张 atlas 的对应页；未命中、相机后方、GBuffer 无几何的 texel 一律写 `alpha = 0`（`= 该 texel 缺内容`）（`:122-124`）。

**为什么用 GBuffer 当材质源**：本步的验收是"atlas 可视化与场景材质一致"，GBuffer 里就是本帧的真实材质；卡片捕获本质是"对每条轴做一次可见性查询"，命中点在本帧可见就能取到正确材质。代价是明确的：**只有本帧屏幕可见的表面能取到材质**（`SurfaceCache_Capture.comp.slang:8-13`）。完整版会把材质换成 bindless 逐材质求值以使 atlas 独立于屏幕 —— 这是第 10 节的一条边界。

**定步长而非 sphere tracing** 的理由也写在头注释里：这里只要"这条轴上的第一个表面"，固定步长实现简单、步数天然有界（AABB 厚度 / 步长），命中判据仍是 $|d| < \mathrm{eps}$（`SurfaceCache_Capture.comp.slang:15-16`）。`eps` 必须大于"场的误差"：`eps = max(1.0 × 近层体素, 0.5 × card.texelWorld × stride)`，`step = max(0.5 × eps, 1.0)`，步数 = `ceil((side + 2) / step)`（`LumenScene_SurfaceCache.cpp:416-418`）。注释里记了这条的来历：此前步长 21.6 > eps 10.9 且 eps 只按卡 texel 算，**20480 个 texel 一个都没命中**（`:397-399`）。

push constant 的 128 B 上限在这里是一条硬边界：捕获的每帧常量（VP 矩阵 / 屏幕 / 两层原点与分辨率）改走 StructuredBuffer（binding 10），push constant 只留 96 B（`LumenScene_SurfaceCache.cpp:265-271`、`SurfaceCache_Capture.comp.slang:27-45`）。此前放 15 个 float4（240 B）被截断，实测 origin 收到 NaN、voxel 收到 0 ⇒ `SampleLayer` 的 `inside` 恒 false ⇒ march 一个都不命中（`LumenScene_SurfaceCache.cpp:268-270`；《设计与实现》§附二十二）。

捕获后有一条**永久护栏**：把 push constant 回报的 `origin.x` / `voxel` 与 CPU 侧比对，对不上就报 ERROR（`LumenScene_SurfaceCache.cpp:485-492`）。

### 4.4 三段预算与跨帧摊销

三个显式预算（`LumenScene.h:258-275`）：

| 预算 | 默认 | 含义 |
|---|---|---|
| `m_BudgetCaptures` | 8 | 本帧最多真正捕获几页 |
| `m_BudgetAllocations` | 8 | 本帧最多分配几个物理页 |
| `m_BudgetFeedbackPages` | 256 | 本帧最多采纳多少条反馈请求 |

三者分开是为了让"卡顿尖峰"没有来源：任何一帧的工作量都被这三个数夹住（`LumenScene.h:259-261`）。`RunCardCapture` 里分三段推进（`LumenScene_SurfaceCache.cpp:356-367`）：先按**分配预算**把 `Requested → Allocating`，再按**捕获预算**把 `Allocating → Capturing`，然后逐页真正捕获 `Capturing → Captured`。没做完的留在原状态，下一帧继续（不回退、不丢弃）。`m_MaxCapturesInAFrame` 专门用来做"无尖峰"检查（应恒 ≤ 预算，`:471`）；前 12 帧逐帧打印捕获量作为直接证据（`:473-476`）。

设计口径与实测一致：预算 8/8/256 时 2 帧收敛，预算减半到 4/4/128 时 4 帧收敛，而任何一帧的捕获量都 ≤ 预算（《设计与实现》§附二十四，第 2753-2766 行）。

### 4.5 LRU 与页池

`AllocatePhysicalPage`（`LumenScene_SurfaceCache.cpp:126-158`）：池空时淘汰"**最久未用且内容有效**"（`Captured`/`Dirty`）的逻辑页，**绝不动正在流水线里的页**（`Requested`/`Allocating`/`Capturing`）。固定池 + 固定页大小（64×64）⇒ 任意时刻每个物理页要么属于某个逻辑页、要么空闲，**不存在碎片**；分配不到一律由 LRU 回收解决（`:118-125`）。真正的 defrag（页块搬移）在没有变长页之前没有收益，列为后续项（《设计与实现》§附二十五，第 2789-2792 行）。

实测（合成漫游，逼出淘汰路径）：页状态 `Captured 64`、物理页 0/64 空闲、**分配成功 343 → 424 → 486、失败恒 0、淘汰 279 → 360 → 422 次**，单帧捕获量恒 = 预算 8（《设计与实现》§附二十五，第 2781-2787 行）。

### 4.6 Feedback：16×16 分块 → 请求 → 排序 → 去重

`SurfaceCache_Feedback.comp.slang`（`numthreads(8,8,1)`）：屏幕按 **16×16 像素**分块，每块取中心像素的世界坐标，找"**包含它的最小 AABB**"那张卡 → 页；$w = 256 \times \mathrm{importance} \times \mathrm{falloff}$，其中 $\mathrm{falloff} = 1/(1 + dist/\mathrm{scale})$（`:62-65`）。`importance` 由 C++ 侧按 `max(0.01, fill × sqrt(side))` 预计算（`LumenScene_SurfaceCache.cpp:1100-1102`）。用"卡 AABB 包含测试"当页映射的理由：步骤 13 的卡片清单本身就是一个足够好的空间索引，加一条"取包含它的最小 AABB"的规则可避免大网格的粗卡把细卡盖掉（`SurfaceCache_Feedback.comp.slang:8-11`）。

两个刻意的设计：

- **每块写自己的槽位，不用原子计数器**（`SurfaceCache_Feedback.comp.slang:67-72`）。注释记了两条理由：非原子版会互相覆盖（实测整屏只剩 1 条）；即使改成原子，"哪些块进得了列表"也会取决于线程完成顺序 ⇒ 请求集合逐帧乱跳，稳定性验收无从谈起。槽位数上限 `kMaxFeedbackTiles = 16384`（= 512×512 屏幕的 16×16 块数；1080p 只需 8160，`LumenScene.h:306`）。
- **C++ 侧排序后必须按页去重**（`LumenScene_SurfaceCache.cpp:1191-1209`）。反馈是逐块产出的，同一张卡会被成百上千个块请求到；直接取排序后的前 N 条 ⇒ 前 64 条**全是同一页**（近处那张大卡），"采纳 top-64"实际只请求到 **1** 页（实测分配成功 25 = 24 个演示页 + 1）。改成"权重最高的前 N 个**不同页**"后请求才铺开。`topN` 同时受物理页数约束（常驻集不可能大于 atlas 页数，否则"分配 → 立刻被 LRU 淘汰 → 下一帧再请求"空转）。

排序本身是**确定性**的：权重降序，权重相同按页号定序（`:1186-1188`）。请求缓冲是**双缓冲**（`kFeedbackSlots = 2`，`LumenScene.h:307-315`）：GPU 写第 N 帧的槽位，CPU 同时读第 N-1 帧的槽位 —— 单缓冲时 CPU 在 GPU 正在写它的时候逐元素读，读到的内容取决于 GPU 写到哪了（实测同一配置两次运行请求数 8103/8115 不同），是**数据竞争**（`LumenScene.h:308-310`）。

统计与环境变量的读回遵循一条统一节拍：**先读上一帧、再清零本帧**。凡是"GPU 原子计数 + 每帧清零"的路径都按这个顺序写，否则读到的一定是 0（`LumenScene_SurfaceCache.cpp:1151-1153,1271`、`LumenScene_SurfaceCache.cpp:998-1005`、`LumenScene_Irradiance.cpp:129-147`）。

### 4.7 命中点着色（消费 atlas）

`RunSurfaceCacheShading`（`LumenScene_SurfaceCache.cpp:546-753`）+ `Lumen_SurfaceCacheSample.comp.slang`：

- 命中点 → 包含它的最小 AABB 卡 → 逻辑页 → 页表里的物理页；
- 页状态必须是 `Captured`/`Dirty` **且 atlas 该 texel 的 alpha > 0** 才算"页命中"；
- 否则写**中性值 0.18**（`pc.atlas = float4(kAtlasPageRes, kAtlasSize, 0.18f, ...)`，`LumenScene_SurfaceCache.cpp:746`）并把 `w` 置 0。**缺页不能返回黑** —— 那会在画面上留黑斑，中性值 + 标记交给反馈去补页（`Lumen_SurfaceCacheSample.comp.slang:5-6`；《设计与实现》§附二十九 第 2900-2902 行）；
- 同时把同一表面的 GBuffer albedo 写进另一个缓冲做对照，判据是"GBuffer 世界坐标与命中点距离 ≤ 0.3% 视距"，容差随视距缩放（否则会把相距十几单位的不同表面判成同一表面；《设计与实现》§附二十九 第 2906-2912 行）；
- 统计槽 14 = "命中但着色源未实现（返回中性值）"，把 `HitLighting` 的未实现状态变成可计数事实（`Lumen_SurfaceCacheSample.comp.slang:129-130`、`LumenScene_SurfaceCache.cpp:699,743-746`）。

对照回读**只在要打印的那一帧**做（每 40 帧一次）：逐条扫 4 万条 × 3 个 16 MB 缓冲是纯诊断开销（`LumenScene_SurfaceCache.cpp:662-666`）。

页命中率的实测演化（同一 1080p 场景）：步骤 22 初版 **8.1%**（基于 `eps = 1 体素` 的假命中点），`eps` 收到几何量级后 **15.5%**（《设计与实现》§附三十三，第 3204-3206 行）。这条说明"页命中率低"里有一大块不是页表的问题，而是命中点本身不在真实表面上。

atlas 自身的内容率也能直接读：有效 texel **23764/262144（9.1%）**，atlas / GBuffer 中位亮度之比 1.11（《设计与实现》§附二十六，第 2800-2802 行）—— 只有本帧可见的表面能取到材质，这条边界在 §附二十二 已记录。

## 5. Screen Probe gather（探针布置 + 半球追踪）

### 5.1 布置与 2×2 自适应合并

单元 = **16×16 像素**，合并单位 = **32×32 tile**（2×2 单元）（`ScreenProbe.slang:41-42`、`ScreenProbe_Gather.comp.slang:47-53`）：

- 每个单元用 **4 点采样**（偏移 4、步长 8）算平均法线与平均世界坐标（`ScreenProbe_Gather.comp.slang:29-45`）；
- 合并条件：**4 个单元都有几何** 且 `worstCos >= mergeParams.x`（`:90-91`）。合并成一个探针时位置取 4 单元均值、`meta.x = 4`；否则每个有效单元各 1 个、`meta.x = 1`（`:92-124`）；
- 阈值默认 **`m_MergeNormalCos = 0.995`**（`LumenScene.h:324`），由 push constant 的 `mergeParams = float4(0.995, 16.0, 0, 0)` 传入（`LumenScene_SurfaceCache.cpp:1041`）。`ScreenProbe.slang` 里另有两条共享常量：`kScreenProbeCellSize = 16`、`kScreenProbeMaxMerge = 4`（`:41-42`）；
- 布置 pass 顺手写出"**16×16 单元 → 探针下标**"映射（`u_CellProbe`，`0xFFFFFFFF` = 无）。合成端按像素查探针；若在片元里遍历上万探针找最近，代价无法接受（`ScreenProbe_Gather.comp.slang:17-19`）；
- 每个 tile 的**最大法线偏差**写进 `u_TileDev`，使 CPU 能在**同一次运行**里算出整条"阈值 → 探针数"曲线（`:7-9`；CPU 侧 `probesAt` 在 `LumenScene_SurfaceCache.cpp:1007-1030`）。

探针容量 `kMaxScreenProbes = 65536`（`LumenScene.h:323`），槽位由 `InterlockedAdd` 原子分配（`ScreenProbe_Gather.comp.slang:94`）。**这件事有个必须写下来的后果**：同一个探针两次运行可能落在不同 slot，所以随机流必须按"探针身份"（`meta.y*4 + meta.w`）而不是"槽位下标"编号，否则"位置 ↔ 方向"的配对每次运行都会变（`ScreenProbe_Trace.comp.slang:60-65`，注释记的实测：背靠背 98.6% 像素不同）。

1080p 实测：tile 总数 **2040**，阈值 cos 0.995 ⇒ **探针 5649**（平坦 tile 占 41.0%）；曲线 `0.999 → 6534 / 0.995 → 5649 / 0.99 → 5169 / 0.98 → 4548 / 0.95 → 3690 / 0.90 → 3144`，单调不增，且 GPU 原子计数与 CPU 用偏差缓冲算的同阈值结果完全一致（《设计与实现》§附二十七，第 2843-2853 行）。单元数 8160（= 120×68）⇒ 最严格阈值下 6534 个探针，与设计 §6 的"1080p ≈ 8K 探针"同量级。

探针缓冲按容量分配（65536 × 96 B = 7.00 MB，实测用量 5649 个）（《设计与实现》§15.3 第 1023 行、§附三十六 第 3414 行）。

### 5.2 半球追踪（SDF sphere tracing）

`ScreenProbe_Trace.comp.slang`（`numthreads(64,1,1)`），每 (探针, 光线) 一个线程：

- 射线数 = `m_ProbeCount × traceRep`，`traceRep` 默认 **8**（合法区间 [8,16]，`LumenTraceConfig.h:36-40`），dispatch = `ceil(total/64)`（`LumenScene_SurfaceCache.cpp:877,903`）；
- 方向：步骤 23 起默认 **均匀半球**（`kSampleModeUniformHemisphere`，`LumenScene.h:38-41`、`LumenScene_SurfaceCache.cpp:887`），由 `ScreenProbeSampling.slang` 的 `SampleUniformHemisphere` 给出（pdf = 1/(2π)，`:43-51`）。GGX 半向量采样（mode 0）保留为步骤 21 的原样行为；
- 随机数：`ProbeRayRandom(probeKey × traceRep + rayIndex, frameSeed)`，与投影 pass **共用同一个头文件**，所以两侧必然拿到同一组方向（`ScreenProbeSampling.slang:53-57`；理由写在文件头 `:3-6`）。采样模式写在 push constant 里，保证"追踪用的方向"与"投影用的方向"只有一个来源（`LumenScene_SurfaceCache.cpp:885-887`）；
- 求交语义（`ScreenProbe_Trace.comp.slang:78-87`）：两层全局场**取 min**（`FieldValue`，`:38-43`；层外返回 `1e30`），安全步长 $t \mathrel{+}= \max(d \times 0.25,\ \mathrm{eps} \times 0.02)$，命中判据 `advanced && d < eps`（必须先走一步），并有 `maxSteps` 与 `maxDist` 两道闸；
- march 参数来自 SDF 配置：`maxSteps = m_SDF.GetMarchMaxSteps()`（默认 **384**）、`maxDist = m_SDF.GetMarchMaxDist()`（默认 **400**）、`eps = kProbeMarchEpsVoxels × 近层体素`（`LumenScene.h:469-470`、`LumenScene_SurfaceCache.cpp:897-898`）。设计 §5 写的是"最大步数 64、收敛阈值 0.1 体素"（《设计与实现》第 190 行），实现把步数放大到 384 —— 下界质量不足时步数会更费，这条已记在 `LumenSDF.h:54`。

**`eps` 是几何容差而不是体素尺度**，这是这条链路上最重要的一次修正（注释 `LumenScene_SurfaceCache.cpp:893-898`）：此前取 1 个近层体素（21.3 世界单位），march 在离真实表面最多一个体素处就判"命中"，于是**命中率 94% 全是假命中** —— 命中距离均值只有 **16.4** 单位，而硬件光追打到的真实表面在几十到几百单位外。改成 `0.1 个体素 ≈ 2.1` 单位后，SDF 命中率掉到 **17.9%**、命中距离均值升到 **55.97** 单位（这才是"贴着表面"的量级）（《设计与实现》§附三十三，第 3186-3196 行）。这也直接解释了为什么"近场 SDF + 远场 HW RT"不是优化，而是让这条链路成立的必要条件。

结果缓冲：每 (探针, 光线) 一条 `float4 (t, hit, dot(dir,n), 0)`，另有一条命中点缓冲 `float4(命中点, 是否命中)`（`ScreenProbe_Trace.comp.slang:18-20,89-90`），各按 `kMaxScreenProbes × 16` 条容量分配（`LumenScene_SurfaceCache.cpp:830-834`）。统计槽 3 = "半球内（`dot(dir,n) > 0`）光线数"，实测 **45192/45192 = 100%**（《设计与实现》§附二十八，第 2883-2887 行）—— 这是"采样方向确实指向场景"的必要条件。

命中点着色（4.7）之后，每 (探针, 光线) 得到一条辐射度值，进入 SH 投影。

## 6. SH 投影与探针滤波

### 6.1 二阶（4 系数）SH

探针结构 **96 B**（6 × 16 B）：位置 / 法线 / uv / `shR` / `shG` / `shB` / `meta`（`ScreenProbe.slang:30-39`）。**一次把步骤 23 要用的 SH 字段也定好**，避免后续每加字段就动一次 C++/Slang 镜像（`:3-5`）。`meta` 的四个字段：`x` = 合并了几个 16×16 单元（1/4）、`y` = 单元索引、`z` = 法线偏差（定点）、`w` = 保留（`ScreenProbe.slang:38`；`w` 在追踪里被当作探针身份的低位用，见 5.1）。

基函数与约定（`ScreenProbeSampling.slang:59-70`，C++ 镜像 `LumenSH.h:19-34`）：

$$Y_{00} = \frac{1}{2}\sqrt{\frac{1}{\pi}} \approx 0.2820948, \qquad Y_{1m} = \frac{1}{2}\sqrt{\frac{3}{\pi}}\,(y, z, x)$$

估计量（均匀半球，$\mathrm{pdf} = 1/(2\pi)$，`Lumen_ScreenProbe_SHProject.comp.slang:6-9,81-84`）：

$$l_i = \frac{1}{N}\sum_j \frac{L_j\, Y_i(d_j)}{\mathrm{pdf}} = \frac{2\pi}{N}\sum_j L_j\, Y_i(d_j)$$

辐照度重建（clamped cosine 卷积的解析系数 $\hat{A}_0 = \pi$、$\hat{A}_1 = 2\pi/3$，`LumenSH.h:36-43`、`ScreenProbeSampling.slang:72-79`）：

$$E(n) = \pi\, l_0\, Y_{00} + \frac{2\pi}{3}\bigl(l_1 Y_1(n) + l_2 Y_2(n) + l_3 Y_3(n)\bigr)$$

**为什么把采样从 GGX 换成均匀半球**（本步唯一一处取舍，《设计与实现》§附三十，第 2981-2986 行）：GGX 的 pdf 也能让估计量无偏，但白炉下 0 阶系数**没有解析值**（要除以 pdf 后求和，权重是 $\pi/\cos\theta$）。均匀半球下 $l_0 = 2\pi Y_{00} = \sqrt{\pi}$ **与采样方向、采样数完全无关** —— 于是"白炉下误差为 0"可以被数值钉死，而不是"看起来很小"。实测：`l0 = 1.7724609`，$\sqrt{\pi} = 1.7724539$，**相对偏差 4.0e-6**（float 累加量级）；白炉下有效光线 45192/45192 = 100%（《设计与实现》§附三十，第 2990-3002 行）。

C++ 侧 `LumenSH.h` 是 shader 的**逐位镜像**（含 PCG 与均匀半球采样，`LumenSH.h:45-86`），目的就是让"白炉 $l_0 = \sqrt{\pi}$"这条解析性质能被单测断言（`LumenSH.h:3-5`）。PCG 常数、`U01` 的 `0x00FFFFFF` 掩码、`ProbeRayRandom` 的两组乘数（3/7919/1 与 7/6271/5）、`BuildBasis` 的退化分支（`|n.z| < 0.999`）都与 shader 逐字一致（`LumenSH.h:46-86` vs `ScreenProbeSampling.slang:18-29,54-57`）。

白炉下 l0 的解析值直接写成常量 `kSHWhiteFurnaceL0 = 1.7724538509055159`（`LumenSH.h:23-24`），CPU 侧的回读换算也在 `LumenScene_SurfaceCache.cpp:1360-1362`：定点累加除 4096（l0 均值）与 65536（相对 √π 的平均绝对偏差）。

两个容易踩的语义点：

- **不在 SH 投影里按"页命中"再过滤一次光线**。步骤 22 对缺页已经返回中性值 0.18（不是黑），那正是它要继续往下的语义；若在投影里再按 `w > 0.5` 过滤，实测每条探针只剩 **0.9 条**有效光线（8 条里 0.9 条），SH 等于没积。改成只按"这条光线有没有打到几何"过滤后，有效光线回到 **93.7%**（`Lumen_ScreenProbe_SHProject.comp.slang:64-72`；《设计与实现》§附三十，第 3019-3022 行）。缺页率高的影响因此从"SH 全是零"降级为"高频细节被中性值抹平"。
- **随机种子必须与"当前躺在光线缓冲里的那批光线"一致**：投影用 `m_TraceFrame - 1`（追踪上一次实际派发时用的种子）。两边各自用自己的帧计数会越差越多（实测 trace 82 / sh 57，差 25 帧），于是投影积的是**另一组方向**（`LumenScene_SurfaceCache.cpp:1415-1420`）。

同一帧里还会用"逐光线求和"独立算一遍参考辐照度 $E_{\mathrm{ref}}(n) = (2\pi/N)\sum_j L_j \max(0, d_j \cdot n)$ 写进另一个缓冲，两者的差就是"SH 带限 + 有限采样"的误差，交给 CPU 侧统计（`Lumen_ScreenProbe_SHProject.comp.slang:11-13,78,91-93`）。白炉下实测平均相对差 **0.0912**（《设计与实现》§附三十；注释里写明 8 条光线下的 9.1% 是固有差，512 条时降到 < 5%）。

### 6.2 空间 + 时域滤波

`LumenScene_ProbeFilter.cpp` + `ScreenProbe_Filter.comp.slang`。**核**（`GetProbeFilterNote()` 的原文，`LumenScene_ProbeFilter.cpp:57-60`）：`"核 3x3 单元 YCoCg AABB + 时域重投影 EMA"`。

**空间级**：以**单元**（16×16 像素）为步长取 **3×3 邻域**（经"单元 → 探针"映射），对每个 SH 系数在 **YCoCg** 里算 $\mu$ 与 $\sigma$，构造

$$\mathrm{AABB} = [\mu - \gamma\sigma,\ \mu + \gamma\sigma]$$

把每个邻居**截断**到该区间后求平均（`ScreenProbe_Filter.comp.slang:117-182`）。在 YCoCg 里做的理由：Y 是亮度、Co/Cg 是色度，在 RGB 里逐通道截断会让色度噪声被亮度噪声掩盖而漏过去（`:7-10`）。合并在 2×2 单元上的探针会在邻域里被取到多次 ⇒ 等效于**按覆盖面积加权**（《设计与实现》§附四十二 ①，第 3719-3721 行）。邻域全空时退化成"只用自己"，不制造黑（`ScreenProbe_Filter.comp.slang:134`）。

**时域级**：把探针世界位置用**上一帧** viewProj 投回上一帧屏幕 → 上一帧单元 → 上一帧探针；门限是**位置差 ≤ 容差**（容差 $= \mathrm{params.w} \times \mathrm{clip.w}$，透视投影下 `clip.w` 就是视图深度）**且** $\mathrm{dot}(n, n_{\mathrm{hist}}) \ge 0.9$；历史值**也截断到同一个 AABB** 后做

$$\mathrm{out} = \mathrm{lerp}\bigl(\mathrm{spatial},\ \mathrm{clamp}(\mathrm{hist})\bigr)$$

（`ScreenProbe_Filter.comp.slang:184-218`）。不截断历史，相机一动 AABB 就变，旧值会被"拖"进来（拖影，`:12-15`）。α 被夹在 $[0, 0.98]$（`:201`）。

参数与模式（`LumenScene.h:392-395`、`LumenScene_ProbeFilter.cpp:110-119`）：

| 项 | 默认 | 环境变量 |
|---|---|---|
| 模式 | 2（空间 + 时域） | `HE_LUMEN_PROBE_FILTER` = `off` / `spatial` / `full` / `keepmean` |
| $\gamma$（AABB 宽度） | 1.0 | `HE_LUMEN_PROBE_FILTER_GAMMA` |
| $\alpha$（时域历史权重） | 0.9 | `HE_LUMEN_PROBE_FILTER_ALPHA` |
| 重投影位置容差 | 0.02（占视图深度比例） | — |

**读写分离 + 历史乒乓**是硬要求：3×3 邻域互相重叠，就地读写的结果取决于线程调度顺序；时域级要在同一次 dispatch 里"读上一帧的探针 j、写本帧的探针 i"，$i \ne j$ 一般成立但同块缓冲既读又写仍是竞态（`LumenScene_ProbeFilter.cpp:9-14`）。结果写进**独立的** `m_ProbeFilteredBuf`（96 B/探针），**下游只读这一份**（`LumenScene.h:131-132`；辐照度 pass 的绑定在 `LumenScene_Irradiance.cpp:101-104`，DDGI 的取用在 `LumenProvider.h:206-210`）。

历史是两份探针镜像（**80 B/探针**，不含 uv/meta）+ 两份单元映射，全部从统一池 `DenoiseHistoryPool` 取（名字 `Lumen_ProbeHistory%u` / `Lumen_CellProbeHistory%u`），池没给才退回自建（`LumenScene_ProbeFilter.cpp:126-146`；池的注入点在 `DeferredPipeline.cpp:283-291`，且必须在池拿到 device **之后** —— 早于那一行 `AcquireBuffer` 只会返回 nullptr）。线程数取 $\max(N_{\mathrm{probe}},\ N_{\mathrm{cell}})$（探针数与单元数取大）：每个单元一个线程把当帧映射抄进历史缓冲，按探针抄会漏掉 3 个单元，那些单元下一帧会拿到两帧前的旧下标（`LumenScene_ProbeFilter.cpp:225-228`；`ScreenProbe_Filter.comp.slang:78-81`）。乒乓使绑定 3/4/5/6 每帧都换，所以描述符**每帧重绑**（`LumenScene_ProbeFilter.cpp:204-212`）。

**白炉为什么仍然精确**：白炉下所有探针的 SH 几乎相同 ⇒ $\sigma \approx 0$ ⇒ AABB 退化成一个点 ⇒ 截断与平均都是恒等，时域 EMA 两端也相同 ⇒ 恒等。所以这一步不是"白炉走另一条路保标度"，而是核本身在白炉下退化为恒等（`ScreenProbe_Filter.comp.slang:17-18`）。实测滤波前后探针 l0 均值都是 **1.77246**（与 §附三十 同值），噪声 0.0000 → 0.0000（《设计与实现》§附四十二 ④，第 3760-3764 行）。

统计缓冲**同时**累计"输入"与"输出"两组一阶/二阶矩，所以噪声下降能在**同一次运行**里读出来，不必跨运行对照（`ScreenProbe_Filter.comp.slang:25-26`；换算在 `LumenScene_ProbeFilter.cpp:157-175`）。三档 A/B 实测（`off` 一档的逐像素辐照度均值 0.44022 与 L5 退出判据在帧 80 的记录**逐位相同**，即"等于没有这一步"是读数而不是承诺）：

| 模式 | 探针 l0 噪声 std/mean | 逐像素辐照度均值 | Lumen 输出 rgb 均值 | 画面高频代理 |
|---|---|---|---|---|
| `off` | 0.3592 | 0.44022 | 0.03480 | 0.002885 |
| `spatial` | 0.2332（−35.1%） | 0.42447 | 0.03350 | 0.002321（−19.5%） |
| `full`（默认） | **0.2177（−39.4%）** | 0.42463 | 0.03321 | **0.002261（−21.6%）** |

（《设计与实现》§附四十二 ②，第 3735-3741 行）

两条"均值修正"尝试（模式 3 的亮度均值保持、限幅 0.5~2；以及 $\gamma = 2$ 放宽 AABB）**都没把输出均值 −4.6% 修回来**（截断通道数 93683 → 21145、差 4 倍，均值几乎不动），所以默认仍取纯 YCoCg AABB（模式 2）（同节 ③，第 3746-3758 行）。模式 3 的实现留在 shader 里（`ScreenProbe_Filter.comp.slang:156-179`）。

### 6.3 逐像素辐照度（探针 → 像素）

`Lumen_ProbeIrradiance.comp.slang`（`numthreads(8,8,1)`）：每个屏幕像素查它所在 16×16 单元的归属探针，用该探针的 4 系数 SH 沿**该像素自己的 GBuffer 法线**重建入射辐照度，再兰伯特出射：

$$L_o = \frac{\mathrm{albedo}}{\pi} \cdot E(n)$$

（`:45-63`）。用像素法线求值等于**免费拿到法线插值**，代价只是每像素 4 次乘加；首版**不做探针间空间插值**（双线性），那属于 §10 的降噪/滤波框架（`:10-12`）。逐通道必须各取自己的 4 个系数，把 R 的线性项用到 G/B 上会让画面偏色（`:14-15`）。背景像素（世界坐标接近 0）与无归属探针的像素写 0 并置 `w = 0`（`:43,47,50`）。

输出纹理是**屏幕尺寸 RGBA16F**，`usage = UnorderedAccess | ShaderResource`（`LumenScene_Irradiance.cpp:30-47`）。分两段落地：compute 写中间纹理 + 全屏 pass 采样贴到 Provider 输出 —— 不让 compute 直接写 Provider 输出的理由写在文件头：输出纹理在本帧被 offscreen pass 当颜色附件、又被当 storage image 写，会踩到 layout/依赖冲突（`LumenScene_Irradiance.cpp:11-13`）。

统计用**辐照度**而不是出射辐亮度（不随 albedo 变化，便于跨帧/跨配置对照）；累加定点倍数是 **1024** 而不是 65536 —— 2073600 像素 × 亮度 0.2 × 65536 会超过 u32 上限，第一版因此把平均亮度读成 0.0018（真值约 0.2）（`Lumen_ProbeIrradiance.comp.slang:25-27,66-70`；换算在 `LumenScene_Irradiance.cpp:130-143`）。

确定性验收模式：`HE_LUMEN_DETERMINISTIC=1` 时每帧末 `WaitIdle()`，让"回读 GPU 计数 → 决定下一帧行为"的时机固定下来，使背靠背转储逐位一致。不开时实测会有抖动（追踪命中 42393 vs 42391、逐像素辐照度均值 0.54495 vs 0.53749）（`LumenScene_Irradiance.cpp:159-166`、`LumenScene.cpp:21-23`）。

## 7. 远场硬件光追与合并

### 7.1 同一条光线再打一次

`RunFarFieldRT`（`LumenScene_Irradiance.cpp:360-543`）用与步骤 21 **完全相同**的探针光线发一次硬件光追：位置、方向、光线号全都复用，`fp.seed = m_TraceFrame - 1`（与 SH 投影同一个种子口径，`LumenScene_Irradiance.cpp:485-487`）。光线数 = `probeCount × traceRep`（`LumenFarFieldPass.cpp:109`）。

`LumenFarFieldPass` 继承 `RTEffectPass`，复用它的 RT 管线 + SBT + set0 生命周期（与 `DDGITracePass` 同一取舍）；代价是基类会顺便建一张 1×1 占位输出纹理（本 pass 的输出是 SSBO，那张纹理从不被用）（`LumenFarFieldPass.h:14-15`、`LumenFarFieldPass.cpp:64-68`）。命中/未命中着色**复用 RTGI 的 `RT_GI.rchit` / `RT_GI.rmiss`**（`LumenFarFieldPass.cpp:40-42`），理由是"远场命中的辐射度必须与 RTGI 同源同量纲，否则步骤 27 的切换会在阈值处出现阶跃"（`LumenFarFieldPass.h:11-12`）。

结果缓冲**每条光线两个 `float4`**：`[2i] = (命中距离, 命中标志, 命中辐射度亮度)`、`[2i+1] = (命中点世界坐标, 1)`（`Lumen_FarFieldMerge.comp.slang:30`、`LumenFarFieldPass.cpp:84-87`）。第一版只按 1 个 `float4`/光线分配，于是 rgen 写出界、踩坏相邻显存 —— 症状是"RT 命中率从 71% 掉到 44%"这类说不通但稳定的读数（`LumenFarFieldPass.cpp:85-86`）。这条与"改布局必须同时改所有读写方"是同一条教训（《设计与实现》§附三十三 第 3218-3222 行）。

### 7.2 逐光线对照（SDF vs 三角形）

`Lumen_FarFieldCompare.comp.slang` 逐光线比较两者的命中距离，按"近带 / 远带"（分界 `m_FarFieldNearBand = 50.0`，`LumenScene.h:446`）与 16 桶相对误差直方图分类统计（整数定点原子加，与线程顺序无关）。比较**必须在改写之前**做（`Lumen_FarFieldMerge.comp.slang:24-25`）。`m_FarFieldTMax = 500`（比 SDF 的 `marchMaxDist = 400` 远，才能看到"只有三角形命中"的那些光线，`LumenScene.h:451`）。

1080p/1080p 实测（45192 条光线）：两侧都命中 **5696**（SDF 命中率 **17.9%**、RT 命中率 **71.2%**）；只有 SDF 命中 2379 / 只有三角形命中 26488 / 两者都未命中 10629；全部命中光线的相对差均值 0.7718、最大 1.0000，≤5% 占 2.2%、≤20% 占 8.5%。分带看：近带 4863 条（相对差均值 0.8514、≤20% 占 1.9%）、远带 833 条（0.3071、≤20% 占 47.4%）—— **近带的低一致率正是"SDF 命中距离不是几何距离"的代价**。合并之后命中率回到 **76.4%**（此前只有 SDF 的 17.9%），页命中 15.5%（《设计与实现》§附三十三，第 3174-3198 行）。

### 7.3 合并：混"材质"而不是混"位置"

`Lumen_FarFieldMerge.comp.slang` 分三类处理一条光线：

- **近场**（SDF 命中且 $t_{\mathrm{sdf}} < t_0$）⇒ 保留 SDF 的命中点；
- **远场**（SDF 未命中，或 $t_{\mathrm{sdf}} \ge t_1$）⇒ 用光追的命中点与距离，并写回 `u_RayHitPos`（步骤 22 的输入）；
- **重叠带 $[t_0, t_1]$ 内** ⇒ 主命中点仍写 SDF 的，同时把光追命中点与**混合权重**写进 fade 缓冲，由着色 pass 对两侧材质做线性混合。

权重曲线是 $w = \mathrm{smoothstep}(t_0, t_1, t_{\mathrm{sdf}})$，$t_0 = T(1 - \omega)$、$t_1 = T(1 + \omega)$（$T$ = 阈值、$\omega$ = 重叠带半宽），默认 $T = 50$、$\omega = 0.2$ ⇒ 重叠带 **[40, 60]**（`Lumen_FarFieldMerge.comp.slang:55-62`；C++ 侧算 $t_0/t_1$ 在 `LumenScene_Irradiance.cpp:528-531`，参数在 `LumenScene.h:434-435`）。用 smoothstep 而不是线性，是为了两端一阶连续；$t_1 = t_0$ 时退化成硬切换，保留 A/B 对照能力（`Lumen_FarFieldMerge.comp.slang:14-16`；环境变量 `HE_LUMEN_FARFIELD_OVERLAP` / `HE_LUMEN_FARFIELD_THRESHOLD`，`LumenScene.cpp:31-36,57-60`）。

**为什么混合必须发生在"材质"而不是"位置"上**：把两个命中点插值出一个中间位置没有物理意义（会落在两个表面之间、取到空气的材质）。所以 merge 只负责"把两个点都交出去"，由着色 pass 各取一次材质再按权重混合 —— 混合的是"看到什么"，不是"在哪"（`Lumen_FarFieldMerge.comp.slang:10-12`）。

还有一条只有踩过才知道的细节：**插值必须插"该路径实际输出的值"，而不是"材质"**。主点缺页时它的输出是中性值 0.18 而 `chosenAlbedo` 是 (0,0,0)，第一版写 `lerp(chosenAlbedo, altValue, w)` ⇒ 主点缺页的射线在带内被拉向 0（变暗），曲线在 $t_0$ 处反而出现一个更深的台阶（实测 0.2020 → 0.1417，−30%）（`Lumen_SurfaceCacheSample.comp.slang:217-224`；《设计与实现》§附三十四 坑 2，第 3284-3287 行）。

fade 缓冲布局是**每光线两个 `float4`**：`[2i] = (光追命中点, 光追权重)`、`[2i+1] = (SDF 距离, SDF 命中, 光追距离, 光追命中)`。第二个条目是给"按距离分桶"的连续性读数用的 —— 分桶必须按**稳定量**（SDF 距离），否则切换前后分桶依据本身会跳变（SDF 命中距离几十、光追命中距离几百），曲线反而失真（`Lumen_FarFieldMerge.comp.slang:32-35`）。

### 7.4 三条分类不变量（可断言）

merge 里对三类光线各加一条**不变量自检**，判据就是分类的定义（`Lumen_FarFieldMerge.comp.slang:67-71,84`）：

| 类别 | 必须成立 | 违例计数槽 |
|---|---|---|
| 纯 SDF（$w \le 0$） | $t_{\mathrm{sdf}} < t_0$ | `u_Stats[3]` |

## 8. 与 Radiance Cache / DDGI 的关系

### 8.1 Radiance Cache 就是 DDGI，不是新写的一套

《设计与实现》§7（第 577-593 行）把"Radiance Cache"定义为**升级现有 `GI_DDGI`**，并明确标注两处**已知降级、不修正**：探针表示从 SH 三波段 9 系数降到二阶 4 系数（表示能力降级，会更糊）、探针分布仍是均匀 3D 网格（省掉了整套 GPU 探针分配 / 失效 / 压实系统）。这两条写在文档里是为了避免后来者当 bug 修。

升级的落地方式是"**投影流程一行没动，只换逐样本辐射度从哪来**"（《设计与实现》§附三十八，第 3473 行）：

- `GI_DDGI::SetScreenProbeInput(...)`（`GI_DDGI.h:47-58`）把 Lumen 的**探针缓冲**、**16×16 单元 → 探针映射**、当帧相机 VP、屏幕尺寸与距离门限交给 DDGI；
- `DDGI.comp.slang` 的 `FetchScreenProbe`（`:98-131`）：DDGI 探针世界位置投到屏幕 → 落在哪个 16×16 单元 → 取该单元的 Screen Probe；
- `EvalScreenProbeRadiance`（`:135-144`）：用该探针的 4 系数**辐射度** SH 在 DDGI 自己的采样方向上求值 $L(d) = \sum_i l_i Y_i(d)$，负值截断（带限表示会振铃，负辐射度没有物理意义），再乘"单侧 → 整球"的对称外推系数。

帧图侧：距离门限取 **1 个 DDGI 格距**（`in.maxMatchDistance = m_DDGI.cellSize`，`DeferredPipeline_FrameGraph.cpp:749-751`），`HE_DDGI_INPUT=traced` 可切回自追踪路径用于 A/B（`:730-734`）。

### 8.2 输入被替换成了什么

三处替换要点：

1. **探针缓冲取的是过滤后的那一份**：`LumenProvider::GetProbeBuffer()` 返回 `m_Scene->GetProbeFilteredBuffer()`，为空才回退未过滤（`LumenProvider.h:206-210`）；未过滤的那份另有 `GetRawProbeBuffer()` 供诊断对照（`:212-214`）。也就是说 DDGI 拿到的是**降噪后**的输入。
2. **单侧 → 整球**：Lumen 的探针只在法线半球采样（积分域 $2\pi$），DDGI 的投影在整球（$4\pi$）上做，直接代入只剩一半能量 ⇒ 乘 `kScreenProbeSymmetricScale = 2.0`（"看不见的那半边与看得见的一样"这一标准近似）。方向性仍来自 Screen Probe —— 那才是本步要的东西（`GI_DDGI.h:90-94`）。
3. **深度一致性门限**（`DDGI.comp.slang:119-128`）：比较"相机到 DDGI 探针的距离"与"相机到屏幕探针的距离"，差超过 $\tau_{\mathrm{abs}} + 0.2\, d_{\mathrm{probe}}$（绝对门限 + 20% 相对松弛）就不采纳。第一版用的是"屏幕探针与探针的世界距离 < 1 个格距"，实测采纳数恒为 0（本场景格距 248 世界单位，网格点常常离任何可见表面都有几百单位）—— 被实测直接证伪并替换（《设计与实现》§附三十八，第 3493-3496 行）。这条门限就是世界空间缓存里"history 重投影"的等价物：DDGI 探针钉在世界空间、相机移动时不需要屏幕空间重投影，要防的反而是"相机一转，某个 DDGI 探针投到完全不同的表面上"。

### 8.3 一帧延迟从哪来

DDGI 段在帧图里注册在 Lumen 段**之前**（`DeferredPipeline_FrameGraph.cpp:726-729`），所以它读到的探针缓冲是**上一帧**的。这既避开了循环依赖（Lumen 的探针要等本帧的 GBuffer 与追踪结果，DDGI 的探针更新又排在 offscreen pass 之前），也是"用上一帧屏幕信息"的标准做法。步骤 35 起，这个"上一帧"同时意味着**已经降噪过**：Lumen 段内的滤波 pass 每帧写出 `m_ProbeFilteredBuf`，DDGI 下一帧读到的正是它（`DeferredPipeline_FrameGraph.cpp:1020-1023`、`LumenProvider.h:203-205`）。

同构性是这件事能这么小的原因：步骤 30 已经把 DDGI 的探针表示收敛到 `kStride = 4`（4 系数、RGB 独立），与 Screen Probe 的 `shR/shG/shB` 同构，投影端 / 评估端 / C++ 分配三处必须同时改（《设计与实现》§附三十七，第 3440-3449 行）。实测 9 系数 → 4 系数后：探针缓冲 256 B/探针 → **64 B/探针**（1408 个探针 ⇒ 360 KB → 90 KB），DDGI 单独使用时 HDR 亮度均值 0.09129 → **0.09118（−0.12%）**、逐像素相关系数 **0.99996**（同节第 3457-3465 行）。

### 8.4 降噪信号登记

Lumen 自己的降噪信号以**缓冲类**信号登记进统一框架（`LumenProvider::DescribeSignals`，`LumenProvider.h:281-301`）：载体不是一张图，而是探针 SH 缓冲。登记判据是 `ProducedThisFrame()`（层栈）而不是 `IsValid()`；核不是双边上双边滤波，所以引导参数位改用 `note` 说明，避免 `LogSummary` 打出两个假的 sigma（`:278-280`）。`s.width = probes, s.height = 1, s.needsUpscale = false` —— 探针是"每 16×16 像素一个"的稀疏载体，由逐像素辐照度级重建（`:294-298`）。

### 10.1 相对 UE5 Lumen 的架构差异（设计文档已记档）

### 10.2 Surface Cache：单次捕获、无多弹射反馈

- **atlas 只有 albedo / normal / emissive 三个通道**（`LumenScene.h:282`、`SurfaceCache_Capture.comp.slang:24-26`），**没有辐照度通道** ⇒ 命中点取到的是材质本身，不是"上一次反弹的结果"，所以这个 Surface Cache 不构成多弹射反馈回路。
- **材质来源是本帧 GBuffer**（`SurfaceCache_Capture.comp.slang:8-13`），只有本帧屏幕可见的表面能取到内容；实测 atlas albedo 有效 texel 占比 **9.1%**（《设计与实现》§附二十六，第 2800 行）。完整版（设计口径）要换成 bindless 逐材质求值，使 atlas 独立于屏幕。
- **emissive 通道目前只写 alpha 有效位**，RGB 恒 0（`SurfaceCache_Capture.comp.slang:124`）—— 也就是说自发光材质目前不会进入命中点着色。
- **命中点着色只取 albedo**，命中点的法线/粗糙度不参与着色（`Lumen_SurfaceCacheSample.comp.slang` 只写 `u_Out.xyz = atlas albedo`）。
- **无 defrag**：固定页大小下不存在碎片，分配不到一律 LRU 解决；真正的页块搬移列为后续项（《设计与实现》§附二十五，第 2789-2792 行）。

### 10.3 SDF 覆盖与精度边界

- **mesh 数与三角形数双上限**：`maxMeshes = 128`、`maxTrisPerMesh = 20000`，超限的 mesh 不建场、回落全局层（`LumenSDF.h:41-42`、`LumenSDF.cpp:204-208`）。实测场景 101 个 mesh 全建成、2 个因三角形数超限跳过（《设计与实现》§附十八，第 2549 行）。
- **显存代价**：R16F × 128³ ≈ 4.2 MB/mesh，全建约 **404 MB**（101 个），是 Lumen 自持显存的主体（《设计与实现》§附十八 第 2550 行、§附三十六 第 3407 行）。
- **远场仍依赖洪泛近似**：mesh 层已换成向量距离变换（误差 1.33 世界单位），但全局层的洪泛仍是"每跳加步长"版，带约 8% 的图测地偏差（`LumenSDF.cpp:508-514`；《设计与实现》§附十四 第 2446-2448 行）。
- **探针 march 的 eps 是几何容差**：`0.1 × 近层体素 ≈ 2.1` 世界单位（`LumenScene.h:470`），比它更细的几何分辨不出；近带（$t < 50$）SDF 与三角形的 ≤20% 一致率只有 1.9%（《设计与实现》§附三十三，第 3180 行）。
- **每 mesh 场是固定分辨率，不按 AABB 大小分配**：小网格相对精细、超大网格相对粗糙（设计 §附五 的后续项，第 276-279 行）。

### 10.4 Screen Probe 与降噪边界

- **无探针间空间插值**：逐像素辐照度按"单元 → 探针"**最近邻**取值，不做双线性；设计把它归给降噪框架（`Lumen_ProbeIrradiance.comp.slang:10-12`）。
- **光线数只有 8 条**（`traceRep` 下限），是"SH 重建辐照度 vs 逐光线求和"仍有 9.1% 平均相对差的主因（有限采样 + 二阶带限的固有差，51 条光线量级下降到 < 5%；《设计与实现》§附三十 第 3028-3030 行）。
- **均匀半球采样是"为白炉可解析"付的代价**：pdf 恒定让 0 阶项有解析值，但单探针方差比余弦采样更大（`ScreenProbeSampling.slang:9-13`）。
- **滤波的 −4.6% 输出均值偏移归因未闭环**：两条"均值修正"都无效，注释与文档都记为"待独立证实"（`ScreenProbe_Filter.comp.slang:173-179`；《设计与实现》§附四十二 ③，第 3757-3758 行）。
- **滤波不改变白炉标度，但不是靠专线**：白炉下 $\sigma \approx 0$ ⇒ AABB 退化为点 ⇒ 核恒等（`ScreenProbe_Filter.comp.slang:17-18`）。

### 10.5 已记档的既有缺陷（与 Lumen 本体无关但影响它的读数）

以下三条在《设计与实现》§附四十二 ⑥ 与 §附四十四（第 4006-4008 行）里以"既存缺陷、未修"列过，其中第一条能在代码里直接看到：

- **`m_ProbeBound` 从不在 resize 时复位**：`LumenScene::OnResize` 复位了探针滤波的一整套状态（`m_ProbeFilterBound`、历史指针、上一帧 viewProj），但**没有**复位 `m_ProbeBound`（`LumenScene.cpp:84-112` 通读可见）。单元映射缓冲 `m_CellProbeBuf` 按旧视口的 `cellsX × cellsY` 分配，而布置 pass 的 `dims.w` 用的是**当帧**单元数（`LumenScene_SurfaceCache.cpp:1038-1040`）⇒ 视口变大时 `u_CellProbe[...]` 会写到缓冲之外。1080p 固定视口下看不到。
- **RTAO 链路自相矛盾**（raw = 0 + 12.5% NaN，重建后 1.0 全覆盖）、**SSGI 在本场景输出恒 0** —— 这两条影响的是"与 Lumen 的对照结论"，不影响 Lumen 本身（《设计与实现》§附四十四，第 4006 行）。
- **剩余 7 条 `expects VK_IMAGE_LAYOUT_GENERAL` 校验告警**：不在 Lumen 已登记的自持图像之列；Lumen 侧已把 10 条压到 7 条（《设计与实现》§附四十四补记，第 4030-4038 行）。

## 11. 性能现状与未达标项

### 11.1 启动期与稳态必须分开读

这是这一步最实在的一条修正。Lumen 首帧要建 101 个 mesh 场，把滚动平均吊了几十帧——步骤 29 报的"计算 pass 27.110 ms / SDF 构建 23.956 ms"是**启动期平均**，不是稳态成本（《设计与实现》§附四十四 结论二，第 3911-3914 行）。

- **启动期峰值**：注释记的实测是 **1996 ms**（`DeferredPipeline_FrameGraph.cpp:1042`），设计文档 §附四十四 记为 **1996~2107 ms**、§附三十六 记为 **2031.005 ms**（第 3390 行）。
- **修的读法**：mesh 场建完的那一刻把**平均值**清零（峰值保留），此后 `AvgMs` 就是稳态 EMA、`PeakMs` 是全程峰值（`DeferredPipeline_FrameGraph.cpp:1041-1054`）。
- **稳态**：计算 pass **3.3 ms**、稳态 SDF 构建 **0.000 ms**（场建完后每帧只是注入/更新）、输出贴图 pass 0.12 ms（《设计与实现》§附四十四，第 3904-3913 行）。

### 11.2 GPU 侧达标、CPU 侧是瓶颈

1080p、静态相机、帧 400 实测（《设计与实现》§附四十四 ②，第 3895-3905 行）：

| 指标 | 关 Lumen | 开 Lumen |
|---|---|---|
| 墙钟帧时 / 帧率 | 34.6 ms / 28.9 fps | **51.5 ms / 19.4 fps** |
| 其中管线 `Render` | 33.7 ms | 50.8 ms |
| 重建帧图 / 编译 / 执行(录制+提交) | 0.15 / 0.03 / 33.7 ms | 0.19 / 0.03 / **50.8 ms** |
| GPU 各 pass 合计 ⇒ 上限 | — | **10.4~14.3 ms ⇒ 70~96 fps** |
| Lumen 计算 pass（GPU，稳态） | — | **3.3 ms** |
| 逐 pass CPU 录制最重 | Shadow 28~33 ms | Shadow 28~33 ms + **`Lumen_SDF_Build` 16.4 ms** |

也就是说：**GPU 侧 10.4~14.3 ms 已经在 16.7 ms 预算内，Lumen 本体的稳态 GPU 成本只有 3.3 ms；整帧 CPU 受限**（19~29 fps），而 CPU 侧最大的一项是**阴影 pass 的 CPU 录制 28~33 ms**（与 Lumen 无关）。

### 11.3 Lumen 计算 pass 的 CPU 录制分解（16.42 ms）

`HE_CPU_PASSES=1` 打印的 12 步分解（每帧，合计 **16.42 ms**；《设计与实现》§附四十四 结论三，第 3917-3922 行）：

```
StepSDF 0.002 / 页表 0.001 / 捕获 0.011 / 反馈 13.239 / 布置 0.258 / 追踪 0.022 /
远场 0.140 / 着色 1.779 / SH 0.916 / 滤波 0.029 / 辐照度 0.021 / 调试 0.002
```

再拆 `RunFeedback`：**读槽位 12.954** / 排序 0.285 / top-N 0.010 / 上传 0.010 ms。也就是那一行 `for (i) if (slots[i].y > 0) req.push_back(slots[i]);` —— **8160 个槽位逐个标量读主机可见（未缓存）显存**，1.6 万次不可缓存读，单次约 0.8 µs。页表上传的 `Map/Unmap`（invalidate/flush）只要 0.008 ms，**不是**它（代码与注释：`LumenScene_SurfaceCache.cpp:1155-1178,1221-1245`；设计文档 §附四十四 ③）。

**这条代价至今仍在**：把逐元素读改成"整块 `memcpy` 到本机内存再过滤"实测把读槽位 12.95 → 1.38 ms、Lumen 计算 pass CPU 16.4 → 4.5 ms、整帧 51.5 → 35.3 ms（19.4 → 28.3 fps），**但三次独立尝试都复现了"辐照度与输出整幅变黑而 CPU 统计一切正常"**，回退即恢复。所以按"读数确定、画面正确"的原则保留了逐元素读，代码里把这段写成一整块注释，明确记下"12.95 ms/帧、占 Lumen 计算 pass CPU 录制的 79%"以及"这条回读路径缺少明确同步"（`LumenScene_SurfaceCache.cpp:1172-1178`；《设计与实现》§附四十四补记 第三步 / 第四步 / 步骤 37 工作暂停，第 3953-3985 行）。

### 11.4 调试视图的开销

SDF 逐像素追踪可视化**默认开启**，稳态 **1.67 ms**，占 Lumen 计算 pass（4.9 ms）的 **34%**；关掉不影响画面（`LumenScene.h:92-95`、`LumenScene.cpp:24-30`）。它的开关是 `HE_LUMEN_SDF_DISABLE_DEBUG=1`，默认保持开启的理由是"转储 `lumen_sdf_trace` 是既有验收凭据"（`LumenScene.cpp:26-27`）。

### 11.5 显存

`LumenScene::LogMemoryUsage()`（`LumenScene_Irradiance.cpp:237-275`）在资源建齐后自报一次（触发点：`m_FarFieldFrame == 60`，`LumenScene_Irradiance.cpp:392`）。实测合计 **596.46 MB**（1080p）（《设计与实现》§附三十六，第 3403-3415 行），逐项：Mesh SDF **404.00 MB**（逐 mesh 128³ R16F × 101）、Global SDF clipmap 32.00 MB（2 层 × (R32U + R32F) 128³）、Surface Cache atlas **6.00 MB**（3 × 512² RGBA16F）、Lumen 输出 + 辐照度纹理 31.64 MB（2 × 屏幕 RGBA16F）、命中点/光线结果缓冲 32.00 MB、着色输出 × 3（atlas / GBuffer 对照 / 最优候选）48.00 MB、远场切换 fade 32.00 MB、其余（探针缓冲 / 远场结果 / 单元映射 / SH 参考 / 卡片与页表）约 11 MB。

两条值得记下的结论：① Mesh SDF **404 MB 与预算的 420 MB 吻合**，是 L1 的既定代价；② **诊断缓冲合计 112 MB**（命中点 32 + 着色输出 48 + fade 32），比"真正的 Lumen 数据"（atlas 6 MB）大一个量级，是**可回收**的（《设计与实现》§附三十六，第 3417-3426 行）。

### 11.6 未达标项与工作暂停

- **1080p/60fps（L6 判据）未达成**。GPU 侧已达标（各 pass 合计 10.4~14.3 ms ⇒ 70~96 fps、Lumen 计算 pass 稳态 3.3 ms）；整帧 CPU 受限（19~29 fps），最大项是阴影 pass 的 CPU 录制 28~33 ms（既有、与 Lumen 无关）与 `Lumen_SDF_Build` 16.4 ms（内含 `RunFeedback` 回读 12.95 ms）（《设计与实现》步骤 37 工作暂停收尾记录，第 3987-3996 行）。
- **步骤 37 已按用户指示暂停**，状态标为"⏸ 未达成：工作暂停"。其中"接入 async compute（中段 compute 段）"这一**功能项未做**，摊销预算与分级画质也未做（同节第 3989-3993 行）。
- **下一次接手的起点（设计文档给的建议顺序，不是本文的判断）**：① 阴影 pass 的 CPU 录制；② `RunFeedback` 回读的 12 ms（先把 Lumen 自持纹理的布局所有权交给 RHI 的 `TextureLayoutTracker`，再重试确定性回读）；③ async compute 支持中段 compute 段 + 跨队列 signal/wait；④ 摊销预算与分级画质（同节第 3997-4005 行）。
