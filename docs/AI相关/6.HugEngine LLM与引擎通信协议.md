# HugEngine LLM 与引擎通信协议

> 定位：说明大模型（LLM）如何与引擎通信、如何创建地图/场景。本协议是方案 1（Agent 的 `ToolUse`）与方案 4（AIGC 的 `GenerateScene`）共用的横切机制。
> 关联文档：`1.HugEngine AI一等公民架构设计.md`、`2.HugEngine AI统一基座设计.md`、`4.HugEngine AIGC创作平台设计.md`。

---

## 1. 核心原则

**LLM 不直接写 C++、不直接改内存。它只输出结构化 JSON（"场景规格"），引擎用一个解释器把 JSON 翻译成 `World` 的变更。**

因为引擎已有反射（`TypeRegistry::FindClass` + `ClassInfo::factory` + `PropertyInfo`），"LLM 输出的任意 JSON"都能被类型安全地变成真实组件。所有变更走命令系统（`he::Command`），因此**确定性、安全、可撤销**。

---

## 2. 双向通道

```
上行（引擎 → LLM）：注入「类型 schema」—— 告诉 LLM 能造什么（语法）
下行（LLM → 引擎）：输出场景 JSON —— 引擎解释执行（语句）
```

### 2.1 上行：引擎先给 LLM 塞"词汇表"

LLM 不知道引擎有哪些组件。先让 `WorldModel::TypeSchema()` 遍历 `TypeRegistry`，把所有组件类型、字段、合法值生成为一段描述，拼进 system prompt：

```json
{
  "component_types": [
    {"type":"TransformComponent","fields":[
       {"name":"position","type":"float3","unit":"m"},
       {"name":"rotation","type":"quat"},
       {"name":"scale","type":"float3"}]},
    {"type":"StaticMeshComponent","fields":[
       {"name":"mesh","type":"asset","filter":".gltf"},
       {"name":"cast_shadow","type":"bool"}]},
    {"type":"LightComponent","fields":[
       {"name":"light_type","type":"enum(Point,Spot,Directional)"},
       {"name":"color","type":"float3"},
       {"name":"intensity","type":"float"}]}
  ]
}
```

这段 schema 就是 LLM 的"语法"——它只能引用 schema 里出现的类型和字段，从根上杜绝"瞎编一个引擎里没有的组件"。

### 2.2 下行：LLM 只输出一份场景 JSON

用户输入「创建一张中世纪村庄地图，黄昏、有房子和篝火」后，LLM 返回：

```json
{
  "name": "中世纪村庄",
  "entities": [
    {"name":"house_01","components":[
       {"type":"TransformComponent","position":[0,0,0],"rotation":[0,0,0,1],"scale":[1,1,1]},
       {"type":"StaticMeshComponent","mesh":"Content/Models/house.glb"}]},
    {"name":"campfire_light","components":[
       {"type":"TransformComponent","position":[3,1,2]},
       {"type":"LightComponent","light_type":"Point","color":[1.0,0.6,0.2],"intensity":8.0}]},
    {"name":"sun","components":[
       {"type":"TransformComponent","position":[0,80,0]},
       {"type":"LightComponent","light_type":"Directional","intensity":3.0}]}
  ]
}
```

注意：LLM 输出的**是数据，不是代码**。它描述"有什么实体、每个实体挂什么组件、属性是多少"，执行交给引擎。

---

## 3. 引擎解释器：JSON → World

```cpp
// 引擎收到 JSON 后（六步全是现有反射 + ECS 能力）
for (auto& ent : json.entities) {
    Entity e = world.CreateEntity(ent.name);                 // 1. 建实体

    for (auto& comp : ent.components) {
        const auto* info = TypeRegistry::FindClass(comp.type); // 2. 反射找类型
        void* ptr = info->factory();                           // 3. 工厂构造（按名 new）

        for (auto& [field, value] : comp.fields) {
            const auto* prop = info->FindProperty(field);      // 4. 反射找属性
            SetByOffset(ptr, *prop, value);                    // 5. GetMemberPtr 按偏移写值
        }
        world.AddComponent(e, (Component*)ptr);                // 6. 挂到实体
    }
}
```

`FindClass` / `factory` / `FindProperty` / `GetMemberPtr` / `AddComponent` 全部是引擎现有能力。因此：

- LLM 造出的 `LightComponent`、`StaticMeshComponent`，与 glTF 导入器造出的实体**是同一种对象**，渲染、编辑器、序列化零区分；
- 整个过程封装成一条 `GenerateSceneCommand`，`Undo()` 销毁刚建的实体——**可撤销**。

## 4. 两种生成模式

### 模式 A：一次性结构化生成（简单地图，一次成型）

```
用户 prompt → schema 注入 → LLM 输出完整 JSON → 解释器一把建完 → 用户预览 → 接受 / 撤销
```

适合"一句话生成一个场景"。

### 模式 B：智能体工具调用循环（复杂地图，迭代式）

复杂地图（先地形 → 放建筑 → 调光照 → 看截图再改）用 agentic 循环，LLM 不一次性吐完，而是**反复调用引擎暴露的"工具"**：

| 工具 | 作用 |
|---|---|
| `spawn_entity(type, fields)` | 造一个实体 |
| `set_transform(entity, pos, rot, scale)` | 摆位置 |
| `query_entities(filter)` | 读回当前场景（观察） |
| `capture_screenshot()` | 截一帧渲染图给 LLM 看 |
| `list_assets(filter)` | 列出可用模型/贴图 |

循环：LLM 调一个工具 → 引擎执行并返回结果（JSON 观察或截图）→ LLM 看结果决定下一步 → …… 直到 LLM 说"完成"。每个工具调用封装成 `he::Command`，可撤销。

模式 B 的关键是**给 LLM 一双"眼睛"**——`capture_screenshot` 让 LLM 能"看到"它建出来的地图，从而自我修正。

## 5. LLM 跑在哪、怎么连

| 后端 | 通信方式 | 用途 |
|---|---|---|
| `RemoteBackend` | HTTP/SSE（OpenAI 兼容或 Anthropic API），流式 token | 云端大模型（质量高、迭代快） |
| `CPUBackend`（GGUF） | 本地进程/库内推理 | 本地小模型（离线、免费） |

引擎侧 `AIPipeline` 后台等 LLM 流式吐完 JSON → 主线程解释执行 → 结果入「待接受队列」→ 用户在 `GenerationQueuePanel` 接受 → `CommandHistory.Execute(GenerateSceneCommand)`。**LLM 推理不阻塞帧循环。**

---

## 6. 错误处理（LLM 不可靠，三层兜底）

LLM 可能输出非法 JSON、编造类型名、给越界值：

1. **JSON Schema 校验**：先按 schema 校验结构，非法直接拒收；
2. **反射校验**：`FindClass` 找不到类型 / `FindProperty` 找不到字段 → 报错并丢弃该条，不产生副作用；
3. **可撤销兜底**：即使部分创建成功，也封装在 `GenerateSceneCommand` 里，出错就 `Undo` 全部回滚。

## 7. 与现有代码的映射

| 协议环节 | 复用的引擎能力 | 位置 |
|---|---|---|
| 上行 schema | `TypeRegistry::ForEachClass` + `ClassInfo`/`PropertyInfo` | `Engine/Reflect/Reflect/ReflectionAPI.h` |
| 下行解释器 · 按名构造 | `ClassInfo::factory` | 同上 |
| 下行解释器 · 按名写值 | `PropertyInfo::FindProperty` + `GetMemberPtr` | 同上 |
| 建实体/挂组件 | `World::CreateEntity` / `World::AddComponent<T>` | `Engine/Scene/Scene/World.h` |
| 可撤销 | `he::Command` / `he::CommandHistory` | `Engine/Editor/Editor/Command.h` |
| 异步不阻塞 | `JobSystem`（Taskflow）+ 流式车道 | `Engine/Core/Threading/JobSystem.h` |
| LLM 执行 | `he::ai::RemoteBackend` / `CPUBackend` | `Engine/AI/Runtime/Backend/` |

---

## 8. 一句话总结

LLM 与引擎之间用"JSON 场景规格"沟通：引擎把反射生成的类型 schema 喂给 LLM 当语法，LLM 按语法吐出场景 JSON，引擎用 `factory` + `PropertyInfo` 把它翻译成真实 Entity/Component，整个过程走命令系统可撤销；复杂场景升级为"LLM 反复调用引擎工具 + 截图自检"的 agentic 循环。
