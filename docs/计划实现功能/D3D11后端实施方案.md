# D3D11 后端实施方案

> **性质**：实施计划（2026-10-24 制定，2026-10-30 修订）。
> **目标**：实现 D3D11 后端，**除光追外**支持 Vulkan 后端现有的全部功能，并跑通样例（01~07，05 除外）。
> **前置事实**（2026-10-30 核对）：
> - `IRHIDevice` 96 个虚函数 + `IRHICommandList` 62 个虚函数 = **158 个接口**；
> - 着色器共 170 个文件，**693 处 `[[vk::`**（其中 `vk::binding` 540 处、`vk::push_constant` 97 处）；
> - 渲染层（`Engine/Render`）对 Vulkan **已无代码依赖**（只剩注释与日志字符串），原先 `GI_RSM.cpp` 的 include 已清掉；
> - 已有可参照的 **D3D12 后端**（`Engine/RHI/D3D12`），其着色器链路、实例号、上传等做法可直接借鉴。
>
> **修订说明（2026-10-30）**：按 D3D12 后端的实际经验修订。主要变化：
> ① 着色器目标改为 SM 5.0 / DXBC（D3D11 不支持 SM 5.1），bindless 对策随之收窄；
> ② 着色器不再逐处改 `[[vk::`，改为复用 ShaderToDxil 的寄存器补丁思路；
> ③ 补充间接参数缓冲、UAV 数量与读取格式、实例号、常量环、围栏等遗漏的硬限制；
> ④ 更新过时的计数与“阶段 0”的完成情况；去掉“渲染层零改动”的说法。

---

## 1. 先说清楚：这个项目的硬阻塞

不是"照着接口实现一遍"就能完成 —— D3D11 与 Vulkan 在下列**结构性差异**上必须做设计取舍，
这些决策会决定整个后端的形态。

### 1.1 着色器模型只到 SM 5.0（决定其余几项的边界）

D3D11 最高支持 **Shader Model 5.0**（FXC 编译、DXBC 字节码）。SM 5.1 及以后是 D3D12 专属，
因此以下能力在 D3D11 **都不可用**：

- **寄存器空间（`space`）**：D3D12 后端“描述符集号 → 寄存器空间”的映射不能用，`(set, binding)` 必须**摊平成单一寄存器编号**；
- **资源数组的动态索引**：SM 5.0 下资源数组只能用常量（或编译期可展开）下标访问；
- **大资源表**：每个着色器阶段最多 128 个 SRV、16 个采样器、14 个常量缓冲。

### 1.2 阻塞一览

| # | 阻塞 | 现状（Vulkan / D3D12 侧） | D3D11 的现实 | 对策 |
|---|---|---|---|---|
| **1** | **Bindless** | 材质 / 纹理 / 骨骼全部走 bindless：着色器里 19 处按材质纹理号动态索引 `u_Textures[]`；D3D12 用 t0..1023 纹理区间 + 每段 256 个的缓冲区间 | **没有 bindless**；SM 5.0 不能动态索引资源数组；每阶段 SRV 上限 128 | ① **纹理数组**：按尺寸 / 格式分组成 `Texture2DArray`，材质里存（数组号, 层号）—— 需改材质系统与纹理加载；② **每次绘制绑定**：材质纹理按需绑到固定槽（CPU 开销大，但改动小）。原方案中的“固定槽位宏展开”在 SM 5.0 下不可行，已删除 |
| **2** | **Mesh Shader** | Nanite 用 mesh shader 硬光栅路径 | 不支持（SM 6.5 起才有） | Nanite 走 **compute 软光栅**（代码里已有 `NaniteRaster` 的 compute 分支），关掉 `m_HardRasterMS`。已核实软光栅只用 32 位原子打包，不依赖 64 位原子 |
| **3** | **间接绘制 / GPU 驱动** | `DrawIndexedIndirectCount`、DGC；间接命令由 compute 写进 `RWStructuredBuffer<IndirectCmd>` | ① 无 DGC、无 indirect count、无一次多条的间接绘制；② **间接参数缓冲必须带 `D3D11_RESOURCE_MISC_DRAWINDIRECT_ARGS`，且不能同时是结构化缓冲** | ① 按“最大条数”在 CPU 端逐条 `DrawIndexedInstancedIndirect`（多余条目的实例数为 0）；② 间接命令改用 `RWByteAddressBuffer` 写，或每帧 `CopyResource` 到专用参数缓冲（涉及 GPU 剔除、逐实例剔除、Nanite） |
| **4** | **Slang 绑定语法** | 693 处 `[[vk::`；D3D12 已解决：Slang 输出 HLSL 后由 ShaderToDxil 按 `vk::binding` 自动补 `register(..., spaceN)`，**着色器源码不改** | 需要 `register(bN/tN/sN/uN)` 且不能带 `space` | **复用 ShaderToDxil 的补丁思路**：新增 DXBC 版本，把 `(set, binding)` 摊平成寄存器编号（每类寄存器独立编号），用 FXC 输出 DXBC。不再逐处改源码 |
| **5** | **异步计算队列** | `QueueType::Compute` 独立队列 + 时间线围栏 | 只有一个 immediate context，无独立计算队列 | 异步 pass 退化为同一上下文里顺序执行（`HasAsyncComputeQueue` 返回 false，RenderGraph 自动走单队列路径） |

### 1.3 其它硬限制（同样必须处理）

| 限制 | 说明 | 对策 |
|---|---|---|
| **UAV 数量** | 特性级别 11_0：像素着色器的 UAV 与渲染目标**共用 8 个槽**（GBuffer 已占 8 个 MRT），计算着色器也只有 8 个 UAV | **要求特性级别 11_1**（64 个 UAV），不支持 11_0 |
| **UAV 类型化读取** | 11_0 / 11_1 只支持 R32 系列格式的 UAV 读取；着色器里有 30 处 `RWTexture<float4/float2>` 声明，其中“既读又写”的需逐一检查 | 依赖 D3D11.3 的 `TypedUAVLoadAdditionalFormats` 能力；不支持时改为 R32 打包或拆成“读 SRV + 写 UAV” |
| **实例号不含起始实例** | D3D11 的 `SV_InstanceID` 同样不含 `StartInstanceLocation`，而引擎用 firstInstance 传对象号 / 簇号（GPU 剔除、Nanite） | 沿用 D3D12 方案：顶点着色器实例号改读**逐实例序号顶点缓冲**（ShaderToDxil 把 `SV_InstanceID` 改写为 `HE_INSTANCEINDEX`），IA 读逐实例数据时会加上起始实例 |
| **推送常量** | D3D11 没有推送常量；每次绘制 `Map(WRITE_DISCARD)` 一个常量缓冲开销很大 | 用 D3D11.1 的 `VSSetConstantBuffers1` / `PSSetConstantBuffers1` / `CSSetConstantBuffers1`（带偏移）实现**常量环**，与 D3D12 后端的常量环做法一致 |
| **时间线围栏** | 引擎用时间线围栏做帧同步与读回判定 | Win10 的 `ID3D11Fence`（D3D11.3，`ID3D11DeviceContext4::Signal / Wait`）；不可用时退化为 `D3D11_QUERY_EVENT` |
| **只读深度** | 引擎在同一 pass 里采样深度时切换只读 DSV | D3D11 支持 `D3D11_DSV_READ_ONLY_DEPTH`，需建两套 DSV 并按 PSO 是否写深度切换 |
| **资源冲突** | 同一资源同时作为 RTV 与 SRV 绑定时，运行时会**静默解绑**其一（调试层只给警告） | 绑定 RTV / UAV 前主动解绑对应 SRV 槽，避免读到空纹理 |

**结论**：阻塞 1（bindless）是**工作量主体**，且会改动材质系统；阻塞 4（着色器）因为可以复用 D3D12 的补丁思路，工作量大幅下降；
阻塞 2 / 3 / 5 和 1.3 的各项是**功能降级或适配取舍**，可以接受，但要写进文档并按能力查询降级。

## 2. 分层实施计划

### 阶段 0：清理与设施（约 1 周）

| 任务 | 内容 | 判据 | 状态 |
|---|---|---|---|
| 0.1 | 去掉渲染层对 Vulkan 头文件的依赖 | 构建通过 | ✅ 已完成（渲染层已无代码依赖） |
| 0.2 | 后端选择：`rhi::Backend` 枚举加 `D3D11`；`DeviceInitDesc::backend` 与 `ResolveBackendFromEnv()`（环境变量 `HE_RHI_BACKEND`）支持 `d3d11` | 启动日志显示所选后端 | ⚠️ 选择机制已有（Vulkan / D3D12），只需加枚举值与工厂分支 |
| 0.3 | `DeviceCaps` 能力查询 | 样例可按能力降级 | ⚠️ 已有 `supportsMeshShaders` / `supportsDGC` / `supportsAsyncCompute` / `maxBindlessResources`；需补 `supportsIndirectCount`，并让渲染层在 `maxBindlessResources == 0` 时走非 bindless 路径 |
| 0.4 | **bindless 方案技术验证**：一个 cube + 1000 材质，分别试“纹理数组”与“每次绘制绑定” | 定下阻塞 1 的方案 | ❌ |

### 阶段 1：D3D11 设备与资源（2~3 周）

| 任务 | 内容 |
|---|---|
| 1.1 | `D3D11Device : IRHIDevice` 骨架（创建 / 销毁 / 能力查询），要求特性级别 11_1，先让 96 个虚函数**全部有实现**（多数可先返回空 / 默认） |
| 1.2 | Buffer / Texture / Sampler / Shader / PSO 的创建与销毁。PSO 拆成 D3D11 的若干状态对象（光栅 / 深度模板 / 混合 / 输入布局）并缓存 |
| 1.3 | 句柄表（复用 A-3 的 `RHIResourceTable`，与其它后端共用同一套语义） |
| 1.4 | SwapChain（`IDXGISwapChain1`，翻转模型）+ `FramePresenter` 适配；垂直同步与允许撕裂的逻辑**参照 D3D12 后端** |
| 1.5 | 描述符集 → 固定槽位的映射（按 1.1 的摊平规则）；bindless 按 0.4 定下的方案实现 |
| 1.6 | 可直接借鉴 D3D12 后端的部分：DXIL / DXBC 反射建输入布局 + 零缓冲补位、逐实例序号缓冲、3D 纹理与 mip 上传、资源调试命名 |

### 阶段 2：命令列表（2 周）

| 任务 | 内容 |
|---|---|
| 2.1 | `D3D11CommandList : IRHICommandList` 骨架（62 个虚函数） |
| 2.2 | **主录制走 immediate context**。原因：deferred context 上 `Map` 只能 `WRITE_DISCARD`、查询结果只能在 immediate context 读取；且很多驱动不原生支持命令列表（用 `D3D11_FEATURE_THREADING` 的 `DriverCommandLists` 查询），运行时模拟时没有收益 |
| 2.3 | **多线程录制（二级命令列表）走 deferred context**：`FinishCommandList` → 主上下文 `ExecuteCommandList`；驱动不支持原生命令列表时，`CreateSecondaryCommandList` 返回空，引擎自动回退单线程录制 |
| 2.4 | 屏障接口（`PipelineBarrier` / `BufferBarrier`）为空操作（D3D11 驱动自动跟踪资源冲突），但需处理 1.3 的 SRV / RTV 冲突解绑 |
| 2.5 | 命令流模式（L4-3）：复用通用的 `RHICommandList`（记录端）与 `RHICommandReplay`（回放成 `IRHICommandList` 调用），由 D3D11 命令列表实现 `EnableCommandStream`。注意 `m_StreamMode` 是 Vulkan 命令列表的私有实现，不能直接复用 |
| 2.6 | GPU 计时：`D3D11_QUERY_TIMESTAMP` + `D3D11_QUERY_TIMESTAMP_DISJOINT`；管线统计：`D3D11_QUERY_PIPELINE_STATISTICS`。`GetQueryResults` 的 `count` 按**查询个数**解释（与 Vulkan / D3D12 一致） |

### 阶段 3：着色器（约 2 周）

| 任务 | 内容 |
|---|---|
| 3.1 | 编译链：Slang `-target hlsl` 输出 HLSL → **DXBC 版补丁工具**（参照 ShaderToDxil：按 `vk::binding` 补 `register`，`(set, binding)` 摊平成寄存器编号，去掉 `space`）→ FXC 编译 `vs_5_0` / `ps_5_0` / `cs_5_0`。也可评估 Slang 直接 `-target dxbc -profile sm_5_0`，但仍需同样的寄存器摊平 |
| 3.2 | 推送常量 → 常量缓冲（寄存器 b0 / b1，配合 1.3 的常量环） |
| 3.3 | 实例号改写（`SV_InstanceID` → `HE_INSTANCEINDEX`），与 D3D12 相同 |
| 3.4 | bindless 替代方案落地（按 0.4 的结论改材质与纹理访问） |
| 3.5 | 间接命令写入改为 `RWByteAddressBuffer`（或增加拷贝到参数缓冲的步骤），见阻塞 3 |
| 3.6 | 逐 pass 验证：从最简单（全屏三角形 / tonemap）到最复杂（Nanite / Lumen）；重点检查 1.3 的 UAV 类型化读取 |

## 3. 与 L4-3（命令流双模式）及 D3D12 后端的关系

```
渲染层（零后端 API）
   ↓ IRHICommandList（158 个接口中的 62 个）
   ├── VulkanCommandList：直连录制（模式 A）或命令流（模式 B）
   ├── D3D12CommandList：直连录制；二级列表为 bundle
   └── D3D11CommandList：immediate context 录制；二级列表为 deferred context
```

**渲染层基本不需要为 D3D11 改动，但不能预期“零改动”。** D3D12 后端落地时，引擎层做过以下修改：
新增 `BufferBarrier` 接口、统一 firstInstance 的实例号语义、修复帧槽位恒为 0、
逐实例剔除派发移出渲染通道、`GetQueryResults` 的 `count` 统一为查询个数等。
D3D11 因为驱动自动跟踪资源冲突，屏障相关的改动用不上；但 **bindless 替代方案**（材质系统）
和**间接命令缓冲格式**一定会改到渲染层。

## 4. 风险与建议

| 风险 | 影响 | 缓解 |
|---|---|---|
| bindless 替代方案选错 | 可能要重写材质系统 | 阶段 0.4 **先做技术验证**再定方案 |
| SM 5.0 能力不足 | 部分 pass（Lumen / Nanite / GI）需要改写 | 阶段 3.6 逐 pass 检查；按 `DeviceCaps` 降级或关闭 |
| UAV 类型化读取格式受限 | 读写 float4 UAV 的 pass 无法直接运行 | 优先检查 D3D11.3 能力；否则改 R32 打包 |
| 无 mesh shader | Nanite 性能大幅下降 | 走 compute 软光栅；性能目标单列 |
| 静默挂起 / 静默失败 | 定位慢（D3D12 后端曾多次遇到） | 阶段 1 就接入 `ID3D11InfoQueue`，把调试层错误打进日志；参考 `docs/已实现功能/D3D12后端实况与后续排查指引.md` 的排查经验 |
| 多后端维护成本 | 每个新功能要实现三遍 | Vulkan 为参考实现，D3D11 按能力降级；新功能先写进能力查询 |

**回归判据**：每次改动着色器链路或引擎层后，Vulkan 与 D3D12 两个后端都要跑一遍 01~07 样例并做截图对比
（与 D3D12 后端开发时的做法一致），保证不回退。

**建议的推进顺序**：阶段 0（含 bindless 技术验证）→ 1 → 2 →（01 / 02 样例跑通）→ 3（逐步）→ 4。
在 01 / 02 跑通之前不要碰 Nanite / Lumen —— 那是最后 20% 却占 50% 工作量的部分。

## 5. 明确排除

| 项 | 原因 |
|---|---|
| 光追（`BuildTLAS` / `BindRTPipeline` / `05.Sponza-PathTracing`） | 用户明确排除；D3D11 也不支持 DXR |
| Mesh Shader | D3D11 不支持，Nanite 改走 compute |
| DGC（设备生成命令） | D3D11 不支持，改走逐条间接绘制 |
| 异步计算队列 | D3D11 只有单一 immediate context，退化为顺序执行 |
| 特性级别 11_0 | UAV 数量（与渲染目标共用 8 个槽）不足以支撑 GBuffer + UAV，只支持 11_1 及以上 |
