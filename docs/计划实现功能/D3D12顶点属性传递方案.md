# D3D12 顶点属性传递方案

> 背景：D3D12 与 Vulkan 在"顶点输入"上的匹配规则不同，本项目已经因此踩坑（详见
> `D3D12与Vulkan差异清单.md` §1.4）。本文给出统一方案，目标是：
> **同一份 Slang 着色器 + 同一套引擎顶点数据，在两个后端上行为一致，且错配能在早期暴露。**

---

## 1. 问题定性

### 1.1 两个后端的匹配规则

| | Vulkan | D3D12 |
|---|---|---|
| 匹配依据 | `location` | **语义名 + 语义索引** |
| 未提供的属性 | 读作默认值（通常 0，w=1）| **PSO 创建失败**（D3D12 要求 IA 覆盖着色器全部输入）|
| 多提供属性 | 忽略 | 允许（多余的 IA 元素不影响）|

⇒ **D3D12 比 Vulkan 严格得多**：布局必须与着色器输入"逐项对上"，多了少了都不行。

### 1.2 本项目当前的真实状态

```
引擎顶点结构（Engine/Scene/Scene/MeshComponent.h）
    struct StaticVertex { float3 position; float3 normal; float2 uv; };
    → 3 个属性，步长 48

ForwardPipeline 声明
    vertexLayout.attributes = { position@0, normal@? , uv@? }   // 3 项

PBR.vert.slang 声明
    position / normal / uv / joints / weights                    // 5 项  ← 不一致
```

后果：D3D12 后端按着色器建 5 属性布局、步长算成 64，而缓冲实际步长 48，
`joints@40` / `weights@44` 越界读到下一顶点的数据 ⇒ 蒙皮矩阵变成垃圾 ⇒ 网格塌缩。
Vulkan 因为缺失属性读默认值而"看起来正常"。

---

## 2. 方案总纲

**单一事实来源 + 严格一致 + 早期校验。**

1. **布局的唯一事实来源是引擎**：`rhi::VertexInputLayout`（属性列表 + 步长）。
   后端**不得**再从着色器反射去"猜"顶点布局。
2. **着色器只声明引擎真正会提供的属性**：声明的集合必须是布局属性的子集。
3. **语义命名全局统一**：一套 `location → 语义名` 映射表，引擎、后端、着色器三方共用。
4. **错配立即报错**：PSO 创建前做一次校验，失败时打印逐项差异（而不是让 D3D 返回一个笼统的 `E_INVALIDARG`）。

---

## 3. 数据模型（RHI 层）

```cpp
// Engine/RHI/RHI/Types.h
enum class VertexFormat : u32 {
    Float1, Float2, Float3, Float4,
    UByte4Norm,   // 4x uint8 归一化
    UByte4,       // 4x uint8 整数（关节索引）
    UShort2, UShort4,
};

struct VertexAttribute {
    u32          location;   // 0..7，与着色器 [[vk::location]] 一致
    u32          binding;    // 顶点缓冲槽（当前只用 0）
    VertexFormat format;
    u32          offset;     // 字节偏移
};

struct VertexInputLayout {
    u32                        stride = 0;   // 0 = 由属性推算
    std::vector<VertexAttribute> attributes;
};
```

**关键约束**：`offset + formatSize(format) <= stride`，越界在声明时就该被抓出来。

---

## 4. 语义命名映射（唯一来源）

位置（location）决定语义名，两个后端都用这张表：

| location | 语义名 | 典型格式 | 说明 |
|---|---|---|---|
| 0 | `POSITION` | `Float3` | 位置 |
| 1 | `NORMAL` | `Float3` | 法线 |
| 2 | `TEXCOORD` | `Float2` | UV0 |
| 3 | `BLENDINDICES` | `UByte4` | 关节索引（蒙皮）|
| 4 | `BLENDWEIGHT` | `Float4` | 关节权重（蒙皮）|
| 5 | `TANGENT` | `Float4` | 切线（可选）|
| 6 | `COLOR` | `Float4` | 顶点色（可选）|

后端按下标生成 `D3D12_INPUT_ELEMENT_DESC.SemanticName`，
着色器里用同一张表写显式语义。**新增属性必须同时更新这张表。**

---

## 5. 着色器侧规范

### 5.1 统一写法

```slang
struct PBRVertexInput {
    [[vk::location(0)]] float3 inPosition : POSITION0;
    [[vk::location(1)]] float3 inNormal   : NORMAL0;
    [[vk::location(2)]] float2 inUV       : TEXCOORD0;
};
```

规则：
- **必须**写成"结构体 + 成员语义"，不能再用全局 `layout(location = N) in ...`
  （Slang 会按变量名字母序编造 `VERTEX_IN_N`，与 location 完全对不上）
- **必须**同时保留 `[[vk::location]]`：Slang 没有能固定 SPIR-V location 的 HLSL 原生属性
- **只声明引擎会提供的属性**：不要为了"将来可能要蒙皮"而多写两个

### 5.2 为什么不能多声明

D3D12 的 PSO 校验要求 IA 覆盖着色器全部输入。多声明的属性若布局里没有，
`CreateGraphicsPipelineState` 直接 `E_INVALIDARG`（本项目已实测到）。

## 6. 后端实现要点（D3D12）

### 6.1 布局构建

```cpp
// D3D12Resources.cpp（PSO 创建处）
if (!desc.vertexLayout.attributes.empty()) {
    elems.clear();
    for (const auto& a : desc.vertexLayout.attributes)
        elems.push_back(MakeElement(a));       // 语义名查表、格式查表、偏移直接用
    m_VertexStride = desc.vertexLayout.stride > 0
                   ? desc.vertexLayout.stride
                   : ComputeStride(desc.vertexLayout);
} else {
    // 仅在没有引擎布局时，才回退到"从着色器签名推断"（兼容旧路径，并打警告）
}
```

**绝不能**在拿到引擎布局之后再用"固定偏移表"覆盖它。

### 6.2 格式映射

| `VertexFormat` | `DXGI_FORMAT` | 字节 |
|---|---|---|
| `Float1` | `R32_FLOAT` | 4 |
| `Float2` | `R32G32_FLOAT` | 8 |
| `Float3` | `R32G32B32_FLOAT` | 12 |
| `Float4` | `R32G32B32A32_FLOAT` | 16 |
| `UByte4` | `R8G8B8A8_UINT` | 4 |
| `UByte4Norm` | `R8G8B8A8_UNORM` | 4 |
| `UShort2` | `R16G16_UINT` | 4 |
| `UShort4` | `R16G16B16A16_UINT` | 8 |

### 6.3 PSO 创建前的校验（新增）

```cpp
// 对每个着色器输入（DXIL 反射得到的 POSITION0 / NORMAL0 ...）：
//   1) 在 elems 里按 (SemanticName, SemanticIndex) 找到对应项，找不到 → 报错
//   2) 该项的格式组件数 必须 >= 着色器输入声明的组件数
//   3) 该项 offset + 大小 <= stride
// 任一不满足：打印 "着色器输入 X 在顶点布局中缺失/不匹配" 并返回失败，
// 而不是让 CreateGraphicsPipelineState 抛 E_INVALIDARG
```

这条校验能把"布局与着色器不一致"从"画面莫名奇妙"降级为"启动即报错"。

## 7. 蒙皮数据的接入路径（将来）

**不要**用"统一声明 5 属性、默认值兜底"的方式硬撑 —— 那是把不存在的属性塞进共享着色器，
会让所有格子都得迁就最复杂的那一种。

推荐做法：

1. 新增 `SkinnedVertex = { position, normal, uv, joints(UByte4), weights(Float4) }`，步长 64，
   由 glTF 蒙皮网格使用；`StaticVertex` 保持 48 不动
2. 蒙皮网格使用**独立的着色器变体**（`PBR.vert` 增加 `skinned` 变体），
   变体里声明 5 个输入；静态网格用 3 输入的变体
3. 两套 `VertexInputLayout` + 两套 PSO，按 mesh 类型选择
4. 引擎的 `MeshComponent` 增加"是否蒙皮"的标记与骨骼缓冲句柄

这样静态路径不会被蒙皮属性污染，蒙皮路径也能真正拿到数据。

## 8. 落地步骤

| 阶段 | 内容 | 验收 |
|---|---|---|
| **① 统一布局来源**（已部分完成）| 后端优先采用 `desc.vertexLayout`；去掉按着色器 5 属性的硬编码偏移 | 打印出的 `engineAttrs/engineStride` 与最终 `elems/stride` 一致 |
| **② 着色器对齐** | 所有顶点着色器只声明布局里有的属性；保留 `[[vk::location]]` + 语义 | 两个后端的着色器都能编过，且 D3D12 的 PSO 创建成功 |
| **③ 加校验** | PSO 创建前做"逐项匹配 + 越界"检查，失败时打印明细 | 故意删掉一个布局项 → 启动时报"着色器输入 NORMAL0 缺失" |
| **④ 回归** | `01.Triangle` / `02.Cube` 在 Vulkan 与 D3D12 下都要正常 | 两个后端截图一致（允许实现细节差异）|
| **⑤ 蒙皮（可选）** | 按 §7 增加 `SkinnedVertex` + 变体 | 蒙皮网格在 D3D12 下正确显示 |

当前进度：① 的代码已改（工作区未提交），② 已改但真实分支仍未跑通，③④⑤ 未开始。
