# D3D12 剩余任务实施指南（RTX 4060）

> 编写日期：2026-10-30（分支 `dx12`，基于提交 `7d5e7755`）
>
> 本文是《D3D12已知问题与未完成功能.md》中 T1～T10 的**实施手册**：每个任务写明目标、现状、涉及文件、
> 实施步骤、验证方法与注意事项。前一轮在 Intel UHD 770 上开发，凡是需要硬件光追、网格着色器、
> 独显性能或 NVIDIA 驱动的部分都留到了这里。
>
> 建议顺序：**准备环境 → T1 → T3 → T5 → T4 → T2 → T7 → T6 → T8 → T9 → T10**。
> T1 / T3 是验证类、成本低；T5（DXR）是最大的一块，05 路径追踪、DDGI 光追、Lumen 远场都依赖它；
> T4、T7 是引擎侧缺陷；T6 / T8 / T9 / T10 视需要再做。

## 0. 准备环境

### 0.1 获取代码与构建

```powershell
git clone <仓库地址> HugEngine_DX12
cd HugEngine_DX12
git checkout dx12
git submodule update --init          # JoltPhysics / glfw / glm / meshoptimizer / spdlog / stb / taskflow
cmake --preset default               # 首次会下载 Sponza 与 Agility SDK 1.620.1（nuget.org，校验 SHA256）
cmake --build Build --config Debug   # 首次全量构建较久
```

- 依赖：Visual Studio 2026（MSVC）、Vulkan SDK（提供 `slangc`、`dxc`、`dxcompiler.dll`，CMake 会自动找最新版本）。
- configure 日志里应有：`Agility SDK: 1.620.1（D3D12_SDK_VERSION=620）`、`D3D12 backend: ENABLED`、
  `D3D12 shader path: DXIL enabled`。
- 性能相关的测量用 Release：`cmake --build Build --config Release`（输出在 `Build\bin\Release`）。

### 0.2 运行与确认设备能力

```powershell
cd Build\bin\Debug
$env:HE_RHI_BACKEND = 'd3d12'
$env:HE_D3D12_DEBUG_LAYER = '1'
.\04.Sponza-Deferred.exe
```

日志里检查三行：

```
[D3D12] 使用适配器: NVIDIA GeForce RTX 4060 ...（适配器按独显显存选择）
[D3D12] 运行时: ...\Build\bin\Debug\D3D12\D3D12Core.dll（exe 请求的 SDK 版本 620）
[D3D12] 设备就绪：bindless=65536 pushConst=256 RT=不支持 网格着色器=支持 最高着色器模型=0x68
```

- `RT=不支持` 是因为 `D3D12Device::CreateDeviceAndQueue` 里 `m_Caps.supportsRayTracing = false;` 写死（T5 要改）。
- 4060 应报 `网格着色器=支持`、着色器模型 `0x68`（6.8）。
- 任何时候日志出现 `[D3D12 ERROR] id=…` 都是调试层报错，验证标准一律是 **0 条**。

### 0.3 回归基线

动手前先在 4060 上跑一遍，记下每个样例的帧率、调试层报错数和截图，作为之后对比的基线：

```powershell
foreach ($s in '01.Triangle','02.Cube','03.Sponza-Forward','04.Sponza-Deferred','06.GILab','07.Nanite') {
  $env:HE_CAPTURE_FRAME = '200'
  # 运行约 30 秒后手动关闭，或用 Start-Process + Stop-Process 自动化
}
```

`HE_CAPTURE_FRAME=N` 会在 exe 目录生成 `capture_frameN.png`（仅 D3D12）。Vulkan 没有等价开关，
需要截图对比时用 RenderDoc 或 PIX 抓帧。

### 0.4 4060 上要额外留意的一点：CPU 可见的存储缓冲

`D3D12Buffer::Initialize`（`Engine/RHI/D3D12/D3D12Resources.cpp`）把**所有带 `BufferUsage::Storage` 的缓冲**
放在 CPU 可读写的自定义堆上（`GetCustomHeapProperties(READBACK)`），因为引擎习惯直接 `Map` 任何 SSBO。
在集显上这就是显存；在 4060 上它是**系统内存**，GPU 经 PCIe 访问。功能上没问题，但 GPU 频繁读写的大缓冲
（GPU Scene、Lumen、Nanite、粒子）会明显变慢。T5 的加速结构与 scratch 缓冲**必须**放在 DEFAULT 堆（见 T5.3）。
如果 4060 上帧率明显低于 Vulkan，优先从这里查：给不需要 CPU 访问的 Storage 缓冲（`cpuAccess=false` 且引擎从不
`Map`）改用 DEFAULT 堆。

## T1. 复测 GPU 验证（GBV）崩溃

**目标**：确认 RTX 4060 上打开 GBV 是否还会崩溃。

**现状**：原崩溃点在系统自带调试层格式化 GBV 消息的 lambda（`NDebug::CGBVMessageLog::DumpMessages`），
当时排除了描述符内容、ImGui 字体槽、根参数范围、`BufferBarrier`、状态跟踪、句柄错配、越界访问。
现在程序自带 Agility SDK 1.620.1 的 `d3d12SDKLayers.dll`，本机（Intel）开 GBV 90 秒无崩溃、0 报错。

**步骤**
1. 依次运行 02 / 04 / 06 / 07，每个跑 2 分钟以上：
   ```powershell
   $env:HE_RHI_BACKEND='d3d12'; $env:HE_D3D12_DEBUG_LAYER='1'; $env:HE_D3D12_GPU_VALIDATION='1'
   ```
2. 确认日志的「运行时」一行指向 exe 旁的 `D3D12\D3D12Core.dll`（即使用的是 Agility 调试层）。
3. **不崩**：问题已随 Agility 调试层解决，把 T1 从状态文档移除。GBV 报出的错误（`GPU-BASED VALIDATION: …`）逐条修。
4. **仍崩**：
   - 先换回系统调试层对比：用 `cmake --preset default -DHUGENGINE_D3D12_AGILITY=OFF` 重新配置并构建
     （**不要只删 `D3D12\` 目录**：exe 导出了 `D3D12SDKVersion`，缺目录时建设备直接失败）。
   - 用 `HE_D3D12_DRED=1` 得到出事的命令列表与 pass 名；崩溃报告里有符号化调用栈（Debug 构建）。
   - 逐步关闭 GI 源 / Nanite / 粒子，二分定位触发它的 pass。

## T2. 复核 Lumen 统计读数

**目标**：确认 `LumenStatsReadback` 改造后 D3D12 与 Vulkan 的 Lumen 统计一致，且不再逐帧累积。

**现状**：追踪 / 着色 / SH / 辐照度 / 探针滤波 / 远场对照与合并 / 距离分桶统计都改为
「GPU 时间线清零 + 读 kMaxFramesInFlight 帧前的回读副本」（`Engine/Render/Lumen/LumenStatsReadback.h`）；
反馈请求槽位为 kMaxFramesInFlight + 1，读已执行完的那份。本机 Lumen 每帧 25 秒，统计没跑出来。

**步骤**
1. 在 `Content\Config\06_GILab.cfg` 里加 `gi_blend_diffuse_lumen=1`（该文件被 gitignore；样例退出时会写回）。
2. 分别用 `HE_RHI_BACKEND=d3d12` 与 `vulkan` 运行 06 至少 400 帧，并设 `HE_CPU_PASSES=1`（每 120 帧打印反馈请求数）。
3. 对比日志里这些行（每 40 帧一次）：
   - `LumenScene 探针追踪（步骤 21）`：命中 / 未命中 / 总数 / 半球内；
   - `LumenScene 逐像素辐照度（步骤 24）`：覆盖像素、均值、最大值；
   - `LumenScene 探针滤波（步骤 35）`；
   - `Lumen Feedback CPU 分解（步骤 37）… 请求 N 条`。
4. **判据**：两个后端的同名统计同一量级（不再是 2040 对 14）；静止相机下统计在多帧间稳定、不单调增长。
5. 若不一致，先看 `RecordSnapshotAndClear` 的调用位置是否在该统计的所有写入 pass 之前（每帧一次），
   以及 `Read` 是否在 `RecordSnapshotAndClear` 之前调用。

## T3. 网格着色器：硬件验证与 WARP 崩溃排查

**目标**：在 4060 上验证 Nanite 的两条网格通道，并查明 WARP 上的崩溃。

**现状**
- D3D12：网格管线经管线状态流创建（`D3D12PipelineState::InitializeMeshPso`），`DrawMeshTasks` /
  `DrawMeshTasksIndirect` / `DrawMeshTasksIndirectCount` 已实现（`D3D12CommandList.cpp`）。
- 着色器：`*.mesh.slang` / `*.task.slang` 生成 `ms_6_6` / `as_6_6` DXIL（`Engine/Shader/CMakeLists.txt`），
  ShaderToDxil 用 `PatchMeshSignature` 修正 Slang 输出的参数修饰；`GBuffer.mesh` 是未完成的桩，不生成 DXIL。
- DXIL 校验要求 `SetMeshOutputCounts` 只调用一次且支配所有输出写入：`Nanite_HardRaster.mesh.slang` 已重写为
  `hardRasterSelectCluster` 统一返回三角形数。**不要**在调用后紧跟 `if (count == 0) return;`，dxc 优化会把调用复制成两份。
- 硬光栅已改为二维派发（宽 `kNaniteRasterDispatchWidth = 1024`），网格组数单维上限 65535。
- WARP 上设 `nanite_mesh_test=1`、`nanite_hard_raster=1` 后访问空指针崩溃（无符号栈）。

**步骤**
1. `Content\Config\07_Nanite.cfg` 写入：
   ```
   nanite_enable=1
   nanite_mesh_test=1
   ```
   先只开 MeshTest（最小网格管线：1 个组输出 4 顶点 / 2 图元写 1×1 目标）。D3D12 + 调试层 + GBV 运行 07，
   日志应有 `网格管线创建成功 name=NaniteMeshTest`，且模块打印的 MeshTest 读数非零（与 Vulkan 对比）。
2. 再加 `nanite_soft_raster=1`、`nanite_hard_raster=1`（硬光栅要求软光栅开启；T4 未修好前软光栅画面本身是错的，
   这里先只看硬光栅的读数与报错）。
3. 若崩溃：Debug 构建的崩溃报告带「函数名 + 文件:行号」（之前 WARP 下无符号，多半是 07 的 PDB 未生成或不匹配，
   重新构建 07 再试）。重点检查 `NaniteRaster::EnsureHardRasterResources` / `RecordHardRasterPass` 里
   `Resolve*` 的返回值（句柄失效时为空）。
4. 对照项：`D3D12PipelineState::IsMesh()` 为真时 `SetPipeline` 仍会设图元拓扑（无害）；
   网格管线的资源状态转换依赖 DXIL 反射（`Initialize` 里已把 `meshShader` / `amplificationShader` 纳入反射）。

**验证**：MeshTest 读数与 Vulkan 一致；硬光栅读数（`kHardStat*`，见 `NaniteRaster.cpp` 的 `ReadbackHardStats`）与 Vulkan 一致；调试层 / GBV 0 报错。

## T4. Nanite 软光栅在 D3D12 下画面错误

**目标**：`nanite_enable=1` + `nanite_soft_raster=1` 时 D3D12 画面与 Vulkan 一致。

**现状**：只开 Nanite 时正常；开软光栅后场景几何几乎全部消失、只剩天空与远景。已修两处（材质数组落错 space、
派发超限），修后调试层与 GPU 验证 0 报错，画面仍错。

**数据流**（`NaniteRaster.cpp` 的 `RecordSoftRasterPass` 与 `Engine/Shader/Shaders/Nanite/`）：
1. `Nanite_GBufferClear.comp`：compute 清 8 张 GBuffer 颜色目标；
2. A 趟 `Nanite_SoftRasterDepth.comp`：逐像素 `InterlockedMin(u_DepthKey[p], key)`（`RWStructuredBuffer<uint>`）；
3. B 趟 `Nanite_SoftRasterWinner.comp`：确定性赢家 `InterlockedMin(u_WinnerID[p], 候选号)`；
4. C 趟 `Nanite_SoftRaster.comp`：等值复检后写 4 张 GBuffer（UAV）；
5. 深度解析 `Nanite_DepthResolve.frag`：全屏三角形按深度键输出 `SV_Depth`，**哨兵 `0xFFFFFFFF` 写 1.0（远平面）**，
   PSO 为 `depthTest=true` + `Always` + `depthWrite=true`。

「整屏只剩天空」最符合的解释：深度键全是哨兵（A 趟没写进去，或深度解析读到的不是那块缓冲），
深度解析把整屏深度写成远平面，Lighting 当作天空。

**步骤**
1. 用 PIX（推荐，D3D12 原生）或 RenderDoc 抓 07 的一帧，逐个 pass 查看：
   - A 趟后 `u_DepthKey` 的内容：是否全是 `0xFFFFFFFF`；
   - A 趟的派发参数、绑定的 `u_DepthKey` 是否与深度解析读的是同一个缓冲；
   - C 趟后 4 张 GBuffer 是否有内容；深度解析后深度附件的值。
2. 若 A 趟没写入：查它的输入，可见簇数 `u_VisibleClusterCount`、簇 / 顶点 / 三角形缓冲是否有数据
   （Nanite 资产上传 `NaniteUpload`、剔除链 `NaniteCull::RecordCullChainPass`）。注意 D3D12 的缓冲状态是
   **每个命令列表从 COMMON 开始**跟踪（`m_BufferStates`），跨 pass 的 UAV → SRV 依赖靠 `EnsureBoundResourceStates`
   按 DXIL 反射补转换；这几个 pass 在同一列表内，重点看反射出的 `ResourceUse`（space / binding）是否对。
3. 若深度键正确但画面仍错：检查深度解析 pass 在 D3D12 下的 `BeginOffscreenPass`。它用 PSO 的 `depthLoadOp`
   决定是否清深度（`D3D12CommandList::BeginOffscreenPass` 里 `clearDepth` 的判断）；再看 SV_Depth 写入时深度附件的状态（DEPTH_WRITE）。
4. 模块自带读数：`NaniteRaster::ReadbackSoftStats`（`kNaniteSoftStat*`：像素数、深度解析像素数、ties 等），
   日志里搜 `soft` / `软光栅`，和 Vulkan 逐项对比。
5. 修好后：07 的 D3D12 截图与 Vulkan（RenderDoc 抓帧）对比；调试层与 GBV 0 报错；再把 `nanite_hard_raster=1` 一起验证（T3）。

## T5. 光线追踪（DXR）

**目标**：D3D12 后端实现 `IRHIDevice` / `IRHICommandList` 的光追接口，05.Sponza-PathTracing、DDGI 光追、
Lumen 远场、RT 反射在 D3D12 下可用，画面与 Vulkan 一致。

**参考实现**：`Engine/RHI/Vulkan/VulkanRT.cpp`（446 行）。引擎侧用法：`Engine/Render/Pipeline/RTPass.cpp`
（BLAS / TLAS 构建、`BuildSBT` 拼着色器表）、`Engine/Render/RT/PTPass.cpp`、`RTEffectPass.cpp`、`ReSTIRPass.cpp`。

### T5.1 接口清单（`Engine/RHI/RHI/RayTracing.h`、`RHI.h`、`CommandList.h`）

| 接口 | D3D12 实现 |
|------|-----------|
| `CreateBLAS(BLASBuildDesc)` / `CreateTLAS(TLASBuildDesc)` | 新类 `D3D12AccelerationStructure`：DEFAULT 堆缓冲，`ALLOW_UNORDERED_ACCESS`，初始状态 `D3D12_RESOURCE_STATE_RAYTRACING_ACCELERATION_STRUCTURE` |
| `GetBLASBuildSizes` / `GetTLASBuildSizes` | `ID3D12Device5::GetRaytracingAccelerationStructurePrebuildInfo` |
| `BuildBLAS(as, scratch, desc, update)` / `BuildTLAS(tlas, scratch, instances, count, update)` | `ID3D12GraphicsCommandList4::BuildRaytracingAccelerationStructure` + 对 AS 的 UAV 屏障 |
| `CreateRTPipelineState(RTPipelineStateDesc)` | `ID3D12Device5::CreateStateObject`（`D3D12_STATE_OBJECT_TYPE_RAYTRACING_PIPELINE`） |
| `IRHIRayTracingPipelineState::GetShaderGroupHandles` | `ID3D12StateObjectProperties::GetShaderIdentifier`，每组 32 字节 |
| `BindRTPipeline` | `SetPipelineState1` + `SetComputeRootSignature`（全局根签名） |
| `TraceRays(SBTDesc, w, h, d)` | `ID3D12GraphicsCommandList4::DispatchRays` |
| `UpdateDescriptorSet(set, binding, IRHIAccelerationStructure*)` | 写 SRV：`ViewDimension = D3D12_SRV_DIMENSION_RAYTRACING_ACCELERATION_STRUCTURE`，`RaytracingAccelerationStructure.Location = AS 的 GPU 地址`，`pResource = nullptr` |
| `CreateBLASHandle` / `CreateTLASHandle` / `CreateRTPipelineStateHandle` 及对应 `Resolve*` / `Destroy*` | 与现有 `HandleTable` 相同模式（`D3D12Device.h` 里 Buffer / Texture 的写法） |
| `SetResourceDebugName(IRHIAccelerationStructure*, name)` | `ID3D12Resource::SetName` |

### T5.2 设备能力

`D3D12Device::CreateDeviceAndQueue` 里删掉 `m_Caps.supportsRayTracing = false;` 的写死，改为查询：

```cpp
D3D12_FEATURE_DATA_D3D12_OPTIONS5 o5{};
m_Device->CheckFeatureSupport(D3D12_FEATURE_D3D12_OPTIONS5, &o5, sizeof(o5));
m_Caps.supportsRayTracing      = o5.RaytracingTier >= D3D12_RAYTRACING_TIER_1_1 && 能取到 ID3D12Device5;
m_Caps.maxRayRecursionDepth    = D3D12_RAYTRACING_MAX_DECLARABLE_TRACE_RECURSION_DEPTH;   // 31
m_Caps.shaderGroupHandleSize   = D3D12_SHADER_IDENTIFIER_SIZE_IN_BYTES;                   // 32
m_Caps.shaderGroupBaseAlignment = D3D12_RAYTRACING_SHADER_TABLE_BYTE_ALIGNMENT;           // 64
```

引擎的 `BuildSBT`（`RTPass.cpp`）按 `shaderGroupBaseAlignment` 对齐每条记录、按 `shaderGroupHandleSize` 拷句柄；
D3D12 的记录对齐要求是 32、表起始对齐是 64，按 64 统一对齐两者都满足。

**建议**：先把 `supportsRayTracing` 打开的条件额外加一个环境开关（如 `HE_D3D12_RT=1`），全部打通前不影响其他样例。

### T5.3 缓冲的堆类型（必须处理）

引擎给光追创建的缓冲（`RTPass.cpp`）：
- scratch：`Storage | AccelerationStruct`，GPU 只写；
- TLAS 实例缓冲：CPU 每帧 `Map` 写入 64 字节的实例；
- SBT：`Storage | AccelerationStruct | Uniform | ShaderBindingTable`，CPU `Map` 写一次。

而 `D3D12Buffer::Initialize` 目前把所有 Storage 缓冲放在 CPU 可见的自定义堆（见 0.4）。需要按用途区分：
- 带 `ShaderBindingTable`：**UPLOAD 堆**（CPU 写、GPU 读，状态 `GENERIC_READ`）；
- 带 `AccelerationStruct` 且不带 `ShaderBindingTable`、不需要 CPU 访问（scratch）：**DEFAULT 堆** + `ALLOW_UNORDERED_ACCESS`，
  构建前状态为 `UNORDERED_ACCESS`；
- 实例缓冲：保持 CPU 可见即可（UPLOAD 或现有自定义堆），GPU 地址需 16 字节对齐（缓冲起始 64KB 对齐，满足）。

加速结构本身由后端自己创建，不经过 `D3D12Buffer`。

### T5.4 几何与实例格式

- `RTGeometryDesc` → `D3D12_RAYTRACING_GEOMETRY_DESC`（`TYPE_TRIANGLES`）：
  `VertexBuffer.StartAddress / StrideInBytes`、`VertexFormat`（`RGB32_FLOAT` → `DXGI_FORMAT_R32G32B32_FLOAT`）、
  `VertexCount = maxVertex`、`IndexBuffer`、`IndexFormat`（`R32_UINT` / `R16_UINT`）、`IndexCount = maxPrimitiveCount * 3`、
  `Transform3x4 = transformBuffer` 的 GPU 地址（可为 0）。几何标志按需设 `OPAQUE`（与 Vulkan 侧保持一致）。
- `ASBuildFlags` → `D3D12_RAYTRACING_ACCELERATION_STRUCTURE_BUILD_FLAGS`：
  `AllowUpdate → ALLOW_UPDATE`、`AllowCompaction → ALLOW_COMPACTION`、`PreferFastTrace → PREFER_FAST_TRACE`、
  `PreferFastBuild → PREFER_FAST_BUILD`、`MinimizeMemory → MINIMIZE_MEMORY`；`update=true` 时加 `PERFORM_UPDATE`
  并设 `SourceAccelerationStructureData`。
- TLAS 实例：引擎的 `TLASInstanceDesc` 是 Vulkan `VkAccelerationStructureInstanceKHR` 的 64 字节布局，与
  `D3D12_RAYTRACING_INSTANCE_DESC` **逐字段一致**（3×4 行主序变换、InstanceID:24、Mask:8、
  ContributionToHitGroupIndex:24、Flags:8、BLAS GPU 地址），实例标志位的数值也相同（1 剔除关闭 / 2 逆时针为正面 /
  4 强制不透明 / 8 强制非不透明），实例缓冲可直接作为 `InstanceDescs` 传入，`DescsLayout = ARRAY`。
- 构建时的输入状态：顶点 / 索引缓冲需处于 `NON_PIXEL_SHADER_RESOURCE`（用 `TransitionBuffer`）；构建后对 AS 发
  `D3D12_RESOURCE_BARRIER_TYPE_UAV` 屏障，TLAS 构建依赖 BLAS 构建完成时也要这条屏障。
- 加速结构**永远停在** `RAYTRACING_ACCELERATION_STRUCTURE` 状态：`EnsureBoundResourceStates` 与设备的状态跟踪必须跳过它
  （SRV 描述符的 `pResource` 为空，`GetSetResource` 返回空即会跳过，实现时确认这一点）。

### T5.5 着色器：生成 DXIL 库

- `Engine/Shader/CMakeLists.txt` 的 `RT_SLANG` 目前只生成 SPIR-V。在 DXIL 段为它们加一组：
  `slangc -target hlsl -stage <raygeneration|miss|closesthit|anyhit|callable|intersection> -entry main`
  （按扩展名 `.rgen/.rmiss/.rchit/.rahit/.rcall/.rint` 选 stage），再 `ShaderToDxil <hlsl> main lib <out>`，
  ShaderToDxil 对 `lib` 已默认用 `lib_6_6` 目标。
- 需要确认并处理：
  1. Slang 生成的 HLSL 是否带 `[shader("raygeneration")]` 之类属性（库目标靠它导出入口；没有就由 ShaderToDxil 补上）；
  2. 库目标下 dxc 不需要 `-E`，ShaderToDxil 对 `lib` 去掉 `-E` 参数；
  3. `PatchRegisters` 对 `RaytracingAccelerationStructure`（如 `RT_Sponza.rgen.slang` 的 `[[vk::binding(0, 0)]] g_TLAS`）
     生成 `register(t0, space0)`；它与普通 SRV 同在 set 的 SRV 表里。
- 每个库都导出名为 `main` 的函数：建状态对象时用 `D3D12_EXPORT_DESC` 重命名（`ExportToRename = L"main"`，
  `Name = L"S<序号>"`），保证状态对象内导出名唯一。
- 引擎侧给 `ShaderBytecode::dxil` 赋值：RT pass（`RTPass` / `PTPass` / `RTEffectPass` / `ReSTIRPass`、Lumen 远场）
  目前只填 `spirv`，需要 include 对应的 `*.dxil.h` 并填 `dxil`（与其他 pass 的写法相同）。

### T5.6 状态对象（RT PSO）

按 `RTPipelineStateDesc` 组装子对象：
1. 每个 `shaders[i]`：`D3D12_DXIL_LIBRARY_DESC`，导出 `S<i>`（重命名自 `main`）；
2. 每个 `RTShaderGroupType::Hit` 组：`D3D12_HIT_GROUP_DESC`，`HitGroupExport = L"H<组序号>"`，
   `ClosestHitShaderImport / AnyHitShaderImport / IntersectionShaderImport` 指向对应的 `S<i>`，
   有 intersection 时 `Type = PROCEDURAL_PRIMITIVE`，否则 `TRIANGLES`；
3. `D3D12_RAYTRACING_SHADER_CONFIG`：`MaxPayloadSizeInBytes = maxPayloadSize`、`MaxAttributeSizeInBytes = maxHitAttributeSize`；
4. `D3D12_RAYTRACING_PIPELINE_CONFIG`：`MaxTraceRecursionDepth = maxRecursionDepth`；
5. 全局根签名：**与图形 / 计算管线同一布局**（8 个根 CBV + 每个 space 的 SRV/UAV/采样器表）。
   现在根签名在 `D3D12PipelineState::Initialize` 里内联创建，先把它抽成一个函数（如 `CreateEngineRootSignature(device)`），
   图形 / 计算 / 光追三处共用；推送常量照旧走根 CBV `b0`（常量环）。
6. 资源状态反射：普通 PSO 用 `IDxcUtils::CreateReflection` 得到 `ID3D12ShaderReflection`；库要改取
   `ID3D12LibraryReflection`，遍历每个函数的绑定资源，填同样的 `ResourceUses`，供绘制 / 派发前补状态转换。

`GetShaderGroupHandles()`：按 `shaderGroups` 的顺序，RayGen / Miss / Callable 取其 `generalShader` 对应的 `S<i>`
的标识符，Hit 取 `H<组序号>` 的标识符，依次拼接（每个 32 字节）。引擎的 `BuildSBT` 再按类型分段写进 SBT 缓冲。

### T5.7 `TraceRays`

`SBTSlot` 只有 `handleOffset` 与 `stride`，没有条数。按 `BuildSBT` 的布局（RayGen → Miss → Hit → Callable 依次相接），
每段大小取「下一段起点 − 本段起点」，最后一段取「缓冲大小 − 起点」：

```cpp
D3D12_DISPATCH_RAYS_DESC d{};
const u64 va = SBT 缓冲 GPU 地址;
d.RayGenerationShaderRecord = { va + sbt.rayGen.handleOffset, sbt.rayGen.stride };
d.MissShaderTable     = { va + sbt.miss.handleOffset,     sbt.hit.handleOffset - sbt.miss.handleOffset,          sbt.miss.stride };
d.HitGroupTable       = { va + sbt.hit.handleOffset,      sbt.callable.handleOffset - sbt.hit.handleOffset,      sbt.hit.stride };
d.CallableShaderTable = { va + sbt.callable.handleOffset, 缓冲大小 - sbt.callable.handleOffset,                 sbt.callable.stride };
d.Width = w; d.Height = h; d.Depth = depth;
```

`stride` 为 0 的段把 `SizeInBytes` 也设为 0。调用前与 `Dispatch` 一样：`EnsureBoundResourceStates()`、
`FlushRootArgs()`（按计算管线下发根参数：`BindRTPipeline` 时把 `m_IsComputePipeline` 置为真）、之后 `AfterDrawOrDispatch()`。

### T5.8 内联光线查询（RayQuery）

计算 / 像素着色器里的 `RayQuery` 只需要 TLAS 的 SRV 与 SM 6.5+（DXIL 已是 6.6），不需要状态对象。
`RaytracingTier >= 1.1` 即可用。

## T6. SM 6.8：用 `SV_StartInstanceLocation` 去掉实例号绕行

**现状**：D3D12 的 `SV_InstanceID` 不含起始实例，而 Vulkan 的 `gl_InstanceIndex` 含。当前绕行：
ShaderToDxil 的 `PatchInstanceId` 把 `: SV_InstanceID` 改成逐实例属性 `: HE_INSTANCEINDEX`，
PSO 在 `kInstanceIndexSlot = 14` 绑一个 `0,1,2,…` 的序号缓冲（`D3D12Device::GetInstanceIndexBufferView`，
容量 `kInstanceIndexCount = 1<<20`）；IA 取逐实例数据时自动加上起始实例。

**可选方案**
- A（推荐的做法，若决定只支持 SM 6.8+ 的设备）：ShaderToDxil 把 `SV_InstanceID` 改为
  「`SV_InstanceID` + 新增参数 `uint heStart : SV_StartInstanceLocation`」，顶点着色器目标改 `vs_6_8`，
  去掉 `kInstanceIndexSlot` 及相关反射逻辑。代价：Intel UHD 770 等 SM 6.7 设备无法运行 D3D12 后端。
- B（同时支持新旧设备）：ShaderToDxil 为顶点着色器多生成一份 6.8 变体（如 `*.vert.dxil68.h`），引擎的
  `ShaderBytecode` 增加可选字段（如 `dxilSM68`），D3D12 建 PSO 时按 `m_HighestShaderModel >= 6.8` 选择。
  代价：所有填 `dxil` 的地方都要多填一份，改动面大。

**建议**：先在 4060 上用 Release 构建测一下现有绕行的开销（实例化网格多的 02.Cube：对比把
`NeedsInstanceIndexBuffer` 路径跳过、实例号恒为 0 时的帧时间）。开销可忽略就保留绕行、关闭 T6；
确有开销再选 A 或 B。

## T7. GPU 驱动的 GBuffer 路径

**目标**：`gbuffer_mode=1`（GPU 模式）下由 GPU 剔除结果驱动 GBuffer 间接绘制，画面与 CPU 模式一致；
在此基础上验证 DGC 等价路径。

**现状**（详见状态文档 T7）
- `GPUCulling::Dispatch` / `SignalPTG` 派发后把 `m_LastVisibleCount` 清零，`GBufferRenderer_GPU` 因 `visCount == 0`
  一直走 CPU 回退。剔除本身在工作（04 帧首读回 19 个可见，关 Hi-Z 为 41 个）。
- 已修：`MeshBatcher` 的间接命令 / DGC 序列 `vertexOffset` 改为 0（合批索引本身已是绝对索引）。
- 未修：
  ① 物体缓冲顺序：间接命令以 `firstInstance = objectID` 索引物体缓冲，`objectID` 是合批顺序（全部网格，04 为 103 个），
     而每帧物体缓冲由 `SceneRenderer::Prepare` 按 CPU 视锥裁剪后的绘制项（04 为 41 个）、按自己的顺序填写；
  ② 单阶段 / PTG 剔除在只有 1 级 Hi-Z（`m_HiZMipCount = 1`）时，`PersistentCull.comp.slang` 的 `IsOccluded`
     在全分辨率深度上只采包围盒投影的 4 个角，不保守；它还用包围盒**最远**深度 `max(ndc.z)` 与样本比较，
     保守判定应使用包围盒**最近**深度。

**步骤**
1. **物体缓冲**：GPU 模式下，物体缓冲按合批顺序写**全部**合批物体（下标 = `objectID`）。
   - `MeshBatcher::Build` 收集时记下每条合批对应的快照条目（新增 `std::vector<u32>`）；
   - 每帧（变换可能变化）在 GBuffer 之前，用与 CPU 路径相同的 `FillObjectData` / 材质填充逻辑，把这些条目写进物体缓冲的
     `[0, N)`；容量受 `kGPUMaxObjects = 1024` 限制；
   - 实例化网格仍走现有的实例路径（`InstanceCuller`），不进合批。
2. **Hi-Z**：两种选择
   - 简单：单阶段 / PTG 模式只做视锥剔除（`hizMips = 0`）；
   - 完整：每帧在 GBuffer 之后构建真正的金字塔，层 L 存 2^L×2^L 足迹的**最远**深度（标准 Z：1 = 远），
     着色器取包围盒最近深度与金字塔样本的最大值比较。可直接复用 `NaniteCull::BuildHiZPyramid`
     （它按 mip 分别建描述符集，避开了 `GPUCulling::BuildHiZPyramid` 逐 mip 更新同一个集导致全部派发用最后状态的问题），
     但要先确认它的金字塔取的是最小还是最大深度、与上述口径一致。
3. **绘制**：去掉 `Dispatch` / `SignalPTG` 里把 `m_LastVisibleCount` 清零的代码；`GBufferRenderer_GPU` 的条件改为
   「GPU 剔除开启 + 间接缓冲与计数缓冲有效」，绘制改用
   `DrawIndexedIndirectCount(indirectBuf, 0, countBuf, 0, GPUCulling::kMaxObjects, sizeof(IndirectDrawCommand))`（本帧 GPU 计数），
   DGC 分支的 `maxDrawCount` 同样改为 `kMaxObjects`。`m_LastVisibleCount` 只作上一帧统计（界面显示）。
4. **验证**：`Content\Config\04_Sponza-Deferred.cfg` 设 `gbuffer_mode=0` 与 `gbuffer_mode=1` 各截第 200 帧
   （`HE_CAPTURE_FRAME=200`），比较 ImGui 面板以外区域，平均差应接近 0（上一轮 CPU 模式两次运行之间为 0.01）。
   D3D12 与 Vulkan 都要测。
5. **DGC**：把 `DeferredPipeline_FrameGraph.cpp` 的 `kDGCEnable` 设为 true（4060 的 Vulkan 若支持
   `VK_EXT_device_generated_commands` 也一起对比），重复第 4 步。

## T9. 截图偶发的后缓冲屏障报错

**现象**：06 用 `HE_CAPTURE_FRAME` 截图时偶发调试层 id=527：截图列表的 `StateBefore = PRESENT` 与后缓冲实际状态不符，
随后主列表的 `RENDER_TARGET → …` 转换也报一次。约 6 次运行出现 1 次。

**线索**：后缓冲有**两套**状态记录：交换链的 `m_BackBufferState`（`BeginRenderPass` 置为 RENDER_TARGET，Present 置回 PRESENT），
以及设备的资源状态表（`BeginOffscreenPass` 以后缓冲 RTV 为附件时经 `FindViewResource` 登记 RENDER_TARGET）。
若某帧只经后者写了后缓冲，`m_BackBufferState` 仍是 PRESENT：Present 不发 → PRESENT 屏障，截图以 PRESENT 为起点，
而设备表认为它是 RENDER_TARGET。

**步骤**
1. 写脚本循环运行 06（`HE_CAPTURE_FRAME=150`，每次 40 秒）20 次以上，统计出现率；出现时开 `HE_TRACE_PASSES=1` 记录那一帧的 pass。
2. 统一状态来源：交换链后缓冲的状态只用一处记录。可在 `BeginOffscreenPass` / `BeginOffscreenPassMRT` 识别出附件是交换链
   后缓冲时（比对 `GetCurrentBackBufferResource()`），同步调用 `MarkBackBufferRendered()`，并让 Present 时把设备表里的
   状态也改回 PRESENT。
3. 验证：循环 20 次以上不再出现；02 / 04 / 06 常规运行 0 报错。

## T10. 模式 2 下支持命令流（已完成）

**原问题**：提交路由（模式 2）下 RHI 线程的回放落后渲染线程最多两帧，而描述符集内容不按帧分版本：
回放时拍的描述符快照、`EnsureBoundResourceStates` 按集内容推导的资源状态转换，用的都是后面帧写入的内容
（实测 06 约 10 帧后 GPU 挂起）。当时有路由时 `D3D12CommandList::EnableCommandStream` 自动关闭流模式。

**根因**（流模式把一切"依赖可变引擎状态"的解析都推迟到了回放时）：
1. `PrepareSetTables` 在回放时才拍描述符快照 ⇒ 内容是录制之后帧写入的；
2. `EnsureBoundResourceStates` 在回放时才按 PSO 反射 + 集内容 + 设备纹理状态表推导转换 ⇒ 屏障 StateBefore /
   目标资源错位；
3. pass 附件（RTV/DSV）转换、显式纹理屏障、拷贝的临时转换同样在回放时才查设备状态表；
4. 回放列表在 RHI 线程上写设备状态表，与录制线程下一帧的写并发（既错序又是数据竞争）。

**做法**（录制期解析 + 回放纯命令）
1. **录制期解析**（`D3D12CommandList`，`m_StreamMode` 分支）：
   - `PrepareSetTables` 在流模式下立即 `SnapshotDescriptorSet` 并编码 `CmdResolvedDescriptorTables`
     （set / srv / uav / sampler 的 GPU 句柄随流走，相当于"描述符集内容按帧分版本"）；
   - `EnsureBoundResourceStates`、pass 附件转换（新增 `ResolveAttachmentTransitions`）、
     `PipelineBarrier(texture)`、`CopyBuffer` / `CopyTextureToTexture` / `CopyTextureToBuffer` /
     `ClearDepthStencil` 的状态转换在录制期算好，经 `EmitBarrier` 编码 `CmdResolvedBarrier`
     （转换 / UAV / 别名 / Discard 四种 op）；
   - 设备级纹理状态表只在录制线程上更新；缓冲状态仍按列表从 COMMON 起跟踪（录制期算）；
   - 绘制 / 派发统一走 `StreamDrawPrologue`（补资源状态 + 拍描述符表）→ 命令入流 → `StreamDrawEpilogue`
     （绘制后屏障 + 消费常量槽），顺序与原生路径一致。
2. **回放纯命令**：回放列表 `MarkAsReplayList()` 后跳过 `PrepareSetTables` / `EnsureBoundResourceStates` /
   `TransitionBuffer` / 各类转换，只执行流里的数据。新增三个 RHI 入口：
   `ApplyResolvedBarrier` / `ApplyResolvedDescriptorTable` / `ApplyResolvedRenderTargets`。
3. **生命周期 / 帧槽位**：
   - 录制期拍下的描述符快照块掩码经 `RHICommandList::AuxMask` 随流交接，回放提交后按回放列表的围栏
     `MarkSetRingChunks` 登记，GPU 用完之前不会覆盖；
   - 命令流槽位 = 飞行帧数 + 1：背压允许渲染线程领先 2 帧，而 Begin 在 Submit 之前，多留一槽才不会
     覆盖仍在回放的流；
   - 影子列表在渲染线程上先创建（`CreateCommandList` 会登记设备命令列表表，非线程安全）。
4. **失效场景回退**：命令流无法承载的调用（光追 BLAS/TLAS 构建、RT 管线绑定、DispatchRays）会把列表标成
   `m_StreamFallback` 并打印明确原因，从下一帧起帧主列表改回直接录制（本帧不挂起、不静默丢整帧）。
5. **顺带修的既有缺陷**：除 06 外的样例（02/03/04/05/07）都没给 `RenderThread` 登记设备，壳模式泵帧时
   `RenderThreadContext.device` 为空 ⇒ 各 pass 的 `ResB/ResT` 解析恒为 nullptr 后空指针。
   现在 `RenderThread::PumpOnce` 在未登记时退回进程级 RHI 设备（各样例都调过 `rhi::SetDevice`），
   02.Cube 也补上了显式的 `renderThread.SetDevice`。
