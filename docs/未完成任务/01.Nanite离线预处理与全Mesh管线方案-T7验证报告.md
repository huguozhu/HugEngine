# T7 一致性验证与基准（Nanite 离线预处理）

> 任务：`docs/未完成任务/01.Nanite离线预处理与全Mesh管线方案.md` 的 T7
> 日期：2026-11-12 | 分支：`feature/nanite-offline-preprocess`
> 复现命令见文末；所有数字都来自本机一次实测（Debug 构建，含日志），不取平均值。

## 1. 结论摘要

| 项 | 结果 |
|---|---|
| 字节一致性（离线读入 == 运行时构建） | ✅ 五段内容逐字节相等（cube / Sponza / 入库 MiniTriangle） |
| 加载时间 | 运行时构建 **2327.8 ms** → 离线读文件+解析 **16.3 ms**（**142.5×**） |
| 派生数据（簇 BVH） | **20.7–25.5 ms**，占运行时构建 **0.9–1.1%** ⇒ **不落盘**（方案 §3.2 的开放项到此关闭） |
| CPU 常驻（资产本体） | 运行时构建 12.78 MiB → 离线文件 13.7 MiB（多出扩展段：材质描述/归属/低模） |
| 进程峰值工作集 | 两条路径都约 84 MB —— 峰值由 **glTF 解析 + 合并几何**主导，不是资产本体 |

## 2. 环境

| 项 | 值 |
|---|---|
| CPU / OS | 本机 Windows，Debug 构建（`build/bin/Debug/MeshPreprocess.exe`） |
| 输入 | `Content/gltf/Sponza/glTF/Sponza.gltf`（103 primitive / 262,267 三角形） |

| 参数 | 默认（簇 64 三角形 / 128 顶点；低模比例 0.02；构建器 v1） |

## 3. 字节一致性

判据：`WriteNaniteFile` 写出的文件，经 `ParseNaniteAsset` 读回后，**固定五段内容**
（簇 / 顶点 / 索引 / 材质 / LOD，即头之后到 LOD 段末尾）与 `BuildNaniteAssetFromGeometry`
的内存产物逐字节相等。

> 头部（96B）不参与比较：v2 头部写入 `extSectionCount` 与 `settingsHash/sourceHash`，
> 运行时内存镜像里没有这两类值 —— 这是格式设计（T2）决定的，不是不一致。

| 资产 | 五段一致性 | 覆盖方式 |
|---|---|---|
| cube（1 簇 / 12 三角形） | PASS | `MeshPreprocess --verify` + 单测 |
| Sponza（8287 簇 / 524,657 三角形） | **PASS** | `MeshPreprocess --verify --benchmark` |
| MiniTriangle（入库测试资产） | PASS | `Tests/TestNaniteGltfReader.cpp`（CI 可跑） |

`--verify` 已接入工具：每次写文件后立即读回比对，失败以退出码 2 报告（构建期脚本会当失败处理）。

## 4. 时间基准（Sponza，mesh 粒度）

| 阶段 | 耗时 | 产物字节 |
|---|---|---|
| 运行时构建（几何 → 资产镜像） | **2327.8 ms** | 13,402,800 |
| 写 `.nanite` v2 文件 | 2.5 ms | 14,408,416 |
| 读文件 + 解析（离线 CPU 部分） | **16.3 ms** | 14,408,416 |
| 簇 BVH 构建（派生数据） | 25.5 ms | — |
| 加速比（运行时构建 ÷ 离线加载） | **142.5×** | — |

要点：

- **加载侧成本从秒级降到毫秒级**：切簇 + 简化 + DAG + 量化打包（2.3 s）完全消失，只剩
  `memcpy` 级的段解析（16 ms）。
- **写文件几乎免费**（2.5 ms）：字节镜像本来就要建，落盘只是多一次顺序写。
- 小资产（cube）绝对值无意义（0.1 ms 级），但仍给出 7.5× 的比值 —— 说明固定开销很小。

## 5. CPU 内存

| 口径 | 运行时构建 | 离线加载 |
|---|---|---|
| 资产本体（CPU 常驻） | 12.78 MiB（方案 §1.1 的既有读数） | 13.7 MiB（含 `MaterialDesc`/`SourceMeshRange`/`FallbackMesh` 扩展段） |
| 进程峰值工作集 | ≈ 84 MB | ≈ 84 MB |

- 峰值由 **glTF 解析 + 合并几何**决定（两条路径在同一进程里都要先拿到几何），
  因此"切换到离线"本身不降低工具进程的峰值；
- 真正要省的是**运行时**的常驻：方案 T12（页数据改为从文件按页读取）才把它降到 0，
  本任务只提供"能按需读页"的文件，不在范围内；
- 资产本体变大 0.9 MiB 是扩展段的代价（材质描述 103 条 + 低模 + 归属），换取的是
  "运行时无需 glTF 与 bindless 索引解析"。

## 6. 派生数据是否落盘：BVH

| 读数 | 值 |
|---|---|
| 簇 BVH 构建（Sponza 8287 簇） | 20.7–25.5 ms（多次运行区间） |
| 占运行时构建比例 | 0.9–1.1% |
| 决策 | **不落盘**：与 2.3 s 的构建成本相比可忽略，落盘反而增加格式复杂度与失效面 |

该结论回填方案 §3.2 的"BVH 是否落盘"（原为"T7 实测后决定"）。
