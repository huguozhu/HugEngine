## 1. 背景与目标

### 1.1 现状

引擎的 Nanite 模块已经实现了「簇切分 → LOD/DAG → 量化打包 → BVH → 软/硬光栅 → 分页流式」的**大部分算法**，但资产全部在**运行时**构建，且有以下几条本方案必须正视的前提：

- **构建代码已是 RHI-free 纯函数**：`Engine/Render/Nanite/NaniteUpload.{h,cpp}` 中的 `BuildNaniteClusters` / `BuildNaniteClusterDAG` / `PackNaniteClusters` / `BuildNaniteAssetFromGeometry` / `BuildNaniteClusterBVH` / `BuildNanitePagePlan` 等不 include 任何 RHI 头，`Tests/CMakeLists.txt` 直接把 `NaniteUpload.cpp` 编进测试目标（这是一条"RHI 依赖不得闯入"的纪律钉子）。
- **GPU 上传不在 `NaniteUpload`**：真正建缓冲、上传、读回校验的是 `NaniteScene::UploadPackedAsset`。
- **`.nanite` 格式已经存在**：`NaniteTypes.h` 定义了 `NaniteFileHeader`（96B，魔数 `NANITE01`，`version`，32B `_reserved` 预留"将来如流式页表"扩展）+ 五段（簇 64B / 顶点 16B / 索引 8B / 材质 32B / LOD 偏移 4B），段偏移**由头部计数推导、不落盘**。文档 10 已把它定为"字节镜像的内存布局契约，也是将来落盘的格式"——只是目前**没有任何文件 I/O**。
- **资产粒度 = 整个场景一份**：`NaniteRenderer::EnsureAssetUploaded` 从 `MeshBatcher` 读**整个场景合并后的几何**构建**一份** `NanitePackedAsset`，门闩 `m_AssetUploaded` 保证只做一次。
- **合并几何未施加世界变换**：`MeshBatcher` 合并时只做顶点 memcpy + baseVertex 偏移（`LumenSDF.h` 头注释明确写了"未施加变换的合并几何"）。Nanite 的实例剔除目前只接了**合成测试实例（纯平移）**，真实场景实例变换尚未接入 ⇒ 现状只在"所有静态网格节点为单位变换"的场景（如 `07.Nanite` 的 Sponza）下几何正确。
- **材质记录含运行时 bindless 索引**：`NaniteMakeMaterialRecord(..., bindlessTextureBase)` 中的 `bindlessTextureBase` 来自 `MeshBatcher` 快照的 `item.object.materialID`，取决于运行时纹理加载顺序。
- **派生数据在运行时生成**：BVH（`NaniteCull` 内调用 `BuildNaniteClusterBVH`）、LOD 元数据（`BuildNaniteClusterLODInfo`）、页划分（`BuildNanitePagePlan`）、Material Bin（`BuildNaniteMaterialBin`）。
- **GBuffer 几何接管已部分完成**：`NaniteSettings::softRaster`（默认 true）在 `enabled` 时让模块接管 GBuffer 几何写入；大簇（`triangleCount > softMaxTriangles`，默认 16）在 `hardRaster`（默认 false）关闭时被跳过，默认阈值下覆盖率仅约 0.16%。硬光栅同时提供 SPIR-V 与 DXIL。
- **两条并存的 mesh shader GBuffer 路线**：① Nanite 硬光栅（`Nanite_HardRaster.mesh`）；② `GBufferRenderer` 的 `HE_GBUFFER_MESH=1`（整网格按 64 三角形分组）。两者都按设备能力位 `supportsMeshShaders` 判断，**与后端无关**，但互不相通。
- **流式页数据源是常驻 CPU 副本**：`NaniteSettings::streaming` 默认关闭，理由之一是要常驻完整资产副本（Sponza 实测 12.78 MiB）。
- **glTF 源不入库**：`.gitignore` 忽略 `Content/gltf/`，新克隆与 CI 上没有源资产。
- **软光栅不逐位可复现**：深度键平局时像素由 UAV 写入顺序决定（`NaniteSettings.h` 的 Material Bin 小节已记录同档两次运行的差异）。

### 1.2 问题

1. **加载期成本**：切簇、简化、量化、BVH 全在运行时，大场景加载慢、内存峰值高；
2. **不可缓存**：同一资产每次启动重建，无法进构建缓存；
3. **资产粒度不可扩展**：整场景一份资产 + 未接真实实例变换，既无法离线（资产内容依赖场景组成），也无法正确渲染带节点变换的多网格场景；
4. **全 MS 未闭环**：硬光栅默认关闭，两条 mesh 版 GBuffer 路线未收敛，阴影/深度 pass 没有 MS 版本；
5. **构建结果不可复现**：运行时构建受场景组成与配置影响，产物不稳定；
6. **流式无真实收益**：页数据来自常驻 CPU 副本，省不下内存。

### 1.3 目标（按优先级）

| # | 目标 | 验收 |
|---|---|---|
| G1 | 现有 RHI-free 构建代码包成静态库 `HugEngineNaniteBuild`，工具与单测共用 | 全量构建 + Nanite 全部单测通过 |
| G2 | `.nanite` 格式升级到 v2 并落盘；新增离线工具 `Tools/MeshPreprocess` | 工具可对测试 glTF 与 Sponza 生成 `.nanite` |
| G3 | 运行时优先读 `.nanite`，缺失/校验失败回退运行时构建 | **离线读入的字节镜像与运行时构建逐字节相等** |
| G4 | 构建期生成资产（hash 增量、缓存、失败不阻塞） | `ProcessMeshes` 可重复执行，第二次零工作量 |
| G5 | 按资产粒度构建 + 运行时多资产 + 真实实例变换 | 带节点变换的多网格场景几何正确 |
| G6 | 硬光栅分流达到可默认开启的质量，收敛 `HE_GBUFFER_MESH` | `nanite_enable=1` 下 GBuffer 不再经过 IA/VS |
| G7 | 阴影/深度 pass 的 MS 变体（可选阶段） | CSM/点光阴影不再使用 IA PSO |
| G8 | 流式页数据改为从文件按页读取并调优 | 见 §5.6 的量化目标 |

### 1.4 非目标

- 不改 Nanite 的误差度量、DAG 割判据、软光栅数学（见文档 10）；
- 默认**不改**簇大小（64 三角形）与量化位数（位置 10 位 / 法线 10+10 / UV unorm16）；若要改，按 §3.5 单独立格式变更任务；
- 不做运行时资产编辑/热重载（后续单独任务）；
- 不重写分页流式机制（页池/页表/反馈/LRU 已存在），只改页数据来源与参数；
- 不移除顶点/索引缓冲本身：RT BLAS（`RTPass` 按网格从 `MeshRegistry` 的 VB/IB 构建）、`LumenSDF`、`MeshBatcher` 仍消费 `StaticVertex` 缓冲。

## 2. 总体方案

```
Content/gltf/*.gltf ──(离线，Tools/MeshPreprocess，按资产/按 primitive)──▶ Content/Processed/*.nanite（v2）
                                                                              │
运行时：NaniteAssetLoader（经 IVfs）读 .nanite ──▶ 材质描述 → bindless 翻译 ──▶ NaniteScene 上传
        ├─ 多资产注册 + 真实实例表（本方案新增）
        ├─ 派生数据：BVH / LOD 元数据 / 页划分 / Material Bin（运行时由纯函数生成）
        ├─ 页表/页池（NaniteStream，已存在；页数据改为从文件读）
        ├─ DAG 遍历 + 剔除（NaniteCull，已存在；改为吃实例变换）
        ├─ 软光栅 / 硬光栅 MS（NaniteRaster，已存在）
        └─ 阴影/深度 pass（本方案新增 MS 变体）
```

**关键设计决定**：

0. **资产粒度 = 按资产（glTF primitive 或 mesh）构建，运行时多资产 + 实例化**。不采用"按场景出一份文件"：后者让离线产物依赖场景组成，编辑器任何改动都会使缓存失效。代价是 `NaniteRenderer` / `NaniteCull` / `NaniteStream` 必须从"单资产"改为"多资产 + 实例表"（见 §5.3 与 T8），这是本方案中最大的一块工作量。
1. **现有 RHI-free 构建文件原样包成静态库**（不搬代码、不改目录），工具与测试都链它；GPU 上传继续留在 `NaniteScene`。
2. **直接把 `.nanite` 落盘并升级到 v2**，不另起新容器格式与新魔数：避免出现两套魔数、两套版本号、两份"真实格式"。
3. **落盘最小必要集，派生数据运行时生成**：沿用现有"偏移由计数推导、派生量不落盘"的设计原则（落盘/派生划分见 §3.2）。
4. **材质落盘为描述，不落 bindless 索引**：运行时加载后翻译（见 §3.3）。
5. **坐标空间契约**：资产内全部几何、簇包围球、法线锥、BVH 均为**资产局部空间**；剔除、LOD 屏幕误差在**世界空间**计算，由实例的 `localToWorld` 变换簇包围球（非均匀缩放时半径取最大轴缩放）。
6. **运行时优先读文件、缺失回退运行时构建**：程序化网格（地形/编辑器实时改网格）仍走回退路径。
7. **全 MS 分阶段**：先让硬光栅分流可默认开启并收敛 `HE_GBUFFER_MESH`，再做阴影/深度，最后移除 GBuffer/阴影的 IA PSO。

## 3. 资产格式 `.nanite` v2

### 3.1 布局

在现有 v1 基础上**只做加法**：

```
NaniteFileHeader（96B，沿用；magic "NANITE01" 不变，version = 2）
  clusterCount / vertexCount / indexCount / materialCount / lodLevelCount / flags
  bboxMin / bboxMax / maxLODError
  _reserved[8] → v2 启用其中若干个 u32：
    builderVersion        // 构建器版本（见 §3.4）
    settingsHash (u32×2)  // 构建参数哈希（64 位）
    sourceHash   (u32×2)  // 源几何哈希（64 位）
    extSectionCount       // 扩展段数（0 = 与 v1 等价）
    （其余仍写 0）
固定五段（沿用 v1，偏移由计数推导，不落盘）：
  ClusterRecord[]         // NaniteClusterRecord 64B；DAG 内嵌于 childClusterOffset/childCount + LOD 偏移
  Vertex[]                // NaniteVertex 16B 交织：R10G10B10A2 位置（簇心基准 + 网格尺度）+ 八面体法线 10+10 + UV unorm16 + quantBias
                          // 按共享内容去重（不是按簇连续）
  Triangle[]              // 3×u16 进 u32[2]
  Material[]              // NaniteMaterialRecord 32B（v2：bindless 字段落盘写 0，运行时回填，见 §3.3）
  LodOffset[]             // 每级一个 u32
扩展段表（v2 新增，紧跟固定五段之后，16B 对齐）：
  ExtSectionEntry[extSectionCount] { type, offset, size, reserved }
  已定义的扩展段类型：
    MaterialDesc          // 材质描述（见 §3.3）
    SourceMeshRange       // 簇 → 源 primitive 归属（若一个 .nanite 含多个 primitive）
    FallbackMesh          // 低模（IA 回退 / RT 代理，可选）
```

说明：

- **不新增独立 `DagNode[]`**：DAG 已内嵌在簇记录中，再存一份等于制造两份可以互相矛盾的真相；
- **不新增独立位置/法线/UV 流**：交织 16B 顶点与按共享内容去重是现有着色器解码与分页单位的前提；
- **不存 `rootNode`**：DAG 是"多根 + 每级 LOD 偏移"模型，根集合由 `LodOffset` 的最高级给出；
- **扩展段才落盘偏移**：固定五段仍由计数推导；扩展段因为可选、数量可变，用段表索引；
- **v1 兼容**：读取器接受 v1（`extSectionCount` 视为 0、哈希视为无效 ⇒ 永远走回退或强制重建）。

### 3.2 落盘 / 派生划分

| 数据 | 处理 | 理由 |
|---|---|---|
| 簇记录 / 顶点 / 三角形 / LOD 偏移 | **落盘** | 构建成本的主体（切簇 + 简化 + 去重 + 量化） |
| 材质描述 | **落盘**（扩展段） | 离线可知；bindless 部分运行时翻译 |
| 簇 → 源 primitive 归属 | **落盘**（扩展段，可选） | 构建时才有原始三角形空间，运行时无法复原 |
| Fallback 低模 | **落盘**（扩展段，可选） | 简化成本高 |
| 页划分 `BuildNanitePagePlan` | **运行时派生** | 纯函数、O(簇数)、依赖 `nanite_page_contents` 运行时配置 |
| 簇 BVH `BuildNaniteClusterBVH` | **运行时派生**（T7 实测后可改为落盘） | 先保持现状；若 T7 基准表明它是加载热点，再作为扩展段落盘 |
| LOD 元数据 `BuildNaniteClusterLODInfo` | **运行时派生** | 由簇记录推出，成本低 |
| Material Bin `BuildNaniteMaterialBin` | **运行时派生** | 依赖运行时材质 ID，且只是诊断读数 |

### 3.3 材质描述与 bindless 翻译

- 离线侧写 `MaterialDesc` 扩展段：每条记录 = glTF 材质索引 + baseColor/metallic/roughness 因子 + 各纹理槽的**源纹理引用**（相对 glTF 的 URI 或 image 索引）+ alphaMode；
- 固定材质段 `NaniteMaterialRecord` 中依赖运行时的字段（`bindlessTextureBase` 等）**落盘写 0**；
- 运行时 `NaniteAssetLoader` 在纹理注册到 bindless 堆后，按 `MaterialDesc` 查到 bindless 索引并回填材质段，再交给 `NaniteScene` 上传；
- 翻译失败（纹理缺失）⇒ 该材质 `textureMask` 清零、打警告，几何照常显示。

### 3.4 版本与缓存

- `version`：格式主版本，任何布局变更 +1（v1 → v2 即本方案）；
- `builderVersion`：`NaniteBuild` 中的常量 `kNaniteBuilderVersion`。**算法或实现变化但格式不变时也必须 +1**，否则旧缓存不会失效；
- `settingsHash`：构建参数（簇大小、量化位数、简化比例、cone 权重、fallback 比例等）的 64 位哈希；
- `sourceHash`：该资产对应的 glTF primitive 几何数据 + 材质描述的 64 位哈希（不含纹理像素：纹理不进 `.nanite`）；
- 运行时任一字段不匹配 ⇒ 视为过期：打警告并回退运行时构建（构建期 `ProcessMeshes` 负责重新生成）。

### 3.5 格式变更规则

改簇大小（如 64 → 128）或量化位数属于**格式变更**，不得只改 CLI 默认值。必须单独立任务并同步修改：
`NaniteTypes.h` 常量与位段 `static_assert`、`NaniteTypes.slang` 解码、硬光栅输出上限 `kNaniteHardRasterMaxVertices/Primitives`、误差上界与对应单测、`version` +1。

## 4. 离线工具 `Tools/MeshPreprocess`

### 4.1 组成

```
Tools/MeshPreprocess/
  main.cpp          # CLI：读 glTF → NaniteBuild → 写 .nanite v2；--stats/--verbose
  CMakeLists.txt    # 链 HugEngineNaniteBuild（meshoptimizer 由它传递）
```

glTF 读取：**新增一份不依赖 ECS 的最小几何读取器**（基于 cgltf，放进 `HugEngineNaniteBuild` 或独立小库），工具与 `Tests/TestNaniteMaterialMap.cpp`、`Tests/TestNaniteMaterialBin.cpp` 共用，替换掉这两个测试中各自复制的读取代码。`Engine/Asset` 的 `glTFLoader` 与 ECS 耦合，不适合 CLI 直接链接。

### 4.2 参数

**所有默认值直接取自 `NaniteTypes.h` / `NaniteUpload.cpp` 的现行常量**，保证默认参数下离线与运行时产物逐字节相等：

```
MeshPreprocess <in.gltf> <out-dir>
  --cluster-triangles=64      # = kNaniteMaxClusterTriangles（改它属于格式变更，见 §3.5）
  --cluster-vertices=128      # = kNaniteMaxClusterVertices（NaniteUpload.cpp 的 kClusterMaxVertices）
  --cone-weight=0.0           # = 现行 meshopt_buildMeshlets 的 cone_weight
  --simplify-ratio=0.5        # = 现行"逐级减半"
  --fallback-ratio=0.02       # 仅影响 FallbackMesh 扩展段，不影响主资产
  --granularity=primitive     # primitive | mesh
  --stats --verbose
```

位置/法线/UV 的量化位数**不提供 CLI 参数**（属于格式本身，见 §3.5）。

### 4.3 构建步骤（与 `NaniteBuild` 对应）

1. 读 glTF primitive（位置/法线/UV/索引、材质描述），按 `--granularity` 分组；
2. 三角形列表校验（非列表需展开）、`baseVertex` 预加；
3. `BuildNaniteClusters()`；
4. `BuildNaniteClusterDAG()`；
5. `PackNaniteClusters()`（材质段 bindless 字段写 0）；
6. 生成扩展段：`MaterialDesc`、`SourceMeshRange`（多 primitive 时）、`FallbackMesh`（可选）；
7. 填写头部 `builderVersion` / `settingsHash` / `sourceHash`，写文件；
8. 打印统计（簇数 / LOD 级数 / 共享顶点数 / 三角形数 / 字节数 / 按默认页参数估算的页数）。

## 5. 运行时改造

### 5.1 `HugEngineNaniteBuild` 静态库

- `NaniteUpload.{h,cpp}` 中的纯函数**原地**包成 `add_library(HugEngineNaniteBuild STATIC ...)`；`HugEngineRender`、测试、工具都链它，meshoptimizer 依赖随之从 `HugEngineRender` 移到该库；
- 测试目标改为链库，而不是直接编译 `NaniteUpload.cpp`；"RHI 依赖闯入即编译失败"的纪律由"库不链接任何 RHI 目标"继续保证；
- GPU 上传保持在 `NaniteScene::UploadPackedAsset`，不动；
- `.nanite` v2 的读写函数（`WriteNaniteFile` / `ReadNaniteFile`，纯内存 ↔ 字节）也放进该库，文件 I/O 由调用方经 `IVfs` 完成。

### 5.2 资产加载与开关

- 新 `NaniteAssetLoader`：经 `IVfs` 读 `.nanite` → `ValidateNaniteFile` + 版本/哈希校验 → 材质 bindless 翻译（§3.3）→ 交 `NaniteScene` 上传；
- 开关并入 `NaniteSettings`（唯一真值），配置层用 cfg 键 **`nanite_offline`**（默认 1 = 优先离线资产），面板可切换。**不使用环境变量**；
- 文件缺失 / 校验失败 / 哈希过期 ⇒ 打警告 + 回退 `BuildNaniteAssetFromGeometry`。

### 5.3 多资产与真实实例变换

- `NaniteScene` 从"一份资产 6 个缓冲"改为"资产注册表"：每个资产一组段（或全部资产拼进共享大缓冲 + 每资产基址表，T8 内决策）；
- 实例表从合成测试实例改为来自场景快照的真实实例：`assetIndex` + `localToWorld` + 世界包围盒；
- `NaniteCull` 的簇剔除与 LOD 误差改为先用实例变换把资产局部空间的簇包围球变到世界空间（坐标空间契约见 §2 第 5 条）；
- 回退路径（运行时构建）同样按资产构建，不再走整场景合并；`MeshBatcher` 只在回退时作为几何来源；
- 合成实例保留为测试档（`nanite_instance_test_count`），不再是唯一实例来源。

### 5.4 构建期集成

- CMake `ProcessMeshes` 目标（类似 `CompileShaders`）：扫描 `Content/gltf`，按 `builderVersion + settingsHash + sourceHash` 增量生成 `Content/Processed/*.nanite`；
- `Content/Processed/` 加入 `.gitignore`；工具失败**不阻塞**构建（运行时回退）；
- `Content/gltf/` 不入库 ⇒ 源资产不存在时 `ProcessMeshes` 输出提示并空跑成功；
- CI 与单测使用**入库的小型测试 glTF**（或程序生成网格）验证"工具可运行 + 格式往返 + 字节一致"。

### 5.5 全 MS 接线

| 阶段 | 内容 |
|---|---|
| MS-1 | 硬光栅分流（`hardRaster`）达到可默认开启：解决默认开启后覆盖率跳变导致的下游转储判据变化（重新冻结基线并说明）；决定 `HE_GBUFFER_MESH` 合并进 Nanite 路线还是废弃 |
| MS-2 | 阴影/深度 pass 增加 MS 变体：复用同一份资产与实例表，每光源独立视锥剔除（CSM 每级、点光每面） |
| MS-3 | 有 Nanite 资产且设备支持 MS 时，不再创建 GBuffer 与阴影的 IA PSO；无资产 / 无 MS 设备回退 |

### 5.6 流式（页数据改为文件）

- 页数据源从"常驻 CPU 完整资产副本"改为"经 `IVfs` 从 `.nanite` 按页读取"（桌面可用内存映射）；
- 页划分仍由 `BuildNanitePagePlan` 运行时派生，页边界对齐"整份共享内容"（`nanite_page_contents`，默认 512）；
- 量化目标（初值，T7 基准后校准）：
  - Sponza 开启流式时，CPU 常驻资产副本从 12.78 MiB 降到 0（只保留页表与页池）；
  - 显存峰值 ≤ 页池容量 + 固定开销；
  - 相机快速移动时每帧上传受 `nanite_page_uploads` 限流，无可见卡顿（帧时间 P99 不超过关闭流式时的 1.2 倍）。

## 6. 平台范围

- **全 MS 只针对 `supportsMeshShaders = true` 的设备**（桌面 D3D12 / Vulkan；部分移动 GPU 虽支持 `VK_EXT_mesh_shader`，但不保证）。移动端与 D3D11 默认走回退路径（IA 或软光栅），T11 的 IA PSO 移除不适用于这些设备；
- `.nanite` 读取一律经 `IVfs`，不使用裸 `fopen`；
- `Content/Processed/` 需接入 Android 的 `Platforms/Android/sync-assets.ps1` / `asset_manifest.txt` 与 OHOS 的 rawfile 打包，否则移动端只能走运行时回退；
- 每项任务保持「Windows 全量构建 + `OhosStubCheck` + 单测」绿。

## 9. 风险与开放问题

| 风险 | 对策 |
|---|---|
| 格式频繁变动 | `version` + `builderVersion` + `settingsHash` 三重失效；格式集中在 `NaniteTypes.h` |
| 构建器输出不确定（哈希表遍历序、多线程） | T2 增加确定性单测；构建器中禁止依赖无序容器遍历序 |
| 多资产改造牵动面大（T8） | 先在 `07.Nanite` 单资产下保持行为不变，再接多资产；合成实例保留为测试档 |
| 材质 bindless 翻译失败 | 清 `textureMask` + 警告，几何照常显示 |
| 硬光栅默认开启导致下游转储基线变化 | T9 显式重新冻结基线并记录原因，不静默改判据 |
| 软光栅不逐位可复现 | 主验收用字节一致，画面对比只作带阈值的辅助判据 |
| `Content/gltf` 不入库 | CI 用入库测试 glTF；`ProcessMeshes` 源缺失空跑 |
| 程序化/动态网格 | 保留运行时构建回退；编辑器保存/导入时构建 |
| MS 输出上限 | 簇大小固定为 64 三角形（`kNaniteHardRasterMaxVertices/Primitives` 已按此配置），改动按 §3.5 |
| 移动端无 MS | 回退路径常驻；T11 不适用于无 MS 设备 |
| 资产体积 | 量化已压缩；后续可加 zstd/lz4（M6 之后单独评估） |

**开放问题（含本次修订的结论）**

1. ~~`.nanite` 随资产提交还是构建期生成？~~ → **结论**：构建期生成、不入库（与 shader 产物一致）；但 glTF 源本身也不入库，CI 依赖入库的小型测试资产。
2. ~~是否支持一个 glTF 多 primitive？~~ → **结论**：按 `--granularity` 分组构建（默认按 primitive），运行时作为多个资产实例化，**不在运行时合并已量化资产**。
3. 阴影 MS 变体复用主光栅可见簇，还是按光源重新剔除？（建议：复用资产与实例表，每光源单独视锥剔除）
4. 是否需要 task/amplification shader 做簇剔除？（建议：先不做，compute 剔除已够）
5. 多资产的 GPU 缓冲组织：每资产独立段 vs 共享大缓冲 + 基址表？（T8 内决策，倾向共享大缓冲以减少描述符切换）
6. BVH 是否落盘？（T7 基准后决定）
