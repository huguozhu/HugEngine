## 4. 五个「静默挂起」陷阱（最有价值的经验）

这五个问题**都不报错、不崩溃、CPU 0%、窗口无响应**，各花 2-6 轮才定位：

| # | 陷阱 | 表现 | 修复 |
|---|---|---|---|
| 1 | **`SetBreakOnSeverity(CORRUPTION, TRUE)`** | 无调试器时进程永久等待 | 改为 `FALSE` |
| 2 | **顶点缓冲 `StrideInBytes = 0`** | `IASetVertexBuffers` 静默阻塞 | 用 PSO 反射出的步长兜底 |
| 3 | **无守卫的 `ImGui::Begin`** | ImGui 无上下文时挂起 | 整块包 `if (imgui.IsInitialized())` |
| 4 | **`GetBindlessHeap()` 返回 nullptr** | 引擎无条件解引用 | 提供非空实现 |
| 5 | **`InfoQueue` 把 ERROR 放进 DenyList** | 所有错误被屏蔽，排查失去线索 | DenyList 只放 INFO/MESSAGE |

**通用教训**：D3D12 的静默挂起优先怀疑「参数为 0 / 空指针 / 调试层断点」，而不是逻辑错误。

## 5. 着色器链路

```
slangc -target hlsl  →  ShaderToDxil（三步补丁）  →  dxc -T <stage>_6_6  →  DXIL  →  *.dxil.h
```

### 三步补丁

| 步骤 | 内容 |
|---|---|
| ① 语义注入 | 按「成员名 + 同名出现次序」分配 `TEXCOORD` / `SV_Position` |
| ② `uint8_t` → `uint` | dxc 不认识该类型（实测 `-D` 宏无效，必须文本替换）|
| ③ `[loop]` 抑制展开 | 给函数体内的 `for` 加属性 |

### 已知的着色器侧坑

| # | 坑 | 修复 |
|---|---|---|
| 1 | DXC 拒绝向量三元（`vec3 ? a : b`）| 改 `step + lerp`（`select()` 也会被展开成三元）|
| 2 | `StructuredBuffer` 不能是数组（SM5.0 限制）| 用 `HE_DECL_SRV_BL2` 退化为单资源 |
| 3 | `Texture2D[64]` / `SamplerState[64]` **可以**是数组 | 保留 |
| 4 | 各阶段 push constant 落在不同寄存器（VS=b0、PS=b1）| 根签名改用 CBV 表覆盖 b0..b7 |

## 9. 第 57~58 轮的新发现（补充）

### 9.1 一个自己引入的严重 bug（已回退）

第 49 轮为了"统一 cbuffer 寄存器"在 `Tools/ShaderToDxil` 里加了 `PatchCBuffers`，
把所有 `cbuffer X : register(bN)` 改成 `register(b0)`。结果：

```
error: resource GIBlendParamsCB_0 at register 0 overlaps with
       resource FrameConstants_0 at register 0, space 0
```

`PBR.frag` 有两个 cbuffer（`b0` 的 GIBlendParams + `b1` 的 FrameConstants），
归一后重叠 ⇒ dxc 拒绝 ⇒ **第 49~55 轮生成的所有 DXIL 都是坏的**，
这直接导致那 7 轮里"三种常量绑定方案全部失败"的误判。

**已回退该补丁**。教训：着色器文本补丁要非常保守，**不要动寄存器分配**。

### 9.2 `HE_D3D12_NO_PS` 实验：排除像素着色器与渲染目标

加开关去掉 PS 与所有 RT 后：

```
[D3D12 PSO] name=ForwardPBR VS=11660B PS=0B RTV0=0 DSV=40 NumRT=0 elems=5
PSO 创建失败 hr=0x80070057
```

⇒ **PS 不是原因，RT 格式也不是原因**。问题在 `PBR.vert` 或它的输入布局。

### 9.3 最后一个定位：顶点输入签名不对齐

反射出的输入布局：

```
VERTEX_IN_0  R32G32B32A32_FLOAT  offset=0
VERTEX_IN_1  R16G16B16A16_?      offset=16
VERTEX_IN_2  R16G16B16A16_?      offset=28
VERTEX_IN_3  R16G16B16A16_?      offset=44
VERTEX_IN_4  R32G32B32A32_FLOAT  offset=56
```

元素跨度到 **offset 56 + 16 = 72**，而引擎给的 `stride = 48`。

⇒ **DXIL 期望 5 个顶点属性（跨 72 字节），而引擎的顶点缓冲只有 48 字节步长**。
这是 SPIR-V 与 DXIL 的**顶点输入签名不对齐** —— 需要改引擎的
`VertexInputLayout` 定义（或让 Slang 的顶点入口只声明实际用到的属性），
不是 RHI 层单方面能解决的。

**建议的后续方向**：
1. 对比 `PBR.vert.slang` 的顶点输入声明与引擎 `MeshComponent` 的顶点格式
2. 让 `ShaderToDxil` 在注入语义时**按引擎的顶点布局裁剪**多余的输入
3. 或者给 `PipelineStateDesc` 加一个"显式顶点布局优先"的开关，用引擎的
   `attributes`（含正确 offset/format）覆盖反射结果

## 11. 第 72 轮：两个新发现（可能指向最终根因）

### 11.1 视图句柄映射被强引用（已修，`79ec732a`）

`D3D12Device::m_ViewResources` 之前是 `unordered_map<UINT64, ComPtr<ID3D12Resource>>`
—— **强引用住每一张纹理**。实测引擎在 12 秒内创建了 **40 张 1920x1080 纹理**
（多张 `RGBA16F` HDR 目标 + `D32` 深度），这意味着每帧十几 MB 显存永不释放，
而且 `句柄 -> 资源` 的查询可能命中早已不该存在的实例。

已改为裸指针 + 纹理析构时注销 RTV/DSV/SRV 句柄。

### 11.2 引擎在运行期高频创建/销毁纹理（**未解决，重点怀疑**）

这是目前最重要的线索：**引擎每帧都在创建新的 HDR 渲染目标**（12 秒 40 张）。

而我们的 D3D12 后端**没有延迟销毁机制**：
`D3D12Texture::~D3D12Texture()` 会立即释放 `ID3D12Resource` 与它的 RTV 描述符堆，
**即使 GPU 还在用它们**。

D3D12 的正确做法是「按帧延迟回收」：
- 资源被 `Release()` 后不立刻销毁，而是推进一个待销毁队列
- 每帧开始时，等待对应帧围栏完成后再真正释放

Vulkan 后端天然有这层（`vkDestroy*` 配合 fence），所以 Vulkan 侧没问题；
D3D12 侧没有，就会出现「上一帧的目标被销毁、这一帧的 RTV 句柄指向已释放的堆」，
表现正是：**清屏与绘制都合法、但都不生效，画面恒黑**。

**这很可能就是 `02.Cube` 黑屏的最后一块拼图。**

### 11.3 下一步实现建议

1. 给 `D3D12Device` 加一个「延迟销毁队列」：`vector<pair<u64 /*frameFence*/, ComPtr<ID3D12Resource>>>`
2. 纹理/缓冲析构时不直接销毁，而是把 `ComPtr` 连同当前帧号入队
