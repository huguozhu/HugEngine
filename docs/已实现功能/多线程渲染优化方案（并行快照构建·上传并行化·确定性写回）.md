## 1. 目标与背景

`15.多线程架构与渲染实现分析.md` §4.3 列出四项待优化，其中三项可做（第四项 SIMD 明确不做 ✗）：

| §4.3 条目 | 当前状态（该文记录） |
|---|---|
| **Entity 遍历单线程** | 串行遍历 World 全部实体（`SceneSnapshotBuilder.cpp:128-181` 的 `BuildObjects`，`ForEach` 在 `:151-178`） |
| **GPU 数据上传串行** | 只有剔除是并行的；`Map` + 逐条写入在主线程（`:58-76`） |
| ~~无 SIMD~~ | 不做 ✗ |
| **结果顺序不确定** | 插入序拼接，跨帧不稳定 |

**三项共用同一套骨架**：**分块并行 + 每块本地缓冲 + 确定性合并** ⇒ 建议一起设计、分三条提交落地、每条都用同一套判据验 ✓

## 2. 三项方案

### 2.1 确定性写回（先做）

**要解决**：现在结果按"插入序"拼接 ⇒ 跨帧顺序不稳定 ✗ ⇒ 打乱下游 **TAA / 时域降噪** 的历史对应关系，也让 A/B 读数不可重复。

**方案**：把"插入序"改成**索引序**，两步写回：

1. **标记**：`hit[entityIndex] = true/false` —— 并行写、无冲突 ⇒ **不需要锁** ✓
2. **紧凑化**：对 `hit` 做**并行前缀和** ⇒ 每个命中实体得到唯一且确定的下标 ⇒ 再并行写回 ✓

**收益**：
- 输出顺序跨帧稳定 ⇒ 不再干扰 TAA / 时域降噪 ✓（最实在的一项）
- 读数**可重复**（同输入两次运行逐元素相同 ✓）—— 这也是后两项方案的判据基础 ✓
- 顺带消掉"锁 + 本地向量"的合并逻辑（标记法天然无竞争 ✓）

**代价**：一次并行扫描 + 一份 `bool/u32` 临时数组；`total` 大时为 O(n) 并行，可控 ✓

**判据**：同输入**两次运行输出逐元素相同**（可写成单测 ✓）

---

### 2.2 并行快照构建（`BuildObjects`）

**要解决**：`ForEach` 串行遍历全部实体 ⇒ 大场景下可能成为 CPU 瓶颈。

**方案**：把 `ForEach` 换成与 §4.2 剔除同款的 `JobSystem::ParallelForChunked`：

1. 一次性取实体总数 `total`
2. `chunkSize` 取 **64**（与剔除一致 ✓）
3. 每个 chunk 在自己**本地**向量里收集快照项（沿用 `SceneRenderer.cpp:36` 的本地合并写法 ✓）
4. chunk **有产出**时才并入全局 ⇒ 锁粒度 = chunk（不是实体），空 chunk 几乎无竞争 ✓

**前提（必须先确认）**：
- 遍历期间 **World 只读**：不得触发惰性组件挂载 / 缓存写入 ✗
- 组件读取**不依赖遍历顺序**（否则并行会改变结果语义 ✗）
- 若 `World::ForEach` 内部有非 const 操作 ⇒ 先改成真正的只读遍历再并行 ✓

**门控**：实体数低于阈值时走串行（小场景并行反而更慢 ✗）；阈值与 `chunkSize` 都要可配 ✓

**判据**：与串行版本**逐元素一致** ✓；收益用《15.多线程架构与渲染实现分析》§10.3 的 CPU 逐项分解读数（新增一列 `BuildObjects`）✓

---

### 2.3 GPU 上传并行化

**要解决**：`Map` + 逐条写入在主线程串行 ⇒ 上传段是 CPU 侧固定开销。

**方案（两级，按收益递增）**：

1. **并行打包 + 单次拷贝**：每个线程把自己那段打包进**独立的连续临时缓冲**（避免假共享 ✗），最后一次 `memcpy` 进 mapped staging；打包布局复用现有带 `static_assert` 的尺寸锁定代码 ✓
2. **去掉 `Map` 往返**：改用 **persistent-mapped** staging（小数据可用 `vkCmdUpdateBuffer`）⇒ 省掉每帧 Map/Unmap 与隐式同步 ✓

**前提**：
- RHI 需暴露"持久映射"与"非一致内存的 flush 语义"（`VK_MEMORY_PROPERTY_HOST_COHERENT_BIT` 是否置位要确认 ✗）
- 打包布局必须与 shader 端逐字段一致（现有 `static_assert` 可复用 ✓）

**风险**：非 coherent 内存**漏 flush** ⇒ 画面偶发错误（比崩溃更难查 ✗）⇒ **先确认内存属性再动** ✓

**判据**：上传段耗时 + 上传内容**逐字节一致**（同一帧 A/B 两次上传比对 ✓）

## 5. 风险与先决条件

| 风险 / 前提 | 影响 | 处置 |
|---|---|---|
| `World::ForEach` 非只读（惰性挂载/缓存） | 并行会引入数据竞争 ✗ | 先改只读遍历；或用"先收集实体 id 再并行取组件"两段式 ✓ |
| `Map` 内存非 coherent，漏 flush | 画面偶发错误（难查 ✗） | 先确认内存属性；必要时显式 flush/invalidate ✓ |
| 小场景并行开销 > 收益 | 反而变慢 ✗ | 按实体数阈值门控 ✓ |
| 结果顺序变化影响下游 TAA/降噪 | 历史对应被破坏 ✗ | 正是 §2.1 要解决的；**必须先做 §2.1** ✓ |
| 引擎当前 worker 数 = `max(1, hardware_concurrency() - 2)` | 并行度与核数绑定 ⇒ 判据要在**不同核数**下都跑一遍 ✓ | 见 `JobSystem` 的派生规则；测试时可用小核数环境复核 ✓ |

### 7.2 逐项 CPU 分解（03.Sponza-Forward，120 帧 avg / max，ms）

| 分段 | avg | max | 占录制总时长 |
|---|---|---|---|
| 快照构建 `BuildObjects` | 0.60 | ~1.0 | ~10% |
| 并行剔除 `Cull` | 0.058 | 0.23 | ~1% |
| 上传 `Upload`（Map + 写回） | **0.013** | 0.14 | **~0.2%** |
| MTCR（并行录制 + 执行） | 0.39 | 0.95 | ~6% |
| 整帧 CPU 录制总计 | 6.1 | — | 100% |

`BuildObjects` 是这三项里唯一还有可观占比的段（约 10%），因此按 §3 的顺序先做它 ✓。
小场景（104 条 < 阈值 1024）走串行路径 ⇒ 读数与改动前一致（0.60 ms），
"并行 vs 串行"的收益要在条目多时才显现：2000 个立方体的合成用例里
**并行 10.1 ms vs 串行 13.1 ms**（Debug，含首次分配偏差）——这也是阈值门控存在的理由。

### 7.3 §2.3 为什么否决（两条独立理由）

1. **占比太小**：上传段实测 0.013 ms，占整帧 CPU 录制的 **0.2%** —— 即使并行到 0 收益，
   上限也只有 0.013 ms；而风险（非一致内存漏 flush ⇒ 偶发花屏，比崩溃更难查 ✗）不成比例。
2. **"去掉 Map 往返"这一半本来就不存在**：RHI 的 `VulkanBuffer` 用
   `VMA_ALLOCATION_CREATE_MAPPED_BIT` **持久映射**（`m_MappedPtr` 生命周期内一直有效），
   并且按 `VK_MEMORY_PROPERTY_HOST_COHERENT_BIT` 记录 `m_IsCoherent`、对非一致内存显式 flush
   ⇒ `Map()` 只是取回那个持久指针，没有每帧映射/解映射与隐式同步 ✗。

将来若出现"数万物体 + 上传段占比上到百分之几"的场景，再按本节口径复测后重新决策 ✓。
